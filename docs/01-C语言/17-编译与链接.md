## 1. 编译的四个阶段

### 1. 整体流程

```
源代码 (.c/.cpp)
    │
    ▼
┌─────────────────────┐
│   1. 预处理        │  展开 #include, #define
└─────────────────────┘
    │
    ▼
预处理后的代码 (.i)
    │
    ▼
┌─────────────────────┐
│   6. 编译          │  翻译成汇编语言
└─────────────────────┘
    │
    ▼
汇编代码 (.s)
    │
    ▼
┌─────────────────────┐
│   3. 汇编          │  翻译成机器码
└─────────────────────┘
    │
    ▼
目标文件 (.o/.obj)
    │
    ▼
┌─────────────────────┐
│   4. 链接          │  组合成可执行文件
└─────────────────────┘
    │
    ▼
可执行文件 (.exe/.out)
```

### 2. 一步完成所有阶段

```bash
# 最常用的方式
gcc main.c -o main        # C语言
g++ main.cpp -o main      # C++
```

## 2. 预处理

### 1. 预处理做什么？

- 展开 `#include` 文件
- 展开 `#define` 宏
- 处理条件编译 `#if`, `#ifdef`
- 删除注释

### 2. 预处理命令

```bash
# 只预处理，输出到 .i 文件
gcc -E main.c -o main.i

# 只预处理，输出到屏幕（查看）
gcc -E main.c | head -56
```

### 3. 预处理示例

```c
// main.c
#include <stdio.h>     // 展开stdio.h的内容
#define MAX 100         // 展开MAX为100
#define ADD(a, b) ((a)+(b))  // 展开宏调用

int main() {
    printf("Max is %d\n", MAX);  // MAX被替换为100
    return 0;
}
```

预处理后：
```c
// 展开了stdio.h的内容...
// MAX被替换为100
// ADD(a,b)被替换为((a)+(b))

int main() {
    printf("Max is %d\n", 100);
    return 0;
}
```

## 3. 编译与汇编

### 1. 编译到汇编

```bash
# 编译到汇编语言，生成 .s 文件
gcc -S main.i -o main.s
# 或者
gcc -S main.c -o main.s
```

### 2. 汇编到目标文件

```bash
# 汇编到目标文件，生成 .o 文件
gcc -c main.s -o main.o
# 或者一步完成
gcc -c main.c -o main.o
```

### 3. 目标文件是什么？

- **机器码**：CPU可以直接执行的二进制指令
- **符号表**：函数和变量的地址信息
- **重定位信息**：哪些地址需要链接时调整

### 4. 查看目标文件

```bash
# Linux: 查看符号表
nm main.o

# Linux: 查看目标文件信息
file main.o

# Windows: 查看目标文件
dumpbin /ALL main.obj
```

## 4. 链接

### 1. 链接做什么？

1. **符号解析**：找到函数和变量的定义
2. **重定位**：调整代码中的地址偏移
3. **组合目标文件**：把多个.o文件合并
4. **链接库**：把用到的库代码加进来

### 2. 链接命令

```bash
# 链接单个目标文件
gcc main.o -o main

# 链接多个目标文件
gcc main.o utils.o -o main

# 链接库
gcc main.o -lm -o main    # -l 指定库名
```

### 3. 静态链接 vs 动态链接

| 类型 | 说明 | 特点 |
|------|------|------|
| 静态链接 | 库代码直接复制到可执行文件 | 文件大，部署简单 |
| 动态链接 | 程序运行时加载库 | 文件小，需要库文件 |

### 4. 链接示例

```c
// utils.h
#ifndef UTILS_H
#define UTILS_H
int add(int a, int b);
#endif

// utils.c
#include "utils.h"
int add(int a, int b) { return a + b; }

// main.c
#include <stdio.h>
#include "utils.h"
int main() {
    printf("7 + 5 = %d\n", add(7, 5));
    return 0;
}
```

编译链接过程：
```bash
# 8. 分别编译
gcc -c utils.c -o utils.o
gcc -c main.c -o main.o

# 6. 链接
gcc main.o utils.o -o main

# 7. 运行
./main
# 输出: 7 + 5 = 8
```

## 5. 目标文件深入

> 💡 **通俗理解 - 目标文件是什么？**

想象你在组装一辆汽车：
- 每个零件（引擎、轮胎、方向盘）都是独立生产的**目标文件**
- 每个零件上贴着标签（**符号表**），标明"我是引擎""我是轮胎"
- 零件之间有接口（**重定位信息**），说明"轮胎需要装在轮轴上"

**目标文件就是"还没组装的零件"，它包含了机器码和元信息，但地址还没最终确定。**

---

> 🔬 **抽象理解 - 目标文件的结构**：
>
> 目标文件并非简单的二进制数据，而是按照特定格式（ELF/PE/COFF）组织的结构化文件。它将不同类型的数据（代码、数据、符号表、重定位信息）分门别类地存储在不同的**段（Section）**中，便于链接器高效处理。

---

### 1. ELF文件格式详解

ELF（Executable and Linkable Format）是Linux/Unix下最主流的可执行文件和目标文件格式。一个ELF文件由四部分组成：

```
┌──────────────────────────┐
│       ELF Header         │  文件头：描述文件整体信息
├──────────────────────────┤
│   Program Header Table   │  程序头表：描述运行时加载的段
│       （可选）            │
├──────────────────────────┤
│                          │
│     Sections (.text,     │  各个段：实际的内容
│     .data, .bss, ...)   │
│                          │
├──────────────────────────┤
│   Section Header Table   │  段头表：描述每个段的属性
└──────────────────────────┘
```

**ELF Header（文件头）** 包含的关键信息：

| 字段 | 说明 |
|------|------|
| e_ident | 魔数（0x7f 'E' 'L' 'F'），标识这是一个ELF文件 |
| e_type | 文件类型（ET_REL=目标文件, ET_EXEC=可执行文件, ET_DYN=共享库） |
| e_machine | 目标架构（EM_386, EM_X86_64, EM_ARM等） |
| e_entry | 程序入口点地址 |
| e_shoff | 段头表在文件中的偏移 |
| e_phoff | 程序头表在文件中的偏移 |
| e_shnum | 段的数量 |
| e_shstrndx | 段名字符串表在段头表中的索引 |

**Section Header Table（段头表）** 描述每个段：

| 字段 | 说明 |
|------|------|
| sh_name | 段名（在字符串表中的偏移） |
| sh_type | 段类型（SHT_PROGBITS, SHT_SYMTAB, SHT_STRTAB等） |
| sh_flags | 段属性（SHF_WRITE可写, SHF_ALLOC需加载, SHF_EXECINSTR可执行） |
| sh_addr | 段在内存中的虚拟地址 |
| sh_offset | 段在文件中的偏移 |
| sh_size | 段的大小 |

**Program Header Table（程序头表）** 描述运行时如何加载：

| 字段 | 说明 |
|------|------|
| p_type | 段类型（PT_LOAD=可加载段, PT_DYNAMIC=动态链接信息） |
| p_vaddr | 段的虚拟地址 |
| p_paddr | 段的物理地址 |
| p_filesz | 段在文件中的大小 |
| p_memsz | 段在内存中的大小（可能大于filesz，多出的部分填6，即BSS） |
| p_flags | 段权限（PF_R可读, PF_W可写, PF_X可执行） |

> 注意：Program Header Table只在可执行文件和共享库中存在，目标文件中没有。

---

### 2. 常见段详解

| 段名 | 说明 | 属性 |
|------|------|------|
| `.text` | 代码段，存放编译后的机器指令 | 只读、可执行 |
| `.data` | 已初始化数据段，存放有初始值的全局/静态变量 | 可读写 |
| `.bss` | 未初始化数据段，存放未初始化的全局/静态变量（不占文件空间） | 可读写 |
| `.rodata` | 只读数据段，存放常量字符串、const变量 | 只读 |
| `.symtab` | 符号表，记录函数和变量的名称与地址 | 链接时使用 |
| `.strtab` | 字符串表，存放段名、符号名等字符串 | 链接时使用 |
| `.shstrtab` | 段名字符串表，专门存放段的名字 | 链接时使用 |
| `.rel.text` | 代码段的重定位表 | 链接时使用 |
| `.rel.data` | 数据段的重定位表 | 链接时使用 |
| `.comment` | 编译器版本信息 | 辅助信息 |
| `.note` | 额外的注释信息 | 辅助信息 |

**各段在内存中的布局**：

```
高地址
┌──────────────┐
│    栈(stack)  │  ← 向下增长
│      ↓       │
├──────────────┤
│              │
│  共享库映射   │
│              │
├──────────────┤
│      ↑       │
│    堆(heap)   │  ← 向上增长
├──────────────┤
│  .bss        │  未初始化数据
├──────────────┤
│  .data       │  已初始化数据
├──────────────┤
│  .rodata     │  只读数据
├──────────────┤
│  .text       │  代码段
└──────────────┘
低地址
```

**.bss段的特殊之处**：

```c
// 这两个变量都在.bss段（不占文件空间，运行时分配并清零）
int g_uninit;            // 未初始化的全局变量
static int s_uninit;     // 未初始化的静态变量

// 这两个变量都在.data段（占文件空间，存储初始值）
int g_init = 46;         // 已初始化的全局变量
static int s_init = 100; // 已初始化的静态变量

// 这个在.rodata段（只读）
const char *msg = "hello";  // 指针本身在.data，字符串"hello"在.rodata
```

### 5. PE格式简介（Windows）

Windows使用PE（Portable Executable）格式，与ELF类似但结构不同：

| 对比项 | ELF（Linux） | PE（Windows） |
|--------|-------------|---------------|
| 文件头 | ELF Header | DOS Header + PE Header |
| 段表 | Section Header Table | Section Table |
| 代码段 | .text | .text |
| 数据段 | .data | .data |
| BSS段 | .bss | .bss（有时合并到.data） |
| 只读数据 | .rodata | .rdata |
| 目标文件 | .o | .obj |
| 可执行文件 | ELF（无扩展名或.out） | .exe |
| 动态库 | .so | .dll |
| 静态库 | .a | .lib |

**Windows下查看目标文件**：

```bash
# 使用dumpbin（Visual Studio自带）
dumpbin /HEADERS sample.obj     # 查看文件头
dumpbin /SYMBOLS sample.obj     # 查看符号表
dumpbin /DISASM sample.obj      # 反汇编
dumpbin /ALL sample.obj         # 查看所有信息

# 使用objdump（MinGW/GCC自带）
objdump -h sample.obj           # 查看段信息
objdump -d sample.obj           # 反汇编
```

## 6. 符号表与符号解析

> 💡 **通俗理解 - 符号表是什么？**

想象一个大型公司：
- 每个员工都有**工牌**（符号名），上面写着姓名和部门
- **符号表**就是公司的"员工花名册"
- **符号解析**就是HR根据花名册找到对应的人
- 如果两个人同名（**符号冲突**），就需要规则来决定谁留下

**符号表记录了"谁在哪里"，符号解析就是"找到对的人"。**

---

> 🔬 **抽象理解 - 符号与符号解析**：
>
> 符号是链接的基本单位。每个函数和全局变量在编译后都成为一个符号，记录在符号表中。链接器的核心任务之一就是**符号解析**——将每个符号的引用与定义匹配起来。如果找不到定义，就会报"undefined reference"错误；如果有多个定义，就会报"multiple definition"错误。

---

### 1. 符号分类

| 类型 | 说明 | 示例 |
|------|------|------|
| 全局符号 | 在当前模块中定义，可被其他模块引用 | `int g_var;` `void func() {}` |
| 外部符号 | 在当前模块中引用，但在其他模块中定义 | `extern int g_var;` `调用printf` |
| 局部符号 | 只在当前模块内部可见 | `static int s_var;` `static void helper() {}` |

```c
// module.c
#include <stdio.h>

int g_counter = 0;           // 全局符号：其他模块可见
static int s_cache = 0;      // 局部符号：仅本模块可见

void process(int x) {        // 全局符号：其他模块可见
    extern void helper();     // 外部符号：定义在其他模块
    s_cache = x;             // 引用局部符号
    helper();                // 引用外部符号
}

static void validate() {     // 局部符号：仅本模块可见
    g_counter++;             // 引用全局符号
}
```

---

### 2. 强符号与弱符号

**强符号**：函数定义和已初始化的全局变量
**弱符号**：未初始化的全局变量，或用 `__attribute__((weak))` 声明的符号

```c
// 强符号示例
int g_strong = 46;                    // 已初始化 → 强符号
void func() { /* ... */ }             // 函数定义 → 强符号

// 弱符号示例
int g_weak;                           // 未初始化 → 弱符号（COMMON符号）
__attribute__((weak)) void hook() {   // 显式弱符号
    printf("default hook\n");
}
```

**链接器处理强/弱符号的规则**：

| 情况 | 结果 |
|------|------|
| 一个强符号 + 多个弱符号 | 选择强符号 |
| 多个弱符号，无强符号 | 选择任意一个弱符号（通常选最大的） |
| 多个强符号 | **链接错误：multiple definition** |

```c
// file1.c
int g_val = 1;     // 强符号

// file2.c
int g_val;         // 弱符号（未初始化）

// 链接结果：选择file1.c中的强符号 g_val = 1
```

```c
// file1.c
int g_val = 1;     // 强符号

// file2.c
int g_val = 0;     // 也是强符号！

// 链接结果：multiple definition of 'g_val'  ← 错误！
```

**弱符号的实际用途——提供默认实现**：

```c
// hook.h
void on_init(void) __attribute__((weak));  // 声明为弱符号

// hook.c
void on_init(void) {                       // 默认实现
    printf("default init\n");
}

// app.c
// 用户可以提供自己的强符号实现来覆盖默认行为
void on_init(void) {                       // 强符号覆盖弱符号
    printf("custom init\n");
}
```

### 3. 符号解析过程

符号解析的核心流程：

```
1. 扫描所有目标文件的符号表
       │
       ▼
2. 建立全局符号表（所有定义的符号集合）
       │
       ▼
3. 对每个未解析的引用（UND符号），在全局符号表中查找定义
       │
       ├─ 找到 → 解析成功，记录地址
       │
       └─ 未找到 → 报错：undefined reference
```

```bash
# 查看目标文件中哪些符号未定义（需要链接时解析）
nm sample.o | grep ' U '
# 输出：
#                  U printf        # U 表示未定义，需要外部提供
#                  U add           # 如果add在其他文件中定义
```

### 4. C++名称修饰（Name Mangling）

C++支持函数重载，同名函数可能有不同参数。编译器通过**名称修饰**将函数签名编码到符号名中：

```cpp
// C++代码
int add(int a, int b) { return a + b; }
double add(double a, double b) { return a + b; }
void print(int x) {}
void print(const char *s) {}
```

编译后的符号名（GCC）：
```
_Z7addii        # add(int, int)
_Z7adddd        # add(double, double)
_Z5printi       # print(int)
_Z5printPKc     # print(const char*)
```

修饰规则：`_Z` + 函数名长度 + 函数名 + 参数类型缩写

| 类型缩写 | 含义 |
|----------|------|
| i | int |
| d | double |
| c | char |
| PKc | pointer to const char |
| v | void |

**使用extern "C"禁止名称修饰**：

```cpp
// C++中调用C库时，必须告诉编译器不要修饰名称
#ifdef __cplusplus
extern "C" {
#endif

int c_library_func(int x);    // 不会被修饰

#ifdef __cplusplus
}
#endif
```

```bash
# 查看C++目标文件的符号（修饰后的）
nm cpp_module.o

# 使用c++filt还原修饰后的符号名
nm cpp_module.o | c++filt
# _Z7addii → add(int, int)
```

### 6. COMMON块概念

COMMON块是链接器处理未初始化全局变量的一种机制：

```c
// file1.c
int g_val;          // 未初始化，编译器标记为COMMON

// file2.c
int g_val;          // 也未初始化，也标记为COMMON

// 链接时不会报错！链接器会选择较大的那个作为最终大小
```

**COMMON符号的特点**：
- 未初始化的全局变量在编译时不确定最终放在哪个段
- 链接器根据所有COMMON符号的定义，选择最大的尺寸
- 最终链接后，COMMON符号被分配到.bss段

```bash
# 使用 -fno-common 选项禁止COMMON块
# 这样未初始化的全局变量会直接放在.bss段
# 如果多个文件定义同名变量，就会报 multiple definition 错误
gcc -fno-common file1.c file2.c -o main

# GCC 10+ 默认使用 -fno-common
```

## 7. 重定位

> 💡 **通俗理解 - 重定位是什么？**

想象你在写一封信，提到"请到7楼找我"：
- 写信时你还不知道自己会被分配到哪栋楼的7楼
- 等确定了具体地址后，你需要把"7楼"改成"5号楼7楼"
- **重定位就是"修改地址"的过程**

编译器在编译每个源文件时，不知道其他文件中函数和变量的实际地址，所以先用占位符（通常是0）代替。链接器把所有文件合并后，确定了每个符号的最终地址，再回头修改这些占位符——这就是重定位。

---

> 🔬 **抽象理解 - 重定位的机制**：
>
> 重定位是链接器最核心的操作之一。当链接器将多个目标文件合并时，每个目标文件中的地址都是相对于文件起始的偏移。合并后，这些地址需要调整为相对于最终可执行文件的偏移。重定位表（.rel.text / .rel.data）记录了所有需要修改的位置和修改方式。

---

### 1. 地址绑定的完整流程

```
编译时
  │  编译器生成目标文件，符号地址为0或相对偏移
  │  重定位表记录"哪些位置需要修改"
  ▼
链接时
  │  链接器合并所有目标文件，分配最终地址
  │  根据重定位表，修改每个需要调整的位置
  ▼
加载时
  │  操作系统加载可执行文件到内存
  │  如果启用了ASLR，动态链接器再次调整地址
  ▼
运行时
     程序执行，所有地址已确定
```

---

### 2. 绝对重定位 vs 相对重定位

**绝对重定位**：直接写入符号的完整虚拟地址

```asm
# 绝对寻址示例（x86-64）
movq $0x401000, %rax    # 将g_val的绝对地址加载到rax
# 链接时：0x401000 被替换为g_var的实际地址
```

**相对重定位**：写入相对于当前指令位置的偏移

```asm
# 相对寻址示例（x86-64的call指令）
callq 0x8f              # 相对偏移调用add函数
# 链接时：0x8f 被替换为 add相对下一条指令的偏移
# 实际地址 = 当前指令地址 + 偏移
```

| 对比项 | 绝对重定位 | 相对重定位 |
|--------|-----------|-----------|
| 修改方式 | 写入完整地址 | 写入偏移量 |
| 位置无关 | 否（地址固定） | 是（可随基地址移动） |
| 适用场景 | 全局变量引用 | 函数调用 |
| PIC支持 | 不支持 | 支持 |

---

## 8. 动态链接深入

> 💡 **通俗理解 - 动态链接是什么？**

想象你开了一家连锁餐厅：
- **静态链接**：每家分店都自带完整的厨房设备和食材仓库（体积大，但独立运行）
- **动态链接**：所有分店共享一个中央厨房（体积小，但依赖中央厨房运转）

**动态链接就是"共享中央厨房"——多个程序共享同一份库代码，节省内存和磁盘空间。**

---

> 🔬 **抽象理解 - PLT与GOT**：
>
> 动态链接的核心挑战是：编译时不知道共享库会被加载到哪个地址。解决方案是**间接寻址**：通过一个中间表（GOT）来查找符号的实际地址。PLT则是实现**延迟绑定**的跳板代码——函数第一次被调用时才解析地址，后续调用直接跳转。

---

### 1. PLT与GOT机制

**GOT（Global Offset Table，全局偏移表）**：
- 存放外部符号的实际地址
- 每个外部符号在GOT中占一个条目
- 运行时由动态链接器填充

**PLT（Procedure Linkage Table，过程链接表）**：
- 存放跳转到GOT对应条目的代码
- 每个外部函数在PLT中占一个条目
- 实现延迟绑定的关键

```
程序代码调用 printf
       │
       ▼
  call printf@plt        ← 跳转到PLT中printf的条目
       │
       ▼
  PLT[printf]:           ← PLT条目
    jmp *GOT[printf]     ← 通过GOT跳转到实际地址
       │
       ├── 第一次调用：GOT[printf]指向PLT的下一行
       │       │
       │       ▼
       │   push 重定位参数     ← 压入标识printf的参数
       │   jmp PLT[0]         ← 跳转到PLT第0项（动态链接器入口）
       │       │
       │       ▼
       │   动态链接器解析printf的实际地址
       │   将地址写入GOT[printf]
       │   跳转到printf执行
       │
       └── 后续调用：GOT[printf]已指向printf实际地址
               │
               ▼
           直接跳转到printf执行（无需再次解析）
```

---

### 2. 延迟绑定（Lazy Binding）原理

延迟绑定是指：函数的地址在**第一次被调用时**才解析，而不是在程序启动时解析所有函数。

**优点**：
- 加快程序启动速度（不需要解析所有函数）
- 减少不必要的解析（未调用的函数永远不会被解析）

**缺点**：
- 第一次调用某函数时会有额外开销
- 运行时可能发生解析错误（而静态链接在链接时就能发现）

```bash
# 禁用延迟绑定（所有符号在启动时解析）
gcc -Wl,-z,now main.c -o main

# 默认启用延迟绑定
gcc -Wl,-z,lazy main.c -o main
```

---

### 3. PLT/GOT的工作流程图

```
┌─────────────────────────────────────────────────────────────┐
│                        程序代码                              │
│                                                             │
│   call printf@plt    ──────────────────┐                    │
│                                        │                    │
└────────────────────────────────────────│────────────────────┘
                                         │
                                         ▼
┌─────────────────────────────────────────────────────────────┐
│                     PLT（过程链接表）                         │
│                                                             │
│  PLT[0]:  push GOT[1]          ← 压入链接器标识             │
│           jmp *GOT[2]          ← 跳转到动态链接器            │
│                                                             │
│  PLT[printf]:                              ①首次调用        │
│    jmp *GOT[printf]  ─────────┐    ←── GOT初始指向下一行    │
│    push reloc_index           │    ← 压入重定位索引          │
│    jmp PLT[0]                 │    ← 跳转到动态链接器        │
│                               │                             │
│  PLT[add]:                    │    ②后续调用                 │
│    jmp *GOT[add]              │    ←── GOT已指向实际地址     │
│    ...                        │                             │
└───────────────────────────────│─────────────────────────────┘
                                │
                    ③动态链接器解析后
                    写入GOT[printf]
                                │
                                ▼
┌─────────────────────────────────────────────────────────────┐
│                    GOT（全局偏移表）                          │
│                                                             │
│  GOT[0]:  .dynamic段的地址                                   │
│  GOT[1]:  link_map结构的地址                                 │
│  GOT[2]:  _dl_runtime_resolve的地址（动态链接器入口）         │
│  GOT[printf]: printf的实际地址  ← 首次调用后被填充           │
│  GOT[add]:    add的实际地址     ← 首次调用后被填充           │
│  ...                                                        │
└─────────────────────────────────────────────────────────────┘
```

## 9. 链接器实战

> 💡 **通俗理解 - 链接器实战**

想象你是一个项目经理：
- **链接器脚本**就是项目计划书，规定每个模块放在哪里
- **链接顺序**就是施工顺序，地基必须在墙壁之前
- **一次定义规则**就是"一个岗位只能有一个人"
- **链接错误**就是项目出了问题，需要排查

---

> 🔬 **抽象理解 - 链接器的实际工作**：
>
> 链接器不仅仅是"把目标文件拼在一起"。它需要处理地址空间分配、符号解析、重定位、库依赖顺序等一系列复杂问题。理解链接器的工作方式，能帮助开发者快速定位和解决编译链接中的各种疑难问题。

---

### 1. 链接器脚本（ld script）基本概念

链接器脚本控制链接器的行为，决定各个段在内存中的布局：

```ld
/* 简单的链接器脚本示例 */
ENTRY(main)                    /* 指定程序入口 */

SECTIONS
{
    . = 0x400000;              /* 起始虚拟地址 */

    .text : {
        *(.text)               /* 所有目标文件的.text段 */
    }

    .rodata : {
        *(.rodata)             /* 所有目标文件的.rodata段 */
    }

    .data : {
        *(.data)               /* 所有目标文件的.data段 */
    }

    .bss : {
        *(.bss)                /* 所有目标文件的.bss段 */
        *(COMMON)              /* COMMON符号 */
    }

    /DISCARD/ : {
        *(.comment)            /* 丢弃注释段 */
        *(.note*)              /* 丢弃注释信息 */
    }
}
```

```bash
# 使用自定义链接器脚本
ld -T my_script.ld main.o utils.o -o main

# 查看默认链接器脚本
ld --verbose

# GCC中使用链接器脚本
gcc -T my_script.ld main.o utils.o -o main
```

---

### 2. 链接顺序问题

链接器对库的顺序非常敏感：**被依赖的库必须放在依赖它的库后面**。

```bash
# 错误：libutils依赖libmath，但libutils在前面
gcc main.o -lutils -lmath -o main
# 可能报错：undefined reference to 'sqrt'（libutils中用到了libmath的函数）

# 正确：libmath在libutils后面
gcc main.o -lmath -lutils -o main
```

**原因**：链接器从左到右处理库文件。处理 `-lutils` 时，它记录了未解析的符号；处理 `-lmath` 时，才找到这些符号的定义。如果顺序反了，链接器处理 `-lmath` 时还不知道需要哪些符号，就会跳过。

```
链接器处理顺序（从左到右）：

  main.o → -lutils → -lmath
     │          │         │
     │          │         └─ 解析utils中未定义的sqrt
     │          └─ 记录未定义的sqrt
     └─ 记录未定义的utils_func

✓ 所有符号都解析成功
```

```bash
# 如果库之间有循环依赖，可以重复指定
gcc main.o -lA -lB -lA -o main

# 或者使用 --start-group / --end-group（性能较差）
gcc main.o -Wl,--start-group -lA -lB -Wl,--end-group -o main
```

### 3. 一次定义规则（ODR）

One Definition Rule（一次定义规则）：每个符号在整个程序中只能有一个定义。

| 规则 | 说明 |
|------|------|
| 全局变量 | 只能在一个翻译单元中定义 |
| 非inline函数 | 只能在一个翻译单元中定义 |
| inline函数 | 可以在多个翻译单元中定义，但定义必须完全相同 |
| 类/结构体定义 | 可以在多个翻译单元中定义，但定义必须完全相同 |

```c
// 违反ODR的示例

// file1.c
int g_val = 46;          // 定义

// file2.c
int g_val = 88;          // 又一个定义！违反ODR

// 链接时报错：multiple definition of 'g_val'
```

**头文件中的正确做法**：

```c
// utils.h
#ifndef UTILS_H
#define UTILS_H

// 声明，不是定义
extern int g_count;

// inline函数可以在头文件中定义
static inline int max(int a, int b) {
    return a > b ? a : b;
}

#endif
```

```c
// utils.c
#include "utils.h"

int g_count = 0;    // 唯一的定义
```

### 4. 常见链接错误排查

**1. undefined reference（未定义引用）**

```
/usr/bin/ld: main.o: in function `main':
main.c:(.text+0x8a): undefined reference to `add'
collect2: error: ld returned 1 exit status
```

**原因与解决**：

| 可能原因 | 解决方法 |
|----------|----------|
| 忘记链接目标文件 | `gcc main.o utils.o -o main` |
| 忘记链接库 | `gcc main.o -lm -o main` |
| 函数名拼写错误 | 检查函数名是否一致 |
| C/C++混合编译缺少extern "C" | 在C头文件中加 `extern "C"` |
| 链接顺序错误 | 把被依赖的库放后面 |

```bash
# 排查步骤
# 1. 检查符号是否存在
nm utils.o | grep add

# 2. 检查是否被名称修饰
nm utils.o | c++filt

# 3. 检查库中是否有该符号
nm -l /usr/lib/libm.a | grep sqrt
```

**2. multiple definition（多重定义）**

```
/usr/bin/ld: utils.o:(.data+0x0): multiple definition of `g_val';
main.o:(.data+0x0): first defined here
```

**原因与解决**：

| 可能原因 | 解决方法 |
|----------|----------|
| 全局变量在多个文件中定义 | 改为 `extern` 声明 + 一个定义 |
| 头文件中定义了非static变量 | 改为 `extern` 声明或 `static` |
| 头文件中定义了非inline函数 | 改为 `static inline` 或移到.c文件 |
| GCC 10+ 默认 -fno-common | 检查是否因COMMON块变化导致冲突 |

**3. 未解析符号（运行时）**

```bash
# 运行时报错
./main: error while loading shared libraries: libfoo.so: cannot open shared object file

# 解决方法8：设置LD_LIBRARY_PATH
export LD_LIBRARY_PATH=/path/to/lib:$LD_LIBRARY_PATH

# 解决方法6：使用 -rpath 嵌入搜索路径
gcc main.o -L/path/to/lib -lfoo -Wl,-rpath,/path/to/lib -o main

# 解决方法7：添加到系统库路径
sudo ldconfig /path/to/lib
```

### 5. LTO（链接时优化）概念

LTO（Link-Time Optimization）是在链接阶段进行跨模块优化的技术：

```bash
# 启用LTO
gcc -flto -O2 main.c utils.c -o main

# 分步编译也支持LTO
gcc -flto -c main.c -o main.o
gcc -flto -c utils.c -o utils.o
gcc -flto main.o utils.o -o main
```

**LTO能做什么**：

| 优化类型 | 说明 |
|----------|------|
| 跨模块内联 | 将其他文件中的函数内联到调用处 |
| 死代码消除 | 删除从未被调用的函数 |
| 常量传播 | 跨模块传播常量值 |
| 虚函数去虚化 | C++中确定虚函数的实际目标 |

**LTO的优缺点**：

| 优点 | 缺点 |
|------|------|
| 更好的优化效果 | 链接时间显著增加 |
| 减少最终可执行文件大小 | 内存消耗增大 |
| 消除跨模块冗余代码 | 调试可能受影响 |

## 10. 静态链接 vs 动态链接深入对比

> 💡 **通俗理解 - 静态链接 vs 动态链接**

想象你需要一本参考书：
- **静态链接**：把整本书复印一份带在身边（重，但随时可用）
- **动态链接**：去图书馆借阅（轻，但依赖图书馆开门）

**两种方式各有利弊，选择取决于具体场景。**

---

> 🔬 **抽象理解 - 静态与动态链接的本质差异**：
>
> 静态链接在编译时完成所有地址绑定，生成完全自包含的可执行文件。动态链接将部分地址绑定推迟到加载时或运行时，依赖动态链接器完成符号解析。两者在启动速度、内存占用、更新便利性等方面各有优劣。

---

> **🎯 鱼与熊掌不可兼得，取舍之间见智慧。**
>
> （静态链接和动态链接各有优劣，选择合适的策略才是关键。）

---

### 1. 静态链接的详细过程

静态链接分为三个主要步骤：

**步骤1：空间与地址分配**

```
1. 扫描所有输入目标文件
2. 收集所有段的长度和属性
3. 合并相同类型的段
4. 计算每个段在输出文件中的虚拟地址

  输入：
  main.o:  .text=0x35  .data=0x08  .bss=0x04
  utils.o: .text=0x20  .data=0x04  .bss=0x04

  合并后：
  .text = 0x35 + 0x20 = 0x55   虚拟地址 0x401000
  .data = 0x08 + 0x04 = 0x0c   虚拟地址 0x400000
  .bss  = 0x04 + 0x04 = 0x08   虚拟地址 0x401000
```

**步骤2：符号解析与重定位**

```
1. 建立全局符号表
2. 解析所有未定义的引用
3. 读取重定位表
4. 计算每个符号的实际地址
5. 修改代码/数据中的地址引用
```

**步骤3：输出可执行文件**

```
1. 写入ELF头
2. 写入Program Header Table
3. 写入各段内容
4. 写入Section Header Table（可省略）
```

---

### 2. 动态链接的详细过程

动态链接分为两个阶段：

**阶段1：程序加载时**

```
1. 操作系统加载可执行文件到内存
2. 检查PT_INTERP段，找到动态链接器路径
   （通常是 /lib64/ld-linux-x86-64.so.6）
3. 加载动态链接器到内存
4. 将控制权交给动态链接器
5. 动态链接器执行：
   a. 读取可执行文件的.dynamic段
   b. 加载所有依赖的共享库
   c. 执行重定位（非延迟绑定的部分）
   d. 初始化各共享库（调用.init段）
   e. 将控制权交给程序入口
```

**阶段2：运行时（延迟绑定）**

```
1. 程序调用外部函数时，跳转到PLT
2. PLT通过GOT查找函数地址
3. 如果是首次调用：
   a. 调用动态链接器的解析函数
   b. 解析函数的实际地址
   c. 将地址写入GOT
   d. 跳转到函数执行
4. 如果是后续调用：
   a. 直接通过GOT跳转到函数执行
```

```bash
# 查看程序使用的动态链接器
readelf -l sample | grep interpreter
# 输出：[Requesting program interpreter: /lib64/ld-linux-x86-64.so.6]

# 查看程序的动态段
readelf -d sample
```

### 3. 性能对比

| 对比维度 | 静态链接 | 动态链接 |
|----------|----------|----------|
| 启动速度 | 快（无需加载共享库） | 较慢（需加载和重定位共享库） |
| 内存占用 | 高（每个进程一份库代码） | 低（多个进程共享库代码） |
| 磁盘空间 | 大（库代码复制到每个程序） | 小（库代码只有一份） |
| 更新便利 | 差（需重新编译） | 好（替换.so文件即可） |
| 部署复杂度 | 低（单文件部署） | 高（需确保库文件存在） |
| 地址空间布局 | 编译时确定 | 运行时确定（支持ASLR） |
| 符号解析 | 编译时完成 | 运行时完成（延迟绑定） |

**内存共享示意图**：

```
静态链接：
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 进程A    │  │ 进程B    │  │ 进程C    │
│ ┌──────┐ │  │ ┌──────┐ │  │ ┌──────┐ │
│ │libc  │ │  │ │libc  │ │  │ │libc  │ │
│ │(副本)│ │  │ │(副本)│ │  │ │(副本)│ │
│ └──────┘ │  │ └──────┘ │  │ └──────┘ │
└──────────┘  └──────────┘  └──────────┘
  内存占用：3 × libc大小

动态链接：
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 进程A    │  │ 进程B    │  │ 进程C    │
│  ↕映射   │  │  ↕映射   │  │  ↕映射   │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │             │             │
     └─────────────┼─────────────┘
                   ▼
            ┌────────────┐
            │   libc.so  │  ← 物理内存中只有一份
            │  (共享)    │
            └────────────┘
  内存占用：1 × libc大小
```

### 4. 混合链接策略

实际项目中，经常同时使用静态链接和动态链接：

```bash
# 默认动态链接
gcc main.c -o main

# 全静态链接
gcc -static main.c -o main

# 混合：大部分动态链接，特定库静态链接
gcc main.c -Wl,-Bstatic -lmylib -Wl,-Bdynamic -lm -o main
# -Wl,-Bstatic 之后的库使用静态链接
# -Wl,-Bdynamic 之后的库恢复动态链接
```

**混合链接的常见场景**：

| 场景 | 策略 | 原因 |
|------|------|------|
| 嵌入式系统 | 全静态链接 | 目标系统可能没有动态链接器 |
| 容器化部署 | 全静态链接 | 减小镜像大小，避免依赖问题 |
| 桌面应用 | 混合链接 | libc等基础库动态链接，业务库静态链接 |
| 插件系统 | 动态链接 | 需要运行时加载插件 |
| 版本敏感的库 | 静态链接 | 避免目标系统库版本不兼容 |

```bash
# 检查可执行文件的链接方式
file main
# 静态链接：ELF 64-bit LSB executable, ... statically linked
# 动态链接：ELF 64-bit LSB executable, ... dynamically linked

# 查看静态链接了哪些库
ldd main
# 静态链接时输出：not a dynamic executable
# 动态链接时输出依赖库列表
```

## 11. 常见问题

**Q：链接错误"undefined reference to xxx"？**
A：链接器找不到函数的定义
```bash
# 检查是否正确链接了目标文件
gcc main.o utils.o -o main

# 检查符号是否存在
nm utils.o | grep xxx

# 检查链接顺序
gcc main.o -lutils -lm -o main   # 被依赖的库放后面
```

**Q：编译错误"undefined reference to main"？**
A：没有定义main函数，或者main函数名拼写错误

**Q：预处理、编译、汇编能分开吗？**
A：可以，GCC支持分步执行
```bash
gcc -E main.c -o main.i   # 预处理
gcc -S main.i -o main.s   # 编译到汇编
gcc -c main.s -o main.o   # 汇编到目标文件
gcc main.o -o main        # 链接
```

**Q：如何查看目标文件中的段？**
A：使用readelf或objdump
```bash
readelf -S main.o          # 查看段头表
objdump -h main.o          # 查看段信息
```

**Q：如何判断一个符号是强符号还是弱符号？**
A：使用nm查看符号类型
```bash
nm main.o
# 大写字母（T, D, B）= 全局强符号
# 小写字母（t, d, b）= 局部符号
# W = 弱符号
# C = COMMON符号（弱符号的一种）
```

**Q：动态链接的程序找不到共享库怎么办？**
A：有三种解决方法
```bash
# 方法1：设置环境变量
export LD_LIBRARY_PATH=/path/to/lib:$LD_LIBRARY_PATH

# 方法2：编译时嵌入搜索路径
gcc main.o -L/path/to/lib -lfoo -Wl,-rpath,/path/to/lib -o main

# 方法3：添加到系统库缓存
echo "/path/to/lib" | sudo tee /etc/ld.so.conf.d/mylib.conf
sudo ldconfig
```

**Q：C和C++混合编程时链接报错怎么办？**
A：通常是因为C++名称修饰导致符号名不匹配
```c
// 在C头文件中使用extern "C"
#ifdef __cplusplus
extern "C" {
#endif

int c_func(int x);    // C函数声明

#ifdef __cplusplus
}
#endif
```
