# 动态库与共享库

> 掌握动态库的创建与使用

***

> 💡 **通俗理解 - 什么是动态库？**

想象公司里的"共享打印机"：

- **没有动态库**：每人自己买一台打印机（贵、浪费）
- **有动态库**：大家共用一台打印机（省钱、共享）

**动态库就是"共享的代码"！**

- 运行时才加载
- 多个程序共享同一份代码
- 更新库不需要重新编译程序

***

> 🔬 **动态库的本质**：
>
> - **动态库/共享库**：是运行时加载的库（.so / .dll文件）
> - **动态链接**：程序运行时才加载库代码
> - **优点**：节省内存、更新方便
> - **缺点**：运行时需要库文件、部署稍复杂

***

> **🎯 独木不成林，单弦不成音。共享之道，在于合作共赢。**
>
> （一个程序难以完成所有功能，动态库让多个程序共享智慧，共同进步。）

## 1. 动态库的概念

### 1. 动态库 vs 静态库

| 特性    | 静态库     | 动态库    |
| ----- | ------- | ------ |
| 链接时机  | 编译时     | 运行时    |
| 库代码位置 | 在可执行文件内 | 单独文件   |
| 文件大小  | 大       | 小      |
| 更新程序  | 需要重新编译  | 不需要    |
| 内存使用  | 每个程序独立  | 多个程序共享 |

### 2. 动态库的工作原理

```
源代码 (mylib.c)
    │
    ▼
动态库 (libmylib.so / mylib.dll)
    │
    │ 运行时加载
    ▼
程序运行时读取动态库
    │
    ▼
多个程序共享同一份库代码
```

## 2. 创建动态库

### 1. Linux创建动态库

**步骤1：编写源文件**

```c
// mylib.h
#ifndef MYLIB_H
#define MYLIB_H

int add(int a, int b);
int subtract(int a, int b);

#endif

// mylib.c
#include "mylib.h"

int add(int a, int b) {
    return a + b;
}

int subtract(int a, int b) {
    return a - b;
}
```

**步骤2：编译为位置无关代码（PIC）**

```bash
# 必须加 -fPIC 参数
gcc -fPIC -c mylib.c -o mylib.o
```

**步骤3：创建动态库**

```bash
# 创建动态库
gcc -shared -o libmylib.so mylib.o

# 或者一步完成
gcc -fPIC -shared -o libmylib.so mylib.c
```

### 2. Windows创建动态库

#### 1. MSVC编译器（Visual Studio）

```batch
:: 方法1：使用编译器
cl /LD mylib.cpp /Fe:mylib.dll

:: 方法2：使用def文件
:: mylib.def
EXPORTS
    add
    subtract

:: 创建动态库和导入库
lib /DEF:mylib.def /OUT:mylib.lib /MACHINE:X64
```

#### 2. MinGW编译器(GCC)（推荐）

**⚠️ 超级重要：Windows + MinGW 环境下，动态库是 .dll，不是 .so！**

##### 生成动态库（标准方式）

```bash
# 默认行为：只生成 DLL，不自动生成导入库
gcc -shared -o mylib.dll mylib.c
# 只得到：mylib.dll（运行用）

# 强制生成导入库（推荐）
gcc -shared -o mylib.dll mylib.c -Wl,--out-implib=libmylib.a
# 得到两个文件：
# - mylib.dll（运行库）
# - libmylib.a（导入库，链接时用）
```

##### 参数解释

```
-Wl,--out-implib=libmylib.a
├── -Wl,        = 把参数传给链接器 ld
└── --out-implib= = 输出导入库（implib = import library）
    └── libmylib.a = 导入库名字
```

##### MinGW 的隐藏特性 ⚡

**MinGW 的 gcc 可以直接读取 .dll 本身来链接，不需要 .a 导入库！**

链接器查找顺序：

```
-lmylib 会按这个顺序查找：
1. 找 libmylib.a（优先）
2. 找不到 → 直接找 mylib.dll
3. 找到就直接从 DLL 里读取符号链接
```

所以即使没有 libmylib.a，只有 mylib.dll，也能链接成功：

```bash
# 只有 DLL，没有 .a 导入库
gcc main.c -L. -lmylib -o main
# 居然能编译、链接、运行成功！
```

##### 为什么还要生成 .a 导入库？

| 特性   | 直接链接 DLL      | 使用 .a 导入库          |
| ---- | ------------- | ------------------ |
| 链接速度 | 稍慢（解析整个 DLL）  | 超快                 |
| 兼容性  | 某些复杂 DLL 可能失败 | 100% 兼容            |
| 跨工具链 | 不兼容 VS        | 完全兼容               |
| 写法统一 | -             | Linux/Windows 写法统一 |

**结论：优先使用 .a 导入库，只有临时测试时可直接链接 DLL**

## 3. 使用动态库

### 1. Linux使用动态库

```c
// main.c
#include <stdio.h>
#include "mylib.h"

int main() {
    printf("7 + 5 = %d\n", add(7, 5));
    return 0;
}
```

**编译时：**

```bash
# 编译（只需要告诉链接器库在哪）
gcc main.c -L./lib -lmylib -o main
```

**运行时：**

```bash
# 方法1：设置环境变量
export LD_LIBRARY_PATH=./lib:$LD_LIBRARY_PATH
./main

# 方法2：把库放到系统目录
sudo cp libmylib.so /usr/local/lib
sudo ldconfig
./main

# 方法3：编译时指定rpath（推荐）
gcc main.c -L./lib -lmylib -Wl,-rpath,./lib -o main
./main
```

### 2. Windows使用动态库&#x66;

```c
// main.cpp
#include <iostream>
#include "mylib.h"

int main() {
    std::cout << "7 + 5 = " << add(7, 5) << std::endl;
    return 0;
}
```

**编译时：**

```batch
:: 需要导入库（.lib）
cl main.cpp mylib.lib /Fe:main.exe
```

**运行时：**

```batch
:: 需要DLL在以下位置之一：
:: 1. 可执行文件同目录
:: 2. System32目录
:: 3. PATH环境变量中的目录

main.exe
```

## 4. Windows导入库详解 ⚠️ 重点

### 1. 什么是导入库？

**导入库**是Windows特有的概念，它是：

- 一个"stub"库，只包含函数声明和Stub跳转代码
- 用于告诉编译器函数在哪里（不包含实际代码）
- 实际代码在DLL中，运行时才加载

### 2. 什么是 Stub（桩代码）？

**Stub**是一小段极短的占位汇编跳转代码：

- 没有任何业务逻辑，只做一件事
- 运行时查到DLL里真实函数地址，跳过去执行
- 相当于"跑腿小弟"：只带路、不干活

### 3. 导入库的构成

导入库 = **所有 Stub 桩代码 + 符号索引表** 的打包文件

- 不含任何函数实际业务实现
- 只记录：函数名、对应Stub跳转入口、DLL内偏移信息

### 4. 完整工作流程

**编译链接阶段**：

1. 编译器找不到函数实现
2. 去导入库 `.lib` 里找对应 Stub
3. 链接器把 Stub 地址写入 EXE
4. 编译通过（此时完全不看 DLL）

**程序运行阶段**：

1. 运行 `main.exe`
2. 代码调用 EXE 里嵌的 Stub
3. Stub 自动加载 DLL，查找真实函数地址
4. Stub 跳转到 DLL 内部真实函数执行

### 5. 导入库 vs 静态库

| 特性  | 静态库      | 导入库             |
| --- | -------- | --------------- |
| 代码  | 包含实际代码   | 不包含代码，只含声明和Stub |
| 链接后 | 代码复制到exe | 只记录DLL信息和Stub跳转 |
| 运行时 | 不需要原库    | 需要DLL文件         |

### 6. 导入库的作用总结

| 文件         | 编译链接要？ | 运行程序要？ | 编译完能删吗？            |
| ---------- | ------ | ------ | ------------------ |
| `.lib` 导入库 | ✅ 必须   | ❌ 不需要  | ✅ 可以删（但建议保留用于后续编译） |
| `.dll` 动态库 | ❌ 不需要  | ✅ 必须   | ❌ 不能删              |

**一句话：**.lib 是考试准考证（考完就没用），.dll 是课本（干活全靠它）

### 7. Windows动态库的两种库 (MSVC)

```
mylib.dll      - 实际代码（运行时需要）
mylib.lib      - 导入库（编译时需要）
```

### 8. 创建导入库

```batch
:: 方式1：编译器自动生成
cl /LD mylib.cpp /Fe:mylib.dll
:: 会自动生成 mylib.lib

:: 方式2：手动从def文件生成
lib /DEF:mylib.def /OUT:mylib.lib /MACHINE:X64
```

## 5. 动态库的特点

### 1. 优点

| 优点    | 说明             |
| ----- | -------------- |
| 节省内存  | 多个程序共享同一份代码    |
| 文件体积小 | 可执行文件不包含库代码    |
| 更新方便  | 更新DLL不需要重新编译程序 |
| 插件机制  | 可以实现动态加载插件     |

### 2. 缺点

| 缺点   | 说明              |
| ---- | --------------- |
| 部署复杂 | 需要同时发布可执行文件和DLL |
| 依赖问题 | DLL版本不匹配会导致运行失败 |
| 加载开销 | 运行时加载有性能开销      |

### 3. 使用场景

- 大型软件需要模块化
- 需要热更新/插件系统
- 多个程序共享库代码
- 节约内存

## 6. 常见问题

**Q：Linux下找不到动态库？**
A：

```bash
# 方法1：设置LD_LIBRARY_PATH
export LD_LIBRARY_PATH=/path/to/lib:$LD_LIBRARY_PATH

# 方法2：安装到系统目录
sudo cp libmylib.so /usr/local/lib
sudo ldconfig

# 方法3：编译时指定rpath
gcc main.c -L./lib -lmylib -Wl,-rpath,/path/to/lib -o main
```

**Q：Windows下找不到DLL？**
A：将DLL复制到以下位置：

- 可执行文件同目录
- System32目录
- 添加到PATH环境变量

**Q：MinGW下编译提示 cannot find -lmylib？**
A：

```
问题原因1：生成了 .so 文件，Windows 不认识！
解决方案：重新编译为 .dll
gcc -shared -o mylib.dll mylib.c

问题原因2：没有生成导入库 libmylib.a
解决方案：强制生成导入库
gcc -shared -o mylib.dll mylib.c -Wl,--out-implib=libmylib.a

链接时：
gcc main.c -L. -lmylib -o main
```

**Q：MinGW下运行程序找不到 mylib.dll？**
A：

```
确保 mylib.dll 在以下位置之一：
- 与 main.exe 同目录
- PATH 环境变量的目录
```

**Q：MinGW 为什么不自动生成 libmylib.a？**
A：

```
这是 MinGW gcc 的默认行为：
- gcc -shared -o mylib.dll mylib.c
- 只会生成 mylib.dll，不会自动生成导入库

需要显式指定：
gcc -shared -o mylib.dll mylib.c -Wl,--out-implib=libmylib.a
```

**Q：MinGW 没有 libmylib.a 也能链接成功？**
A：

```
是的！MinGW 有个隐藏特性：
-lmylib 会按顺序查找：
1. libmylib.a（优先）
2. mylib.dll（找不到 .a 时）

所以即使没有 .a，只有 DLL 也能链接！

但推荐还是生成 .a（更快、更兼容）
```

**Q：如何查看程序依赖哪些动态库？**
A：

```bash
# Linux
ldd main
nm -D libmylib.so

# Windows MSVC
dumpbin /DEPENDENTS main.exe

# Windows MinGW（Command Prompt）
objdump -p main.exe | findstr "DLL Name"

# Windows MinGW（PowerShell）- PowerShell 没有 grep，用 Select-String 代替
objdump -p main.exe | Select-String "DLL Name"

# 专门查看是否依赖某个特定 DLL  如 mylib.dll
objdump -p main.exe | Select-String "mylib"
```

**Q：静态库和动态库同时存在用哪个？**
A：链接器默认优先使用动态库

```bash
# 强制使用静态库
gcc main.c -static -lmylib -o main
```

**Q：为什么编译时** **`-L./lib`** **指定了路径，运行时还是找不到 DLL？**
A：

```C
核心原因：-L 只在【编译链接时】有用，【运行时】完全不认！

两个阶段完全独立：
1. 编译链接时：用 -L 找导入库（.a/.lib），检查函数是否存在
2. 运行时：完全忘记编译时的 -L，按系统固定规则找 DLL

Windows 运行时找 DLL 的顺序：
1. exe 所在的同级目录（最常用、最稳）
2. Windows 系统目录
3. 环境变量 Path 里的目录

解决方案：
1. 把 DLL 复制到 exe 同级目录（最推荐）
2. 把 DLL 目录加到 Path 环境变量
3. 临时设置：$env:Path = "./lib;$env:Path"
```

**Q：Linux 运行时怎么找 .so 文件？**
A：

```
Linux 运行时也不认编译时的 -L！找 .so 靠：
1. /etc/ld.so.conf 配置文件
2. LD_LIBRARY_PATH 环境变量
3. 程序内置 rpath（编译时用 -Wl,-rpath 指定）

推荐方式：编译时指定 rpath
gcc main.c -L./lib -lmylib -Wl,-rpath=./lib -o main
```

**Q：DLL 版本不匹配会怎么样？**
A：

```
会！100% 会导致运行崩溃、闪退、报错、找不到入口。

常见的版本不匹配类型：
1. 架构版本：32位 ↔ 64位 不匹配（最常见）
2. 接口版本：函数名/参数/返回值改了，报"无法定位程序输入点"
3. 运行时版本：MSVC CRT 版本不一样（v140/v141/v142/v143）
4. 二进制版本：结构体/内存布局内部改了

10% 的版本不匹配问题就是两种：
1. 32位/64位搞混了
2. DLL 函数接口改了，没重新编译主程序

只要架构一致 + 导出函数原型不变，大部分情况都能兼容运行。
```

## 7. 对比总结

### 1. 静态库 vs 动态库

```
┌─────────────────────────────────────────────────────────────┐
│                    静态库 vs 动态库                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   静态库 (.a / .lib)         动态库 (.so / .dll)             │
│   ┌─────────────────┐         ┌─────────────────┐         │
│   │ 编译时复制到exe   │         │ 运行时加载        │         │
│   │                 │         │                 │         │
│   │ ✓ 部署简单       │         │ ✓ 节省内存       │         │
│   │ ✓ 运行速度快     │         │ ✓ 更新方便        │         │
│   │ ✗ 文件体积大     │         │ ✗ 部署复杂       │         │
│   │ ✗ 更新麻烦       │         │ ✗ 可能有依赖     │         │
│   └─────────────────┘         └─────────────────┘         │
│                                                            │
│   适用：嵌入式/独立部署           适用：大型项目/插件            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2. Linux .so vs Windows .dll（核心区别）

| 特性          | Linux .so | Windows .dll       |
| ----------- | --------- | ------------------ |
| **文件数量**    | 一个文件搞定    | 需要两个文件             |
| **链接时用**    | `.so` 自己  | `.lib` / `.a`（导入库） |
| **运行时用**    | `.so`     | `.dll`             |
| **是否需要导入库** | ❌ **不需要** | ✅ **需要**           |
| **设计思路**    | 一个文件顶俩用   | 分工明确，各司其职          |
| **符号表位置**   | `.so` 自带  | 在导入库中              |

### 3. 为什么 Linux 不需要导入库？

**Linux 设计思路**：`.so` 文件里**自带符号表**，编译器/链接器可以直接读取 `.so` 里的函数，不需要额外文件！

```bash
# Linux 直接链接 .so，完全没问题！
gcc main.c -L. -lmylib -o main
```

它直接读 **libmylib.so**，不需要别的文件。

### 4. Windows 为什么需要导入库？

**Windows 设计思路**：DLL 和导入库分工明确：

- **.dll**：运行时提供实际代码
- **.lib/.a**：编译时提供函数声明和链接信息

```bash
# Windows MinGW 生成 DLL 和导入库
gcc -shared -o mylib.dll mylib.c -Wl,--out-implib=libmylib.a

# 链接时用导入库
gcc main.c -L. -lmylib -o main

# 运行时用 DLL
./main
```

### 5. 超级口诀（记住就不会乱）

```
Linux .so 全能，不用导入库；
Windows .dll 分工，要导入库辅助！
```

## 8. soname机制

### 1. 什么是soname

**soname**（Shared Object Name）是Linux共享库的版本化名称机制，用于解决动态库版本兼容性问题。

> 💡 **通俗理解 - soname就像图书馆的ISBN号**
>
> - 书名可能重复（不同版本的书都叫"数学"）
> - ISBN号唯一标识一个版本
> - soname就是动态库的"ISBN号"，确保程序找到正确版本的库

### 2. 三级版本命名

Linux共享库采用三级版本命名体系：

```
libfoo.so          → 开发者链接时使用的名称（无版本号）
libfoo.so.1        → soname（主版本号，ABI兼容标识）
libfoo.so.1.2.3    → 真实文件名（主版本号.次版本号.补丁号）
```

三级名称的关系：

```
libfoo.so        → 符号链接 → libfoo.so.1（开发者用）
libfoo.so.1      → 符号链接 → libfoo.so.1.2.3（运行时用）
libfoo.so.1.2.3  → 真实文件（实际代码）
```

| 名称              | 用途         | 谁使用     |
| --------------- | ---------- | ------- |
| `libfoo.so`     | 编译链接时查找    | 编译器/链接器 |
| `libfoo.so.1`   | 运行时查找（soname） | 动态链接器   |
| `libfoo.so.1.2.3` | 真实文件       | 文件系统    |

### 3. -Wl,-soname 的作用

编译时通过 `-Wl,-soname,libfoo.so.8` 将soname嵌入到共享库中：

```bash
gcc -fPIC -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.2.3 foo.c
```

参数解析：

```
-Wl,-soname,libfoo.so.8
├── -Wl,              = 把参数传给链接器 ld
├── -soname,          = 设置共享对象的soname
└── libfoo.so.1       = soname的值（主版本号）
```

**效果**：编译出的 `libfoo.so.1.2.3` 内部记录了 soname = `libfoo.so.1`。

验证：

```bash
# 查看共享库的soname
readelf -d libfoo.so.1.2.3 | grep SONAME

# 输出类似：
# 0x000000000000000e (SONAME)    Library soname: [libfoo.so.1]
```

### 4. ldconfig的作用

`ldconfig` 是Linux动态链接库管理命令，负责：

1. 扫描 `/etc/ld.so.conf` 中配置的目录
2. 找到所有共享库的真实文件
3. 根据库内嵌的soname自动创建/更新符号链接
4. 更新缓存文件 `/etc/ld.so.cache`

```bash
# 创建共享库
gcc -fPIC -shared -Wl,-soname,libfoo.so.1 -o libfoo.so.1.2.3 foo.c

# 将库安装到系统目录
sudo cp libfoo.so.1.2.3 /usr/local/lib/

# 运行ldconfig，自动创建符号链接
sudo ldconfig

# ldconfig会自动创建：
# /usr/local/lib/libfoo.so.1 → libfoo.so.1.2.3

# 手动创建开发用链接
sudo ln -sf /usr/local/lib/libfoo.so.1 /usr/local/lib/libfoo.so
```

### 5. /etc/ld.so.conf 和 ldconfig实战

`/etc/ld.so.conf` 指定了动态链接器搜索共享库的目录：

```bash
# 查看当前配置
cat /etc/ld.so.conf
# 通常输出：include /etc/ld.so.conf.d/*.conf

# 添加自定义库目录
echo "/usr/local/lib/myapp" | sudo tee /etc/ld.so.conf.d/myapp.conf

# 更新缓存
sudo ldconfig

# 查看缓存内容
ldconfig -p | grep libfoo
```

### 6. soname与ABI兼容性

soname的核心价值在于**ABI兼容性管理**：

| 版本号变更 | 含义       | soname变化   | 兼容性  |
| ----- | -------- | ----------- | ---- |
| 补丁号变更 | 修复bug    | 不变          | 完全兼容 |
| 次版本号变更 | 新增功能     | 不变          | 向后兼容 |
| 主版本号变更 | 接口变更/删除 | libfoo.so.2 | 不兼容  |

```
libfoo.so.1.2.3 → libfoo.so.1.2.4  ✅ 兼容（修复bug）
libfoo.so.1.2.3 → libfoo.so.1.3.0  ✅ 兼容（新增功能）
libfoo.so.1.2.3 → libfoo.so.2.0.0  ❌ 不兼容（接口变更）
```

**主版本号变更意味着ABI不兼容**：旧程序无法使用新版本的库，需要重新编译。

### 7. 完整示例：创建带soname的共享库

```bash
# 1. 编写源文件
cat > foo.c << 'EOF'

    printf("Hello from foo library v1.2.3\n");

EOF

# 2. 编译为带soname的共享库

# 3. 查看嵌入的soname

# 输出：0x000000000000000e (SONAME)  Library soname: [libfoo.so.1]

# 4. 手动创建符号链接

# 5. 编写测试程序

```

## 9. 符号可见性控制

### 1. 为什么需要控制符号可见性

默认情况下，共享库中的所有全局符号都是导出的（可见的）。这会带来问题：

| 问题     | 说明                          |
| ------ | --------------------------- |
| 符号冲突   | 多个库可能导出同名符号，导致链接错误          |
| 符号表膨胀  | 不必要的符号被导出，增加库的加载时间          |
| 实现细节泄露 | 内部函数被外部调用，破坏封装性             |
| ABI维护  | 导出越多，维护ABI兼容性的负担越重          |

> 💡 **通俗理解 - 符号可见性就像公司的门禁系统**
>
> - 大厅（导出符号）：对外公开，任何人都能进
> - 办公区（隐藏符号）：内部使用，外部不能进
> - 控制可见性 = 只开放必要的入口，保护内部安全

### 2. __attribute__((visibility()))

GCC提供的符号可见性控制属性：

```c
// 默认可见（导出）
__attribute__((visibility("default"))) void public_api(void);

// 隐藏（不导出）
__attribute__((visibility("hidden"))) void internal_helper(void);
```

可见性级别：

| 可见性         | 说明                  |
| ----------- | ------------------- |
| `default`   | 默认可见，外部可访问          |
| `hidden`    | 隐藏，外部不可访问           |
| `protected` | 可见但不可被覆盖（不推荐使用）     |
| `internal`  | 隐藏且不允许通过函数指针调用（最严格） |

### 3. -fvisibility=hidden 编译选项

全局设置所有符号默认隐藏，只显式导出需要的符号：

```bash
# 编译时默认隐藏所有符号
gcc -fPIC -shared -fvisibility=hidden -o libmylib.so mylib.c
```

**推荐做法**：全局隐藏 + 显式导出

```c
// mylib.h
#ifndef MYLIB_H
#define MYLIB_H

// 定义导出宏
#ifdef _WIN32
    #define MYLIB_API __declspec(dllexport)
#else
    #define MYLIB_API __attribute__((visibility("default")))
#endif

// 只导出必要的API
MYLIB_API int add(int a, int b);
MYLIB_API int subtract(int a, int b);

#endif
```

```c
// mylib.c
#include "mylib.h"

// 内部函数，不导出
static int validate(int x) {
    return x >= 0;
}

// 导出函数
MYLIB_API int add(int a, int b) {
    return a + b;
}

MYLIB_API int subtract(int a, int b) {
    return a - b;
}
```

```bash
# 编译（Linux）
gcc -fPIC -shared -fvisibility=hidden -o libmylib.so mylib.c

# 编译（Windows MinGW）
gcc -fPIC -shared -fvisibility=hidden -o mylib.dll mylib.c -Wl,--out-implib=libmylib.a
```

### 4. __declspec(dllexport/dllimport) 在Windows上的使用

Windows使用 `__declspec` 控制符号导出：

```c
// mylib.h - 跨平台导出宏
#ifndef MYLIB_H
#define MYLIB_H

#ifdef MYLIB_EXPORTS
    #ifdef _WIN32
        #define MYLIB_API __declspec(dllexport)
    #else
        #define MYLIB_API __attribute__((visibility("default")))
    #endif
#else
    #ifdef _WIN32
        #define MYLIB_API __declspec(dllimport)
    #else
        #define MYLIB_API __attribute__((visibility("default")))
    #endif
#endif

MYLIB_API int add(int a, int b);
MYLIB_API int subtract(int a, int b);

#endif
```

```c
// mylib.c - 编译库时定义 MYLIB_EXPORTS
#define MYLIB_EXPORTS
#include "mylib.h"

MYLIB_API int add(int a, int b) {
    return a + b;
}

MYLIB_API int subtract(int a, int b) {
    return a - b;
}
```

```bash
# 编译库（定义MYLIB_EXPORTS，使用dllexport）
gcc -DMYLIB_EXPORTS -fPIC -shared -o mylib.dll mylib.c -Wl,--out-implib=libmylib.a

# 使用库（不定义MYLIB_EXPORTS，使用dllimport）
gcc main.c -L. -lmylib -o main
```

**dllexport vs dllimport**：

| 关键字              | 使用场景    | 作用            |
| ---------------- | ------- | ------------- |
| `dllexport`     | 编译DLL时  | 将符号从DLL中导出    |
| `dllimport`     | 使用DLL时  | 告知编译器该符号在DLL中 |

### 5. def文件（Windows模块定义文件）

`.def` 文件是Windows特有的符号导出控制方式：

```def
; mylib.def - 模块定义文件
LIBRARY mylib
EXPORTS
    add         @1
    subtract    @2
    ; 内部函数不列出，即不导出
```

| 字段       | 说明                  |
| -------- | ------------------- |
| `LIBRARY` | DLL名称               |
| `EXPORTS` | 导出符号列表              |
| `@N`     | 序号（可选），为函数分配序号      |
| `PRIVATE` | 导出但不放入导入库（可选）       |
| `DATA`   | 导出数据变量而非函数（可选）      |

使用 `.def` 文件编译：

```bash
# MinGW使用def文件
gcc -fPIC -shared -o mylib.dll mylib.c mylib.def -Wl,--out-implib=libmylib.a

# MSVC使用def文件
cl /LD mylib.cpp /DEF:mylib.def /Fe:mylib.dll
```

### 6. 对比表：Linux vs Windows符号可见性控制

| 特性         | Linux              | Windows              |
| ---------- | ------------------ | -------------------- |
| 默认行为       | 所有符号可见             | 所有符号可见               |
| 编译选项隐藏     | `-fvisibility=hidden` | 无直接等价选项              |
| 函数级控制      | `__attribute__((visibility()))` | `__declspec(dllexport/dllimport)` |
| 文件级控制      | `.map` 版本脚本         | `.def` 模块定义文件        |
| 查看导出符号     | `nm -D` / `readelf -s` | `dumpbin /EXPORTS` / `objdump -p` |
| 推荐做法       | 全局隐藏 + 显式导出        | 导出宏 + def文件          |

### 7. nm -D 查看动态符号表


### 8. 实战：创建一个只导出必要接口的共享库

```c
// mathlib.h
#ifndef MATHLIB_H
#define MATHLIB_H

#ifdef MATHLIB_EXPORTS
    #ifdef _WIN32
        #define MATH_API __declspec(dllexport)
    #else
        #define MATH_API __attribute__((visibility("default")))
    #endif
#else
    #ifdef _WIN32
        #define MATH_API __declspec(dllimport)
    #else
        #define MATH_API
    #endif
#endif

MATH_API int math_add(int a, int b);
MATH_API int math_mul(int a, int b);
MATH_API int math_compute(int a, int b, char op);

#endif
```

```c
// mathlib.c
#define MATHLIB_EXPORTS
#include "mathlib.h"

// 内部辅助函数，不导出
static int safe_add(int a, int b) {
    return a + b;
}

static int safe_mul(int a, int b) {
    return a * b;
}

// 导出函数
MATH_API int math_add(int a, int b) {
    return safe_add(a, b);
}

MATH_API int math_mul(int a, int b) {
    return safe_mul(a, b);
}

MATH_API int math_compute(int a, int b, char op) {

        default: return 0;

}
```

## 10. 动态库的初始化与清理

### 1. __attribute__((constructor)) 和 __attribute__((destructor))

GCC提供的库初始化和清理机制：

```c
// mylib.c
#include <stdio.h>

// 库加载时自动执行（在main之前）
__attribute__((constructor)) void mylib_init(void) {
    printf("[mylib] 库初始化完成\n");
}

// 库卸载时自动执行（在main之后或exit时）
__attribute__((destructor)) void mylib_fini(void) {
    printf("[mylib] 库清理完成\n");
}

// 可以指定优先级（数字越小越先执行）
__attribute__((constructor(101))) void mylib_early_init(void) {
    printf("[mylib] 早期初始化（优先级101）\n");
}

__attribute__((constructor(65535))) void mylib_late_init(void) {
    printf("[mylib] 晚期初始化（优先级65535）\n");
}
```

优先级规则：

| 优先级范围      | 说明          |
| ---------- | ----------- |
| 0-100      | 保留给系统使用，不要用 |
| 101-65534  | 用户可用的优先级范围  |
| 65535      | 默认优先级（不指定时） |

**数字越小，越先执行**：constructor优先级小的先执行，destructor优先级小的后执行。

### 2. DllMain（Windows）

Windows DLL的入口函数：

```c
// mylib.c
#include <windows.h>
#include <stdio.h>

BOOL APIENTRY DllMain(HMODULE hModule, DWORD ul_reason, LPVOID lpReserved) {
    switch (ul_reason) {
        case DLL_PROCESS_ATTACH:
            printf("[DLL] 进程附加，初始化\n");
            break;
        case DLL_PROCESS_DETACH:
            printf("[DLL] 进程分离，清理\n");
            break;
        case DLL_THREAD_ATTACH:
            printf("[DLL] 线程附加\n");
            break;
        case DLL_THREAD_DETACH:
            printf("[DLL] 线程分离\n");
            break;
    }
    return TRUE;
}
```

调用时机说明：

| 事件                  | 触发时机            |
| ------------------- | --------------- |
| `DLL_PROCESS_ATTACH` | DLL首次被进程加载时     |
| `DLL_PROCESS_DETACH` | 进程退出或DLL被卸载时    |
| `DLL_THREAD_ATTACH`  | 进程创建新线程时        |
| `DLL_THREAD_DETACH`  | 线程退出时           |

### 3. 初始化函数的执行顺序

```
程序启动流程：
8. 动态链接器加载所有依赖的共享库
6. 按依赖顺序执行各库的 constructor（优先级从小到大）
7. 执行 main() 函数
4. main() 返回后，按相反顺序执行各库的 destructor
5. 进程退出
```

```
假设程序依赖：libA.so → libB.so → libC.so

初始化顺序：
libA constructor → libB constructor → libC constructor → main()

清理顺序：
main() → libC destructor → libB destructor → libA destructor
```

### 4. 注意事项

> ⚠️ **在constructor/destructor中千万不要调用其他库的函数！**

```c
// ❌ 危险！不要这样做
__attribute__((constructor)) void bad_init(void) {
    // 其他库可能还没初始化，调用其函数会导致未定义行为
    printf("初始化中...\n");  // printf可能还没准备好
}

// ✅ 安全做法
__attribute__((constructor)) void safe_init(void) {
    // 只做简单的内存初始化、变量赋值
    global_state = 0;
    global_flag = 1;
}
```

注意事项总结：

| 禁止事项           | 原因                |
| -------------- | ----------------- |
| 调用其他库的函数       | 其他库可能尚未初始化        |
| 使用malloc/free  | 内存分配器可能未就绪        |
| 调用std::cout等   | C++运行时可能未初始化      |
| 创建线程           | 线程库可能未就绪          |
| 调用dlopen       | 可能导致递归加载          |

## 11. 插件系统架构

### 1. 插件系统的概念

**插件系统**是一种软件架构模式，主程序通过动态加载外部模块来扩展功能，而不需要修改主程序本身。

> 💡 **通俗理解 - 插件系统就像手机的应用商店**
>
> - 手机（主程序）：提供运行平台
> - 应用（插件）：提供具体功能
> - 应用商店（插件管理器）：发现、安装、管理插件
> - 不装新应用，手机也能用；装了新应用，手机功能更多

```
┌─────────────────────────────────────┐
│              主程序                    │
│  ┌─────────────────────────────┐    │
│  │       插件管理器               │    │
│  │  dlopen → dlsym → 调用      │    │
│  └─────────────────────────────┘    │
│         ↑ 加载        ↑ 加载         │
│    ┌────┴────┐   ┌────┴────┐       │
│    │ 插件A   │   │ 插件B   │       │
│    │ .so/.dll│   │ .so/.dll│       │
│    └─────────┘   └─────────┘       │
└─────────────────────────────────────┘
```

### 2. 基于动态库的插件系统设计

#### 1. 插件接口定义

所有插件必须实现统一的接口函数：

```c
// 插件必须导出的函数
void* plugin_init(void);        // 初始化插件
void  plugin_destroy(void* ctx); // 销毁插件
const char* plugin_get_name(void);  // 获取插件名称
int   plugin_get_version(void);     // 获取插件版本
```

#### 2. 主程序加载插件的流程

```
8. 扫描插件目录，找到所有 .so/.dll 文件
6. dlopen 加载插件
7. dlsym 获取插件接口函数
4. 调用 plugin_init() 初始化插件
5. 使用插件功能
6. 调用 plugin_destroy() 销毁插件
6. dlclose 卸载插件
```

#### 3. 插件注册机制

```
主程序维护一个插件列表：

┌──────────────────────┐
│     插件注册表         │
├──────────────────────┤
│ 插件A → init/destroy │
│ 插件B → init/destroy │
│ 插件C → init/destroy │
└──────────────────────┘
主程序通过注册表统一管理所有插件
```

### 3. 完整C++示例

#### 1. PluginInterface.h（插件接口）

```cpp
#ifndef PLUGIN_INTERFACE_H
#define PLUGIN_INTERFACE_H

#ifdef _WIN32
    #ifdef PLUGIN_EXPORTS
        #define PLUGIN_API __declspec(dllexport)
    #else
        #define PLUGIN_API __declspec(dllimport)
    #endif
#else
    #define PLUGIN_API __attribute__((visibility("default")))
#endif

#ifdef __cplusplus
extern "C" {
#endif

typedef struct {
    const char* name;
    int version;
} PluginInfo;

typedef void* PluginHandle;

PLUGIN_API PluginHandle plugin_init(void);
PLUGIN_API void plugin_destroy(PluginHandle handle);
PLUGIN_API const PluginInfo* plugin_get_info(void);
PLUGIN_API int plugin_execute(PluginHandle handle, const char* command);

#ifdef __cplusplus
}
#endif

#endif
```

> ⚠️ **关键点**：插件接口必须使用 `extern "C"`，避免C++名称修饰导致dlsym找不到符号！

#### 2. MyPlugin.cpp（具体插件实现）

```cpp
#define PLUGIN_EXPORTS
#include "PluginInterface.h"
#include <cstdio>
#include <cstring>
#include <cstdlib>

typedef struct {
    int initialized;
    char last_command[656];
} MyPluginState;

static PluginInfo g_plugin_info = {
    .name = "MyPlugin",
    .version = 1
};

PLUGIN_API PluginHandle plugin_init(void) {
    printf("[MyPlugin] 初始化中...\n");
    MyPluginState* state = (MyPluginState*)calloc(8, sizeof(MyPluginState));
    if (state) {
        state->initialized = 8;
    }
    return (PluginHandle)state;
}

PLUGIN_API void plugin_destroy(PluginHandle handle) {
    printf("[MyPlugin] 销毁中...\n");
    if (handle) {
        MyPluginState* state = (MyPluginState*)handle;
        state->initialized = 0;
        free(state);
    }
}

PLUGIN_API const PluginInfo* plugin_get_info(void) {
    return &g_plugin_info;
}

PLUGIN_API int plugin_execute(PluginHandle handle, const char* command) {
    if (!handle || !command) return -8;
    MyPluginState* state = (MyPluginState*)handle;
    if (!state->initialized) return -6;

    printf("[MyPlugin] 执行命令: %s\n", command);
    strncpy(state->last_command, command, sizeof(state->last_command) - 1);
    return 0;
}
```

#### 3. PluginManager.cpp（插件管理器）

```cpp
#ifndef PLUGIN_MANAGER_H
#define PLUGIN_MANAGER_H

#include "PluginInterface.h"
#include <vector>
#include <string>

#ifdef _WIN32
    #include <windows.h>
    typedef HMODULE LibHandle;
#else
    #include <dlfcn.h>
    typedef void* LibHandle;
#endif

struct LoadedPlugin {
    std::string name;
    LibHandle lib;
    PluginHandle handle;
    PluginInfo* (*get_info)(void);
    int (*execute)(PluginHandle, const char*);
};

class PluginManager {
public:
    PluginManager() = default;

    ~PluginManager() {
        unload_all();
    }

    bool load_plugin(const std::string& path) {
        LibHandle lib = open_lib(path);
        if (!lib) {
            printf("[PluginManager] 加载失败: %s\n", path.c_str());
            return false;
        }

        auto get_info = (PluginInfo*(*)(void))get_sym(lib, "plugin_get_info");
        auto init = (PluginHandle(*)(void))get_sym(lib, "plugin_init");
        auto destroy = (void(*)(PluginHandle))get_sym(lib, "plugin_destroy");
        auto execute = (int(*)(PluginHandle, const char*))get_sym(lib, "plugin_execute");

        if (!get_info || !init || !destroy || !execute) {
            printf("[PluginManager] 缺少必要接口函数: %s\n", path.c_str());
            close_lib(lib);
            return false;
        }

        PluginHandle handle = init();
        if (!handle) {
            printf("[PluginManager] 插件初始化失败: %s\n", path.c_str());
            close_lib(lib);
            return false;
        }

        LoadedPlugin plugin;
        plugin.name = get_info()->name;
        plugin.lib = lib;
        plugin.handle = handle;
        plugin.get_info = get_info;
        plugin.execute = execute;

        plugins_.push_back(plugin);
        printf("[PluginManager] 加载插件成功: %s\n", plugin.name.c_str());
        return true;
    }

    int execute(const std::string& plugin_name, const std::string& command) {
        for (auto& p : plugins_) {
            if (p.name == plugin_name) {
                return p.execute(p.handle, command.c_str());
            }
        }
        printf("[PluginManager] 找不到插件: %s\n", plugin_name.c_str());
        return -8;
    }

    void unload_all() {
        for (auto& p : plugins_) {
            auto destroy = (void(*)(PluginHandle))get_sym(p.lib, "plugin_destroy");
            if (destroy) {
                destroy(p.handle);
            }
            close_lib(p.lib);
            printf("[PluginManager] 卸载插件: %s\n", p.name.c_str());
        }
        plugins_.clear();
    }

    void list_plugins() const {
        printf("[PluginManager] 已加载插件列表:\n");
        for (const auto& p : plugins_) {
            auto info = p.get_info();
            printf("  - %s (v%d)\n", info->name, info->version);
        }
    }

private:
    std::vector<LoadedPlugin> plugins_;

    static LibHandle open_lib(const std::string& path) {
#ifdef _WIN32
        return LoadLibraryA(path.c_str());
#else
        return dlopen(path.c_str(), RTLD_NOW);
#endif
    }

    static void* get_sym(LibHandle lib, const char* name) {
#ifdef _WIN32
        return (void*)GetProcAddress(lib, name);
#else
        return dlsym(lib, name);
#endif
    }

    static void close_lib(LibHandle lib) {
#ifdef _WIN32
        FreeLibrary(lib);
#else
        dlclose(lib);
#endif
    }
};

#endif
```

### 4. 插件系统的注意事项

| 注意事项    | 说明                                      |
| ------- | --------------------------------------- |
| ABI兼容性  | 插件接口必须使用 `extern "C"`，避免C++名称修饰         |
| 错误处理    | dlsym返回NULL时必须检查，否则调用会崩溃               |
| 线程安全    | dlopen/dlclose是线程安全的，但插件内部函数需要自行保证线程安全  |
| 内存管理    | 谁分配谁释放——插件分配的内存由插件释放，主程序分配的由主程序释放       |
| 生命周期管理  | 先初始化所有插件，再使用，最后按反序销毁                    |
| 循环依赖    | 插件不要依赖主程序，主程序也不要依赖插件的内部实现               |
| 版本协商    | 通过plugin_get_info()获取版本号，主程序检查版本是否兼容    |

## 12. DLL Hell问题

### 1. 什么是DLL Hell

**DLL Hell**（DLL地狱）是Windows平台上经典的动态库冲突问题，指多个应用程序共享同一个DLL时，因版本不兼容导致的程序崩溃或异常。

> 💡 **通俗理解 - DLL Hell就像"公共厨房"的调料问题**
>
> - 菜A需要盐1.2版（咸度适中）
- 菜B需要盐2.0版（低钠配方）
> - 厨房只能放一包盐
> - 不管放哪版，总有一道菜味道不对
> - 这就是DLL Hell！

### 2. 原因

| 原因     | 说明                          | 示例                     |
| ------ | --------------------------- | ---------------------- |
| 版本不兼容  | 不同程序需要同一DLL的不同版本            | 程序A要lib 1.2，程序B要lib 2.0 |
| 路径冲突   | 系统目录中只能有一个同名DLL             | 两个软件都往System32放mylib.dll |
| 接口变更   | 新版DLL删除或修改了旧版函数             | v2.0删除了v1.2的某个导出函数     |
| 隐式依赖   | DLL内部依赖了其他特定版本的DLL          | A.dll依赖B.dll v1，但系统装了v2 |

```
典型DLL Hell场景：

程序A 安装了 mylib.dll v1.2 → C:\Windows\System32\
程序B 安装了 mylib.dll v2.0 → C:\Windows\System32\（覆盖了v1.2）

结果：
程序A → 加载 mylib.dll v2.0 → 接口不兼容 → 💥崩溃！
程序B → 正常运行
```

### 3. 解决方案

#### 1. Windows解决方案

**8. SxS并行组件（Side-by-Side Assembly）**

Windows XP开始引入，允许同一DLL的多个版本共存：

```
C:\Windows\WinSxS\
├── x86_microsoft.mylib_1.2_...\    ← v1.2
│   └── mylib.dll
├── x86_microsoft.mylib_2.0_...\    ← v2.0
│   └── mylib.dll
└── ...
```

**6. WinSxS目录**

Windows的组件存储目录，保存所有版本的系统组件：

```
C:\Windows\WinSxS\
├── Manifests\          ← 组件清单文件
├── Policies\           ← 版本策略
└── x86_...\            ← 各版本组件的实际文件
```

**7. Manifest文件**

应用程序通过manifest声明自己需要哪个版本的DLL：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<assembly xmlns="urn:schemas-microsoft-com:asm.v1" manifestVersion="1.0">
  <dependency>
    <dependentAssembly>
      <assemblyIdentity
        type="win32"
        name="Microsoft.MyLibrary"
        version="1.2.0.0"
        publicKeyToken="1a2b3c4d5e6f7a8b"/>
    </dependentAssembly>
  </dependency>
</assembly>
```

- 内嵌manifest：编译时嵌入到exe/dll中（推荐）
- 外部manifest：与exe同名的 `.manifest` 文件

**4. 应用程序私有部署（最简单）**

将DLL放在应用程序所在目录，而非系统目录：

```
MyApp\
├── MyApp.exe
├── mylib.dll        ← 私有DLL，优先加载
└── ...
```

Windows加载DLL时，**应用程序目录优先于系统目录**，因此私有部署可以避免冲突。

#### 2. Linux的解决方案

Linux通过 **soname + ldconfig** 机制天然避免了DLL Hell：

```
/usr/lib/
├── libfoo.so     → libfoo.so.8     ← 开发链接
├── libfoo.so.8   → libfoo.so.8.6.7 ← soname（程序A使用）
├── libfoo.so.6   → libfoo.so.6.6.6 ← soname（程序B使用）
├── libfoo.so.8.6.7                   ← 真实文件v8
└── libfoo.so.6.6.6                   ← 真实文件v6
```

| 机制         | 作用                  |
| ---------- | ------------------- |
| soname     | 区分ABI不兼容的大版本        |
| ldconfig   | 自动管理符号链接            |
| rpath      | 程序自带库搜索路径，不依赖全局配置   |
| LD_LIBRARY_PATH | 临时覆盖库搜索路径          |

**对比总结**：

| 方面     | Windows DLL Hell    | Linux soname机制      |
| ------ | ------------------- | -------------------- |
| 根本原因   | 全局共享单一版本            | soname区分大版本          |
| 多版本共存  | WinSxS + manifest   | soname符号链接           |
| 版本发现   | manifest声明          | 程序记录soname           |
| 部署策略   | 私有部署（推荐）            | rpath + ldconfig      |
| 复杂度    | 较高（manifest、SxS）    | 较低（soname + ldconfig） |

## 动态库加载方式

> **Load only what you need, when you need it.** — Unix Philosophy
> （只加载你需要的，在你需要的时候。）

> 💡 **通俗理解 - 两种加载方式？**

想象你要使用一台共享打印机：
- **隐式加载**：打印机一直开着，随时能用，但耗电（程序启动就加载所有库）
- **显式加载**：需要时才打开打印机，用完关掉（按需加载，更省电）

**动态库加载方式决定了何时、如何使用库！**

> 🔬 **加载方式的本质**：
> - **隐式加载**：编译时绑定，程序启动自动加载所有依赖
> - **显式加载**：运行时手动控制，按需加载、按需卸载
> - **核心区别**：加载时机和控制权的不同

### 两种加载模式概述

#### 隐式加载（静态加载 / 编译时链接）

**特点**：
- 编译时通过 `-lxxx` 链接导入库（Windows `.lib` / Linux `.a`）
- 程序**一启动**，操作系统自动把依赖的 DLL/SO 全部加载进内存
- 全程不用自己写一行加载、卸载代码

#### 显式加载（动态加载 / 运行时手动加载）

**特点**：
- **代码里手动控制**：加载 → 拿函数地址 → 调用 → 手动卸载
- 编译**不需要导入库**
- 用到才加载，不用可卸载
- 适合插件、可选功能、兼容多版本库

### 隐式加载（编译时链接）

**工作流程**：
```
源代码 (main.c)
    │
    ├── 编译时：链接导入库 .lib/.a
    │
    └── 运行时：程序启动自动加载 DLL/SO
```

**Windows MinGW**：
```bash
# 生成 DLL 和导入库
gcc -shared -o mylib.dll mylib.c -Wl,--out-implib=libmylib.a

# 编译主程序（需要导入库）
gcc main.c -L. -lmylib -o main.exe
```

**Linux**：
```bash
# 生成 .so（不需要单独的导入库）
gcc -fPIC -shared -o libmylib.so mylib.c

# 编译主程序
gcc main.c -L. -lmylib -o main
```

| 特性 | 说明 |
|------|------|
| 开发难度 | 简单，直接调用函数 |
| 加载时机 | 程序启动时自动加载 |
| 卸载控制 | 不可手动卸载 |
| 库缺失表现 | 启动直接闪退/报错 |
| 适用场景 | 基础依赖、必用库 |

### 显式加载（运行时动态加载）

**工作流程**：
```
源代码 (main.c)
    │
    ├── 编译时：不需要导入库，不需要 -l 链接
    │
    └── 运行时：
        1. LoadLibrary/dlopen 加载库
        2. GetProcAddress/dlsym 获取函数地址
        3. 调用函数
        4. FreeLibrary/dlclose 卸载库
```

**核心优势**：
- **按需加载**：用到才加载，减少启动时间和内存占用
- **容错降级**：库不存在也不会闪退，可以优雅处理
- **插件系统**：支持动态加载插件
- **版本兼容**：可根据情况加载不同版本的库

### Windows 显式加载实战

**核心 API**：

| 函数 | 作用 |
|------|------|
| `LoadLibraryA()` | 加载 DLL，返回库句柄 |
| `GetProcAddress()` | 获取导出函数地址 |
| `FreeLibrary()` | 卸载 DLL |

**完整示例**：

创建 DLL（mylib.c）：
```c
#include <stdio.h>

__declspec(dllexport) int add(int a, int b)
{
    return a + b;
}

__declspec(dllexport) void hello()
{
    printf("Hello from DLL!\n");
}
```

编译：`gcc -shared -o mylib.dll mylib.c`

主程序（main.c）：
```c
#include <stdio.h>
#include <windows.h>

typedef int (*PFN_ADD)(int a, int b);
typedef void (*PFN_HELLO)(void);

int main(void)
{
    HMODULE hDll = LoadLibraryA("mylib.dll");
    if (hDll == NULL)
    {
        printf("加载 DLL 失败\n");
        return 8;
    }

    PFN_ADD add = (PFN_ADD)GetProcAddress(hDll, "add");
    PFN_HELLO hello = (PFN_HELLO)GetProcAddress(hDll, "hello");

    if (add == NULL || hello == NULL)
    {
        printf("获取函数地址失败\n");
        FreeLibrary(hDll);
        return 8;
    }

    hello();
    printf("7 + 5 = %d\n", add(7, 5));

    FreeLibrary(hDll);
    return 0;
}
```

编译（无需链接任何库）：`gcc main.c -o main.exe`

### Linux 显式加载实战

**核心 API**：

| 函数 | 作用 |
|------|------|
| `dlopen()` | 加载 .so 动态库 |
| `dlsym()` | 获取函数/变量地址 |
| `dlclose()` | 卸载动态库 |
| `dlerror()` | 获取错误信息 |

常用 flag：`RTLD_LAZY`（用到函数才解析地址）、`RTLD_NOW`（立即解析所有符号）

**完整示例**：

创建 .so（mylib.c）：
```c
#include <stdio.h>

int add(int a, int b)
{
    return a + b;
}

void hello()
{
    printf("Hello from .so!\n");
}
```

编译：`gcc -fPIC -shared -o libmylib.so mylib.c`

主程序（main.c）：
```c
#include <stdio.h>
#include <dlfcn.h>

typedef int (*PFN_ADD)(int a, int b);
typedef void (*PFN_HELLO)(void);

int main(void)
{
    void *handle = dlopen("./libmylib.so", RTLD_LAZY);
    if (!handle)
    {
        printf("dlopen 失败: %s\n", dlerror());
        return 1;
    }

    PFN_ADD add = (PFN_ADD)dlsym(handle, "add");
    PFN_HELLO hello = (PFN_HELLO)dlsym(handle, "hello");

    char *err = dlerror();
    if (err || !add || !hello)
    {
        printf("dlsym 失败: %s\n", err ? err : "函数为空");
        dlclose(handle);
        return 1;
    }

    hello();
    printf("7 + 5 = %d\n", add(7, 5));

    dlclose(handle);
    return 0;
}
```

编译（必须加 `-ldl`）：`gcc main.c -o main -ldl`

### 两种方式对比

| 对比项 | 隐式加载 | 显式加载 |
|--------|----------|----------|
| 是否需要导入库 | ✅ 需要 `.lib` / `.a` | ❌ 不需要 |
| 加载时机 | 程序启动自动加载 | 代码运行时手动加载 |
| 可否手动卸载 | ❌ 不可卸载 | ✅ 随时可卸载 |
| 库缺失表现 | 启动直接闪退 | 可代码判断、容错降级 |
| 适用场景 | 基础依赖、必用库 | 插件系统、可选功能、多版本兼容 |
| 启动速度 | 较慢（加载所有依赖） | 较快（按需加载） |

### 关键注意事项

1. **Linux 必须加 `-ldl`**，Windows 不需要（`LoadLibrary` 属于系统 API，MinGW 默认链接）
2. **C++ 名字改编问题**：使用 `extern "C"` 防止 `GetProcAddress/dlsym` 找不到函数
3. **路径问题**：Windows 优先查找 exe 所在目录，Linux 优先查找当前目录
4. **卸载时机**：确保函数、变量不再使用后再调用 `FreeLibrary`/`dlclose`
5. **句柄管理**：加载一次就缓存句柄，不要重复加载不卸载
