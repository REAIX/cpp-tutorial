>

## 1. 为什么需要命名空间

### 1. 名字冲突问题

> 在C语言中，所有全局符号共享同一个命名空间，很容易发生名字冲突。比如你定义了一个 `list` 函数，但第三方库也定义了一个 `list` 函数，链接时就会报错。命名空间通过"分组"解决了这个问题。

在大型项目开发中，名字冲突（`name collision`）是最令人头疼的问题之一。考虑以下场景：

```cpp
// ===== 你的代码 =====
void process(int data) {
    // 处理整型数据
}

struct Node {
    int value;
    Node* next;
};

// ===== 第三方库A的代码 =====
void process(const char* data) {
    // 处理字符串数据
}

struct Node {
    double x, y;
};

// ===== 第三方库B的代码 =====
void process(float data) {
    // 处理浮点数据
}
```

上述代码中，三个 `process` 函数和两个 `Node` 结构体产生了严重的名字冲突。在C语言时代，开发者只能通过前缀来规避：

```cpp
// C语言风格的"命名空间"——手动前缀
void mylib_process(int data);
struct mylib_node { /* ... */ };

void liba_process(const char* data);
struct liba_node { /* ... */ };

void libb_process(float data);
```

这种方式虽然可行，但存在明显缺陷：

| 问题 | 说明 |
|------|------|
| 名称冗长 | `mylib_data_structure_node_create()` 难以阅读和书写 |
| 容易遗漏 | 忘记加前缀就会产生冲突 |
| 无法嵌套 | 无法表达层次关系 |
| 不够优雅 | 前缀只是约定，编译器不会强制检查 |

### 2. C++命名空间的解决方案

C++通过 `namespace` 关键字提供了一种语言级别的解决方案：

```cpp
// 不同命名空间可以有同名函数
namespace CompanyA {
    void processData() { /* A公司的实现 */ }
}

namespace CompanyB {
    void processData() { /* B公司的实现 */ }
}

// 调用时通过作用域解析运算符明确指定
CompanyA::processData();  // 调用A公司的版本
CompanyB::processData();  // 调用B公司的版本
```

命名空间的核心优势：

- **编译器强制隔离**：不同命名空间中的同名符号不会冲突，编译器通过"名称修饰"（`name mangling`）为它们生成不同的内部名称
- **层次化组织**：命名空间可以嵌套，形成清晰的逻辑层次
- **按需引入**：通过 `using` 机制可以选择性地引入符号，而非全部暴露
- **ADL支持**：参数依赖查找让代码更简洁，同时保持类型安全

### 3. 命名空间与作用域的关系

命名空间本质上是一种**作用域**。理解这一点对于掌握命名空间至关重要：

```cpp
int value = 0;              // 全局作用域

namespace NS {
    int value = 1;          // NS 命名空间作用域

    namespace Inner {
        int value = 2;      // NS::Inner 命名空间作用域
    }
}

void demo() {
    int value = 3;          // 局部作用域

    std::cout << value << std::endl;           // 3（局部）
    std::cout << NS::value << std::endl;       // 1（命名空间）
    std::cout << NS::Inner::value << std::endl;// 2（嵌套命名空间）
    std::cout << ::value << std::endl;         // 0（全局）
}
```

> 💡 **提示**：`::value` 中的前置 `::` 表示从全局命名空间开始查找，这在被局部变量遮蔽时非常有用。

## 2. 命名空间的定义与基本用法

### 1. 命名空间的定义

```cpp
namespace MyNamespace {
    int value = 42;
    void func() {
        // ...
    }
    class MyClass {
        // ...
    };
}
```

命名空间中可以包含几乎所有声明：变量、函数、类、模板、另一个命名空间等。但**不能直接包含可执行语句**——所有语句必须位于函数体内。

### 2. 命名空间的特点

- 命名空间可以分离在不同的文件中定义
- 命名空间可以嵌套
- 命名空间可以匿名（没有名字）
- 命名空间可以起别名

### 3. 跨文件定义命名空间

命名空间的一个重要特性是**可以在不同文件中追加定义**，编译器会将它们合并：

```cpp
// ===== file1.h =====
namespace MyLib {
    void funcA();  // 声明
}

// ===== file2.h =====
namespace MyLib {
    void funcB();  // 声明，与 file1.h 属于同一个命名空间
}

// ===== file1.cpp =====
#include "file1.h"

namespace MyLib {
    void funcA() {  // 定义
        // ...
    }
}

// ===== file2.cpp =====
#include "file2.h"

namespace MyLib {
    void funcB() {  // 定义
        // ...
    }
}
```

> ⚠️ **注意**：这种跨文件定义的特性使得命名空间天然适合组织大型项目的代码。标准库 `std` 就是在数十个头文件中分别定义的。

### 4. 命名空间中的前向声明

与类一样，命名空间中的实体也可以前向声明：

```cpp
namespace Graphics {
    class Shape;      // 前向声明
    void draw(Shape& shape);
}

// 后续在别处定义
class Graphics::Shape {
    // 完整定义
};
```

## 3. 使用命名空间成员

### 1. 作用域解析运算符 `::`

```cpp
// 通过 :: 访问命名空间成员
MyNamespace::value = 100;
MyNamespace::func();
MyNamespace::MyClass obj;
```

这是最安全、最明确的访问方式，**始终推荐使用**。虽然书写稍长，但代码意图清晰，不会产生歧义。

### 2. using声明

`using` 声明（`using declaration`）将命名空间中的**特定成员**引入当前作用域：

```cpp
using MyNamespace::value;  // 引入单个成员

value = 200;  // 可以直接使用，不需要 MyNamespace::
```

`using` 声明具有以下特点：

```cpp
namespace NS {
    int x = 10;
    int y = 20;
}

void demo() {
    using NS::x;    // 只引入 x，不引入 y

    std::cout << x << std::endl;    // ✅ OK：x 已引入
    // std::cout << y << std::endl;  // ❌ 错误：y 未引入
    std::cout << NS::y << std::endl; // ✅ OK：使用完整限定

    int x = 99;     // ❌ 错误！与 using 声明冲突
}
```

> 💡 **提示**：`using` 声明引入的名称与当前作用域的同名变量会冲突，编译器会报错。这是一种**安全机制**，防止意外遮蔽。

### 3. using指令

`using` 指令（`using directive`）将命名空间中的**所有成员**引入当前作用域：

```cpp
using namespace MyNamespace;  // 引入整个命名空间

value = 300;
func();  // 所有成员都可以直接使用
```

`using` 指令的风险在于**名称污染**：

```cpp
namespace LibA {
    void process() { std::cout << "LibA" << std::endl; }
}

namespace LibB {
    void process() { std::cout << "LibB" << std::endl; }
}

void demo() {
    using namespace LibA;
    using namespace LibB;

    // process();  // ❌ 二义性！LibA::process 和 LibB::process 冲突

    LibA::process();  // ✅ 必须显式指定
    LibB::process();  // ✅ 必须显式指定
}
```

### 4. 对比表

| 方式 | 语法 | 作用范围 | 推荐度 | 风险 |
|------|------|---------|-------|------|
| 完整限定 | `std::cout` | 每次使用 | ⭐⭐⭐⭐⭐ | 无 |
| using声明 | `using std::cout;` | 声明所在作用域 | ⭐⭐⭐⭐ | 低 |
| using指令 | `using namespace std;` | 声明所在作用域 | ⭐⭐ | 高 |
| 别名 | `namespace ab = a::b;` | 声明所在作用域 | ⭐⭐⭐⭐ | 无 |

### 5. using声明 vs using指令的深层区别

两者不仅仅是"引入一个"和"引入全部"的区别，在名称查找行为上也有本质差异：

```cpp
namespace NS {
    void func(int) { std::cout << "NS::func(int)" << std::endl; }
}

void func(double) { std::cout << "global func(double)" << std::endl; }

void demo_using_declaration() {
    using NS::func;   // using 声明：NS::func 隐藏全局 func
    func(3.14);       // 调用 NS::func(int)！double 被隐式转换为 int
    // 全局 func(double) 被隐藏了
}

void demo_using_directive() {
    using namespace NS;  // using 指令：NS 中的名称参与重载决议
    func(3.14);          // 调用全局 func(double)！更好的匹配
    // 两者都可见，重载决议选择最佳匹配
}
```

> 🔬 **深入理解**：`using` 声明会将引入的名称放入当前作用域，**隐藏**外层作用域的同名函数；`using` 指令只是让命名空间中的名称"可见"，它们与外层作用域的同名函数**共同参与重载决议**。

### 6. 最佳实践

```cpp
// ✅ 头文件中：永远不要使用 using namespace std;
// 因为头文件会被多个源文件包含，using指令会污染所有包含者的命名空间

// .h 头文件 - 使用完整限定
#ifndef MYCLASS_H
#define MYCLASS_H

#include <string>

class MyClass {
    std::string name;  // ✅ 使用完整限定
public:
    explicit MyClass(const std::string& n);
};

#endif

// .cpp 源文件 - 可以在函数内使用 using 声明
#include "myclass.h"
#include <iostream>

MyClass::MyClass(const std::string& n) : name(n) {
    using std::cout;  // ✅ 在函数作用域内使用 using 声明
    cout << "Created: " << name << std::endl;
}

// 或者使用 using 指令（仅限 .cpp 文件）
#include <vector>
#include <string>
using namespace std;  // ⚠️ 仅在 .cpp 中使用

void example() {
    vector<string> names;  // 可以直接使用
    names.push_back("Alice");
}
```

**`using` 使用规则总结**：

| 场景 | 推荐做法 | 原因 |
|------|---------|------|
| 头文件中 | 完整限定 `std::string` | 避免污染包含者的命名空间 |
| 头文件中 | ❌ 禁止 `using namespace` | 影响范围不可控 |
| `.cpp` 文件顶部 | `using namespace std;` 可接受 | 影响仅限当前文件 |
| 函数内部 | `using std::cout;` 推荐 | 影响范围最小 |
| 局部代码块 | `using` 声明最安全 | 限制在最小作用域 |

## 4. 命名空间的高级用法

### 1. 嵌套命名空间

```cpp
namespace Outer {
    namespace Inner {
        void func() {}
    }
}

// C++17: 简化嵌套命名空间定义
namespace Outer::Inner {
    void func() {}
}

// 访问嵌套命名空间
Outer::Inner::func();
```

嵌套命名空间在实际项目中非常常见，用于表达逻辑层次：

```cpp
namespace Company {
    namespace Project {
        namespace Module {
            class CoreEngine { /* ... */ };
        }
    }
}

// C++17 简化写法
namespace Company::Project::Module {
    class CoreEngine { /* ... */ };
}

// 使用时
Company::Project::Module::CoreEngine engine;
```

> 💡 **提示**：C++17 的嵌套命名空间写法 `namespace A::B::C` 等价于传统的逐层嵌套写法，但更简洁。如果你的项目使用 C++17 或更高标准，推荐使用新写法。

### 2. 匿名命名空间

```cpp
// 匿名命名空间中的成员具有内部链接性
// 相当于 static 关键字的效果

namespace {
    int internalVar = 42;  // 仅当前翻译单元可见
    void internalFunc() {} // 仅当前翻译单元可见
}
```

匿名命名空间是C++中替代 `static` 关键字的推荐方式，它具有以下特点：

```cpp
// ===== file1.cpp =====
namespace {
    int counter = 0;           // 内部链接性，仅 file1.cpp 可见
    void helper() { counter++; }
}

void publicFunc() {
    helper();       // ✅ 同一文件内可以直接调用
    counter++;      // ✅ 同一文件内可以直接访问
}

// ===== file2.cpp =====
namespace {
    int counter = 0;           // 不同的实体！与 file1.cpp 的 counter 无关
}

void anotherFunc() {
    counter++;      // 访问的是 file2.cpp 自己的 counter
}
```

**匿名命名空间 vs `static`**：

| 特性 | 匿名命名空间 | `static` |
|------|------------|---------|
| 变量 | ✅ 支持 | ✅ 支持 |
| 函数 | ✅ 支持 | ✅ 支持 |
| 类/结构体 | ✅ 支持 | ❌ 不支持 |
| 模板 | ✅ 支持 | ❌ 不支持 |
| C++推荐度 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |

> ⚠️ **注意**：在C++中，匿名命名空间是比 `static` 更通用的方式。`static` 只能用于变量和函数，而匿名命名空间可以包含类定义和模板定义。

### 3. 命名空间别名

```cpp
// 为长命名空间起别名
namespace AB = A::B::C::D;

AB::func();  // 等价于 A::B::C::D::func()
```

命名空间别名在处理深层嵌套的命名空间时非常有用：

```cpp
namespace boost { namespace filesystem { namespace detail {
    void some_function();
}}}

// 使用别名简化
namespace bfs_detail = boost::filesystem::detail;
bfs_detail::some_function();
```

> 💡 **提示**：别名是**别名**而非新命名空间。`AB::func()` 和 `A::B::C::D::func()` 引用的是同一个实体，两者可以互换使用。

### 4. 内联命名空间（C++11）

```cpp
// 内联命名空间的成员可以直接从外层命名空间访问
namespace Library {
    inline namespace V2 {
        void func() { std::cout << "V2" << std::endl; }
    }

    namespace V1 {
        void func() { std::cout << "V1" << std::endl; }
    }
}

Library::func();      // 调用 V2 版本
Library::V1::func();  // 显式调用 V1 版本
```

内联命名空间的核心用途是**版本管理**。它允许库作者在不破坏向后兼容性的情况下发布新版本：

```cpp
namespace MyMathLib {
    // 当前版本（内联），用户无需修改代码即可获得新实现
    inline namespace V2 {
        double sqrt(double x) {
            // 更精确的实现
            return /* ... */;
        }
    }

    // 旧版本仍然可用
    namespace V1 {
        double sqrt(double x) {
            // 旧实现
            return /* ... */;
        }
    }
}

// 用户代码
MyMathLib::sqrt(2.0);     // 自动使用 V2 版本
MyMathLib::V1::sqrt(2.0); // 显式使用旧版本
```

内联命名空间的特性总结：

| 特性 | 说明 |
|------|------|
| 透明访问 | 外层命名空间可以直接访问内联命名空间的成员 |
| 版本切换 | 修改 `inline` 关键字的位置即可切换默认版本 |
| ABI兼容 | 内联命名空间的符号与外层命名空间共享 `mangled name` |
| 模板特化 | 外层命名空间可以特化内联命名空间中的模板 |

### 5. 命名空间与函数重载

命名空间对函数重载有重要影响：

```cpp
namespace NS {
    void process(int x) { std::cout << "NS process(int)" << std::endl; }
}

void process(double x) { std::cout << "global process(double)" << std::endl; }

void demo() {
    process(3.14);      // 调用全局 process(double)
    NS::process(42);    // 调用 NS::process(int)

    using NS::process;  // using 声明引入重载
    process(42);        // 调用 NS::process(int)
    process(3.14);      // ⚠️ 仍然调用 NS::process(int)！全局版本被隐藏
}
```

## 5. 命名空间与库设计

### 1. 为库设计命名空间

命名空间是库设计中最重要的组织工具之一。一个设计良好的命名空间结构应该：

- **名称唯一**：避免与其他库冲突
- **层次清晰**：反映模块的逻辑关系
- **易于使用**：用户不需要写过长的限定名

```cpp
// 一个典型的库命名空间设计
namespace reai {                    // 顶层：公司/组织名
    namespace network {             // 子模块：网络
        class HttpClient { /* ... */ };
        class TcpSocket { /* ... */ };
        namespace detail {          // 实现细节（用户不应直接使用）
            class ConnectionPool { /* ... */ };
        }
    }
    namespace math {                // 子模块：数学
        class Matrix { /* ... */ };
        class Vector { /* ... */ };
    }
}
```

### 2. `detail` 子命名空间模式

在C++库设计中，`detail` 是一个广泛使用的约定，用于存放**实现细节**：

```cpp
namespace mylib {
    // 公共API
    template<typename T>
    void sort(Container<T>& c) {
        detail::sort_impl(c.begin(), c.end());
    }

    // 实现细节——用户不应直接使用
    namespace detail {
        template<typename Iterator>
        void sort_impl(Iterator begin, Iterator end) {
            // 具体排序实现
        }

        // 辅助元函数
        template<typename T>
        struct type_traits { /* ... */ };
    }
}
```

> 💡 **提示**：`detail` 命名空间是一种约定，而非语言强制。但几乎所有主流C++库（Boost、Range-v3、fmtlib 等）都遵循这一约定。用户如果直接使用 `detail` 中的内容，后果自负。

### 3. 版本化命名空间

使用内联命名空间实现库的版本管理：

```cpp
namespace mylib {
    inline namespace v2 {
        // 当前版本API
        template<typename T>
        auto transform(const std::vector<T>& v) -> std::vector<T>;
    }

    namespace v1 {
        // 旧版本API，仍可使用
        void transform_legacy(int* data, size_t size);
    }
}

// 用户代码
mylib::transform(vec);       // 使用 v2
mylib::v1::transform_legacy(data, size);  // 使用 v1
```

### 4. 命名空间与头文件组织

良好的命名空间设计应与头文件结构对应：

```cpp
// ===== mylib/math.hpp =====
namespace mylib::math {
    class Matrix { /* ... */ };
    class Vector { /* ... */ };
}

// ===== mylib/network.hpp =====
namespace mylib::network {
    class HttpClient { /* ... */ };
}

// ===== mylib/all.hpp =====  (便捷头文件)
#include "mylib/math.hpp"
#include "mylib/network.hpp"
// 用户只需 #include <mylib/all.hpp>
```

### 5. 避免过度嵌套

虽然命名空间可以无限嵌套，但过深的嵌套会降低代码可读性：

```cpp
// ❌ 过度嵌套
namespace company::project::module::submodule::feature::detail {
    class MyClass {};  // 访问时需要写一长串限定名
}

// ✅ 适当层级
namespace company::project::feature {
    namespace detail {
        class MyClass {};
    }
}
```

**经验法则**：命名空间嵌套深度一般不超过3层，使用别名来简化过长的限定名。

## 6. ADL（参数依赖查找）

### 1. ADL基本概念

ADL（`Argument-Dependent Lookup`，参数依赖查找），也称为 Koenig 查找（以其发明者 Andrew Koenig 命名），是C++特有的名称查找规则：**编译器会根据函数参数的类型所属命名空间来查找函数**。

```cpp
namespace MyNamespace {
    struct MyType {};
    void process(MyType) { std::cout << "MyNamespace::process" << std::endl; }
}

int main() {
    MyNamespace::MyType obj;
    process(obj);  // ADL：编译器在 MyNamespace 中查找 process
    return 0;
}
```

上面的代码中，虽然 `process` 没有加 `MyNamespace::` 限定，但编译器通过 ADL 找到了 `MyNamespace::process`，因为参数 `obj` 的类型 `MyNamespace::MyType` 属于 `MyNamespace` 命名空间。

### 2. ADL为什么重要

ADL 最典型的应用场景是**运算符重载**：

```cpp
namespace std {
    // 标准库中 operator<< 的重载
    template<typename CharT, typename Traits>
    class basic_ostream { /* ... */ };

    // 为各种类型重载 operator<<
}

namespace MyLib {
    class BigNum {
        // ...
        friend std::ostream& operator<<(std::ostream& os, const BigNum& n) {
            return os << n.to_string();
        }
    };
}

int main() {
    MyLib::BigNum num;
    std::cout << num;  // ADL 生效！
    // 编译器查找 operator<< 时，除了 std 命名空间，
    // 还会在参数 num 的命名空间 MyLib 中查找
}
```

如果没有 ADL，你必须写成 `MyLib::operator<<(std::cout, num)`，这显然违背了运算符重载的设计初衷。

### 3. ADL的查找规则

当编译器遇到一个无限定的函数调用时，ADL会在以下关联命名空间中查找：

```cpp
namespace A {
    namespace B {
        struct Point {};       // 类类型定义在 A::B 中
        void draw(Point) {}   // ADL 可以找到
    }

    void render(B::Point) {}  // ADL 也可以找到（外层命名空间）
}

void demo() {
    A::B::Point p;
    draw(p);     // ✅ ADL 找到 A::B::draw
    render(p);   // ✅ ADL 找到 A::render
}
```

ADL 的关联命名空间包括：

| 参数类型 | 查找的命名空间 |
|---------|--------------|
| 类类型 `T` | `T` 所属的命名空间及其外层命名空间 |
| 类模板特化 `T<A, B>` | `T`、`A`、`B` 所属的命名空间 |
| 指针类型 `T*` | `T` 所属的命名空间 |
| 引用类型 `T&` | `T` 所属的命名空间 |

### 4. ADL与 `std::swap` 的经典案例

ADL 最常见的实际应用之一是自定义 `swap` 函数：

```cpp
namespace mylib {
    class Matrix {
        int* data_;
        size_t size_;
    public:
        Matrix(size_t s) : data_(new int[s]()), size_(s) {}
        ~Matrix() { delete[] data_; }

        // 在类的命名空间中提供 swap
        friend void swap(Matrix& a, Matrix& b) noexcept {
            using std::swap;  // 引入 std::swap 作为后备
            swap(a.data_, b.data_);
            swap(a.size_, b.size_);
        }
    };
}

void demo() {
    using std::swap;   // 引入 std::swap
    mylib::Matrix a(100), b(200);
    swap(a, b);        // ADL 找到 mylib::swap，而非 std::swap
}
```

> 💡 **提示**：这就是为什么C++惯用法推荐 `using std::swap; swap(a, b);` 而非 `std::swap(a, b);`——前者可以通过 ADL 调用用户自定义的高效 `swap`，后者只能调用标准库的通用版本（可能涉及不必要的拷贝）。

### 5. ADL的陷阱

ADL 有时会产生令人意外的行为：

```cpp
namespace Lib {
    struct Data {};
    void process(Data) { std::cout << "Lib::process" << std::endl; }
}

void process(const Lib::Data& d) {
    std::cout << "global process" << std::endl;
}

void demo() {
    Lib::Data d;
    process(d);  // ⚠️ 二义性！Lib::process 和全局 process 都匹配
}
```

**防御ADL意外行为的策略**：

```cpp
// 策略1：使用完整限定名
Lib::process(d);  // 明确指定

// 策略2：在函数调用外层加括号
(process)(d);     // 禁用 ADL！只查找普通名称查找的结果

// 策略3：避免在全局命名空间中定义与库函数同名的函数
```

> 🔬 **深入理解**：在函数名外加括号 `(func)(args)` 会禁用 ADL。这是因为C++标准规定，ADL 只在"无限定的函数名"上触发，而加括号的表达式不再是简单的无限定标识符。

## 8. 最佳实践与常见陷阱

### 1. 命名空间最佳实践

```cpp
// ✅ 为项目使用唯一的顶层命名空间
namespace mycompany_mycrypto {
    class AES { /* ... */ };
}

// ✅ 使用 C++17 嵌套命名空间语法
namespace mycompany::crypto::v2 {
    class AES { /* ... */ };
}

// ✅ 在 .cpp 文件中使用匿名命名空间替代 static
namespace {
    const int kBufferSize = 4096;  // 内部链接常量
    bool validate_key(const std::string& key) { /* ... */ return true; }
}

// ✅ 使用 detail 命名空间隐藏实现细节
namespace mylib::detail {
    // 用户不应直接使用的内部实现
}
```

### 2. 常见陷阱

#### 陷阱1：头文件中的 `using namespace`

```cpp
// ❌ 危险！头文件中的 using namespace 影响所有包含者
// math_utils.h
#include <vector>
using namespace std;  // 污染所有包含此头文件的代码

// 用户代码
#include "math_utils.h"
#include <list>
// 现在 std 的所有符号都在全局作用域中
// 可能与用户自己的代码冲突
```

```cpp
// ✅ 正确做法：头文件中使用完整限定
// math_utils.h
#include <vector>

class MathUtils {
    static std::vector<double> compute(const std::vector<double>& input);
};
```

#### 陷阱2：命名空间中的名称遮蔽

```cpp
namespace Outer {
    int value = 10;

    namespace Inner {
        int value = 20;  // 遮蔽了 Outer::value

        void demo() {
            std::cout << value << std::endl;        // 20（Inner::value）
            std::cout << Outer::value << std::endl; // 10（显式指定）
        }
    }
}
```

#### 陷阱3：匿名命名空间中的非局部变量

```cpp
// ❌ 匿名命名空间中的变量在每次包含时都会生成独立副本
// header.h
namespace {
    int counter = 0;  // 每个 .cpp 包含此头文件都会有独立的 counter
}

// ✅ 如果需要跨文件共享，使用 extern 或内联函数
inline int& get_counter() {
    static int counter = 0;  // C++17 保证唯一实例
    return counter;
}
```

#### 陷阱4：ADL导致的意外调用

```cpp
namespace Lib {
    struct Data {};
    void swap(Data&, Data&) { /* 自定义交换 */ }
}

void demo() {
    using std::swap;
    Lib::Data a, b;
    swap(a, b);  // ✅ ADL 找到 Lib::swap

    // 但如果有人写了：
    std::swap(a, b);  // ❌ 绕过了自定义 swap，可能效率低下
}
```

#### 陷阱5：跨翻译单元的命名空间不一致

```cpp
// file_a.h
namespace MyLib {  // 注意：拼写为 MyLib
    void funcA();
}

// file_b.h
namespace Mylib {  // ❌ 拼写错误！Mylib ≠ MyLib
    void funcB();
}

// 这是两个不同的命名空间！
MyLib::funcA();   // OK
Mylib::funcB();   // OK，但与 MyLib 无关
// MyLib::funcB();  // ❌ 错误：funcB 不在 MyLib 中
```

### 3. 命名空间设计检查清单

在为项目设计命名空间时，参考以下检查清单：

- [ ] 顶层命名空间名称是否足够唯一（避免与常见库冲突）？
- [ ] 命名空间层次是否反映了模块的逻辑结构？
- [ ] 实现细节是否放在 `detail` 子命名空间中？
- [ ] 是否使用了内联命名空间进行版本管理？
- [ ] 头文件中是否避免了 `using namespace`？
- [ ] 匿名命名空间是否替代了 `static`？
- [ ] 命名空间别名是否用于简化过长的限定名？
- [ ] 自定义类型是否提供了 ADL 可发现的 `swap`？

### 4. 编码规范检查清单

- [ ] 命名风格是否在整个项目中保持一致？
- [ ] 类名是否使用 PascalCase？
- [ ] 成员变量是否有统一的命名约定（如 `name_` 后缀）？
- [ ] 常量是否使用 `constexpr`/`const` 而非宏？
- [ ] `#include` 顺序是否遵循规范？
- [ ] 是否配置了 `clang-format` 等格式化工具？
- [ ] 注释是否使用 Doxygen 风格？
- [ ] 是否避免了"魔法数字"（硬编码的常量值）？

## 9. 本章小结

### 1. 核心知识点

| 概念 | 说明 | 使用场景 |
|------|------|---------|
| 命名空间 | 避免名字冲突的机制 | 大型项目、库开发 |
| using声明 | 引入单个命名空间成员 | 函数内使用，安全可控 |
| using指令 | 引入整个命名空间 | 仅在 .cpp 文件中使用 |
| 匿名命名空间 | 替代 `static` 实现内部链接 | 文件级私有变量和函数 |
| 内联命名空间 | 版本管理 | 库的版本化发布 |
| 命名空间别名 | 简化长命名空间 | 深层嵌套命名空间 |
| ADL | 参数依赖查找 | 运算符重载、自定义类型函数 |
| 编码规范 | 统一代码风格 | 团队协作、开源项目 |

### 2. 关键规范

1. **头文件中永远不要使用 `using namespace std;`**
2. **使用完整限定名 `std::cout` 而不是裸写 `cout`**
3. **类名使用 PascalCase，函数和变量使用 snake_case**
4. **保持代码风格一致，使用代码格式化工具**
5. **使用匿名命名空间替代 `static`**
6. **用 `detail` 子命名空间隐藏实现细节**
7. **为自定义类型提供 ADL 可发现的 `swap`**
