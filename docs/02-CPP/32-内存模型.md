> 💡 **通俗理解 - 什么是内存模型？**

想象一个公司里有多个员工（线程）共用一块白板（内存）：

**问题1：指令重排 = 员工做事的顺序可能被打乱**

```
老板说：先写报告A，再写报告B

但实际发生：
- 编译器优化：发现写B更快，先做B再做A
- CPU执行：两个核心同时工作，顺序不确定

结果：其他员工来看白板时，可能看到B完成了但A还没开始！
```

**问题2：可见性 = 一个人写的东西，其他人不一定马上能看到**

```
员工甲在白板上写了"项目完成"
但由于缓存机制，这个信息还在甲的笔记本里（CPU缓存）
员工乙去看白板，看到的还是旧信息"进行中"

这就是"可见性问题"！
```

**内存模型就是"公司规章制度"：**
- 规定什么情况下可以调整做事顺序
- 规定什么时候必须通知其他人
- 保证大家看到的白板信息是一致的

> 🔬 **抽象理解 - 内存模型的本质**：
>
> - **内存模型**：定义了多线程程序中，读写操作如何影响内存，以及这些操作的顺序和可见性规则
> - **happens-before**：是一种"因果关系"，如果A happens-before B，那么A的结果对B一定可见
> - **内存序**：控制编译器和CPU的重排行为，以及数据在不同线程间的可见性时机
> - **核心价值**：让程序员能够在性能和正确性之间做出权衡

## 1. 内存模型基础

### 1. 为什么需要内存模型

**生活中的例子：快递分拣中心**

想象一个快递分拣中心，有多个工人（线程）处理包裹（数据）：

```
源代码顺序        编译器重排        CPU重排
扫描包裹A         扫描包裹A         扫描包裹B
贴标签B          贴标签B          扫描包裹A

// 单个工人：最终结果一样
// 多个工人协作：可能导致包裹B已经发走，但A还没扫描！
```

### 2. 两大问题

| 问题 | 生活比喻 | 技术说明 |
|------|---------|----------|
| **重排** | 厨师做菜时先炒菜后洗菜（为了效率） | 编译器/CPU可能重排指令顺序 |
| **可见性** | 一个人在手机上发消息，其他人要等服务器同步才能看到 | 一个线程的修改何时对其他线程可见 |

### 3. 单线程 vs 多线程

```cpp
// 单线程：完全没问题
int a = 1;
int b = 2;
// 无论怎么重排，最后a=1, b=2

// 多线程：可能出问题！
// 线程1:
data = 42;      // A
ready = true;   // B

// 线程2:
if (ready) {    // C
    print(data); // D：可能打印0而不是42！
}
```

## 2. happens-before关系

### 1. 核心概念

**happens-before = "因果关系"或"先后保证"**

> 💡 **生活比喻：多米诺骨牌**

想象一排多米诺骨牌：
- 如果A倒下会导致B倒下，那么"A happens-before B"
- A的效果（倒下）对B可见
- A一定在B之前发生

**三种建立方式：**

| 类型 | 比喻 | 代码示例 |
|------|------|----------|
| **sequenced-before** | 同一人做事的先后顺序 | `a=1; b=2;` 在同一线程 |
| **synchronizes-with** | 两个人之间的信号传递 | 线程1发信号，线程2收到 |
| **transitive** | 传递性：A→B, B→C 则 A→C | 连锁反应 |

### 2. 示例详解

```cpp
int data = 0;
bool ready = false;

// 线程1（生产者）
data = 42;              // A：准备数据
ready.store(true, std::memory_order_release);  // B：发布信号（release）

// 线程2（消费者）
while (!ready.load(std::memory_order_acquire)) {}  // C：等待信号（acquire）
assert(data == 42);     // D：使用数据

// 因果关系链：
// A sequenced-before B  （同一线程内顺序）
// B synchronizes-with C  （release-acquire同步）
// C sequenced-before D   （同一线程内顺序）
// 
// 根据传递性：A happens-before D
// 所以D一定能看到A的效果：data == 42
```

> 🔬 **抽象理解**：
>
> happens-before不是时间上的先后，而是**逻辑上的因果**。即使B在物理时间上先执行，只要A happens-before B，A的效果对B就一定是可见的。

## 3. 数据竞争

### 1. 正式定义

> 💡 **生活比喻：两个人同时改同一份文件**

想象两个人（线程）同时编辑同一份共享文档：
- 一个人在写第3页，另一个人也在写第3页 → **冲突！**
- 一个人在写第3页，另一个人在读第3页 → **可能读到半新半旧的内容！**
- 一个人在写第3页，另一个人在读第5页 → **没问题**

**C++标准中的正式定义：**

一个程序包含**数据竞争**（data race），当且仅当满足以下所有条件：

1. 两个不同的线程**同时访问**同一内存位置
2. 至少一个是**写操作**（非原子写）
3. 它们之间**没有happens-before关系**

```
数据竞争 = 并发访问 + 至少一个写 + 无happens-before

线程1: write(x)  ──┐
                    ├── 同时！无happens-before → 数据竞争！
线程2: write(x)  ──┘

线程1: write(x)  ──┐
                    ├── 同时！无happens-before → 数据竞争！
线程2: read(x)   ──┘

线程1: read(x)   ──┐
                    ├── 同时！但都是读 → 不是数据竞争
线程2: read(x)   ──┘
```

### 2. 数据竞争导致未定义行为

> ⚠️ **关键：数据竞争不是"可能出错"，是"任何结果都可能"！**

C++标准明确规定：包含数据竞争的程序具有**未定义行为**（Undefined Behavior）。这意味着：

| 你可能以为的 | 实际可能发生的 |
|-------------|---------------|
| 读到旧值 | 读到半写半旧的"撕裂值" |
| 读到新值 | 编译器优化后根本不读内存 |
| 结果不确定但合理 | 程序崩溃、死循环、甚至更诡异的行为 |

```cpp
int counter = 0;  // 非原子变量

// 线程1
counter++;  // 读-改-写，不是原子操作

// 线程2
counter++;  // 同样读-改-写

// 数据竞争！可能结果：counter == 1（丢失一次更新）
// 也可能：counter == 2（恰好交错正确）
// 也可能：任何其他值（未定义行为！）
```

### 3. 数据竞争 vs 竞态条件

> 💡 **生活比喻：数据竞争 vs 竞态条件**

- **数据竞争**：两个人同时改同一行代码 → 违反规则，必须避免
- **竞态条件**：两个人按顺序改，但顺序不同结果不同 → 逻辑问题，需要设计

| 特性 | 数据竞争（Data Race） | 竞态条件（Race Condition） |
|------|----------------------|---------------------------|
| **本质** | 同时访问同一内存，至少一个写 | 时序依赖导致结果不正确 |
| **后果** | 未定义行为（C++标准规定） | 逻辑错误，但行为是定义好的 |
| **是否必须消除** | **必须**，否则程序无意义 | 视需求而定，有时可容忍 |
| **消除方式** | 互斥锁/原子操作 | 更好的算法设计 |
| **关系** | 数据竞争一定是竞态条件 | 竞态条件不一定有数据竞争 |

```cpp
// 竞态条件但无数据竞争（用锁保护了）
std::mutex mtx;
int balance = 100;

void withdraw(int amount) {
    std::lock_guard<std::mutex> lock(mtx);  // 无数据竞争
    if (balance >= amount) {
        balance -= amount;  // 但如果两个线程同时检查balance >= amount
    }                       // 可能都通过检查，导致余额为负
}                           // 这是竞态条件，不是数据竞争

// 数据竞争（无任何保护）
int shared = 0;
// 线程1: shared = 1;
// 线程2: shared = 2;
// 同时写入，无happens-before → 数据竞争！
```

### 4. 示例：一个简单的数据竞争

```cpp
#include <iostream>
#include <thread>

int shared_value = 0;  // 非原子变量，无保护

void writer() {
    shared_value = 42;  // 写操作
}

void reader() {
    std::cout << shared_value << std::endl;  // 读操作
    // 可能输出：0、42、或其他任何值（未定义行为）
}

int main() {
    std::thread t1(writer);
    std::thread t2(reader);
    t1.join();
    t2.join();
    return 0;
}
```

### 5. 如何消除数据竞争

| 方法 | 适用场景 | 示例 |
|------|---------|------|
| **互斥锁** | 保护复杂临界区 | `std::mutex` + `std::lock_guard` |
| **原子操作** | 简单的标志位、计数器 | `std::atomic<int>` |
| **线程局部存储** | 每个线程需要独立副本 | `thread_local` |

```cpp
// 方法1：互斥锁
std::mutex mtx;
int shared_value = 0;

void safe_writer() {
    std::lock_guard<std::mutex> lock(mtx);
    shared_value = 42;
}

void safe_reader() {
    std::lock_guard<std::mutex> lock(mtx);
    std::cout << shared_value << std::endl;
}

// 方法2：原子操作
std::atomic<int> atomic_value{0};

void safe_atomic_writer() {
    atomic_value.store(42, std::memory_order_release);
}

void safe_atomic_reader() {
    std::cout << atomic_value.load(std::memory_order_acquire) << std::endl;
}

// 方法3：线程局部存储
thread_local int local_value = 0;  // 每个线程有自己的副本

void thread_func() {
    local_value = 42;  // 无竞争，每个线程独立
}
```

## 4. 修改顺序与释放序列

### 1. 修改顺序（Modification Order）

> 💡 **生活比喻：版本控制系统**

想象一个共享文档的版本历史：
- 每次修改都产生一个新版本
- 所有人看到的版本顺序是一致的
- 但不同人可能看到的是不同版本（有人还没拉取最新）

**C++标准保证：**

对于同一个原子变量的所有写操作，存在一个**全局一致的修改顺序**（modification order）。所有线程对这个原子变量的写入，在修改顺序中都有一个确定的位置。

```
原子变量 x 的修改顺序（全局一致）：

时间 →  x=0  →  x=1  →  x=3  →  x=5  →  x=2
         ↑       ↑       ↑       ↑       ↑
       初始值  线程A写  线程B写  线程A写  线程C写

所有线程看到的写入顺序都是：0 → 1 → 3 → 5 → 2
但不同线程可能"看到"不同的当前值（取决于读取时机）
```

**关键规则：**

| 规则 | 说明 |
|------|------|
| 写入有全序 | 同一原子变量的所有写操作有全局一致的顺序 |
| 读取看到某次写入 | 读操作看到修改顺序中某次写入的值 |
| 不能看到"过去"的值 | 一旦看到了某次写入，不会再看到更早的写入 |
| relaxed也遵守 | 即使是relaxed内存序，修改顺序也是一致的 |

```cpp
std::atomic<int> x{0};

// 线程A
x.store(1, std::memory_order_relaxed);

// 线程B
x.store(2, std::memory_order_relaxed);

// 线程C
int r = x.load(std::memory_order_relaxed);
// r 可能是 0、1 或 2
// 但修改顺序一定是 0→1→2 或 0→2→1 之一（全局一致）
// 不存在线程D看到0→1→2而线程E看到0→2→1的情况
```

### 2. 释放序列（Release Sequence）

> 💡 **生活比喻：接力传递**

想象一个接力赛跑：
- 第一棒（release）把接力棒传出去
- 中间的选手（同一线程的后续写操作）继续传递
- 最后一棒（acquire）接住

**释放序列的定义：**

一个release操作A之后的**释放序列**包含以下操作：

1. 由**同一线程**在A之后对同一原子变量执行的写操作
2. 任何线程对同一原子变量的read-modify-write操作（如`fetch_add`、`compare_exchange`）

```
释放序列示意图：

线程1（生产者）:  store(release) → store(relaxed) → store(relaxed)
                   └────── 释放序列 ──────────────────────┘

线程2（中间者）:  fetch_add(relaxed)  ← RMW操作，也属于释放序列

线程3（消费者）:  load(acquire)  ← 可以与线程1的release建立synchronizes-with
```

### 3. 释放序列如何扩展synchronizes-with关系

**核心规则：** 如果一个acquire操作读取了释放序列中的某个值，那么release操作与acquire操作之间建立synchronizes-with关系。

```
没有释放序列时：
  release(A) ──→ 只有直接读到A的acquire才能同步

有释放序列时：
  release(A) ──→ relaxed写(B) ──→ relaxed写(C) ──→ acquire读到C
  └────────── 释放序列 ──────────────────────────┘
  A synchronizes-with acquire（即使acquire读到的是C而不是A！）
```

### 4. 代码示例：释放序列在生产者-消费者中的作用

```cpp
#include <atomic>
#include <thread>
#include <vector>
#include <iostream>

std::atomic<int> index{0};
int data[10];

void producer() {
    for (int i = 0; i < 5; ++i) {
        data[i] = i * 10;
        // 第一次store是release，后续是relaxed
        // 但它们都在同一个释放序列中
        if (i == 0) {
            index.store(i + 1, std::memory_order_release);  // release操作
        } else {
            index.store(i + 1, std::memory_order_relaxed);  // 同一线程的后续写
        }
    }
}

void consumer() {
    int expected = 0;
    // compare_exchange_weak是RMW操作，属于释放序列
    // 即使没有直接读到release写入的值，也能建立同步
    while (index.load(std::memory_order_acquire) < 5) {
        // 等待生产者完成
    }
    // 由于释放序列，所有data[0..4]的写入对消费者可见
    for (int i = 0; i < 5; ++i) {
        std::cout << "data[" << i << "] = " << data[i] << std::endl;
    }
}

int main() {
    std::thread t1(producer);
    std::thread t2(consumer);
    t1.join();
    t2.join();
    return 0;
}
```

> 🔬 **抽象理解**：
>
> 释放序列的意义在于：**一次release可以"覆盖"后续多个relaxed写操作**。生产者只需在第一次写入时使用release，后续的relaxed写入也能被消费者正确感知，从而减少不必要的同步开销。

## 5. 内存栅栏

### 1. 什么是内存栅栏？

> 💡 **生活比喻：检查站**

想象一条公路上有检查站（栅栏）：
- 检查站之前的车辆必须全部通过，才能开放后面的道路
- 检查站之后的车辆必须等待检查站开放
- 检查站本身不搬运货物，只控制通行顺序

**内存栅栏（Memory Fence/Barrier）** 是一种同步原语，它：
- 不执行任何数据读写
- 只限制编译器和CPU的**指令重排**
- 确保栅栏前后的内存操作不会跨越栅栏

### 2. 两种栅栏

| 栅栏 | 作用域 | 头文件 |
|------|--------|--------|
| `std::atomic_thread_fence` | 线程间同步 | `<atomic>` |
| `std::atomic_signal_fence` | 信号处理函数与主程序间同步 | `<atomic>` |

### 3. std::atomic_thread_fence

**线程间栅栏**，用于在多线程环境中建立同步关系。

```cpp
#include <atomic>

// 栅栏的内存序参数决定了栅栏的类型
// acquire栅栏：栅栏之后的读写不能重排到栅栏之前
std::atomic_thread_fence(std::memory_order_acquire);

// release栅栏：栅栏之前的读写不能重排到栅栏之后
std::atomic_thread_fence(std::memory_order_release);

// seq_cst栅栏：同时具有acquire和release语义，且参与全局顺序
std::atomic_thread_fence(std::memory_order_seq_cst);
```

### 4. std::atomic_signal_fence

**信号处理函数与主程序间的栅栏**，用于信号处理函数（signal handler）与主程序之间的同步。

```cpp
#include <atomic>
#include <csignal>

volatile sig_atomic_t signal_flag = 0;
int shared_data = 0;

void signal_handler(int) {
    // 信号处理函数中设置标志
    signal_flag = 1;
    // 确保signal_flag的写入在shared_data写入之后
    std::atomic_signal_fence(std::memory_order_release);
}

int main() {
    shared_data = 42;
    // 确保shared_data的写入在signal_flag写入之前
    std::atomic_signal_fence(std::memory_order_release);
    signal_flag = 0;

    std::signal(SIGINT, signal_handler);

    while (!signal_flag) {
        // 等待信号
    }
    // 确保读取signal_flag之后再读取shared_data
    std::atomic_signal_fence(std::memory_order_acquire);
    // 此时shared_data == 42 是保证的
    return 0;
}
```

> ⚠️ **注意**：`atomic_signal_fence`不产生任何硬件屏障指令，它只限制编译器的重排。因为信号处理函数与主程序运行在同一线程，不需要处理器间的同步。

### 5. 栅栏与原子操作内存序参数的区别

| 特性 | 原子操作的内存序参数 | 独立栅栏 |
|------|-------------------|---------|
| **绑定操作** | 绑定到特定的原子读/写操作 | 独立存在，不绑定任何操作 |
| **重排限制** | 只限制与该原子操作相关的重排 | 限制栅栏前后所有内存操作的重排 |
| **灵活性** | 简单直接，推荐优先使用 | 更灵活，可与非原子操作配合 |
| **典型用途** | 原子变量的同步 | 非原子变量与原子操作的协调 |

```
原子操作方式：
  写data → atomic.store(release)  // release绑定到store操作
  读data ← atomic.load(acquire)   // acquire绑定到load操作

栅栏方式：
  写data → fence(release) → atomic.store(relaxed)  // release独立于store
  读data ← fence(acquire) ← atomic.load(relaxed)   // acquire独立于load
```

### 6. 栅栏的使用场景

**场景：非原子变量与原子操作的协调**

当需要在非原子变量和原子变量之间建立同步时，栅栏特别有用。

```cpp
// 不使用栅栏：必须用原子操作包装所有同步
std::atomic<bool> ready{false};
int data = 0;

void producer() {
    data = 42;
    ready.store(true, std::memory_order_release);  // release绑定到ready
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {}  // acquire绑定到ready
    assert(data == 42);
}
```

### 7. 代码示例：用atomic_thread_fence实现release-acquire模式

```cpp
#include <atomic>
#include <thread>
#include <cassert>
#include <iostream>

std::atomic<bool> ready{false};
int data = 0;

void producer_with_fence() {
    data = 42;  // 非原子写
    // release栅栏：保证data的写入在栅栏之后的所有写之前完成
    std::atomic_thread_fence(std::memory_order_release);
    ready.store(true, std::memory_order_relaxed);  // relaxed即可，栅栏已提供保证
}

void consumer_with_fence() {
    while (!ready.load(std::memory_order_relaxed)) {}  // relaxed即可
    // acquire栅栏：保证在栅栏之后的所有读之前完成ready的读取
    std::atomic_thread_fence(std::memory_order_acquire);
    assert(data == 42);  // 保证看到producer的写入
    std::cout << "data = " << data << std::endl;
}

int main() {
    std::thread t1(producer_with_fence);
    std::thread t2(consumer_with_fence);
    t1.join();
    t2.join();
    return 0;
}
```

> 🔬 **抽象理解**：
>
> 栅栏的同步规则：
> - **release栅栏 + acquire栅栏**：如果acquire栅栏之后的读操作读到了release栅栏之前的写操作（通过原子变量传递），则release栅栏之前的所有写对acquire栅栏之后的所有读可见
> - 栅栏比原子操作的内存序参数更灵活，但更容易出错，**优先使用原子操作的内存序参数**

## 6. 硬件内存模型映射

### 1. 为什么需要了解硬件映射？

> 💡 **生活比喻：不同国家的交通规则**

C++内存模型是"国际交通规则"，但不同国家（硬件架构）有自己的实现方式：
- 有些国家规则严格（x86），大部分规则自动满足
- 有些国家规则宽松（ARM），需要更多显式操作

了解硬件映射有助于：
- 理解不同平台上并发程序的性能差异
- 排查平台相关的并发bug
- 做出更合理的内存序选择

### 2. x86的TSO模型

**Total Store Order（完全存储定序）** 是x86架构的内存模型：

```
x86 TSO特点：
1. 读操作不会与其他读操作重排
2. 写操作不会与其他写操作重排
3. 写操作不会与之前的读操作重排
4. 读操作可能与之前的写操作重排（StoreLoad重排）← 唯一允许的重排！

     CPU核心           写缓冲区          内存
写操作 ──→ [写缓冲区] ──→ 内存
读操作 ──→ 先查写缓冲区 → 再查内存

每个核心有自己的写缓冲区，读操作可能从自己的写缓冲区读到"还没到内存"的值
```

**x86 TSO的含义：**

| C++操作 | x86是否自动满足 | 需要额外指令 |
|---------|----------------|-------------|
| acquire load | ✅ 自动满足 | 无 |
| release store | ✅ 自动满足 | 无 |
| StoreLoad顺序 | ❌ 不满足 | `mfence` 或 `lock` 前缀指令 |
| seq_cst | 需要保证StoreLoad | `mfence` 或 `lock xchg` |

### 3. ARM的弱序模型

**Weakly Ordered（弱序）** 是ARM架构的内存模型：

```
ARM弱序特点：
1. 读操作可能与读操作重排
2. 写操作可能与写操作重排
3. 读操作可能与写操作重排
4. 写操作可能与读操作重排
← 几乎所有重排都可能发生！

     CPU核心
读操作 ──→ 可能重排
写操作 ──→ 可能重排

需要显式的屏障指令来保证顺序
```

**ARM的屏障指令：**

| 指令 | 全称 | 作用 |
|------|------|------|
| `dmb` | Data Memory Barrier | 数据内存屏障，保证屏障前后的内存操作顺序 |
| `dsb` | Data Synchronization Barrier | 数据同步屏障，比dmb更强，等待所有内存操作完成 |
| `isb` | Instruction Synchronization Barrier | 指令同步屏障，刷新流水线 |

### 4. C++内存序到硬件屏障的映射表

| C++内存序 | x86 | ARM |
|-----------|-----|-----|
| `relaxed` | 无屏障 | 无屏障 |
| `acquire` | 无额外屏障（TSO自动满足） | `dmb ish`（数据内存屏障） |
| `release` | 无额外屏障（TSO自动满足） | `dmb ish`（数据内存屏障） |
| `acq_rel` | 无额外屏障（TSO自动满足） | `dmb ish`（数据内存屏障） |
| `seq_cst` | `mfence` 或 `lock xchg` | `dmb ish` + `dsb ish` |

**映射解读：**

```
relaxed：
  x86 → 无指令（本身就不需要）
  ARM → 无指令（但可能被重排）

acquire（读操作）：
  x86 → 普通mov指令即可（TSO保证读不会与后面的操作重排）
  ARM → dmb ish（防止读与后面的操作重排）

release（写操作）：
  x86 → 普通mov指令即可（TSO保证写不会与前面的操作重排）
  ARM → dmb ish（防止写与前面的操作重排）

seq_cst：
  x86 → mfence（防止StoreLoad重排）或 lock xchg（原子交换）
  ARM → dmb ish + dsb ish（完全屏障）
```

### 5. 性能影响对比

```cpp
// 同一段代码在不同架构上的性能差异

std::atomic<int> counter{0};

// relaxed：x86和ARM都无额外开销
counter.fetch_add(1, std::memory_order_relaxed);
// x86: lock inc [counter]      ← 只需要原子性，不需要屏障
// ARM: ldaxr + stlxr           ← 独占访问，无屏障

// seq_cst：x86需要mfence，ARM需要完整屏障
counter.fetch_add(1, std::memory_order_seq_cst);
// x86: lock xadd [counter]     ← lock前缀隐含了mfence语义
// ARM: dmb ish + ldaxr + stlxr + dmb ish  ← 前后都需要屏障
```

> 🔬 **抽象理解**：
>
> - x86是"强序"架构，大部分C++内存序自动满足，只有seq_cst需要额外开销
> - ARM是"弱序"架构，除了relaxed外都需要显式屏障指令
> - 这就是为什么在ARM上选择合适的内存序对性能影响更大
> - **在x86上用seq_cst"以防万一"开销不大，但在ARM上可能显著影响性能**

## 7. 内存序详解

### 1. 什么是内存序？

> 💡 **生活比喻：快递配送的不同级别**

想象你在网上购物，选择不同的配送方式：

| 配送方式 | 速度 | 保证 | 适用场景 |
|---------|------|------|----------|
| **普通快递（relaxed）** | 最快 | 只保证送到，不保证顺序 | 不着急的东西 |
| **次日达（acquire/release）** | 较快 | 保证第二天到 | 一般紧急 |
| **顺丰特快（seq_cst）** | 最慢 | 保证按顺序送达 | 非常重要的文件 |

**内存序就是"数据配送的速度和保证级别"！**

### 2. 六种内存序详解

| 内存序 | 生活比喻 | 技术说明 | 开销 |
|--------|---------|----------|------|
| `memory_order_relaxed` | 普通平邮，只保证到达 | 无同步，只保证原子性 | 最低 ⚡ |
| `memory_order_consume` | 部分签收（已弃用） | 依赖数据的操作不能重排 | 低 |
| `memory_order_acquire` | 收件人签收 | 读操作，后续读写不能重排到此之前 | 低 📥 |
| `memory_order_release` | 发件人发货 | 写操作，之前读写不能重排到此之后 | 低 📤 |
| `memory_order_acq_rel` | 双向确认 | 读-修改-写，同时具有acquire和release | 中 ↔️ |
| `memory_order_seq_cst` | 挂号信，全局排序 | 顺序一致性，所有线程看到相同顺序 | 最高 🔒 |

### 3. 内存序关系图

```
                  同步强度（保证程度）
relaxed ← consume ← acquire ← acq_rel ← seq_cst
                release ← acq_rel ← seq_cst

                  性能开销（速度）
relaxed → consume → acquire → acq_rel → seq_cst
                release → acq_rel → seq_cst

💡 记忆口诀：越强的保证 = 越慢的速度
```

### 4. 选择指南

| 场景 | 推荐内存序 | 理由 |
|------|-----------|------|
| 简单计数器 | `relaxed` | 只需要原子性，不需要同步 |
| 标志位设置 | `release` | 发布数据给其他线程 |
| 标志位读取 | `acquire` | 等待其他线程的数据 |
| 生产者-消费者 | `acquire/release` | 成对使用，建立同步 |
| 复杂同步逻辑 | `seq_cst` | 最简单，最安全 |
| **不确定时** | **`seq_cst`** | **安全优先！** |

## 8. 原子操作与内存序

### 1. relaxed - 无同步

```cpp
std::atomic<int> counter{0};

void increment() {
    counter.fetch_add(1, std::memory_order_relaxed);
    // 只保证计数器本身原子递增
    // 不保证其他变量的顺序
}
```

### 2. acquire/release - 生产者-消费者

```cpp
std::atomic<bool> ready{false};
int data = 0;

void producer() {
    data = 42;  // A
    ready.store(true, std::memory_order_release);  // B：release保证A在B之前
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {}  // C：acquire保证D在C之后
    assert(data == 42);  // D：保证看到A的效果
}
```

### 3. seq_cst - 顺序一致性（默认）

```cpp
std::atomic<bool> x{false}, y{false};
bool r1 = false, r2 = false;

// 线程1：先store x，再load y
x.store(true, std::memory_order_seq_cst);
r1 = y.load(std::memory_order_seq_cst);

// 线程2：先store y，再load x
y.store(true, std::memory_order_seq_cst);
r2 = x.load(std::memory_order_seq_cst);

// seq_cst保证：不可能 r1==false && r2==false
// （两个store在全局序中必有一个先于另一个load，
//   因此至少有一个load能看到对应的store为true）
// （relaxed可能发生：两个load都在两个store之前执行）
```

### 4. 选择指南

| 场景 | 推荐内存序 |
|------|-----------|
| 简单计数器 | `relaxed` |
| 生产者-消费者 | `acquire/release` |
| 复杂同步 | `seq_cst` |
| 不确定 | `seq_cst`（安全优先） |

## 9. 常见并发模式

### 1. 双重检查锁（DCLP）

```cpp
class Singleton {
    static std::atomic<Singleton*> instance;
    static std::mutex mtx;

public:
    static Singleton* getInstance() {
        Singleton* tmp = instance.load(std::memory_order_acquire);
        if (!tmp) {
            std::lock_guard<std::mutex> lock(mtx);
            tmp = instance.load(std::memory_order_relaxed);
            if (!tmp) {
                tmp = new Singleton();
                instance.store(tmp, std::memory_order_release);
            }
        }
        return tmp;
    }
};
```

### 2. 一次性初始化

```cpp
// C++11 更好的方式
std::once_flag flag;
BigObject* obj = nullptr;

void init() {
    std::call_once(flag, []() {
        obj = new BigObject();
    });
}
```
