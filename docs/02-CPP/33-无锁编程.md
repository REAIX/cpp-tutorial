> 💡 **通俗理解 - 什么是无锁编程？**

**传统加锁 = 排队上厕所**

想象一个公共厕所只有一个隔间（共享资源）：
- 第一个人进去，锁门（加锁）
- 其他人只能在外面等（阻塞）
- 如果这个人睡着了不出来（死锁），所有人都卡住
- 如果这个人突然晕倒（线程崩溃），其他人也进不去

**无锁编程 = 开放式更衣室**

想象健身房更衣室有很多储物柜：
- 每个人都有自己的柜子（局部操作）
- 想换柜子时，用CAS机制："如果这个柜子还是空的，我就占用它"
- 如果失败了（被别人占了），立即尝试下一个柜子（重试）
- 永远不会有人被卡住，总有人在进展

> 🔬 **抽象理解 - 无锁编程的本质**：
>
> - **无锁编程**：使用原子操作（特别是CAS）代替互斥锁，避免线程阻塞
> - **核心思想**：与其让失败的线程等待，不如让它重试或做其他事
> - **优势**：没有死锁风险，更好的并发性能，容错性更强
> - **代价**：代码复杂度高，容易出现ABA问题，调试困难
> - **适用场景**：高并发、低延迟要求的系统（如游戏引擎、高频交易）

## 1. 无锁编程基础

### 1. 进度保证级别

> 💡 **生活比喻：餐厅点餐的不同方式**

| 级别 | 餐厅比喻 | 技术说明 | 例子 |
|------|---------|----------|------|
| **阻塞（Blocking）** | 只有一个服务员，必须等他服务完当前顾客 | 锁可能导致死锁 | `std::mutex` |
| **无障碍（Obstruction-free）** | 如果其他顾客都走了，你总能点到餐 | 单独执行的线程总能完成 | 简单的CAS循环 |
| **无锁（Lock-free）** | 总有顾客能点到餐（可能不是你） | 至少一个线程总能取得进展 | `std::atomic` |
| **无等待（Wait-free）** | 每个顾客都能在固定时间内点到餐 | 每个线程总能在有限步内完成 | 复杂的无锁算法 |

**层级关系：**
```
阻塞 → 无障碍 → 无锁 → 无等待（保证越来越强，可实现难度越来越大）

集合关系：无等待 ⊂ 无锁 ⊂ 无障碍
（保证越强的算法集合越小，实现越难）
```

### 2. 核心工具：CAS操作

**CAS = Compare-And-Swap（比较并交换）**

> 💡 **生活比喻：自动售货机**

想象一台自动售货机：
```
你想买可乐（期望值 = 空槽位）

CAS操作流程：
1. 检查：这个槽位是空的吗？（Compare）
2. 如果是：放入硬币，取出可乐（Swap）
3. 如果不是（已被别人买了）：返回失败，重新选择

伪代码：
while (true) {
    if (槽位 == 空) {
        槽位 = 已购买;
        return 成功;
    } else {
        // 被别人抢先了，重试或放弃
        continue;
    }
}
```

```cpp
#include <atomic>

std::atomic<int> x{0};

// 原子读
int v = x.load(std::memory_order_acquire);

// 原子写
x.store(42, std::memory_order_release);

// CAS（Compare-And-Swap）
int expected = 0;
bool success = x.compare_exchange_weak(expected, 1);
// 如果 x == expected（都是0），则 x = 1，返回true
// 否则 expected = x的当前值，返回false
```

## 2. CAS操作

### 1. compare_exchange_weak vs strong

```cpp
std::atomic<int> x{0};

// weak：可能spurious failure（即使值匹配也可能返回false）
int expected = 0;
while (!x.compare_exchange_weak(expected, 1)) {
    // expected 已被更新为当前值
    // 在循环中使用weak通常更好（性能）
}

// strong：保证不会spurious failure
int exp = 0;
if (x.compare_exchange_strong(exp, 1)) {
    // 成功
}
```

### 2. CAS循环模式

```cpp
template<typename T>
bool atomic_update(std::atomic<T>& atom, T desired) {
    T expected = atom.load(std::memory_order_relaxed);
    while (!atom.compare_exchange_weak(expected, desired,
            std::memory_order_release, std::memory_order_relaxed)) {
        // CAS失败，expected已被更新，重试
    }
    return true;
}
```

## 3. 无锁栈

```cpp
#include <atomic>
#include <memory>

template<typename T>
class LockFreeStack {
    struct Node {
        T data;
        Node* next;
        Node(T val) : data(std::move(val)), next(nullptr) {}
    };

    std::atomic<Node*> head_{nullptr};

public:
    void push(T value) {
        Node* new_node = new Node(std::move(value));
        new_node->next = head_.load(std::memory_order_relaxed);

        while (!head_.compare_exchange_weak(new_node->next, new_node,
                std::memory_order_release, std::memory_order_relaxed)) {
            // CAS失败，new_node->next已被更新，重试
        }
    }

    std::optional<T> pop() {
        Node* old_head = head_.load(std::memory_order_acquire);

        while (old_head && !head_.compare_exchange_weak(old_head, old_head->next,
                std::memory_order_acquire, std::memory_order_relaxed)) {
            // CAS失败，重试
        }

        if (old_head) {
            T value = std::move(old_head->data);
            // 注意：这里存在内存回收问题（见ABA问题）
            // 简单起见，此处省略安全回收
            return value;
        }
        return std::nullopt;
    }
};
```

## 4. 无锁队列（Michael-Scott Queue）

### 1. 为什么需要无锁队列

> 💡 **生活比喻：食堂打饭 vs 传话游戏**

```
无锁栈 = 食堂打饭
  所有人都在同一个窗口排队，后到的人先拿到饭（LIFO）
  最后来的反而最先被服务，不公平

无锁队列 = 传话游戏
  按照到达顺序依次处理（FIFO），公平合理
  生产者从队尾加入，消费者从队头取走，互不干扰
```

无锁队列比无锁栈更实用，因为：
- **公平性**：FIFO保证先到先服务，避免饥饿
- **生产者-消费者模型**：队列天然支持多生产者、多消费者
- **更低争用**：入队操作tail，出队操作head，两端分离减少竞争

### 2. Michael-Scott队列的设计思想

> 💡 **比喻：医院叫号系统**

```
医院叫号系统：
  哨兵节点 = 当前叫号屏幕上显示的号码（不对应真实病人）
  入队 = 新病人取号，排在最后
  出队 = 叫下一个号，屏幕翻到下一位

关键：屏幕上显示的号码本身不是病人，只是标记"当前位置"
```

**核心设计：哨兵节点（dummy node）**

```
空队列：
  head → [dummy] ← tail
           ↓
          null

入队一个元素后：
  head → [dummy] → [A] ← tail
                    ↓
                   null

再入队一个元素：
  head → [dummy] → [A] → [B] ← tail
                           ↓
                          null
```

哨兵节点的作用：
- **统一操作**：无论队列是否为空，head和tail始终指向有效节点
- **避免空判断**：出队时只需移动head，不需要特殊处理空队列
- **简化CAS**：入队只需修改tail->next和tail，出队只需修改head

**入队操作：CAS修改tail指针**

```
入队流程（假设队列：head → [dummy] → [A] ← tail）：

步骤1：创建新节点
  new_node = [B]

步骤2：尝试将新节点链接到tail后面
  CAS(tail->next, null, new_node)
  成功：tail->next = [B]

步骤3：尝试移动tail
  CAS(tail, old_tail, new_node)
  成功：tail = [B]

结果：head → [dummy] → [A] → [B] ← tail
```

**出队操作：CAS修改head指针**

```
出队流程（假设队列：head → [dummy] → [A] → [B] ← tail）：

步骤1：读取head和next
  old_head = head  // [dummy]
  next = old_head->next  // [A]

步骤2：CAS移动head
  CAS(head, old_head, next)
  成功：head = [A]

步骤3：取走数据
  value = next->data  // A的数据

步骤4：释放旧的dummy节点
  delete old_head  // 释放[dummy]

结果：head → [A] → [B] ← tail
  （[A]变成了新的dummy节点）
```

**处理"滞后tail"问题**

> 💡 **比喻：快递分拣员来不及**

```
正常情况：分拣员（tail）总是跟在最后一个包裹后面
滞后情况：包裹来得太快，分拣员还没走到最后，新包裹又来了

  tail还指向旧位置：  head → [dummy] → [A] → [B] ← tail
  但[A]后面已经加了[C]：[A] → [C]

解决方案：帮助推进tail
  当线程发现tail->next != null，说明tail滞后了
  主动帮tail往前推：CAS(tail, old_tail, tail->next)
```

### 3. 完整C++代码实现

```cpp
#include <atomic>
#include <memory>
#include <optional>

template<typename T>
class LockFreeQueue {
    struct Node {
        std::shared_ptr<T> data;
        Node* next;
        Node() : data(nullptr), next(nullptr) {}
        explicit Node(T val) : data(std::make_shared<T>(std::move(val))), next(nullptr) {}
    };

    std::atomic<Node*> head_;
    std::atomic<Node*> tail_;

    // 待回收节点列表（简单的延迟释放方案）
    static inline std::atomic<Node*>& retire_list() {
        static std::atomic<Node*> list{nullptr};
        return list;
    }

    static void retire_node(Node* node) {
        node->next = retire_list().load(std::memory_order_relaxed);
        while (!retire_list().compare_exchange_weak(node->next, node,
                std::memory_order_release, std::memory_order_relaxed)) {}
    }

public:
    LockFreeQueue() {
        Node* dummy = new Node();
        head_.store(dummy, std::memory_order_relaxed);
        tail_.store(dummy, std::memory_order_relaxed);
    }

    ~LockFreeQueue() {
        while (dequeue().has_value()) {}
        Node* final_dummy = head_.load(std::memory_order_relaxed);
        delete final_dummy;
        // 释放待回收列表
        Node* node = retire_list().load(std::memory_order_relaxed);
        while (node) {
            Node* next = node->next;
            delete node;
            node = next;
        }
    }

    void enqueue(T value) {
        Node* new_node = new Node(std::move(value));
        Node* old_tail = tail_.load(std::memory_order_acquire);

        for (;;) {
            Node* next = old_tail->next;

            if (old_tail == tail_.load(std::memory_order_acquire)) {
                if (next == nullptr) {
                    // tail后面没有节点，尝试链接新节点
                    Node* null_ptr = nullptr;
                    if (old_tail->next == nullptr &&
                        __atomic_compare_exchange_n(
                            &old_tail->next, &null_ptr, new_node,
                            false, __ATOMIC_RELEASE, __ATOMIC_RELAXED)) {
                        // 链接成功，尝试推进tail
                        tail_.compare_exchange_strong(old_tail, new_node,
                            std::memory_order_release, std::memory_order_relaxed);
                        return;
                    }
                } else {
                    // tail滞后了，帮助推进tail
                    tail_.compare_exchange_strong(old_tail, next,
                        std::memory_order_release, std::memory_order_relaxed);
                }
            }
            old_tail = tail_.load(std::memory_order_acquire);
        }
    }

    std::optional<T> dequeue() {
        Node* old_head = head_.load(std::memory_order_acquire);

        for (;;) {
            Node* old_tail = tail_.load(std::memory_order_acquire);
            Node* next = old_head->next;

            if (old_head == head_.load(std::memory_order_acquire)) {
                if (old_head == old_tail) {
                    if (next == nullptr) {
                        // 队列为空
                        return std::nullopt;
                    }
                    // tail滞后，帮助推进
                    tail_.compare_exchange_strong(old_tail, next,
                        std::memory_order_release, std::memory_order_relaxed);
                } else {
                    // 读取数据并尝试移动head
                    std::shared_ptr<T> data = next->data;
                    if (head_.compare_exchange_strong(old_head, next,
                            std::memory_order_acquire, std::memory_order_relaxed)) {
                        // 成功出队，延迟释放旧dummy节点
                        retire_node(old_head);
                        return std::optional<T>(std::move(*data));
                    }
                }
            }
            old_head = head_.load(std::memory_order_acquire);
        }
    }

    bool empty() const {
        Node* h = head_.load(std::memory_order_acquire);
        Node* t = tail_.load(std::memory_order_acquire);
        return h == t;
    }
};
```

> ⚠️ **注意**：上述实现使用简单的延迟释放列表处理内存回收，生产环境建议使用更完善的策略（如Epoch-based Reclamation或Hazard Pointer，见8.7节）。

### 4. 性能分析

| 维度 | 分析 |
|------|------|
| **入队争用** | 多线程同时入队时，只有一个线程CAS成功，其余重试 |
| **出队争用** | 多线程同时出队时，只有一个线程CAS成功，其余重试 |
| **入队+出队** | 操作不同端（tail vs head），争用低于无锁栈 |
| **滞后tail** | 偶尔需要帮助推进tail，增加一次CAS，但整体影响小 |
| **内存开销** | 每个节点一个shared_ptr管理数据，开销略高于裸指针 |
| **缓存友好性** | 队列节点分散在堆上，缓存局部性较差 |

**与无锁栈对比：**

| 对比项 | 无锁栈 | 无锁队列 |
|--------|--------|----------|
| 操作模式 | LIFO | FIFO |
| 争用热点 | head（入栈出栈都操作head） | head和tail分离 |
| 公平性 | 后进先出，可能饥饿 | 先进先出，公平 |
| 实现复杂度 | 较简单 | 较复杂（哨兵节点+滞后tail） |
| 实用性 | 特定场景 | 通用生产者-消费者 |

## 5. ABA问题

### 1. 核心定义

CAS 操作只比较当前值是否等于期望值，**无法感知中间是否发生过变化**。当值从 A 变为 B 再变回 A 时，CAS 会认为"没有变化"而成功执行，但实际状态已被篡改。

```
纯正 ABA 流程：
1. 初始状态：状态A
2. 中间被修改成：状态B
3. 再被改回：状态A
4. 线程只对比最终是A，认为没变化，执行出错
```

> ⚠️ **关键区分**：ABA 问题有两个维度，必须分开理解，不可混用。

### 2. 类型1：值状态版（纯数值 A→B→A）

> 💡 **比喻：存钱取钱**

```
场景还原：

时刻T1: 你卡里余额1000元（状态A），准备取钱
时刻T2: 别人偷偷转走500，余额变成500（状态B）
        又立刻转回500，余额变回1000（回到状态A）
时刻T3: 你查询余额还是1000，以为全程没被动过，正常执行取钱逻辑

问题：数值还原，你察觉不到中间变动，业务逻辑出错
```

**技术解释：**
```cpp
std::atomic<int> balance(1000);  // 状态A

// 线程1：准备取钱
int expected = balance.load();   // 读取 1000（状态A）
// ... 被抢占 ...

// 线程2：中间操作
balance.store(500);              // 状态B：转走500
balance.store(1000);             // 回到状态A：转回500

// 线程1：恢复执行
balance.compare_exchange_strong(expected, 500);  // CAS成功！
// 以为余额没变，但中间其实被操作过，业务逻辑可能出错
```

**适用场景**：计数器、标志位等纯数值的 CAS 操作。

### 3. 类型2：引用复用版（地址不变，对象替换）

> 💡 **比喻：宿舍床位**

```
场景还原（床位号 = 内存地址）：

时刻T1: 你看到3号床位空着（head=3号），打算入住
时刻T2: 别人先把3号床位分配出去住满人，
        之后这人搬走，又安排另一个新人住进来再搬走，
        床位再次变空
时刻T3: 你只认床位编号还是3号空位，直接入住

真相：还是3号床位地址，但已经不是最开始那个空闲状态的原始床位流转，
      中间经过多次占用释放，你误判状态
```

**技术解释（链表场景）：**
```
初始状态: A → B → C

线程1读取: head = A (期望next是B)

线程2执行:
  pop() → head = B
  pop() → head = C
  push(A') → head = A' (新的A，但地址相同)

线程1CAS:
  检查: head == A? ✓ (地址相同)
  设置: head = B ✗ (B已经被弹出了！)

结果: 链表损坏！
```

**适用场景**：无锁链表、队列等基于指针 CAS 的数据结构。

### 4. 两种类型对比

| 维度 | 类型1：值状态版 | 类型2：引用复用版 |
|------|---------------|-----------------|
| 变化对象 | 数值/状态来回变 A→B→A | 地址不变，里面承载的实体彻底换了 |
| 核心矛盾 | 东西没变，数值来回改 | 编号/地址不变，对象已替换 |
| 典型场景 | 计数器、标志位 | 链表、队列的指针CAS |
| 后果 | 业务逻辑误判 | 数据结构损坏 |
| 比喻 | 存钱取钱：余额1000→500→1000 | 宿舍床位：3号床位空→满→空，但中间换了人 |

### 5. 解决方案

#### 1. 方案1：带版本号的指针（推荐）

> 💡 **比喻：给床位编号+时间戳**

每次床位变化，不仅检查床位号，还检查版本号：

```cpp
template<typename T>
class VersionedPointer {
    struct Pair {
        T* ptr;
        uint64_t version;  // 版本号，每次修改都递增
    };

    // 注意：在大多数64位平台上，std::atomic 对超过8字节的结构不保证 lock-free，
    // 可能内部使用互斥锁。如果需要真正的 lock-free，可以考虑将版本号嵌入指针低位。
    std::atomic<Pair> data_;

public:
    bool cas(Pair expected, Pair desired) {
        desired.version = expected.version + 1;  // 版本号+1
        return data_.compare_exchange_strong(expected, desired);
    }
};

// 即使指针值相同（A==A），版本号不同也会CAS失败
```

**效果：**
```
初始: (ptr=A, ver=1) → B

线程2操作后:
  (ptr=A, ver=2) → C  // 版本号变了！

线程1CAS:
  期望: (ptr=A, ver=1)
  实际: (ptr=A, ver=2)
  结果: CAS失败！✓ 正确检测到变化
```

#### 2. 方案2：Hazard Pointer（危险指针）

> 💡 **比喻：贴"使用中"标签**

每个线程声明自己正在使用的指针，其他线程不能回收：

```cpp
// 每个线程声明自己正在使用的指针
thread_local void* hazard_ptr = nullptr;

void safe_reclaim(Node* node) {
    // 将node放入待回收列表
    // 定期扫描hazard指针，确认无人在使用后释放
}
```

**工作流程：**
```
线程1: hazard_ptr = A  // "我正在用A，别回收！"
线程2: 想回收A
       检查hazard_ptr列表
       发现A被线程1占用
       跳过A，稍后再试
```

#### 3. 方案3：引用计数

> 💡 **比喻：图书馆借书系统**

每本书有借阅计数器，只有没人借时才能下架：

```cpp
struct Node {
    T data;
    std::atomic<int> ref_count;  // 引用计数
    std::atomic<Node*> next;
};

// 使用前: ref_count++
// 使用后: ref_count--
// 计数为0时: 安全删除
```

## 6. std::atomic\<shared_ptr\>（C++20）

### 1. C++20之前：shared_ptr的线程安全问题

> 💡 **比喻：公共白板上的便签**

```
shared_ptr的引用计数 = 便签上的"使用人数"
shared_ptr管理的对象 = 白板上的内容

C++20之前：
  引用计数是原子的（便签上的数字自动更新，不会出错）
  但shared_ptr对象本身的访问不是原子的！
  （白板内容可能被同时擦写，看到不一致的状态）

线程1: auto p = global_ptr;  // 读取global_ptr
线程2: global_ptr = make_shared<int>(42);  // 修改global_ptr
结果: 竞争条件！p可能指向半更新状态
```

**关键区分：**

| 操作 | 线程安全？ | 说明 |
|------|-----------|------|
| 不同shared_ptr对象各自读/写 | ✅ 安全 | 各自独立，引用计数原子 |
| 同一个shared_ptr对象被多线程读 | ✅ 安全 | 只读无竞争 |
| 同一个shared_ptr对象被多线程读写 | ❌ 不安全 | 对象本身的控制块可能竞争 |
| 引用计数的增减 | ✅ 安全 | 引用计数是原子操作 |

C++17的变通方案：

```cpp
// 方案1：用mutex保护shared_ptr
std::mutex mtx;
std::shared_ptr<int> global_ptr;

void safe_update() {
    std::lock_guard<std::mutex> lock(mtx);
    global_ptr = std::make_shared<int>(42);
}

// 方案2：用atomic_load/store（C++11已弃用，C++20移除）
// std::atomic_load(&global_ptr);  // C++20中已移除
// std::atomic_store(&global_ptr, new_ptr);  // C++20中已移除
```

### 2. C++20：std::atomic\<std::shared_ptr\<T\>\>

C++20引入了 `std::atomic<std::shared_ptr<T>>`，提供对shared_ptr的原子操作：

```cpp
#include <atomic>
#include <memory>

std::atomic<std::shared_ptr<int>> atomic_ptr;

// 原子读取
auto p = atomic_ptr.load();
// p是shared_ptr<int>的副本，引用计数安全递增

// 原子写入
atomic_ptr.store(std::make_shared<int>(42));

// 原子交换
auto old = atomic_ptr.exchange(std::make_shared<int>(100));

// 原子CAS
auto expected = atomic_ptr.load();
auto desired = std::make_shared<int>(200);
bool success = atomic_ptr.compare_exchange_strong(expected, desired);
// 如果atomic_ptr == expected，则atomic_ptr = desired，返回true
// 否则expected = atomic_ptr当前值，返回false
```

### 3. 支持的操作

| 操作 | 方法 | 说明 |
|------|------|------|
| 原子读 | `load()` | 返回shared_ptr副本 |
| 原子写 | `store()` | 原子替换当前值 |
| 原子交换 | `exchange()` | 原子替换并返回旧值 |
| 弱CAS | `compare_exchange_weak()` | 可能虚假失败 |
| 强CAS | `compare_exchange_strong()` | 不会虚假失败 |
| 等待 | `wait()` | 阻塞直到值变化（C++20） |
| 通知 | `notify_one()/notify_all()` | 唤醒等待线程 |

### 4. 代码示例：用atomic\<shared_ptr\>实现无锁数据结构

```cpp
#include <atomic>
#include <memory>
#include <optional>
#include <vector>

// 无锁栈（C++20版本，使用atomic<shared_ptr>自动管理内存）
template<typename T>
class LockFreeStack20 {
    struct Node {
        T data;
        std::shared_ptr<Node> next;
        explicit Node(T val) : data(std::move(val)), next(nullptr) {}
    };

    std::atomic<std::shared_ptr<Node>> head_;

public:
    LockFreeStack20() : head_(nullptr) {}

    void push(T value) {
        auto new_node = std::make_shared<Node>(std::move(value));
        auto old_head = head_.load(std::memory_order_acquire);

        do {
            new_node->next = old_head;
        } while (!head_.compare_exchange_weak(old_head, new_node,
                std::memory_order_release, std::memory_order_acquire));
        // CAS失败时old_head自动被更新为当前值，无需重新load
    }

    std::optional<T> pop() {
        auto old_head = head_.load(std::memory_order_acquire);

        do {
            if (!old_head) {
                return std::nullopt;
            }
        } while (!head_.compare_exchange_weak(old_head, old_head->next,
                std::memory_order_acquire, std::memory_order_acquire));

        return std::optional<T>(std::move(old_head->data));
        // old_head离开作用域后，引用计数自动递减
        // 无需手动释放内存！
    }

    bool empty() const {
        return head_.load(std::memory_order_acquire) == nullptr;
    }
};
```

> 💡 **atomic\<shared_ptr\>的优势**
>
> - **自动内存管理**：shared_ptr引用计数确保节点在无人使用时自动释放
> - **无ABA问题**：即使指针值相同，shared_ptr是不同的对象，CAS比较的是shared_ptr的内部状态
> - **代码简洁**：无需手动管理内存回收
>
> ⚠️ **代价**：
> - **性能开销**：每次CAS操作都需要原子地修改引用计数，开销高于裸指针
> - **非lock-free保证**：`std::atomic<std::shared_ptr<T>>` 不保证是lock-free的，实现可能内部使用互斥锁
> - **适用场景**：对性能要求不是极致的场景，或作为原型开发的快速方案

## 7. 内存回收策略深入

### 1. 无锁数据结构的根本难题：何时释放内存？

> 💡 **比喻：会议室清理问题**

```
传统加锁：
  清洁工等所有人离开后打扫（锁释放后安全删除）
  简单，但需要等待

无锁编程：
  清洁工不知道是否还有人留在会议室
  如果有人在用，就不能打扫（否则悬空指针）
  如果一直不打扫，会议室越来越多（内存泄漏）

核心矛盾：
  线程A读到了节点指针 → 线程B删除了该节点 → 线程A访问已释放内存 → 崩溃！
```

**问题本质：**

```
时刻1: 线程A读取 head = node_X
时刻2: 线程B弹出 node_X 并 delete node_X
时刻3: 线程A访问 node_X->next → 悬空指针！未定义行为！
```

这个难题有以下几种经典解决方案：

### 2. Epoch-based Reclamation（基于纪元的回收）

> 💡 **比喻：垃圾分类的"大扫除日"**

```
小区物业规定：
  每周一是大扫除日
  只清理两周前产生的垃圾
  本周和上周的垃圾先存着，因为可能还有人翻找

对应关系：
  大扫除日 = epoch切换
  两周前 = 2个epoch之前的内存
  翻找 = 线程正在访问
```

**原理：**

```
全局epoch：1 → 2 → 3 → 1 → 2 → 3 → ...（循环）

每个线程：
  1. 进入临界区时，声明当前epoch
  2. 退出临界区时，清除声明
  3. 删除节点时，标记为"epoch_N待回收"

回收规则：
  只有当所有线程都已离开epoch N-2时，才能回收epoch N-2的节点
  （确保没有线程还在访问这些节点）
```

**代码示意：**

```cpp
#include <atomic>
#include <array>
#include <vector>

class EpochReclaimer {
    static constexpr int NUM_EPOCHS = 3;

    std::atomic<int> global_epoch_{0};
    std::array<std::atomic<int>, 128> thread_epochs_;  // 每个线程的epoch

    // 每个epoch的待回收列表
    std::array<std::vector<void*>, NUM_EPOCHS> retire_lists_;

    static thread_local int local_epoch_;
    static thread_local bool in_critical_;

public:
    EpochReclaimer() {
        for (auto& e : thread_epochs_) {
            e.store(-1, std::memory_order_relaxed);
        }
    }

    // 进入临界区
    void enter_critical() {
        in_critical_ = true;
        local_epoch_ = global_epoch_.load(std::memory_order_acquire);
        thread_epochs_[thread_id()].store(local_epoch_, std::memory_order_release);
    }

    // 离开临界区
    void leave_critical() {
        thread_epochs_[thread_id()].store(-1, std::memory_order_release);
        in_critical_ = false;
    }

    // 延迟回收节点
    void retire(void* ptr) {
        int cur = global_epoch_.load(std::memory_order_acquire);
        retire_lists_[cur].push_back(ptr);
        try_advance_epoch();
    }

    // 尝试推进全局epoch
    void try_advance_epoch() {
        int cur = global_epoch_.load(std::memory_order_acquire);
        int next = (cur + 1) % NUM_EPOCHS;

        // 检查是否所有线程都已离开next epoch
        for (auto& e : thread_epochs_) {
            int te = e.load(std::memory_order_acquire);
            if (te == next) {
                return;  // 还有线程在next epoch，不能推进
            }
        }

        // 可以推进epoch，先回收next epoch的旧内存
        for (void* ptr : retire_lists_[next]) {
            operator delete(ptr);
        }
        retire_lists_[next].clear();

        global_epoch_.store(next, std::memory_order_release);
    }

private:
    int thread_id() {
        static std::atomic<int> counter{0};
        static thread_local int id = counter.fetch_add(1, std::memory_order_relaxed);
        return id % 128;
    }
};

thread_local int EpochReclaimer::local_epoch_ = -1;
thread_local bool EpochReclaimer::in_critical_ = false;
```

**优缺点：**

| 优点 | 缺点 |
|------|------|
| 批量回收，效率高 | 延迟回收可能导致内存占用偏高 |
| 读者开销极小（只需读写epoch） | 推进epoch需要检查所有线程 |
| 实现相对简单 | 需要线程配合进入/离开临界区 |

### 3. Hazard Pointer（危险指针）

> 💡 **比喻：施工区域的"正在施工"警示牌**

```
施工现场：
  工人在危险区域放置"正在施工"警示牌
  其他工人看到警示牌，就不会拆除这个区域
  工人离开后，取走警示牌，该区域可以被拆除

对应关系：
  警示牌 = hazard pointer
  危险区域 = 正在访问的节点
  拆除 = 释放内存
```

**原理：**

```
每个线程拥有少量hazard pointer槽位（通常1-2个）

使用流程：
  1. 线程读取指针前，先将该指针存入hazard slot
  2. 再次确认该指针未被其他线程修改（double-check）
  3. 安全访问该指针指向的内存
  4. 访问完毕后，清除hazard slot
  5. 想要释放节点时，检查所有hazard slot
     如果该节点被任何hazard slot引用，延迟释放
     如果没有被引用，安全释放
```

**代码示意：**

```cpp
#include <atomic>
#include <array>

template<typename T>
class HazardPointerManager {
    static constexpr int MAX_THREADS = 128;
    static constexpr int HP_PER_THREAD = 2;

    // 每个线程的hazard pointer槽位
    std::array<std::atomic<T*>, MAX_THREADS * HP_PER_THREAD> hp_slots_;

    // 待回收列表（每线程独立）
    static constexpr int RETIRE_THRESHOLD = MAX_THREADS * HP_PER_THREAD * 2;

    struct RetiredNode {
        T* ptr;
        RetiredNode* next;
    };

    static inline thread_local RetiredNode* retire_list_ = nullptr;
    static inline thread_local int retire_count_ = 0;

public:
    HazardPointerManager() {
        for (auto& slot : hp_slots_) {
            slot.store(nullptr, std::memory_order_relaxed);
        }
    }

    // 获取当前线程的hazard pointer槽位
    std::atomic<T*>& get_hazard_slot(int index = 0) {
        static thread_local int tid = get_thread_id();
        return hp_slots_[tid * HP_PER_THREAD + index];
    }

    // 保护一个指针
    T* protect(std::atomic<T*>& src, int slot_index = 0) {
        T* ptr;
        do {
            ptr = src.load(std::memory_order_acquire);
            get_hazard_slot(slot_index).store(ptr, std::memory_order_release);
        } while (ptr != src.load(std::memory_order_acquire));
        // double-check：确保保护的是最新值
        return ptr;
    }

    // 清除保护
    void clear_hazard(int slot_index = 0) {
        get_hazard_slot(slot_index).store(nullptr, std::memory_order_release);
    }

    // 延迟回收
    void retire(T* ptr) {
        auto* node = new RetiredNode{ptr, retire_list_};
        retire_list_ = node;
        retire_count_++;

        if (retire_count_ >= RETIRE_THRESHOLD) {
            scan_and_reclaim();
        }
    }

    // 扫描并回收安全的节点
    void scan_and_reclaim() {
        // 收集所有hazard pointer
        std::vector<T*> hazard_ptrs;
        for (auto& slot : hp_slots_) {
            T* p = slot.load(std::memory_order_acquire);
            if (p) hazard_ptrs.push_back(p);
        }

        // 遍历待回收列表
        RetiredNode* prev = nullptr;
        RetiredNode* curr = retire_list_;
        int new_count = 0;

        while (curr) {
            bool is_hazard = false;
            for (T* hp : hazard_ptrs) {
                if (curr->ptr == hp) {
                    is_hazard = true;
                    break;
                }
            }

            if (!is_hazard) {
                // 安全释放
                delete curr->ptr;
                if (prev) {
                    prev->next = curr->next;
                } else {
                    retire_list_ = curr->next;
                }
                RetiredNode* to_delete = curr;
                curr = curr->next;
                delete to_delete;
            } else {
                prev = curr;
                curr = curr->next;
                new_count++;
            }
        }
        retire_count_ = new_count;
    }

private:
    static int get_thread_id() {
        static std::atomic<int> counter{0};
        static thread_local int id = counter.fetch_add(1, std::memory_order_relaxed);
        return id % MAX_THREADS;
    }
};
```

**优缺点：**

| 优点 | 缺点 |
|------|------|
| 内存回收及时 | 每次读取都需要写hazard slot，开销较大 |
| 读者开销可控 | scan操作需要遍历所有hazard slot，O(P*H) |
| 无需全局epoch同步 | 每个节点需要额外空间存储RetiredNode |
| 适用于任意数据结构 | 实现复杂，容易出错 |

### 4. RCU（Read-Copy-Update）

> 💡 **比喻：政府公告栏更新**

```
政府公告栏：
  市民（读者）随时可以看公告栏，无需任何手续
  工作人员（写者）想修改公告时：
    1. 复制一份旧公告
    2. 在副本上修改
    3. 原子地替换公告栏指针指向新版本
    4. 等待所有正在看旧公告的市民离开后，销毁旧公告

关键：读者零开销，写者承担所有成本
```

**原理：**

```
读者端（几乎零开销）：
  1. 进入读侧临界区（通常只是禁用抢占或递增计数器）
  2. 读取数据（无需任何同步操作）
  3. 离开读侧临界区

写者端：
  1. 创建数据的新副本（Copy）
  2. 修改新副本
  3. 原子地更新指针指向新副本（Update）
  4. 等待所有之前的读者离开宽限期（Grace Period）
  5. 释放旧副本
```

**Linux内核RCU示例：**

```c
// Linux内核中的RCU使用模式

struct data {
    int value;
    struct rcu_head rcu;
};

// 读者端（几乎零开销）
int read_value(struct data** global_ptr) {
    rcu_read_lock();          // 进入读侧临界区（禁用抢占）
    struct data* p = rcu_dereference(*global_ptr);  // 读取指针
    int val = p->value;       // 安全访问数据
    rcu_read_unlock();        // 离开读侧临界区
    return val;
}

// 写者端
void update_value(struct data** global_ptr, int new_val) {
    struct data* old = rcu_dereference(*global_ptr);
    struct data* new_node = kmalloc(sizeof(*new_node), GFP_KERNEL);
    *new_node = *old;                     // 复制旧数据
    new_node->value = new_val;            // 修改副本
    rcu_assign_pointer(*global_ptr, new_node);  // 原子更新指针
    call_rcu(&old->rcu, free_callback);   // 宽限期后回调释放
}
```

**用户态RCU（liburcu）示例：**

```cpp
#include <urcu.h>
#include <urcu-pointer.h>

struct config {
    int timeout;
    int retry_count;
    struct rcu_head rcu;
};

struct config* global_cfg;

// 读者端
int get_timeout() {
    rcu_read_lock();
    struct config* cfg = rcu_dereference(global_cfg);
    int val = cfg->timeout;
    rcu_read_unlock();
    return val;
}

// 写者端
void update_timeout(int new_timeout) {
    struct config* old = rcu_dereference(global_cfg);
    struct config* new_cfg = new config(*old);
    new_cfg->timeout = new_timeout;
    rcu_assign_pointer(global_cfg, new_cfg);
    synchronize_rcu();  // 等待宽限期
    delete old;
}
```

**优缺点：**

| 优点 | 缺点 |
|------|------|
| 读者几乎零开销 | 写者开销大（复制+等待宽限期） |
| 读多写少场景性能极佳 | 不适合写密集场景 |
| 读端无内存屏障（x86） | 宽限期可能较长，内存占用高 |
| Linux内核广泛验证 | 用户态实现复杂，依赖外部库 |

### 5. 三种策略对比

| 维度 | Epoch-based | Hazard Pointer | RCU |
|------|-------------|----------------|-----|
| **读者开销** | 极小（读写epoch） | 中等（写hazard slot+double-check） | 极小（禁用抢占或递增计数器） |
| **写者开销** | 小（标记+批量回收） | 中等（扫描hazard slot） | 大（复制数据+等待宽限期） |
| **内存回收延迟** | 中等（2个epoch后） | 较小（阈值触发扫描） | 较大（宽限期可能很长） |
| **适用场景** | 通用无锁结构 | 通用无锁结构 | 读多写少 |
| **实现复杂度** | 中等 | 较高 | 高（依赖运行时支持） |
| **写端并发** | 支持 | 支持 | 通常单写者（多写者需额外同步） |
| **成熟实现** | crossbeam（Rust） | hazard_pointer（C++提案） | Linux内核、liburcu |
| **语言支持** | 无内置 | C++26提案中 | 无内置 |

> 💡 **选择建议**
>
> - **快速原型**：`std::atomic<std::shared_ptr<T>>`（C++20），最简单但性能一般
> - **通用高性能**：Epoch-based Reclamation，平衡了性能和实现复杂度
> - **精确控制**：Hazard Pointer，内存回收最及时，但实现复杂
> - **读多写少**：RCU，读者零开销，但写者代价大
> - **生产环境**：优先使用成熟库（boost::lockfree、Folly、crossbeam等）

## 8. 无锁编程的调试

### 1. 为什么无锁代码难以调试

> 💡 **比喻：抓鬼**

```
传统bug = 白天抓小偷
  现场留有痕迹，容易追踪

无锁bug = 半夜抓鬼
  出现条件极其苛刻（特定时序、特定CPU缓存状态）
  复现概率极低（百万分之一）
  一旦加上打印就消失了（改变了时序）
  多线程交错顺序几乎无限
```

**无锁代码的典型问题：**

| 问题类型 | 表现 | 难度 |
|----------|------|------|
| 数据竞争 | 偶发错误结果 | ⭐⭐⭐ |
| ABA问题 | 链表损坏 | ⭐⭐⭐⭐ |
| 内存序错误 | 偶发读到旧值 | ⭐⭐⭐⭐⭐ |
| 悬空指针 | 偶发崩溃 | ⭐⭐⭐⭐ |
| 活锁 | 性能下降但不崩溃 | ⭐⭐⭐ |

### 2. TSan检测数据竞争

**ThreadSanitizer（TSan）** 是编译器内置的数据竞争检测工具：

```bash
# 编译时启用TSan
g++ -fsanitize=thread -g -O1 lockfree.cpp -o lockfree

# 运行程序，TSan会自动检测数据竞争
./lockfree
```

**TSan输出示例：**

```
==================
WARNING: ThreadSanitizer: data race (pid=12345)
  Write of size 8 at 0x7b0400000000 by thread T2:
    #0 Node::next lockfree.cpp:15 (lockfree+0x401234)
    #1 push lockfree.cpp:28 (lockfree+0x401256)

  Previous read of size 8 at 0x7b0400000000 by thread T1:
    #0 Node::next lockfree.cpp:15 (lockfree+0x401230)
    #1 pop lockfree.cpp:42 (lockfree+0x401290)

  Location is heap block of size 24 at 0x7b0400000000
==================
```

**TSan的局限：**

| 局限 | 说明 |
|------|------|
| 不识别原子操作 | 可能对正确的atomic操作误报 |
| 性能开销大 | 程序运行速度降低5-15倍 |
| 内存开销大 | 额外消耗5-10倍内存 |
| 只能检测执行到的路径 | 未覆盖的并发路径无法检测 |
| 不检测ABA问题 | ABA不是数据竞争，是逻辑错误 |

### 3. ThreadSanitizer + 无锁代码的最佳实践

```cpp
// 1. 确保所有共享变量都是std::atomic
std::atomic<int> counter{0};  // 正确
int counter = 0;              // 错误！TSan会报数据竞争

// 2. 使用正确的内存序
// 先用memory_order_seq_cst确保正确性
// 确认无误后，再优化为更宽松的内存序
std::atomic<Node*> head_{nullptr};

void push(T val) {
    Node* n = new Node(std::move(val));
    n->next = head_.load(std::memory_order_seq_cst);  // 先用seq_cst
    while (!head_.compare_exchange_weak(n->next, n,
            std::memory_order_seq_cst, std::memory_order_seq_cst)) {}
}

// 3. 用TSan验证后，逐步替换为更高效的内存序
// head_.load(std::memory_order_acquire)
// head_.compare_exchange_weak(..., std::memory_order_release, std::memory_order_relaxed)
```

### 4. 压力测试策略

> 💡 **比喻：地震测试**

```
普通测试 = 轻轻摇晃建筑
  大部分时候没问题，但遇到真正的地震就塌了

压力测试 = 模拟8级地震
  长时间运行 + 多线程 + 随机延迟 = 最大化并发冲突概率
```

```cpp
#include <atomic>
#include <thread>
#include <vector>
#include <random>
#include <chrono>
#include <iostream>
#include <cassert>

// 压力测试框架
template<typename Queue>
void stress_test(Queue& q, int num_threads, int ops_per_thread) {
    std::atomic<int> total_pushed{0};
    std::atomic<int> total_popped{0};
    std::atomic<bool> start_flag{false};

    auto worker = [&](int thread_id) {
        // 等待所有线程就绪
        while (!start_flag.load(std::memory_order_acquire)) {}

        std::mt19937 rng(thread_id);
        std::uniform_int_distribution<int> dist(1, 100);

        for (int i = 0; i < ops_per_thread; ++i) {
            int val = dist(rng);

            if (val > 30) {
                q.enqueue(thread_id * ops_per_thread + i);
                total_pushed.fetch_add(1, std::memory_order_relaxed);
            } else {
                auto result = q.dequeue();
                if (result.has_value()) {
                    total_popped.fetch_add(1, std::memory_order_relaxed);
                }
            }

            // 随机延迟，增加交错可能性
            if (dist(rng) < 5) {
                std::this_thread::yield();
            }
            if (dist(rng) < 2) {
                std::this_thread::sleep_for(std::chrono::microseconds(dist(rng)));
            }
        }
    };

    // 启动所有线程
    std::vector<std::thread> threads;
    for (int i = 0; i < num_threads; ++i) {
        threads.emplace_back(worker, i);
    }

    // 同时开始
    start_flag.store(true, std::memory_order_release);

    for (auto& t : threads) {
        t.join();
    }

    // 排空队列
    int remaining = 0;
    while (q.dequeue().has_value()) {
        remaining++;
    }

    // 验证：推入总数 = 弹出总数 + 剩余
    int pushed = total_pushed.load();
    int popped = total_popped.load();
    std::cout << "推入: " << pushed
              << " 弹出: " << popped
              << " 剩余: " << remaining << std::endl;
    assert(pushed == popped + remaining);

    std::cout << "压力测试通过！" << std::endl;
}
```

### 5. 使用std::latch/barrier同步测试点（C++20）

```cpp
#include <latch>
#include <barrier>
#include <thread>
#include <vector>
#include <iostream>

// 使用latch确保所有线程同时开始
template<typename Queue>
void test_with_latch(Queue& q, int num_threads) {
    std::latch start_latch(num_threads);
    std::latch ready_latch(num_threads);
    std::atomic<bool> go{false};

    auto producer = [&](int id) {
        ready_latch.count_down();  // 通知主线程：我准备好了
        start_latch.wait();        // 等待所有线程就绪后同时开始
        for (int i = 0; i < 1000; ++i) {
            q.enqueue(id * 1000 + i);
        }
    };

    auto consumer = [&](int id) {
        ready_latch.count_down();
        start_latch.wait();
        for (int i = 0; i < 1000; ++i) {
            q.dequeue();
        }
    };

    std::vector<std::thread> threads;
    for (int i = 0; i < num_threads; ++i) {
        if (i % 2 == 0) {
            threads.emplace_back(producer, i);
        } else {
            threads.emplace_back(consumer, i);
        }
    }

    ready_latch.wait();  // 等待所有线程就绪
    start_latch.count_down(num_threads);  // 同时释放所有线程

    for (auto& t : threads) {
        t.join();
    }
}

// 使用barrier在测试的多个阶段之间同步
template<typename Queue>
void test_with_barrier(Queue& q, int num_threads, int num_phases) {
    // 每个阶段结束时同步
    std::barrier sync_point(num_threads, []() noexcept {
        // 每个阶段完成时执行的回调（可选）
        std::cout << "阶段完成" << std::endl;
    });

    auto worker = [&](int id) {
        for (int phase = 0; phase < num_phases; ++phase) {
            // 阶段内工作
            if (phase % 2 == 0) {
                for (int i = 0; i < 100; ++i) {
                    q.enqueue(id * 1000 + phase * 100 + i);
                }
            } else {
                for (int i = 0; i < 100; ++i) {
                    q.dequeue();
                }
            }
            // 等待所有线程完成当前阶段
            sync_point.arrive_and_wait();
        }
    };

    std::vector<std::thread> threads;
    for (int i = 0; i < num_threads; ++i) {
        threads.emplace_back(worker, i);
    }
    for (auto& t : threads) {
        t.join();
    }
}
```

### 6. 调试检查清单

| 检查项 | 说明 |
|--------|------|
| 所有共享变量是否都是atomic？ | 非atomic共享变量必然有数据竞争 |
| 内存序是否正确？ | 先用seq_cst验证，再优化 |
| CAS循环是否可能死循环？ | 确保CAS失败时能重新读取最新值 |
| 节点释放后是否还有线程访问？ | 使用安全的内存回收策略 |
| 是否存在ABA问题？ | 检查指针CAS是否需要版本号 |
| 是否存在活锁？ | 添加退避策略（exponential backoff） |
| TSan是否通过？ | 编译时启用-fsanitize=thread |
| 压力测试是否长时间通过？ | 至少运行数百万次操作 |
| 不同平台是否一致？ | x86内存模型比ARM严格，ARM上更容易暴露问题 |
