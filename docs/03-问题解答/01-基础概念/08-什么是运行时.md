# 什么是运行时

> **The runtime is the bridge between your code and the machine.** — someone
> （运行时是代码与机器之间的桥梁。）

***

### 1. 要点直击

**运行时**（Runtime）= 程序运行时需要的支持环境。C 有运行时（C Runtime），C++ 也有运行时（C++ Runtime），只是比 Java/Python 的运行时小得多。

***

### 2. 运行时的核心职责

运行时在程序启动到退出期间，默默承担以下工作：

```
+--------+     +----------------+     +----------+
| 加载器  | --> | 运行时初始化     | --> | main执行 |
+--------+     +----------------+     +----------+
                  |      ↑                    |
                  v      |                    v
              全局构造 ←--                   main返回
                  |                          |
                  v                          v
              全局析构 ←--                 退出清理
```

| 阶段 | 运行时行为 |
|------|-----------|
| 加载 | 加载器将程序映射到内存，跳转到入口点 |
| 初始化 | 设置栈指针、初始化全局变量、调用静态构造函数 |
| 执行 | 提供标准库函数支持（printf、malloc、new、异常等） |
| 清理 | 调用 atexit 注册的函数、析构全局对象、刷新缓冲区 |

### 3. C 的运行时

| 组件 | 作用 |
|------|------|
| crt0/crt1 | 程序入口点，调用 main |
| libc | 标准库函数（printf, malloc, strcpy...） |
| 启动代码 | 初始化栈、堆、全局变量 |
| 退出代码 | 调用 atexit 函数，刷新缓冲区 |

在 Windows 上 C 运行时是 `msvcrt.dll`（MSVC）或 `ucrtbase.dll`（UCRT），在 Linux 上是 `glibc` 或 `musl`。

### 4. C++ 在 C 运行时基础上多了什么

| 额外组件 | 作用 |
|----------|------|
| libstdc++/libc++ | C++ 标准库（STL, iostream, string...） |
| libsupc++ | 异常处理、RTTI、new/delete |
| 全局构造/析构 | 静态对象的构造和析构调用 |

```cpp
#include <iostream>

struct GlobalObject {
    GlobalObject() { std::cout << "全局构造\n"; }
    ~GlobalObject() { std::cout << "全局析构\n"; }
};

GlobalObject g_obj;  // main之前构造，main之后析构

int main() {
    std::cout << "main 执行\n";
    return 0;
}
```

输出顺序：
```
全局构造    ← 运行时在main之前调用
main 执行   ← 程序逻辑
全局析构    ← 运行时在main返回之后调用
```

### 5. 与 Java/Python 运行时的区别

| 特性 | C/C++ | Java | Python |
|------|:---:|:---:|:---:|
| 运行时大小 | 小（几MB） | 大（JVM，几十MB） | 大（解释器） |
| 内存管理 | 手动/半自动 | GC | GC |
| 执行方式 | 编译为机器码 | 字节码+JIT | 解释执行 |
| 启动速度 | 极快 | 慢 | 慢 |
| 平台依赖性 | 编译时绑定 | JVM跨平台 | 解释器跨平台 |
| 运行时依赖 | 静态/动态链接 | 必须安装JRE | 必须安装解释器 |

### 6. 运行时选择的影响

**静态链接 vs 动态链接运行时：**

```bash
# 静态链接：程序自包含，体积大，不依赖系统运行时
g++ -static main.cpp -o app_static

# 动态链接：程序体积小，依赖系统已安装的运行时
g++ main.cpp -o app_dynamic
# Windows依赖 msvcrt.dll / ucrtbase.dll
# Linux依赖 libc.so.6 / libstdc++.so.6
```

| 方案 | 优点 | 缺点 |
|------|------|------|
| 静态链接 | 无外部依赖，部署简单 | 可执行文件大，无法共享运行时 |
| 动态链接 | 文件小，共享运行时，可更新 | 需要目标系统有匹配的运行时 |

### 7. 可以没有运行时吗

```bash
# freestanding 模式：不依赖标准库
g++ -ffreestanding -nostdlib -Os ...

# 嵌入式/内核开发常用
# 只能用编译器内置函数，不能调用任何库函数
```

freestanding 环境下的限制：
- 没有 main 函数（入口点自定）
- 不能使用标准库（printf、malloc等）
- 不能使用异常和 RTTI
- 需要自己实现启动代码

### 8. 极简总结

**运行时 = 程序执行所需的底层支持 → C/C++有轻量级运行时 → 比Java/Python小而快 → 可在freestanding模式下完全去掉**

### 9. crt0启动代码详解

> **crt0是程序真正的入口，main只是运行时为你准备好的舞台。**

程序不是从 `main` 开始执行的——加载器跳转的第一个地址是 `_start`，它由 crt0（C Runtime Zero）提供。整个启动链涉及多个目标文件，按顺序链接：

```
crt1.o  →  crti.o  →  crtbegin.o  →  [你的程序]  →  crtend.o  →  crtn.o
```

各文件职责：

| 文件 | 职责 |
|------|------|
| crt1.o / crt0.o | 提供 `_start` 入口点，设置栈和参数，调用 `__libc_start_main` |
| crti.o | 定义 `.init` 段和 `.fini` 段的头部（函数序言 prologue） |
| crtbegin.o | 配合 `.init_array` / `.fini_array`，处理 C++ 全局构造/析构 |
| crtend.o | 配合 `.init_array` / `.fini_array` 的尾部 |
| crtn.o | 定义 `.init` 段和 `.fini` 段的尾部（函数尾声 epilogue） |

**`_start` 到 `main` 的完整调用链：**

```asm
; crt1.o 中的 _start（x86-64 Linux 简化版）
_start:
    xor  ebp, ebp          ; 清零帧指针，标记最外层栈帧
    mov  r9, rdx           ; 保存 rtld_fini（动态链接器注销函数）
    pop  rsi               ; argc ← 栈顶弹出参数个数
    mov  rdx, rsp          ; argv ← 当前栈指针（参数数组）
    and  rsp, 0xFFFFFFFFFFFFFFF0  ; 16字节对齐栈
    push rax               ; 对齐用
    push rsp               ; 传递栈指针给 __libc_start_main

    ; 调用 __libc_start_main(main, argc, argv, init, fini, rtld_fini, stack_end)
    call __libc_start_main

    ; 如果 __libc_start_main 返回（不应该），调用 abort
    call abort
```

`__libc_start_main` 内部做了什么：

```
__libc_start_main:
    1. 保存 main 函数指针
    2. 初始化 libc（线程局部存储、标准流、环境变量等）
    3. 注册 __libc_csu_fini 为 atexit 处理函数
    4. 遍历 .init_array 段，调用每个函数指针（全局构造）
    5. 调用 main(argc, argv, envp)
    6. 将 main 返回值传给 exit()
```

验证启动链：

```bash
# 查看 ELF 入口点
readelf -h ./app | grep "Entry point"

# 反汇编 _start
objdump -d ./app | grep -A 30 "<_start>:"

# 查看链接了哪些 crt 目标文件
gcc -v main.cpp 2>&1 | grep crt
```

### 10. .init_array 和 .fini_array 段

> **.init_array 是全局构造函数的注册表，.fini_array 是全局析构函数的注册表。**

编译器将全局/静态对象的构造函数指针放入 `.init_array` 段，析构函数指针放入 `.fini_array` 段。运行时在启动/退出时遍历这些段并逐个调用。

**段的结构：**

```
.init_array 段（全局构造函数指针表）:
+------------------+
| &__cxx_global_var_init  |  ← 构造 GlobalObject
| &__cxx_global_var_init  |  ← 构造另一个全局对象
| ...                     |
+------------------+

.fini_array 段（全局析构函数指针表）:
+------------------+
| &__dtor_for_g_obj       |  ← 析构 GlobalObject
| &__dtor_for_another     |  ← 析构另一个全局对象
| ...                     |
+------------------+
```

**与 .ctors / .dtors 的历史演变：**

| 特性 | .ctors / .dtors（旧） | .init_array / .fini_array（新） |
|------|----------------------|-------------------------------|
| 标准 | GCC 专有扩展 | ELF 标准（glibc 2.3+） |
| 调用顺序 | 逆序（从高地址到低地址） | 正序（从低地址到高地址） |
| 优先级 | 通过段名 `.ctors.PPPPP` | 通过段名 `.init_array.PPPPP` |
| 现状 | 已废弃，仅兼容保留 | 当前标准方案 |

编译器如何生成这些段：

```cpp
// 源码
struct Foo {
    Foo()  { /* 构造 */ }
    ~Foo() { /* 析构 */ }
};
Foo global_foo;

// 编译器大致生成（伪代码）：
__attribute__((section(".init_array")))
static void (*__init_foo)() = __cxx_global_var_init;

void __cxx_global_var_init() {
    global_foo.Foo();  // 调用构造函数
    // 在 .fini_array 注册析构函数
    __cxa_atexit((void(*)(void*))global_foo.~Foo, &global_foo, &__dso_handle);
}
```

查看实际段内容：

```bash
# 查看 .init_array 段
objdump -s -j .init_array ./app

# 查看 .fini_array 段
objdump -s -j .fini_array ./app

# 查看所有相关段
readelf -S ./app | grep -E "init_array|fini_array|ctors|dtors"
```

**优先级机制：**

```cpp
// 优先级数值越小，越先构造（但越后析构）
__attribute__((constructor(101))) void early_init()   { /* 最先执行 */ }
__attribute__((constructor(65535))) void late_init()  { /* 最后执行 */ }
__attribute__((destructor(101)))  void late_fini()    { /* 最后执行 */ }
__attribute__((destructor(65535))) void early_fini()  { /* 最先执行 */ }
```

### 11. atexit 注册顺序

> **atexit 是 LIFO 栈——最后注册的函数最先执行，就像叠盘子一样。**

`atexit` 和 `__cxa_atexit` 都遵循 LIFO（后进先出）顺序。全局析构函数通过 `__cxa_atexit` 注册，因此也遵循此规则。

```cpp
#include <cstdlib>
#include <iostream>

void cleanup1() { std::cout << "cleanup1\n"; }
void cleanup2() { std::cout << "cleanup2\n"; }
void cleanup3() { std::cout << "cleanup3\n"; }

struct Global {
    Global()  { std::cout << "Global构造\n"; }
    ~Global() { std::cout << "Global析构\n"; }
};

Global g;

int main() {
    std::atexit(cleanup1);  // 第1个注册
    std::atexit(cleanup2);  // 第2个注册
    std::atexit(cleanup3);  // 第3个注册
    std::cout << "main\n";
    return 0;
}
```

输出：

```
Global构造    ← 运行时通过 __cxa_atexit 注册析构（比 atexit 更早注册）
main
cleanup3      ← LIFO：最后注册的最先执行
cleanup2
cleanup1
Global析构    ← __cxa_atexit 注册的析构也在 LIFO 顺序中
```

**注册数量限制：**

```cpp
// atexit 注册数量有限制，由 ATEXIT_MAX 宏定义
#include <cstdlib>
std::cout << "ATEXIT_MAX = " << std::ATEXIT_MAX << "\n";
// 最小保证值：32（POSIX 规定）
// glibc 实际值：2^31（几乎无限制）
// MSVC 实际值：约 2000+
```

**`atexit` vs `__cxa_atexit`：**

| 特性 | `atexit` | `__cxa_atexit` |
|------|----------|----------------|
| 标准 | C/C++ 标准 | C++ ABI 内部接口 |
| 参数 | `void (*func)()` | `void (*func)(void*)`, `void* arg`, `void* dso_handle` |
| 用途 | 用户注册清理函数 | 编译器注册全局析构 |
| DSO 支持 | 无 | 通过 `dso_handle` 支持动态库卸载 |

**动态库卸载时的交互：**

当 `dlclose()` 卸载一个动态库时，`__cxa_atexit` 通过 `__dso_handle` 只调用属于该库的析构函数，而 `atexit` 注册的函数无法区分来源，可能导致卸载后调用已释放内存的代码（use-after-free）。

### 12. 全局对象构造/析构的完整流程

> **从加载器到 exit，运行时走完了一条精心设计的流水线。**

```
┌─────────────────────────────────────────────────────────────┐
│                      操作系统加载器                           │
│  1. 将 ELF/PE 映射到内存                                     │
│  2. 加载动态库依赖                                           │
│  3. 跳转到入口点 _start                                      │
└──────────────────────┬──────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────────┐
│                      _start (crt1.o)                         │
│  4. 清零 ebp，获取 argc/argv/envp                            │
│  5. 对齐栈                                                   │
│  6. 调用 __libc_start_main                                   │
└──────────────────────┬───────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────────┐
│                  __libc_start_main (libc)                     │
│  7. 初始化线程局部存储 (TLS)                                   │
│  8. 初始化标准流 (stdin/stdout/stderr)                        │
│  9. 初始化堆 (malloc)                                        │
│  10. 注册 __libc_csu_fini 到 atexit                          │
│  11. 遍历 .init_array，调用每个构造函数指针                     │
│      → 全局对象的构造函数在此执行                               │
│      → __attribute__((constructor)) 函数在此执行               │
└──────────────────────┬───────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────────┐
│                      main()                                  │
│  12. 程序逻辑执行                                             │
│  13. return N;  →  等价于 exit(N)                            │
└──────────────────────┬───────────────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────────────┐
│                      exit() (libc)                           │
│  14. 按 LIFO 顺序调用 atexit / __cxa_atexit 注册的函数        │
│      → atexit 注册的清理函数                                  │
│      → 全局对象的析构函数（通过 __cxa_atexit 注册）             │
│  15. 刷新并关闭所有打开的文件流                                │
│  16. 删除临时文件 (tmpfile 创建的)                             │
│  17. 遍历 .fini_array，调用每个析构函数指针                     │
│  18. 调用 _exit() → 内核系统调用 → 进程终止                    │
└──────────────────────────────────────────────────────────────┘
```

**跨翻译单元的构造顺序：**

```cpp
// a.cpp
struct A { A() { std::cout << "A\n"; } };
A a;  // 翻译单元1的全局对象

// b.cpp
struct B { B() { std::cout << "B\n"; } };
B b;  // 翻译单元2的全局对象

// a和b的构造顺序未定义！C++标准不规定跨TU的初始化顺序
// 同一TU内按定义顺序构造，析构顺序与构造相反
```

**构造顺序问题的解决方案：**

```cpp
// 方案1：Construct On First Use Idiom（首次使用时构造）
Logger& logger() {
    static Logger instance;  // 函数内static，首次调用时构造
    return instance;
}

// 方案2：nifty counter idiom（也被 iostream 使用）
// iostream.h 内部：
namespace std {
    inline ios_base::Init __io_init;  // 每个TU都有一份，确保iostream初始化
}
```

### 13. 运行时版本兼容性

> **"在我机器上能跑"的根源——运行时版本不匹配。**

**glibc 符号版本问题：**

glibc 使用符号版本机制（Symbol Versioning），同一函数可以有多个版本：

```bash
# 查看 glibc 版本
ldd --version

# 查看程序依赖的符号版本
objdump -T ./app | grep GLIBC

# 典型输出：
# glibc      GLIBC_2.2.5  malloc
# glibc      GLIBC_2.28   statx
# glibc      GLIBC_2.34   pthread_create
```

```bash
# 在 glibc 2.35 上编译，在 glibc 2.17 上运行 → 报错
./app: /lib64/libc.so.6: version `GLIBC_2.34' not found

# 解决方案1：在最低目标版本的系统上编译
# 解决方案2：指定符号版本
g++ -Wl,--wrap=pthread_create ...

# 解决方案3：静态链接（但有坑）
g++ -static main.cpp -o app  # glibc 不推荐静态链接
```

**libstdc++ Dual ABI 问题：**

GCC 5.1 引入了新的 C++11 ABI，`std::string` 和 `std::list` 的实现发生了变化：

```cpp
// 旧 ABI（GCC < 5.1）：std::string 使用写时复制（COW）
// 新 ABI（GCC >= 5.1）：std::string 使用 SSO（小字符串优化）

// 检查当前使用的 ABI
#include <string>
std::cout << _GLIBCXX_USE_CXX11_ABI << "\n";
// 1 = 新 ABI，0 = 旧 ABI

// 强制使用旧 ABI 编译（兼容旧库）
g++ -D_GLIBCXX_USE_CXX11_ABI=0 main.cpp

// 链接时 ABI 不匹配的症状：
// undefined reference to `std::basic_string<...>::~basic_string()'
// 符号签名不同导致链接失败
```

| ABI 特性 | 旧 ABI（COW） | 新 ABI（SSO） |
|----------|--------------|--------------|
| `std::string` | 写时复制 | 小字符串优化 |
| `std::list` | sizeof 包含计数 | sizeof 更小 |
| 符号名 | `_ZNSs` | `_ZNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEE` |
| 兼容宏 | `_GLIBCXX_USE_CXX11_ABI=0` | `_GLIBCXX_USE_CXX11_ABI=1` |

**Windows 运行时对比：**

| 特性 | MSVCRT (旧) | UCRT (新，VS2015+) |
|------|------------|-------------------|
| 来源 | 各VS版本独立 | Windows 10 统一组件 |
| 分发 | 随 VS 安装 | Windows Update 推送 |
| 兼容性 | 版本间不兼容 | 统一版本，向前兼容 |
| printf | MS 扩展格式 | C99 标准兼容 |
| 文件 | msvcrt.dll | ucrtbase.dll |
| 推荐度 | 不推荐新项目使用 | 推荐使用 |

```bash
# MSVC 编译时选择运行时
cl /MD main.cpp    # 动态链接 UCRT (推荐)
cl /MT main.cpp    # 静态链接 UCRT
cl /MDd main.cpp   # 动态链接 UCRT Debug 版
```

### 14. freestanding 模式深入

> **freestanding = 裸机模式，编译器只提供最基本保证，其余全部自己来。**

C++ 标准将实现分为两种：

| 类型 | 定义 |
|------|------|
| **Hosted** | 完整标准库，有 main 函数，有操作系统支持 |
| **Freestanding** | 最小化标准库，无 main 函数要求，无操作系统假设 |

**freestanding 下可用的头文件（C++20）：**

```
C 头文件（freestanding 可用）：
  <float.h>      浮点数特性
  <iso646.h>     替代记号（and/or/not）
  <limits.h>     整数范围
  <stdalign.h>   对齐支持
  <stdarg.h>     可变参数
  <stdbool.h>    布尔类型
  <stddef.h>     ptrdiff_t/size_t/nullptr_t
  <stdint.h>     固定宽度整数
  <stdnoreturn.h> _Noreturn

C++ 头文件（freestanding 可用）：
  <cfloat>       <climits>      <cstdarg>
  <cstddef>      <cstdint>      <cstdlib>（部分：abort/exit/atexit等）
  <type_traits>  <limits>       <version>
  <coroutine>    <concepts>     <initializer_list>
  <new>          <exception>    <source_location>
  <compare>      <bit>          <atomic>（可选）
  <ciso646>      <contract>（C++26）
```

**freestanding 下必须自己实现什么：**

```cpp
// 1. 入口点（没有 main，入口名自定义）
void kernel_main() {
    // 初始化硬件...
    // 初始化堆分配器...
    // 进入主循环...
}

// 2. 链接脚本（定义内存布局）
/*
ENTRY(kernel_main)
SECTIONS {
    . = 0x100000;          内核加载地址
    .text : { *(.text) }
    .rodata : { *(.rodata) }
    .data : { *(.data) }
    .bss : { *(.bss) }
}
*/

// 3. 堆分配器（没有 malloc/new）
struct SimpleHeap {
    uint8_t* base;
    size_t offset;
    void* alloc(size_t size) {
        void* p = base + offset;
        offset += size;
        return p;
    }
};

// 4. 全局构造调用（运行时不会帮你调用）
void call_constructors() {
    extern void (*__init_array_start[])();
    extern void (*__init_array_end[])();
    for (auto fn = __init_array_start; fn < __init_array_end; fn++) {
        (*fn)();
    }
}

// 5. operator new/delete 的最简实现
void* operator new(size_t size) { return simple_heap.alloc(size); }
void operator delete(void*) noexcept { /* bump allocator 无法释放 */ }
```

**内核/裸机开发示例：**

```cpp
// 最小化内核入口（x86-64，freestanding）
#include <cstdint>
#include <cstddef>

static uint16_t* const VGA_BUFFER = (uint16_t*)0xB8000;

void vga_print(const char* str, uint8_t color = 0x0F) {
    static int pos = 0;
    while (*str) {
        VGA_BUFFER[pos++] = (uint16_t)(*str++) | ((uint16_t)color << 8);
    }
}

extern "C" void kernel_main(void) {
    vga_print("Hello from freestanding C++!");
    while (1) { __asm__ volatile("hlt"); }
}
```

### 15. 运行时与调试的关系

> **调试信息是运行时的地图，strip 是撕掉地图——程序照样跑，但迷路了没人能帮你。**

**调试信息格式：**

| 平台 | 调试格式 | 存储位置 |
|------|---------|---------|
| Linux/GCC | DWARF | 嵌入 ELF 的 `.debug_*` 段 |
| Windows/MSVC | PDB | 独立 `.pdb` 文件 |
| macOS/Clang | DWARF | 最初嵌入 Mach-O，后提取到 dSYM 包 |

**DWARF 如何依赖运行时：**

```
DWARF 调试段：
.debug_info     → 类型定义、变量位置、函数范围
.debug_line     → 源码行号与机器码的映射
.debug_frame    → 栈帧回溯信息（依赖运行时的栈布局）
.debug_str      → 字符串表
.debug_abbrev   → 缩写表
```

调试器需要运行时的配合才能正确工作：

```
1. 栈回溯 → 需要 .debug_frame + 运行时的栈帧布局
   GDB: bt 命令依赖帧指针（ebp/rbp）或 DWARF CFI 信息

2. 异常捕获 → 需要 .eh_frame 段（DWARF 子集）
   运行时用 .eh_frame 做栈展开（stack unwinding）
   异常处理和调试共享同一套栈展开信息

3. 动态库符号 → 运行时加载器维护的链接映射
   GDB: info sharedlibrary 查看运行时加载的动态库
```

**strip 对运行时的影响：**

```bash
# strip 不同级别的效果
strip ./app                     # 移除符号表和调试信息
strip --strip-unneeded ./app    # 保留动态符号，移除其余
strip --strip-debug ./app       # 只移除调试段

# 对比文件大小
-rwxr-xr-x  1 user  48K  app_debug      未strip
-rwxr-xr-x  1 user  12K  app_stripped   strip后
```

| strip 操作 | 对运行时的影响 | 对调试的影响 |
|-----------|--------------|-------------|
| 移除 `.debug_*` 段 | **无影响**，程序正常运行 | 无法源码级调试 |
| 移除符号表 | **无影响**，动态链接用 `.dynsym` | 无法按函数名设断点 |
| 移除 `.eh_frame` | **有影响**，异常处理和栈展开失败 | 无法回溯调用栈 |
| 移除 `.dynsym` | **有影响**，动态链接失败 | 程序无法启动 |

**安全的 strip 实践：**

```bash
# 1. 先保存调试信息到单独文件
objcopy --only-keep-debug ./app ./app.debug

# 2. strip 程序
strip --strip-unneeded ./app

# 3. 给程序添加调试链接（指向 .debug 文件）
objcopy --add-gnu-debuglink=./app.debug ./app

# GDB 调试时自动加载 .debug 文件
# 部署时只发布 strip 后的程序，.debug 文件存档
```

**Core Dump 与运行时：**

```bash
# 启用 core dump
ulimit -c unlimited

# 程序崩溃后分析
gdb ./app core
(gdb) bt          # 需要 .eh_frame 才能回溯
(gdb) info locals # 需要 DWARF 才能查看局部变量

# 没有 debug info 的 core dump 只能看到：
(gdb) bt
# ?? ()                          ← 无符号信息
# ?? () from /lib64/libc.so.6   ← 只有动态库符号
# ?? ()
```

**运行时 = 启动代码(crt0) + 初始化(.init_array) + 标准库(libc/libstdc++) + 退出清理(atexit/.fini_array) → 版本兼容是部署的坑 → freestanding可以完全脱离 → 调试信息是运行时的地图，strip要谨慎**
