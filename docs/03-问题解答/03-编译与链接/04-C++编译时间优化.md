# C++编译时间优化
> 📖 相关章节：[编译与链接](../../01-C语言/17-编译与链接.md)、[静态库](../../01-C语言/18-静态库.md)、[动态库](../../01-C语言/19-动态库与共享库.md)、[CMake](../../01-C语言/23-CMake构建系统.md)

> "餐厅优化出菜速度——提前备菜（预编译头）、减少菜单项（前向声明）、合并订单（统一构建）。"

***

### 1. 核心定义

**C++ 编译时间优化** = 减少从源码到可执行文件耗时的策略和技巧。

C++ 编译慢是出了名的，大型项目增量编译动辄数分钟，全量编译可能数小时。优化编译时间直接影响开发效率和迭代速度。

***

### 2. 生活类比

**餐厅出菜速度优化**：

| 餐厅问题 | 对应 C++ 问题 | 优化方法 |
|------|------|------|
| 每道菜都从零备料 | 每个 .cpp 都重新解析头文件 | 预编译头（提前备菜） |
| 菜单太长，厨师记不住 | 头文件包含太多，编译器解析慢 | 前向声明（减少菜单项） |
| 厨房太小，一次只能做一道菜 | 单线程编译 | 并行构建 / 分布式构建 |
| 每次改一道菜，所有菜都重做 | 改一个头文件，所有依赖文件重编译 | Pimpl / 接口与实现分离 |
| 食材重复采购 | 同一代码多次编译 | ccache（缓存编译结果） |

### 3. 编译慢的根因分析

#### 1. C++ 编译模型的问题

```
a.h ──→ b.cpp ──→ b.o ──┐
a.h ──→ c.cpp ──→ c.o ──┤──→ 链接 ──→ 可执行文件
a.h ──→ d.cpp ──→ d.o ──┘
```

**问题**：`a.h` 被三个 .cpp 包含，就要被解析三次。如果 `a.h` 又包含了其他头文件，解析次数指数级增长。

#### 2. 根因分类

| 根因 | 说明 | 影响 |
|------|------|------|
| 头文件重复包含 | 同一头文件被多个 .cpp 解析 | 编译时间线性增长 |
| 头文件嵌套过深 | A 包含 B，B 包含 C…… | 解析时间指数增长 |
| 模板实例化 | 每个编译单元独立实例化相同模板 | 重复工作 |
| 内联函数膨胀 | 头文件中大量 inline 函数 | 解析和代码生成慢 |
| 链接时间过长 | 大量 .o 文件合并 | 全量构建慢 |
| 单线程编译 | 默认一次编译一个文件 | CPU 利用率低 |

#### 3. 如何诊断编译慢

```bash
# Clang: 生成编译时间报告
clang++ -ftime-report main.cpp

# GCC: 生成编译时间报告
g++ -ftime-report main.cpp

# CMake: 分析编译时间
cmake --build . --target help  # 查看所有目标
cmake --build . -j8            # 并行构建

# 使用 Clang Build Analyzer
clang-build-analyzer build_log.json
```

### 4. 预编译头（Precompiled Headers）

#### 1. 原理

将不常变化的头文件预先编译成二进制格式，后续编译直接加载，跳过解析步骤。

```
普通编译:  stdio.h + stdlib.h + string → 每次解析
预编译头:  stdio.h + stdlib.h + string → 预编译一次 → pch.pch → 后续直接加载
```

#### 2. CMake 配置

```cmake
# CMake 3.16+ 原生支持预编译头
target_precompile_headers(my_target
    PRIVATE
        <vector>
        <string>
        <map>
        <memory>
        <algorithm>
        "my_common_header.h"
)
```

#### 3. 手动配置（GCC/Clang）

```bash
# 生成预编译头
g++ -x c++-header common.h -o common.h.gch

# 使用预编译头（include 时编译器自动查找 .gch）
g++ -include common.h main.cpp -o main
```

#### 4. 预编译头的注意事项

| 注意点 | 说明 |
|------|------|
| 只放不常变化的头 | 预编译头变了，所有依赖文件都要重编译 |
| 跨平台差异 | MSVC 用 .pch，GCC 用 .gch，Clang 用 .pch |
| 必须是第一个 include | 预编译头之前不能有其他代码（部分编译器要求） |
| PCH 命中条件 | 编译选项必须与生成 PCH 时一致 |

### 5. 前向声明

#### 1. 原理

只声明类名，不包含完整头文件，减少依赖。

```cpp
// 不需要知道 Foo 的完整定义，只需要知道它存在
class Foo;

class Bar {
    Foo* foo_ptr;
    Foo& foo_ref;
    // Foo foo_val;  // 错误！值类型需要完整定义

    void process(Foo* f);
};
```

#### 2. 什么时候可以用前向声明

| 场景 | 能否用前向声明 | 原因 |
|------|:---:|------|
| 指针/引用类型 | 可以 | 只需要知道类名 |
| 函数参数/返回值（指针/引用） | 可以 | 同上 |
| 值类型成员 | 不可以 | 编译器需要知道大小 |
| 继承基类 | 不可以 | 需要完整定义 |
| 调用成员函数 | 不可以 | 需要知道函数签名 |

#### 3. 前向声明的代码示例

```cpp
// engine.h
#pragma once
#include <memory>

class Renderer;
class PhysicsWorld;
class SoundSystem;

class Engine {
    std::unique_ptr<Renderer> renderer_;
    std::unique_ptr<PhysicsWorld> physics_;
    std::unique_ptr<SoundSystem> sound_;

public:
    Engine();
    ~Engine();

    void run();
};

// engine.cpp — 在实现文件中包含完整头文件
#include "engine.h"
#include "renderer.h"
#include "physics_world.h"
#include "sound_system.h"

Engine::Engine()
    : renderer_(std::make_unique<Renderer>())
    , physics_(std::make_unique<PhysicsWorld>())
    , sound_(std::make_unique<SoundSystem>())
{}

Engine::~Engine() = default;

void Engine::run() {
    renderer_->render();
    physics_->step();
    sound_->play();
}
```

**效果**：修改 `renderer.h` 不会导致所有包含 `engine.h` 的文件重编译，只有 `engine.cpp` 重编译。

> 详见 [5. 前向声明](03-前向声明与包含头文件.md) 了解更多前向声明的用法和陷阱。

### 6. Pimpl（Pointer to Implementation）

#### 1. 原理

将类的私有成员移到单独的实现类中，头文件只保留指针，彻底隔离实现细节。

```cpp
// widget.h — 公共头文件，不暴露实现细节
#pragma once
#include <memory>

class Widget {
public:
    Widget();
    ~Widget();

    void do_something();
    int get_value() const;

private:
    struct Impl;
    std::unique_ptr<Impl> pimpl_;
};

// widget.cpp — 实现文件，包含所有私有依赖
#include "widget.h"
#include "heavy_header_a.h"
#include "heavy_header_b.h"
#include <vector>
#include <string>

struct Widget::Impl {
    std::vector<std::string> data_;
    HeavyObjectA obj_a_;
    HeavyObjectB obj_b_;

    void internal_process() {
        // 实现细节
    }
};

Widget::Widget() : pimpl_(std::make_unique<Impl>()) {}
Widget::~Widget() = default;

void Widget::do_something() {
    pimpl_->internal_process();
}

int Widget::get_value() const {
    return static_cast<int>(pimpl_->data_.size());
}
```

#### 2. Pimpl 的编译时间收益

| 修改内容 | 无 Pimpl | 有 Pimpl |
|------|------|------|
| 修改私有成员 | 所有包含 widget.h 的文件重编译 | 只有 widget.cpp 重编译 |
| 新增私有依赖 | 所有包含 widget.h 的文件重编译 | 只有 widget.cpp 重编译 |
| 修改实现逻辑 | 所有包含 widget.h 的文件重编译 | 只有 widget.cpp 重编译 |

**核心收益**：将头文件依赖从"传递依赖"变成"实现文件私有依赖"。

> 详见 [FAQ 86 Pimpl](24-什么是Pimpl惯用法.md) 了解 Pimpl 的完整用法和注意事项。

### 7. C++20 模块（Modules）

#### 1. 原理

模块取代头文件的 `#include` 机制，编译一次后生成二进制接口文件（BMI），后续直接使用，无需重复解析。

#### 2. 传统头文件 vs 模块

| 维度 | 头文件 (#include) | 模块 (import) |
|------|------|------|
| 解析次数 | 每个编译单元都解析一次 | 只解析一次，后续直接加载 |
| 宏污染 | 包含后宏会影响后续代码 | 模块不导出宏 |
| 顺序依赖 | include 顺序影响结果 | import 顺序无关 |
| 隔离性 | 差（所有内容暴露） | 好（只导出指定的声明） |
| 编译速度 | 慢 | 快 |

#### 3. 模块代码示例

```cpp
// math_utils.cppm — 模块接口文件
export module math_utils;

export int add(int a, int b) {
    return a + b;
}

export int multiply(int a, int b) {
    return a * b;
}

// 内部函数不导出
int internal_helper(int x) {
    return x * x;
}
```

```cpp
// main.cpp
import math_utils;
#include <iostream>

int main() {
    std::cout << add(3, 4) << std::endl;
    std::cout << multiply(3, 4) << std::endl;
    return 0;
}
```

#### 4. 模块的现状

| 编译器 | 支持情况 |
|------|------|
| MSVC | 完整支持 |
| GCC | 大部分支持（GCC 11+） |
| Clang | 大部分支持（Clang 16+） |
| CMake | 3.28+ 原生支持 |

**注意**：模块是 C++20 特性，目前生态还在建设中，大型项目迁移需要谨慎。

### 8. include-what-you-use 工具

#### 1. 原理

静态分析代码，检测头文件中哪些是真正需要的、哪些是多余的。

#### 2. 安装和使用

```bash
# 安装（Ubuntu）
sudo apt install iwyu

# 对单个文件分析
include-what-you-use main.cpp

# CMake 集成
cmake -DCMAKE_CXX_INCLUDE_WHAT_YOU_USE=include-what-you-use ..

# 批量修复
iwyu_tool.py -p build_dir | fix_includes.py
```

#### 3. 典型输出

```
main.cpp should add these lines:
#include <vector>          // for vector

main.cpp should remove these lines:
- #include <algorithm>     // 不需要
- #include <iostream>      // 不需要（如果没用到）
```

#### 4. 常见的冗余 include 模式

| 冗余模式 | 说明 |
|------|------|
| 传递依赖 | A 包含 B，B 包含 C，A 不需要直接包含 C |
| 未使用的 include | 包含了但没用到任何符号 |
| 可以用前向声明替代 | 只用了指针/引用，不需要完整定义 |

### 9. 分布式构建（ccache / distcc）

#### 1. ccache：编译结果缓存

```bash
# 安装
sudo apt install ccache

# 配置 CMake 使用 ccache
cmake -DCMAKE_CXX_COMPILER_LAUNCHER=ccache ..

# 查看缓存统计
ccache -s

# 清空缓存
ccache -C
```

**原理**：缓存编译结果，相同源码 + 相同编译选项 → 直接复用 .o 文件。

**典型收益**：

| 场景 | 无 ccache | 有 ccache |
|------|------|------|
| 切换分支后重新编译 | 全量编译 | 缓存命中，秒级 |
| clean 后重新编译 | 全量编译 | 缓存命中，秒级 |
| 多人共享缓存（远程） | 各自编译 | 共享缓存，首次慢后续快 |

#### 2. distcc：分布式编译

```bash
# 安装
sudo apt install distcc

# 配置可用的编译服务器
distcc --set-hosts "192.168.1.10/8,192.168.1.11/8"

# CMake 配置
cmake -DCMAKE_CXX_COMPILER_LAUNCHER=distcc ..

# 监控编译任务分布
distccmon-text
```

**原理**：将编译任务分发到多台机器并行执行。

#### 3. ccache + distcc 组合

```bash
# CMake 配置同时使用两者
cmake \
    -DCMAKE_CXX_COMPILER_LAUNCHER="ccache;distcc" \
    ..
```

#### 4. Ninja 构建系统

```bash
# CMake 生成 Ninja 构建文件（比 Make 更快）
cmake -G Ninja ..
ninja -j8
```

Ninja 比 Make 更快的原因：更少的启动开销、更智能的依赖分析、更好的并行调度。

### 10. 与前向声明(faq-95)/Pimpl(faq-86)/inline(faq-14)的关系

#### 1. 与前向声明的关系

[5. 前向声明](03-前向声明与包含头文件.md) 讲的是前向声明本身的语法和用法，本 FAQ 将其作为编译时间优化的手段之一。

**核心联系**：前向声明是减少头文件依赖的第一步，效果立竿见影。

#### 2. 与 Pimpl 的关系

[FAQ 86 Pimpl](24-什么是Pimpl惯用法.md) 讲的是 Pimpl 的完整用法，本 FAQ 将其作为编译时间优化的进阶手段。

**核心联系**：Pimpl 是前向声明的终极形态——不仅前向声明类，还把所有私有成员都移走。

#### 3. 与 inline 的关系

[FAQ 14 inline关键字的真实含义](../01-基础概念/14-inline关键字的真实含义.md) 讲了 inline 的本质——不是"内联展开"的指令，而是"允许重复定义"的链接许可。

**与编译时间的关系**：

| inline 的行为 | 对编译时间的影响 |
|------|------|
| 头文件中大量 inline 函数 | 增加每个编译单元的解析量，编译变慢 |
| 模板隐式 inline | 同上 |
| 合理使用 inline | 短小函数内联可减少函数调用开销，但编译时间可能增加 |

**建议**：不要为了"性能"在头文件中写大量 inline 函数，现代编译器会自动内联。

#### 4. 优化手段的优先级

```
1. 预编译头        — 投入低，收益高，优先做
2. 前向声明        — 投入低，收益中，随手做
3. include 清理    — 投入中，收益中，用 iwyu 工具
4. Pimpl          — 投入高，收益高，关键类做
5. C++20 模块     — 投入高，收益高，新项目考虑
6. ccache/distcc  — 投入低，收益高，CI 环境必做
```

***

### 11. 极简总结

**C++ 编译慢的根因是头文件重复解析，优化核心是减少依赖和重复工作。**

| 要点 | 说明 |
|------|------|
| 根因 | 头文件重复包含、模板重复实例化、单线程编译 |
| 预编译头 | 提前编译不常变的头文件，立竿见影 |
| 前向声明 | 只声明类名，不包含完整头文件 |
| Pimpl | 私有成员移到实现文件，彻底隔离依赖 |
| C++20 模块 | 取代 #include，编译一次直接复用 |
| ccache | 缓存编译结果，切换分支秒级重编译 |
| 一句话 | 减少依赖、减少重复、增加并行 |
