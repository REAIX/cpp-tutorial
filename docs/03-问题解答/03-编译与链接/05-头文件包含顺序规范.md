# 头文件包含顺序规范
> 📖 相关章节：[多文件编程](../../01-C语言/16-多文件编程.md)、[预处理器](../../01-C语言/10-预处理器.md)

> "穿衣服的顺序——内衣→衬衫→外套，顺序不对会暴露不该露的"——头文件包含顺序影响编译依赖和隐藏依赖的检测。

***

### 1. 核心定义

- **头文件包含顺序** = `#include` 指令的排列顺序，直接影响编译依赖的可见性和隐藏依赖的暴露
- **隐藏依赖** = 一个头文件依赖另一个头文件的符号，但没有显式 `#include`，恰好因为其他头文件间接包含了它

关键点：**对应头文件放第一个，能检测出隐藏依赖；顺序错了，隐藏依赖就藏起来了**。

***

### 2. 生活类比

**穿衣服的顺序**：

| 概念 | 类比 | 对应代码 |
|------|------|---------|
| 对应头文件 | 内衣——必须先穿，否则直接暴露 | `foo.cpp` 第一个包含 `foo.h` |
| C 系统头文件 | 衬衫——穿在内衣外面 | `<stdio.h>` `<stdlib.h>` |
| C++ 系统头文件 | 西装外套——穿在衬衫外面 | `<vector>` `<string>` |
| 其他库头文件 | 领带/胸针——装饰性附加 | `<boost/...>` `<gtest/...>` |
| 项目内头文件 | 外套口袋里的私人物品 | `"bar.h"` `"utils.h"` |

**顺序错误的风险**：

```
正确顺序（内衣→衬衫→外套）：
  内衣遮住身体 → 衬衫遮住内衣 → 外套遮住衬衫
  → 每一层都独立完整，不依赖外层

错误顺序（外套→衬衫→内衣）：
  外套遮住了身体 → 你以为衬衫不需要
  → 脱掉外套后，发现衬衫根本遮不住（隐藏依赖暴露）
```

**头文件的道理一样**：

```
正确：foo.h → 系统头 → 项目头
  foo.h 排第一，如果它缺少某个 #include，
  编译 foo.cpp 时立刻报错（因为前面的头文件还没被包含）

错误：系统头 → 项目头 → foo.h
  系统头间接提供了 foo.h 需要的符号
  → foo.h 的隐藏依赖被掩盖，单独包含 foo.h 时才报错
```

***

### 3. Google C++ Style Guide 推荐顺序

Google C++ 风格指南推荐的包含顺序（从上到下）：

| 顺序 | 类别 | 示例 | 用途 |
|:---:|------|------|------|
| 1 | 对应头文件 | `"foo.h"` | 检测 foo.h 的隐藏依赖 |
| 2 | C 系统头文件 | `<cstdio>` `<cstring>` | C 标准库 |
| 3 | C++ 系统头文件 | `<vector>` `<string>` | C++ 标准库 |
| 4 | 其他库头文件 | `<boost/...>` `<gtest/...>` | 第三方库 |
| 5 | 项目内头文件 | `"bar.h"` `"utils.h"` | 本项目其他模块 |

**排序规则**：

- 同一类内按字母顺序排列
- 项目内头文件用 `""` 包围，系统/库头文件用 `<>` 包围
- 每个类别之间用空行分隔

#### 1. 正确的包含顺序示例

```cpp
// foo.cpp

#include "foo.h"           // 1. 对应头文件

#include <algorithm>       // 2. C 系统头（C++ 风格）
#include <cstdio>
#include <cstring>

#include <map>             // 3. C++ 系统头
#include <string>
#include <vector>

#include <gtest/gtest.h>   // 4. 其他库头

#include "bar.h"           // 5. 项目内头
#include "utils.h"
```

#### 2. 错误的包含顺序示例

```cpp
// foo.cpp（错误示范）

#include <vector>          // 系统头在前
#include <string>
#include "bar.h"           // 项目头在中间
#include "foo.h"           // 对应头文件不在第一个！
#include <gtest/gtest.h>   // 其他库头混在项目头后面
#include "utils.h"
```

**问题**：`foo.h` 不在第一个，如果 `foo.h` 依赖 `<string>` 但忘记 `#include <string>`，因为 `<string>` 在前面已经被包含，编译不会报错——隐藏依赖被掩盖了。

***

### 4. 为什么对应头文件放第一个

#### 1. 隐藏依赖检测原理

```
包含顺序：foo.h → <string> → <vector>

编译 foo.cpp 时：
1. 预处理器先展开 foo.h
2. foo.h 用到了 std::string，但没有 #include <string>
3. 此时 <string> 还没被包含 → 编译报错！
4. 修复：在 foo.h 中添加 #include <string>

结果：foo.h 变得自包含（self-contained），可以独立使用
```

```
包含顺序：<string> → <vector> → foo.h

编译 foo.cpp 时：
1. 预处理器先展开 <string> 和 <vector>
2. 再展开 foo.h
3. foo.h 用到了 std::string，虽然没有 #include <string>
4. 但 <string> 已经在前面被包含了 → 编译通过！
5. 换一个 .cpp 文件单独包含 foo.h → 编译失败

结果：foo.h 有隐藏依赖，只在 foo.cpp 中碰巧能编译
```

#### 2. 代码示例：隐藏依赖

```cpp
// person.h（有隐藏依赖）
#pragma once
#include <string>

class Person {
    std::string name_;  // 依赖 <string>
    int age_;
public:
    Person(const std::string& name, int age);
    std::string info() const;  // 返回 string
};
```

```cpp
// person.cpp（正确顺序）
#include "person.h"       // 第一个包含对应头文件

#include <algorithm>      // C 系统头
#include <cstdio>

#include <sstream>        // C++ 系统头
#include <string>

#include "format_utils.h" // 项目内头
```

```cpp
// person.cpp（错误顺序——隐藏依赖被掩盖）
#include <sstream>        // C++ 系统头在前
#include <string>
#include "format_utils.h" // 项目头
#include "person.h"       // 对应头文件在最后

// 如果 person.h 忘记了 #include <string>
// 这里不会报错，因为 <string> 已经在前面被包含了
// 但其他文件单独 #include "person.h" 时会编译失败
```

#### 3. 自包含（Self-contained）原则

**每个头文件都应该能独立编译**——即只 `#include "foo.h"` 就能通过编译，不需要额外包含其他头文件。

验证方法：

```cpp
// test_foo_self_contained.cpp
#include "foo.h"
// 仅包含 foo.h，不包含其他任何头文件
// 如果编译通过，说明 foo.h 是自包含的
int main() {
    return 0;
}
```

### 5. 对比表格

| 包含顺序 | 隐藏依赖 | 编译依赖 | 可维护性 |
|----------|:---:|:---:|:---:|
| 对应头文件放第一个 | 能检测 | 清晰 | 好 |
| 对应头文件放最后 | 被掩盖 | 模糊 | 差 |
| 随意排列 | 可能掩盖 | 混乱 | 很差 |
| 按类别分组排序 | 能检测 | 清晰 | 最好 |

| 类别 | 符号 | 示例 | 说明 |
|------|------|------|------|
| 对应头文件 | `""` | `"foo.h"` | 必须第一个 |
| C 系统头 | `<>` | `<cstdio>` `<cstring>` | C 标准库的 C++ 版本 |
| C++ 系统头 | `<>` | `<vector>` `<string>` | C++ 标准库 |
| 其他库头 | `<>` | `<boost/...>` | 第三方库 |
| 项目内头 | `""` | `"bar.h"` | 本项目其他模块 |

### 6. 常见误区

#### 1. 误区1：头文件顺序无所谓，能编译就行

```cpp
// a.h
#pragma once
class A { /* ... */ };

// b.h
#pragma once
#include <string>
class B {
    std::string name_;
    A a_;  // 依赖 a.h，但没有 #include "a.h"
};

// main.cpp
#include "a.h"    // 先包含 a.h
#include "b.h"    // 再包含 b.h → 编译通过！
// 但 #include "b.h" 单独使用会报错
```

**正确做法**：在 `b.h` 中添加 `#include "a.h"`，使其自包含。

#### 2. 误区2：用 #pragma once 就不需要关心顺序

`#pragma once` 防止重复包含，但不解决隐藏依赖问题。顺序错误仍然会掩盖缺失的 `#include`。

#### 3. 误区3：把所有 #include 都放在 .cpp 中，头文件不放

```cpp
// person.h（错误：头文件不包含所需依赖）
#pragma once
class Person {
    std::string name_;  // 用了 string 但没 include
};

// person.cpp
#include "person.h"
#include <string>  // 在 .cpp 中包含
```

**问题**：其他文件 `#include "person.h"` 时编译失败。

**正确做法**：头文件中包含自己需要的所有依赖。

```cpp
// person.h（正确：自包含）
#pragma once
#include <string>  // 头文件自己包含所需依赖

class Person {
    std::string name_;
};
```

#### 4. 误区4：前置声明可以完全替代 #include

```cpp
// person.h
#pragma once
#include <string>

class Address;  // 前置声明，减少编译依赖

class Person {
    std::string name_;
    Address* addr_;  // 指针/引用可以用前置声明
    // Address addr_; // 错误！值类型必须 #include 完整定义
};
```

前置声明只能用于指针、引用和函数声明，不能用于值类型、继承和需要知道完整大小的场景。

***

### 7. 极简总结

**对应头文件放第一个，按类别分组排序**

| 要点 | 说明 |
|------|------|
| 核心原则 | 对应头文件放第一个，检测隐藏依赖 |
| 推荐顺序 | 对应头 → C 系统头 → C++ 系统头 → 其他库头 → 项目头 |
| 自包含 | 每个头文件应能独立编译，不依赖外部间接包含 |
| 隐藏依赖 | 顺序错误会掩盖缺失的 #include |
| 一句话 | 穿衣服从内到外，包含从头文件开始 |
