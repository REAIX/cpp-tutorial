# 什么是动态链接与静态链接
> 📖 相关章节：[编译与链接](../../01-C语言/17-编译与链接.md)、[静态库](../../01-C语言/18-静态库.md)、[动态库与共享库](../../01-C语言/19-动态库与共享库.md)

> 链接是编译的最后一步——选择静态还是动态，直接影响程序体积、启动速度、内存占用和部署方式。

***

### 1. 先抓核心

静态链接将库代码直接嵌入可执行文件，动态链接在运行时加载共享库——前者自包含但体积大，后者轻量但依赖环境。

***

### 2. 静态链接的原理与特点

静态链接在编译期将目标文件（`.o`/`.obj`）和静态库（`.a`/`.lib`）中的所有被引用符号解析并合并到最终可执行文件中：

```
源文件.c ──编译──> 目标文件.o ──┐
                               ├──静态链接──> 可执行文件（自包含）
静态库.a ──提取被引用的.o ──────┘
```

```cpp
#include <cstdio>

int add(int a, int b) {
    return a + b;
}

int main() {
    int result = add(3, 4);
    std::printf("3 + 4 = %d\n", result);
    return 0;
}
```

**Linux 静态编译**：
```bash
g++ -static main.cpp -o main_static
```

**Windows (MSVC) 静态编译**：
```bash
cl /MT main.cpp
```

| 特点 | 说明 |
|------|------|
| 可执行文件体积 | 大（包含所有库代码） |
| 启动速度 | 快（无需运行时查找库） |
| 部署 | 简单（单文件即可运行） |
| 内存占用 | 多个实例各自加载，不共享 |
| 库更新 | 需重新编译可执行文件 |
| 符号冲突 | 可能出现重复定义 |

***

### 3. 动态链接的原理与特点

动态链接在运行时由动态链接器（Linux: `ld-linux.so`，Windows: `ntdll.dll`）加载共享库并解析符号：

```
源文件.c ──编译──> 目标文件.o ──┐
                               ├──动态链接──> 可执行文件（含引用表）
动态库.so/.dll ──运行时加载 ────┘
```

**Linux 动态编译**：
```bash
g++ main.cpp -o main_dynamic
```

**Windows (MSVC) 动态编译**：
```bash
cl /MD main.cpp
```

| 特点 | 说明 |
|------|------|
| 可执行文件体积 | 小（仅含引用信息） |
| 启动速度 | 稍慢（需加载和重定位） |
| 部署 | 需确保库文件存在 |
| 内存占用 | 多进程共享同一库的代码段 |
| 库更新 | 替换库文件即可（需兼容） |
| 符号冲突 | 可能出现版本不兼容 |

***

### 4. 静态链接 vs 动态链接对比

| 对比维度 | 静态链接 | 动态链接 |
|----------|----------|----------|
| 链接时机 | 编译期 | 运行期 |
| 可执行文件大小 | 大 | 小 |
| 启动速度 | 快 | 稍慢 |
| 运行时内存 | 各实例独立 | 代码段共享 |
| 库更新 | 需重新编译 | 替换库文件 |
| 部署复杂度 | 低（单文件） | 高（需附带库） |
| 磁盘占用 | 多份拷贝 | 一份共享 |
| 符号解析 | 编译期完成 | 运行期延迟绑定 |
| 典型场景 | 嵌入式、独立工具 | 桌面应用、系统库 |

**实际大小对比**（Linux，同一程序）：

```bash
$ g++ -static hello.cpp -o hello_static
$ g++ hello.cpp -o hello_dynamic
$ ls -lh hello_static hello_dynamic
-rwxr-xr-x 1 user user 1.8M hello_static
-rwxr-xr-x 1 user user  16K hello_dynamic
```

### 5. Linux 平台：.a / .so 与工具链

**静态库（`.a`）**本质是 `.o` 文件的归档（ar archive）：

```bash
g++ -c mathlib.cpp -o mathlib.o
ar rcs libmath.a mathlib.o

g++ main.cpp -L. -lmath -o main
```

**动态库（`.so`）**是位置无关代码（PIC）编译的共享对象：

```bash
g++ -fPIC -shared mathlib.cpp -o libmath.so

g++ main.cpp -L. -lmath -o main
export LD_LIBRARY_PATH=.:$LD_LIBRARY_PATH
./main
```

| 工具 | 用途 |
|------|------|
| `ar` | 创建/管理静态库 `.a` |
| `nm` | 查看目标文件中的符号 |
| `ldd` | 查看可执行文件依赖的动态库 |
| `objdump` | 反汇编、查看段信息 |
| `readelf` | 查看 ELF 文件头、段、符号表 |
| `ldconfig` | 更新动态链接器缓存 |

**查看依赖关系**：

```bash
$ ldd main_dynamic
linux-vdso.so.1
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
/lib64/ld-linux-x86-64.so.2
```

**soname 机制**：

```bash
g++ -fPIC -shared -Wl,-soname,libmath.so.1 mathlib.cpp -o libmath.so.1.0.0
ln -sf libmath.so.1.0.0 libmath.so.1
ln -sf libmath.so.1 libmath.so
```

| 文件 | 作用 |
|------|------|
| `libmath.so.1.0.0` | 实际库文件（含版本号） |
| `libmath.so.1` | soname 链接（接口兼容） |
| `libmath.so` | 开发链接（编译时使用） |

> **soname 规则**：接口兼容的更新只改小版本号，soname 不变；接口不兼容时 soname 递增，旧程序仍可使用旧版库。

### 6. Windows 平台：.lib / .dll 与工具链

Windows 的链接模型与 Linux 有重要区别：

| 概念 | Linux | Windows |
|------|-------|---------|
| 静态库 | `.a` | `.lib`（静态） |
| 动态库 | `.so` | `.dll` |
| 导入库 | 不需要 | `.lib`（导入库，配合 DLL 使用） |
| 运行时加载器 | `ld-linux.so` | `ntdll.dll` + `kernel32.dll` |

**Windows DLL 的两种链接方式**：

**方式一：隐式链接（编译时，需要 .lib 导入库）**：

```cpp
#include <cstdio>

__declspec(dllexport) int add(int a, int b) {
    return a + b;
}
```

```cpp
#include <cstdio>

__declspec(dllimport) int add(int a, int b);

int main() {
    std::printf("3 + 4 = %d\n", add(3, 4));
    return 0;
}
```

```bash
cl /LD mathlib.cpp
cl main.cpp mathlib.lib
```

**方式二：显式链接（运行时，使用 LoadLibrary）**：

```cpp
#include <windows.h>
#include <cstdio>

typedef int (*AddFunc)(int, int);

int main() {
    HMODULE hDll = LoadLibrary(TEXT("mathlib.dll"));
    if (!hDll) {
        std::printf("无法加载 DLL\n");
        return 1;
    }

    AddFunc add = (AddFunc)GetProcAddress(hDll, "add");
    if (!add) {
        std::printf("无法找到函数\n");
        FreeLibrary(hDll);
        return 1;
    }

    std::printf("3 + 4 = %d\n", add(3, 4));
    FreeLibrary(hDll);
    return 0;
}
```

| MSVC 运行时选项 | 说明 |
|-----------------|------|
| `/MT` | 静态链接 CRT（多线程静态版） |
| `/MTd` | 静态链接 CRT（Debug 版） |
| `/MD` | 动态链接 CRT（多线程 DLL 版） |
| `/MDd` | 动态链接 CRT（Debug DLL 版） |

> **Windows 注意**：`/MT` 和 `/MD` 混用会导致 CRT 状态不一致，是 DLL 地狱的常见原因。

### 7. 运行时动态加载：dlopen / dlsym vs LoadLibrary / GetProcAddress

**Linux：dlopen / dlsym**：

```cpp
#include <dlfcn.h>
#include <cstdio>

typedef int (*AddFunc)(int, int);

int main() {
    void* handle = dlopen("./libmath.so", RTLD_LAZY);
    if (!handle) {
        std::printf("dlopen 失败: %s\n", dlerror());
        return 1;
    }

    dlerror();
    AddFunc add = (AddFunc)dlsym(handle, "add");
    const char* error = dlerror();
    if (error) {
        std::printf("dlsym 失败: %s\n", error);
        dlclose(handle);
        return 1;
    }

    std::printf("3 + 4 = %d\n", add(3, 4));
    dlclose(handle);
    return 0;
}
```

```bash
g++ main.cpp -ldl -o main
```

| dlopen 标志 | 含义 |
|-------------|------|
| `RTLD_LAZY` | 延迟绑定，用到时才解析符号 |
| `RTLD_NOW` | 立即解析所有符号 |
| `RTLD_GLOBAL` | 加载的符号对后续 dlopen 可见 |
| `RTLD_LOCAL` | 符号仅本库可见（默认） |

**跨平台封装**：

```cpp
#if defined(_WIN32)
#include <windows.h>
#else
#include <dlfcn.h>
#endif

class DynamicLib {
#if defined(_WIN32)
    HMODULE handle_ = nullptr;
#else
    void* handle_ = nullptr;
#endif
public:
    bool open(const char* path) {
#if defined(_WIN32)
        handle_ = LoadLibraryA(path);
#else
        handle_ = dlopen(path, RTLD_LAZY);
#endif
        return handle_ != nullptr;
    }

    void* symbol(const char* name) {
#if defined(_WIN32)
        return (void*)GetProcAddress(handle_, name);
#else
        return dlsym(handle_, name);
#endif
    }

    void close() {
#if defined(_WIN32)
        if (handle_) FreeLibrary(handle_);
#else
        if (handle_) dlclose(handle_);
#endif
        handle_ = nullptr;
    }

    ~DynamicLib() { close(); }
};
```

### 8. 符号解析与重定位

链接的核心任务是符号解析——将引用（undefined symbol）与定义（defined symbol）匹配：

```
目标文件 A:  调用 foo()  ──引用──>  未解析
目标文件 B:  定义 foo()  ──定义──>  解析完成
```

**符号可见性**：

```cpp
#if defined(_WIN32)
#define EXPORT __declspec(dllexport)
#define IMPORT __declspec(dllimport)
#else
#define EXPORT __attribute__((visibility("default")))
#define IMPORT
#endif

extern "C" EXPORT int public_api(int x);
int internal_helper(int x);
```

| 控制方式 | Linux | Windows |
|----------|-------|---------|
| 导出符号 | `__attribute__((visibility("default")))` | `__declspec(dllexport)` |
| 隐藏符号 | `__attribute__((visibility("hidden")))` | 不加 dllexport 即不导出 |
| 默认行为 | 默认全部导出（可加 `-fvisibility=hidden` 改变） | 默认不导出 |
| 导入符号 | 不需要特殊声明 | `__declspec(dllimport)` |
| C 链接 | `extern "C"` 避免名称修饰 | `extern "C"` 避免名称修饰 |

**查看符号**：

```bash
nm -D libmath.so
objdump -T libmath.so
```

**名称修饰（Name Mangling）**：

```bash
$ echo 'int add(int, int)' | c++filt
$ nm libmath.so | c++filt
```

### 9. 性能影响与优化

| 阶段 | 静态链接 | 动态链接 |
|------|----------|----------|
| 编译链接 | 较慢（需合并所有 .o） | 较快（仅记录引用） |
| 启动加载 | 快（直接执行） | 稍慢（需加载 .so/.dll + 重定位） |
| 函数调用 | 直接地址 | PLT/GOT 间接跳转（首次有开销） |
| 内存使用 | 各进程独立拷贝 | 代码段共享，数据段 COW |
| 磁盘占用 | 多份冗余 | 一份共享 |

**PLT/GOT 机制**（Linux 动态链接）：

```
调用 foo() ──> PLT[foo] ──> GOT[foo] ──> 首次: 解析真实地址并填入GOT
                                    ──> 后续: 直接跳转到真实地址
```

**优化建议**：

```bash
g++ -fPIC -shared -O2 \
    -Wl,-Bsymbolic \
    -Wl,--as-needed \
    -Wl,-z,relro \
    -Wl,-z,now \
    libmath.cpp -o libmath.so
```

| 链接选项 | 作用 |
|----------|------|
| `-Bsymbolic` | 优先在库内解析符号，减少 PLT 跳转 |
| `--as-needed` | 只记录实际使用的依赖 |
| `-z,relro` | 只读重定位段（安全） |
| `-z,now` | 禁止延迟绑定（安全，但启动慢） |

### 10. 混合链接与常见问题

**混合使用静态库和动态库**：

```bash
g++ main.cpp -L. -lmath_static -lutils_dynamic -o main
```

**常见问题与解决方案**：

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| `undefined reference` | 符号未找到 | 检查库顺序（被依赖的放后面） |
| `cannot open shared object file` | 运行时找不到 .so | 设置 `LD_LIBRARY_PATH` 或 `ldconfig` |
| `DLL not found` | 运行时找不到 .dll | 放到 exe 同目录或 PATH 中 |
| `symbol lookup error` | 版本不兼容 | 检查 soname / DLL 版本 |
| 重复定义 | 静态库和动态库有相同符号 | 使用 `-Wl,--allow-multiple-definition` 或重构 |
| CRT 不一致 | `/MT` 和 `/MD` 混用 | 统一 CRT 链接方式 |
| ODR 违反 | 同一头文件不同实现 | 确保接口和实现一致 |

**库链接顺序**（Linux）：

```bash
g++ main.o -lA -lB -lC
```

> **规则**：被依赖的库放后面。如果 A 依赖 B，则 `-lA -lB`，不能反过来。这是因为链接器从左到右扫描，只记录未解析符号，遇到定义时才填充。

**静态链接全部库（Linux）**：

```bash
g++ -static main.cpp -lpthread -lm -o main
```

> **注意**：glibc 不推荐静态链接，因为 NSS（Name Service Switch）等模块无法静态链接。musl libc 更适合静态链接。

### 11. 极简总结

| 概念 | 要点 |
|------|------|
| 静态链接 | 编译期合并，体积大，部署简单，启动快 |
| 动态链接 | 运行时加载，体积小，共享内存，需管理依赖 |
| Linux 静态库 | `.a`（ar 归档），`ar rcs` 创建 |
| Linux 动态库 | `.so`（共享对象），`-fPIC -shared` 编译 |
| Windows 静态库 | `.lib`（静态），`lib.exe` 创建 |
| Windows 动态库 | `.dll` + `.lib`（导入库），`__declspec(dllexport)` |
| 运行时加载 | Linux: `dlopen/dlsym`，Windows: `LoadLibrary/GetProcAddress` |
| soname | 接口版本管理，兼容更新不改 soname |
| 符号解析 | 被依赖库放后面，注意名称修饰 |
| 混合链接 | 统一 CRT，注意库顺序，避免 ODR 违反 |
| 性能 | 静态启动快，动态共享内存；PLT/GOT 有间接跳转开销 |
