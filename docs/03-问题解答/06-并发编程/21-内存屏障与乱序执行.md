# 内存屏障与乱序执行详解
> 📖 相关章节：[多线程基础](../../02-CPP/29-多线程基础.md)、[线程同步](../../02-CPP/30-线程同步.md)、[原子操作](../../02-CPP/31-原子操作与异步编程.md)、[无锁编程](../../02-CPP/33-无锁编程.md)

> "你让助手先寄信再打电话，但助手可能先打电话再寄信——内存屏障就是'必须先寄完信才能打电话'的强制令。"

***

### 1. 核心定义

**内存屏障（Memory Barrier / Memory Fence）** = 一条指令，阻止编译器或 CPU 对屏障前后的指令进行特定类型的重排。

**乱序执行（Out-of-Order Execution）** = 编译器和 CPU 为了提升性能，可能将你写的代码顺序打乱执行，只要单线程结果不变即可——但多线程下可能出问题。

关键点：**单线程看不出来，多线程才会暴露**。乱序执行对单线程是透明的（结果不变），但在多线程中，一个线程可能看到另一个线程的"半完成"状态。

***

### 2. 生活类比

**寄信与打电话**：

你给助手布置了两个任务：
1. 先寄一封信
2. 再给客户打电话

助手为了效率，可能**先打电话再寄信**（乱序执行），因为打电话更紧急、寄信可以等。

在单任务视角下，两件事都完成了，没区别。但如果客户接到电话后立刻去信箱找信——**信还没寄出**，客户就看到了不一致的状态。

**内存屏障 = 强制令**："寄完信之前，不许打电话！"——保证顺序，牺牲一点效率。

***

### 3. 两种重排：编译器重排 vs CPU 重排

#### 1. 编译器重排

编译器在优化阶段，可能将源代码中的语句顺序打乱：

```cpp
int data = 0;
bool ready = false;

void writer() {
    data = 42;       // 源码顺序：先写数据
    ready = true;    // 源码顺序：后设标志
}

void reader() {
    if (ready) {
        print(data);  // 期望输出 42，但可能输出 0
    }
}
```

编译器可能将 `ready = true` 提前到 `data = 42` 之前，因为在单线程视角下两者没有依赖关系。

**阻止编译器重排的方法**：

| 方法 | 说明 |
|------|------|
| `std::atomic` | 原子操作自带编译器屏障 |
| `asm volatile("" ::: "memory")` | GCC/Clang 内联汇编屏障 |
| `std::atomic_thread_fence` | C++11 标准屏障 |

#### 2. CPU 重排

即使编译器按顺序生成指令，CPU 在执行时也可能动态调度：

| CPU 架构 | Store-Store 重排 | Store-Load 重排 | Load-Load 重排 | Load-Store 重排 |
|----------|:---:|:---:|:---:|:---:|
| x86/x86_64 | 不允许 | **允许** | 不允许 | 不允许 |
| ARM | 允许 | 允许 | 允许 | 允许 |
| PowerPC | 允许 | 允许 | 允许 | 允许 |
| RISC-V | 允许 | 允许 | 允许 | 允许 |

**x86 是强内存序（TSO）**，只允许 Store-Load 重排；ARM/PowerPC 是弱内存序，几乎所有类型都可能重排。

#### 3. 两种重排的对比

| 维度 | 编译器重排 | CPU 重排 |
|------|------|------|
| 发生阶段 | 编译期 | 运行期 |
| 可见性 | 源码级，看汇编可知 | 硬件级，难以直接观测 |
| 阻止方法 | 编译器屏障 | CPU 屏障指令 |
| 影响范围 | 所有平台 | 依赖 CPU 架构 |

### 4. 无屏障时重排导致的问题

#### 1. 经典问题：发布-订阅模式中的半初始化

```cpp
#include <iostream>
#include <thread>

int data = 0;
bool ready = false;

void writer() {
    data = 42;
    ready = true;
}

void reader() {
    while (!ready) {
    }
    std::cout << "data = " << data << std::endl;
}

int main() {
    std::thread t1(writer);
    std::thread t2(reader);
    t1.join();
    t2.join();
    return 0;
}
```

**可能的问题**：

| 时序 | 线程 writer | 线程 reader |
|------|------|------|
| T1 | `ready = true`（被重排到前面） | - |
| T2 | - | 看到 `ready == true`，退出循环 |
| T3 | - | 读 `data`，得到 0（还没写入！） |
| T4 | `data = 42`（被重排到后面） | - |

**根因**：`ready = true` 和 `data = 42` 之间没有屏障，CPU/编译器可能重排。

#### 2. 经典问题：DCL 中的半初始化对象

详见 [双重检查锁DCL为什么有风险](./06-双重检查锁DCL为什么有风险.md)。

DCL 的风险本质上就是乱序执行：`instance = new Object()` 可能被拆成"分配内存 → 赋值指针 → 初始化成员"，编译器/CPU 可能将"赋值指针"提前，导致其他线程看到未初始化的对象。

### 5. C++ 六种内存序

C++11 定义了六种内存序（`std::memory_order`），从弱到强：

| 内存序 | 简写 | 语义 | 对应屏障 |
|--------|------|------|------|
| `memory_order_relaxed` | relaxed | 无顺序保证，只保证原子性 | 无屏障 |
| `memory_order_consume` | consume | 依赖数据的读不会被重排到前面 | 数据依赖屏障（C++17 起不推荐使用） |
| `memory_order_acquire` | acquire | 本线程所有后续读写不会被重排到此操作之前 | 读屏障（Load-Load + Load-Store） |
| `memory_order_release` | release | 本线程所有之前的读写不会被重排到此操作之后 | 写屏障（Store-Store + Load-Store） |
| `memory_order_acq_rel` | acq_rel | acquire + release 的组合 | 读写屏障 |
| `memory_order_seq_cst` | seq_cst | 顺序一致性，全局统一顺序 | 全屏障 + 全局总序 |

#### 1. relaxed：无屏障

```cpp
#include <atomic>
#include <iostream>
#include <thread>

std::atomic<int> counter{0};

void increment() {
    for (int i = 0; i < 1000000; ++i) {
        counter.fetch_add(1, std::memory_order_relaxed);
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();
    std::cout << counter.load(std::memory_order_relaxed) << std::endl;
    return 0;
}
```

**特点**：只保证 `fetch_add` 本身是原子的（不会撕裂读/写），但不保证与其他原子操作的顺序。

**适用场景**：简单计数器，不用于同步。

#### 2. acquire / release：最常用的配对

```cpp
#include <atomic>
#include <iostream>
#include <thread>

int data = 0;
std::atomic<bool> ready{false};

void writer() {
    data = 42;
    ready.store(true, std::memory_order_release);
}

void reader() {
    while (!ready.load(std::memory_order_acquire)) {
    }
    std::cout << "data = " << data << std::endl;
}

int main() {
    std::thread t1(writer);
    std::thread t2(reader);
    t1.join();
    t2.join();
    return 0;
}
```

**同步关系**：

```
writer 线程:                    reader 线程:
  data = 42                       while (!ready.load(acquire))
  ready.store(true, release)  ──→  退出循环
                                   print(data)  // 保证看到 42
```

- **release** 保证：`data = 42` 不会被重排到 `ready.store` 之后
- **acquire** 保证：`print(data)` 不会被重排到 `ready.load` 之前
- **配对效果**：release 写 + acquire 读 = 建立同步关系，保证 data 可见

#### 3. acq_rel：读修改写操作

```cpp
#include <atomic>
#include <iostream>
#include <thread>

std::atomic<int> counter{0};

void worker() {
    for (int i = 0; i < 100000; ++i) {
        counter.fetch_add(1, std::memory_order_acq_rel);
    }
}

int main() {
    std::thread t1(worker);
    std::thread t2(worker);
    t1.join();
    t2.join();
    std::cout << counter.load() << std::endl;
    return 0;
}
```

**适用场景**：读-修改-写（RMW）操作，既需要获取之前的结果，又需要发布自己的修改。

#### 4. seq_cst：默认最强序

```cpp
std::atomic<int> x{0};
std::atomic<int> y{0};

void thread1() {
    x.store(1, std::memory_order_seq_cst);
}

void thread2() {
    y.store(1, std::memory_order_seq_cst);
}

void thread3() {
    int a = x.load(std::memory_order_seq_cst);
    int b = y.load(std::memory_order_seq_cst);
}
```

**特点**：所有 seq_cst 操作存在一个全局统一顺序，所有线程看到的一致。

**代价**：在 ARM 等弱内存序架构上，seq_cst 需要插入全屏障，性能开销较大。

#### 5. 六种内存序的屏障语义总结

| 内存序 | 屏障类型 | 阻止的重排 | 性能开销 |
|--------|------|------|------|
| relaxed | 无 | 无 | 最低 |
| consume | 数据依赖屏障 | 依赖数据的读重排 | 低（C++17 起不推荐） |
| acquire | 读屏障 | Load-Load, Load-Store | 中 |
| release | 写屏障 | Store-Store, Load-Store | 中 |
| acq_rel | 读写屏障 | acquire + release | 较高 |
| seq_cst | 全屏障 + 全局总序 | 所有重排 | 最高 |

### 6. acquire/release 屏障的正确用法

#### 1. 模式1：发布-订阅（一个写者，多个读者）

```cpp
#include <atomic>
#include <iostream>
#include <thread>
#include <vector>

struct Config {
    int width;
    int height;
    bool enabled;
};

Config g_config;
std::atomic<bool> config_ready{false};

void publish_config() {
    g_config.width = 1920;
    g_config.height = 1080;
    g_config.enabled = true;
    config_ready.store(true, std::memory_order_release);
}

void use_config(int id) {
    while (!config_ready.load(std::memory_order_acquire)) {
    }
    std::cout << "Thread " << id << ": "
              << g_config.width << "x" << g_config.height
              << ", enabled=" << g_config.enabled << std::endl;
}

int main() {
    std::thread publisher(publish_config);
    std::vector<std::thread> readers;
    for (int i = 0; i < 3; ++i) {
        readers.emplace_back(use_config, i);
    }
    publisher.join();
    for (auto& t : readers) {
        t.join();
    }
    return 0;
}
```

**要点**：
- 写者用 `release` 发布标志
- 读者用 `acquire` 读取标志
- release-acquire 配对保证：标志为 true 时，Config 的所有字段一定可见

#### 2. 模式2：双重检查锁（DCL）的正确实现

```cpp
#include <atomic>
#include <iostream>
#include <thread>
#include <mutex>

class Singleton {
    static std::atomic<Singleton*> instance;
    static std::mutex mtx;
    int value;

    Singleton() : value(42) {}

public:
    static Singleton* get_instance() {
        Singleton* tmp = instance.load(std::memory_order_acquire);
        if (tmp == nullptr) {
            std::lock_guard<std::mutex> lock(mtx);
            tmp = instance.load(std::memory_order_relaxed);
            if (tmp == nullptr) {
                tmp = new Singleton();
                instance.store(tmp, std::memory_order_release);
            }
        }
        return tmp;
    }

    int get_value() const { return value; }
};

std::atomic<Singleton*> Singleton::instance{nullptr};
std::mutex Singleton::mtx;

int main() {
    auto worker = []() {
        Singleton* s = Singleton::get_instance();
        std::cout << "value = " << s->get_value() << std::endl;
    };

    std::thread t1(worker);
    std::thread t2(worker);
    t1.join();
    t2.join();
    return 0;
}
```

**与无屏障 DCL 的区别**：

| 版本 | 外层读 | 内层写 | 安全性 |
|------|------|------|------|
| 无屏障 DCL | 普通读 | 普通写 | 不安全（可能看到半初始化对象） |
| acquire/release DCL | `acquire` 读 | `release` 写 | 安全（保证初始化完成后才发布指针） |

#### 3. 模式3：使用 std::atomic_thread_fence

```cpp
#include <atomic>
#include <iostream>
#include <thread>

int data = 0;
std::atomic<bool> ready{false};

void writer() {
    data = 42;
    std::atomic_thread_fence(std::memory_order_release);
    ready.store(true, std::memory_order_relaxed);
}

void reader() {
    while (!ready.load(std::memory_order_relaxed)) {
    }
    std::atomic_thread_fence(std::memory_order_acquire);
    std::cout << "data = " << data << std::endl;
}

int main() {
    std::thread t1(writer);
    std::thread t2(reader);
    t1.join();
    t2.join();
    return 0;
}
```

**`atomic_thread_fence` vs 原子操作的内存序参数**：

| 维度 | `atomic_thread_fence` | 原子操作的内存序参数 |
|------|------|------|
| 作用范围 | 独立屏障，影响所有内存操作 | 只影响该原子操作 |
| 灵活性 | 更灵活，可与 relaxed 操作配合 | 更常用，更简洁 |
| 可读性 | 较低 | 较高 |
| 推荐度 | 特殊场景 | 日常首选 |

### 7. 与 DCL(faq-38) 和 C++ 内存模型的关系

#### 1. 与 DCL 的关系

[双重检查锁DCL为什么有风险](./06-双重检查锁DCL为什么有风险.md) 详细分析了 DCL 的风险根因——正是乱序执行。本 FAQ 则从更底层的角度解释了：

- **DCL 的问题** = 乱序执行的具体表现（Store-Store 重排导致指针先赋值、对象后初始化）
- **DCL 的修复** = 使用内存屏障（acquire/release 或全屏障）阻止重排
- **DCL 的替代** = C++11 的 `std::call_once` / Meyer's Singleton，内部自动使用屏障

#### 2. 与 C++ 内存模型的关系

C++ 内存模型定义了多线程程序中，对共享变量的访问如何相互可见：

| 概念 | 说明 |
|------|------|
| **happens-before** | 如果 A happens-before B，则 A 的效果对 B 可见 |
| **synchronizes-with** | release 操作与 acquire 操作建立同步关系 |
| **sequenced-before** | 同一线程内的语句顺序 |
| **inter-thread-happens-before** | 跨线程的 happens-before 关系 |

**核心规则**：

```
release 写 ──synchronizes-with──→ acquire 读
    ↓                                    ↓
之前的写操作                        之后的读操作
happens-before                   happens-before
```

这就是 acquire/release 配对能保证数据可见性的理论基础。

### 8. 常见陷阱

| 陷阱 | 后果 | 修复 |
|------|------|------|
| 用 `volatile` 替代内存屏障 | C++ 的 `volatile` 不提供内存屏障 | 用 `std::atomic` 或 `atomic_thread_fence` |
| relaxed 用于同步 | 无法建立 happens-before 关系 | 同步用 acquire/release，计数用 relaxed |
| 只在写端加 release，读端用 relaxed | 读端可能重排，看到旧数据 | 读端必须用 acquire 配对 |
| 在 x86 上测试通过就认为安全 | x86 是强内存序，ARM 上可能崩溃 | 考虑跨平台，用标准内存序 |
| consume 难以实现，编译器退化为 acquire | C++17 起不推荐使用 consume | 直接用 acquire |

***

### 9. 极简总结

**内存屏障 = 阻止指令重排的强制令，保证多线程下的可见性顺序。**

| 要点 | 说明 |
|------|------|
| 根因 | 编译器和 CPU 都可能重排指令，单线程无感，多线程出问题 |
| 两类重排 | 编译器重排（编译期）+ CPU 重排（运行期） |
| 六种内存序 | relaxed < consume < acquire < release < acq_rel < seq_cst |
| 最常用配对 | release 写 + acquire 读 = 建立同步关系 |
| 一句话 | 能用 seq_cst 就用 seq_cst，性能敏感再用 acquire/release |
