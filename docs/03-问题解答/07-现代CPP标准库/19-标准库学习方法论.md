### 5. 学习标准库的正确姿势

#### 1. 先学接口，再学实现

- 90%的场景只需要知道"怎么用"
- 10%的性能敏感场景才需要知道"底层怎么实现"

```cpp
#include <vector>

void use_vector() {
    std::vector<int> v;
    v.push_back(1);
    v.push_back(2);
    v.push_back(3);

    for (const auto& elem : v) {
        std::cout << elem << " ";
    }
}
```

用`vector`不需要知道它怎么扩容，但当你需要优化性能时，才需要了解扩容策略（通常2倍增长）。

#### 2. 先学常用，再学冷门

- 常用：vector/string/map/sort/unique_ptr
- 冷门：deque/forward_list/priority_queue的底层细节
- 帕累托法则：20%的API覆盖80%的使用场景

#### 3. 读cppreference，不读标准文档

- cppreference.com：最权威的在线参考
- C++标准文档：法律条文风格，不适合学习

cppreference使用方法：

1. 搜索组件名（如 `std::vector`）
2. 查看成员函数列表
3. 关注"Parameters""Return value""Exceptions"
4. 底部的"Example"直接可运行

#### 4. 写代码验证，不背API

每学一个组件，写一个小程序验证：

```cpp
#include <vector>
#include <iostream>

void explore_vector_growth() {
    std::vector<int> v;
    size_t last_cap = 0;

    for (int i = 0; i < 100; i++) {
        v.push_back(i);
        if (v.capacity() != last_cap) {
            std::cout << "size=" << v.size()
                      << " capacity=" << v.capacity() << "\n";
            last_cap = v.capacity();
        }
    }
}
```

### 10. 标准库组件的底层实现原理速查

> "知道底层实现，才能在性能敏感时做出正确选择。"

#### 10.1 vector 扩容策略

`std::vector` 在内存中维护一段连续空间。当空间不足时，重新分配更大的内存，将旧数据搬移过去，再释放旧内存。

**扩容因子**：主流实现（libstdc++、libc++、MSVC STL）均为 **2倍增长**。

```
push_back 触发扩容的过程：

size=0, capacity=0  →  分配1个元素空间
size=1, capacity=1  →  满，扩容到2
size=2, capacity=2  →  满，扩容到4
size=3, capacity=4  →  未满
size=4, capacity=4  →  满，扩容到8
size=5, capacity=8  →  未满
...

扩容时发生了什么：
1. 分配新内存（size * 2）
2. 移动/拷贝旧元素到新内存
3. 释放旧内存
4. 更新内部指针
```

**均摊分析**：每次 push_back 的均摊时间复杂度为 O(1)。证明思路——n 次 push_back 总拷贝次数为 1+2+4+...+n/2 < n，均摊每次 < 1 次拷贝。

```cpp
#include <vector>
#include <iostream>

void observe_vector_growth() {
    std::vector<int> v;
    size_t last_cap = 0;
    int realloc_count = 0;

    for (int i = 0; i < 1000000; i++) {
        v.push_back(i);
        if (v.capacity() != last_cap) {
            std::cout << "size=" << v.size()
                      << " capacity=" << v.capacity()
                      << " (第" << ++realloc_count << "次扩容)\n";
            last_cap = v.capacity();
        }
    }
}
```

**关键启示**：如果预先知道元素数量，`reserve()` 可以避免所有扩容开销。

#### 10.2 map 的红黑树实现

`std::map` 和 `std::set` 底层使用**红黑树**（Red-Black Tree），一种自平衡二叉搜索树。

**红黑树性质**：
1. 每个节点是红色或黑色
2. 根节点是黑色
3. 叶子节点（NIL）是黑色
4. 红色节点的子节点必须是黑色（不能有连续红节点）
5. 从任一节点到其所有叶子节点的路径包含相同数量的黑色节点

这些性质保证树的高度 ≤ 2·log₂(n+1)，从而确保操作为 O(log n)。

```
std::map<int, std::string> 的内部结构（简化）：

          8(B)
        /      \
      4(R)     12(R)
     /   \     /    \
   2(B)  6(B) 10(B) 14(B)

每个节点存储：key、value、color、left、right、parent
迭代器按中序遍历，因此总是有序的
```

**节点内存开销**：每个节点额外存储 3 个指针（left/right/parent）+ 1 个颜色位，约 24-25 字节（64位系统）。

#### 10.3 unordered_map 的哈希表实现

`std::unordered_map` 底层使用**开链法**（Separate Chaining）哈希表。

```
bucket 数组：每个 bucket 是一个链表

bucket[0] → [k1,v1] → [k2,v2] → nullptr
bucket[1] → nullptr
bucket[2] → [k3,v3] → nullptr
bucket[3] → [k4,v4] → [k5,v5] → [k6,v6] → nullptr  ← 冲突链过长
bucket[4] → nullptr
...

当 load_factor > max_load_factor（默认1.0）时，
触发 rehash，bucket 数量翻倍
```

**关键参数**：
- `load_factor()` = size / bucket_count，默认最大负载因子为 1.0
- `max_load_factor()` 可调整，值越小空间换时间
- `rehash(n)` 强制重建哈希表，bucket 数量 ≥ n

```cpp
#include <unordered_map>
#include <iostream>

void observe_unordered_map() {
    std::unordered_map<int, int> m;
    m.max_load_factor(0.75f);

    for (int i = 0; i < 100; i++) {
        m[i] = i * 2;
        if (i % 20 == 0) {
            std::cout << "size=" << m.size()
                      << " buckets=" << m.bucket_count()
                      << " load_factor=" << m.load_factor() << "\n";
        }
    }
}
```

**与 map 的选择**：需要有序遍历或范围查询用 `map`，只需快速查找用 `unordered_map`。

#### 10.4 string 的 SSO（Small String Optimization）

大多数标准库实现使用 SSO：短字符串直接存储在对象内部，不分配堆内存。

```
std::string 的内存布局（以 libstdc++ 为例，64位系统）：

总大小：32 字节

短字符串模式（长度 ≤ 15）：
┌──────────────────────────────────┬────┬────┐
│  char data[16]                   │size│cap │
│  "hello\0..."                    │ 5  │15  │
└──────────────────────────────────┴────┴────┘
0                                15  16  17-31

长字符串模式（长度 > 15）：
┌──────────┬──────────┬──────────┬──────────┐
│  ptr     │  size    │  cap     │          │
│  ───────→│  100     │  127     │          │
└──────────┴──────────┴──────────┴──────────┘
0          8          16         24        31
           ↓
     堆上分配的字符数组

SSO 阈值：
- libstdc++ (GCC)：15 字节
- libc++ (Clang)：22 字节（64位系统）
- MSVC STL：15 字节
```

**性能影响**：短字符串操作无堆分配，对大量小字符串场景性能提升显著。

```cpp
#include <string>
#include <iostream>

void demonstrate_sso() {
    std::string s1 = "hi";
    std::string s2 = "this is a long string that exceeds SSO";

    std::cout << "短字符串 sizeof=" << sizeof(s1) << "\n";
    std::cout << "长字符串 sizeof=" << sizeof(s2) << "\n";

    const char* addr_before = s1.data();
    s1 += "!";  // 短字符串追加，仍在SSO内，地址不变
    const char* addr_after = s1.data();
    std::cout << "SSO追加后地址" << (addr_before == addr_after ? "不变" : "改变") << "\n";
}
```

#### 10.5 shared_ptr 控制块的内存布局

`std::shared_ptr` 通过控制块（Control Block）管理引用计数和对象生命周期。

```
make_shared 创建（推荐，单次分配）：

┌─────────────────────────────────────────┐
│              控制块 + 对象（合并分配）      │
├──────────┬──────────┬──────────┬────────┤
│ strong   │ weak     │ vtable   │ T obj  │
│ count=1  │ count=0  │ ptr      │        │
├──────────┼──────────┼──────────┼────────┤
│ 8 bytes  │ 8 bytes  │ 8 bytes  │sizeof(T)│
└──────────┴──────────┴──────────┴────────┘

new + shared_ptr 构造（两次分配，不推荐）：

堆上对象：           堆上控制块：
┌──────────┐        ┌──────────┬──────────┬──────────┐
│ T obj    │  ←───  │ strong   │ weak     │ vtable   │
│          │        │ count=1  │ count=0  │ ptr      │
└──────────┘        └──────────┴──────────┴──────────┘

shared_ptr 对象本身（栈上）：
┌──────────┬──────────┐
│ T* ptr   │ ctrl*    │
│          │          │
└──────────┴──────────┘
  8 bytes    8 bytes   = 16 bytes (64位)
```

**为什么 `make_shared` 更优**：
1. 只有一次堆分配（控制块和对象合并）
2. 缓存局部性更好（对象和控制块相邻）
3. 异常安全（避免 new 和 shared_ptr 构造之间的异常泄漏）

**注意**：`make_shared` 的副作用——当 strong_count 归零但 weak_count 不为零时，对象内存不会释放（因为和控制块合并分配），直到 weak_count 也归零。

### 12. 标准库的异常安全保证

> "异常安全不是'不抛异常'，而是'异常发生后状态仍然正确'。"

#### 12.1 三级异常安全保证

| 等级 | 名称 | 含义 | 例子 |
|------|------|------|------|
| 基本保证 | Basic Guarantee | 异常发生后，对象处于有效状态，无资源泄漏 | `vector::push_back` |
| 强保证 | Strong Guarantee | 异常发生后，操作回滚，状态与操作前完全一致 | `vector::reserve` |
| 不抛出保证 | Nothrow Guarantee | 操作保证不抛出异常 | `vector::size` |

```cpp
#include <vector>
#include <stdexcept>
#include <iostream>

class Widget {
public:
    Widget(int v) : val(v) { std::cout << "构造 " << val << "\n"; }
    ~Widget() { std::cout << "析构 " << val << "\n"; }
private:
    int val;
};

void basic_guarantee_example() {
    std::vector<Widget> v;
    v.emplace_back(1);
    v.emplace_back(2);

    try {
        v.emplace_back(3);  // 如果这里扩容时抛出bad_alloc
                            // v仍然有效，1和2仍在其中（基本保证）
                            // 但v可能已经搬移过了
    } catch (const std::bad_alloc&) {
        // v仍然可用，只是可能少了新元素
    }
}

void strong_guarantee_example() {
    std::vector<int> v = {1, 2, 3};
    size_t old_size = v.size();

    try {
        v.push_back(4);  // push_back提供基本保证，不提供强保证
                          // 因为扩容搬移可能失败，旧内存已释放
    } catch (...) {
        // 基本保证：v有效，但不确定是3个还是4个元素
    }
}
```

#### 12.2 各容器操作的异常安全等级

**vector**

| 操作 | 保证等级 | 说明 |
|------|---------|------|
| `push_back` | 基本 | 扩容搬移失败时，旧数据可能已搬移部分 |
| `insert` | 基本 | 同 push_back |
| `reserve` | 强 | 失败时 vector 不变 |
| `resize` | 基本 | 新元素构造失败时，已构造的不会回滚 |
| `pop_back` | 不抛出 | 不涉及构造/析构异常 |
| `swap` | 不抛出 | 只交换指针 |
| `clear` | 不抛出 | 析构不允许抛异常 |
| `operator[]` | 不抛出 | 纯内存访问 |

**map/set**

| 操作 | 保证等级 | 说明 |
|------|---------|------|
| `insert` | 强 | 插入失败时树不变 |
| `erase` | 不抛出 | 析构不允许抛异常 |
| `find` | 不抛出 | 只读操作 |
| `operator[]` | 基本 | 可能插入默认值，构造失败时树不变（强），但语义上改变了容器 |
| `swap` | 不抛出 | 只交换内部指针 |

**unordered_map/set**

| 操作 | 保证等级 | 说明 |
|------|---------|------|
| `insert` | 强 | 插入失败时表不变 |
| `erase` | 基本 | rehash 期间失败可能导致部分元素丢失 |
| `rehash` | 基本 | 失败时表可能处于中间状态 |

#### 12.3 编写异常安全代码的原则

```cpp
#include <memory>
#include <vector>

class SafeContainer {
public:
    void add_item(std::unique_ptr<int> item) {
        data_.push_back(nullptr);          // 先扩展vector（可能抛异常）
        data_.back() = std::move(item);    // 再转移所有权（不抛异常）
    }

    void safe_swap(SafeContainer& other) noexcept {
        using std::swap;
        swap(data_, other.data_);          // swap不抛异常
    }

private:
    std::vector<std::unique_ptr<int>> data_;
};
```

**原则**：
1. 先做可能失败的操作，再修改状态
2. 使用 RAII 管理资源，确保析构函数不抛异常
3. 使用 `swap` 实现强保证（copy-and-swap 惯用法）
4. 标记不抛异常的函数为 `noexcept`

### 13. 标准库的线程安全规则详解

> "C++标准库的线程安全规则非常精确，误解会导致难以调试的数据竞争。"

#### 13.1 三条核心规则

| 规则 | 含义 | 例子 |
|------|------|------|
| 不同对象安全 | 不同线程操作不同对象，总是安全的 | 线程A操作 `map1`，线程B操作 `map2` |
| 同一对象只读安全 | 不同线程同时读同一对象，是安全的 | 线程A调用 `m.find()`，线程B调用 `m.find()` |
| 同一对象有写不安全 | 一个线程写，其他线程读写都不安全 | 线程A调用 `m.insert()`，线程B调用 `m.find()` |

```
安全矩阵：

              线程B:读    线程B:写
线程A:读       ✅安全      ❌不安全
线程A:写       ❌不安全    ❌不安全
```

#### 13.2 常见误解纠正

**误解1："const成员函数都是线程安全的"**

```cpp
std::vector<int> v = {1, 2, 3};

// 线程A
int x = v.size();  // const，但内部可能访问共享状态

// 线程B
v.push_back(4);    // 修改vector

// ❌ 不安全！即使线程A调用的是const函数
```

**误解2："不同容器之间总是安全的"**

```cpp
std::vector<int> v1 = {1, 2, 3};
std::vector<int> v2 = {4, 5, 6};

// 线程A
v1.push_back(10);

// 线程B
v2.push_back(20);

// ✅ 安全，操作不同对象
```

**误解3："原子操作意味着容器线程安全"**

```cpp
std::atomic<int> counter{0};
std::vector<int> v;

// 线程A
counter++;
v.push_back(counter);

// 线程B
counter++;
v.push_back(counter);

// ❌ 不安全！counter是原子的，但vector不是
// 两个线程同时push_back是数据竞争
```

**误解4："读自己的写总是安全的"**

```cpp
std::map<int, int> m;

// 线程A
m[1] = 10;
int x = m[1];  // 读自己刚写的

// 线程B
m[2] = 20;

// ❌ 不安全！虽然A读的是自己写的key=1，
// 但map的内部结构（红黑树）被B修改了
```

#### 13.3 正确的多线程使用模式

```cpp
#include <vector>
#include <mutex>
#include <shared_mutex>
#include <algorithm>

class ThreadSafeVector {
public:
    void push_back(int val) {
        std::unique_lock lock(mutex_);  // 写锁
        data_.push_back(val);
    }

    int at(size_t idx) const {
        std::shared_lock lock(mutex_);  // 读锁（允许多个读者）
        return data_.at(idx);
    }

    size_t size() const {
        std::shared_lock lock(mutex_);  // 读锁
        return data_.size();
    }

private:
    mutable std::shared_mutex mutex_;
    std::vector<int> data_;
};
```

#### 13.4 特殊情况：std::atomic 与 std::mutex

| 组件 | 线程安全 | 说明 |
|------|---------|------|
| `std::atomic<T>` | ✅ | 原子操作本身线程安全 |
| `std::mutex` | ✅ | lock/unlock 本身线程安全 |
| `std::shared_mutex` | ✅ | 读写锁本身线程安全 |
| `std::condition_variable` | ✅ | wait/notify 本身线程安全 |
| `std::future/promise` | ✅ | get/set 本身线程安全 |
| 其他所有标准库组件 | ❌ | 需要外部同步 |

### 16. 常见反模式

> "知道什么不该做，比知道什么该做更重要。"

#### 16.1 vector 频繁 push_back 不 reserve

```cpp
// ❌ 反模式：不知道大小时也不 reserve
std::vector<int> v;
for (int i = 0; i < 1000000; i++) {
    v.push_back(i);  // 多次扩容，大量拷贝
}

// ✅ 正确：预知大小时 reserve
std::vector<int> v;
v.reserve(1000000);
for (int i = 0; i < 1000000; i++) {
    v.push_back(i);  // 零扩容
}

// ✅ 正确：不确定大小时，先收集再 reserve
std::vector<int> v;
size_t count = count_items();  // 先计数
v.reserve(count);
for (int i = 0; i < count; i++) {
    v.push_back(i);
}
```

**性能差异**：100万元素插入，不 reserve 约 3ms，reserve 后约 1.5ms，差距随元素变大而增大。

#### 16.2 map 的 operator[] 副作用

```cpp
std::map<std::string, int> scores;

// ❌ 危险：[] 会在key不存在时插入默认值
int val = scores["alice"];  // 如果"alice"不存在，会插入{"alice", 0}

// ✅ 正确：只读时用 at 或 find
try {
    int val = scores.at("alice");  // 不存在时抛出 out_of_range
} catch (const std::out_of_range&) {
    // 处理不存在的情况
}

// ✅ 正确：检查存在性
auto it = scores.find("alice");
if (it != scores.end()) {
    int val = it->second;
}

// ❌ 特别危险：在循环中使用 []
for (const auto& name : names) {
    if (scores[name] > 90) {  // 每次访问都可能插入！
        // ...
    }
}

// ✅ 正确
for (const auto& name : names) {
    auto it = scores.find(name);
    if (it != scores.end() && it->second > 90) {
        // ...
    }
}
```

#### 16.3 shared_ptr 循环引用

```cpp
#include <memory>
#include <iostream>

class Node {
public:
    std::shared_ptr<Node> next;
    std::shared_ptr<Node> prev;  // ❌ 循环引用！
    ~Node() { std::cout << "析构\n"; }
};

void memory_leak() {
    auto a = std::make_shared<Node>();
    auto b = std::make_shared<Node>();
    a->next = b;
    b->prev = a;  // 循环引用：a↔b，引用计数永远不为0
    // 离开作用域后，a和b都不会被析构！内存泄漏！
}

// ✅ 正确：用 weak_ptr 打破循环
class NodeFixed {
public:
    std::shared_ptr<NodeFixed> next;
    std::weak_ptr<NodeFixed> prev;  // weak_ptr 不增加引用计数
    ~NodeFixed() { std::cout << "析构\n"; }
};

void no_leak() {
    auto a = std::make_shared<NodeFixed>();
    auto b = std::make_shared<NodeFixed>();
    a->next = b;
    b->prev = a;  // weak_ptr 不阻止析构
    // 离开作用域后，a和b正常析构
}
```

**判断规则**：如果两个对象互相持有 `shared_ptr`，必然循环引用。解决方案：将其中一个方向改为 `weak_ptr`。

#### 16.4 auto_ptr 遗留问题

```cpp
// ❌ C++98 时代的 auto_ptr（C++17已移除）
std::auto_ptr<int> p1(new int(42));
std::auto_ptr<int> p2 = p1;  // p1 变为空！所有权已转移
// 此时 *p1 是未定义行为

// ✅ C++11+ 使用 unique_ptr
std::unique_ptr<int> p1 = std::make_unique<int>(42);
// std::unique_ptr<int> p2 = p1;  // 编译错误！禁止拷贝
std::unique_ptr<int> p2 = std::move(p1);  // 显式转移，p1 变为 nullptr

// ✅ 需要共享所有权时用 shared_ptr
auto p1 = std::make_shared<int>(42);
auto p2 = p1;  // 引用计数+1，两者都有效
```

**迁移建议**：全局搜索 `auto_ptr`，替换为 `unique_ptr`（独占）或 `shared_ptr`（共享）。

#### 16.5 std::regex 性能陷阱

```cpp
#include <regex>
#include <iostream>
#include <chrono>

void regex_performance_trap() {
    std::string text(10000, 'a');
    text += "b";  // 在末尾放一个b

    // ❌ 陷阱：std::regex 使用回溯引擎，某些模式指数级慢
    std::regex dangerous(R"(a*a*a*a*a*a*a*a*a*a*b)");
    // 这个模式在文本不匹配时需要指数级回溯

    auto start = std::chrono::steady_clock::now();
    bool match = std::regex_search(text, dangerous);  // 可能要几秒甚至几分钟
    auto end = std::chrono::steady_clock::now();

    auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(end - start);
    std::cout << "耗时: " << ms.count() << "ms\n";

    // ✅ 替代方案1：使用第三方正则库（如 re2、Boost.Regex）
    // ✅ 替代方案2：简化正则模式，避免嵌套量词
    std::regex simple(R"(a+b)");  // 线性时间
}

// ❌ 另一个陷阱：在循环中反复构造 regex
void loop_regex_bad() {
    for (int i = 0; i < 1000; i++) {
        std::regex r(R"(\d+)");  // 每次都编译正则！极慢
        // ...
    }
}

// ✅ 正确：编译一次，重复使用
void loop_regex_good() {
    std::regex r(R"(\d+)");  // 只编译一次
    for (int i = 0; i < 1000; i++) {
        // 使用 r ...
    }
}
```

**std::regex 性能总结**：
- 编译正则表达式很慢（毫秒级），避免在循环中编译
- 某些模式匹配很慢（指数级回溯），避免嵌套量词如 `(a*)*`
- 如果性能关键，考虑使用 RE2（Google，保证线性时间）或 PCRE2

***

### 17. 扩展总结

**标准库深度学习路线**：

| 层级 | 内容 | 目标 |
|------|------|------|
| 第一层 | 接口与用法 | 能正确使用 |
| 第二层 | 时间复杂度与选择 | 能选对容器 |
| 第三层 | 底层实现原理 | 能优化性能 |
| 第四层 | 异常安全与线程安全 | 能写健壮代码 |
| 第五层 | 源码阅读与版本差异 | 能深入定制 |

**核心心法**：标准库不是黑盒——当你遇到性能问题或奇怪行为时，底层实现原理就是你的调试钥匙。
