# 多线程调试与内存问题排查指南
> 📖 相关章节：[调试技巧](../../04-工程实践/06-调试技巧.md)、[多线程基础](../../02-CPP/27-多线程基础.md)

## 1. 通俗理解

把调试想象成去医院看病：

- **调试 = 看病**：找出问题所在，对症下药
- **多线程调试 = 给多个同时运动的病人看病**：难在它们互相影响，一个病人的动作会改变另一个病人的状态
- **内存泄漏 = 慢性病**：一点点消耗体力，慢慢耗死，症状不明显但后果严重
- **内存溢出 = 急性病**：突然崩溃，像心脏病发作一样猝不及防

不同的医院（IDE）有不同的检查设备（调试工具）：VS Code 用 GDB 听诊器，Visual Studio 有核磁共振（并行堆栈图），CLion 集成了各种化验仪器（Valgrind/ASan）。

## 2. 多线程调试的挑战

### 1. 为什么多线程调试比单线程难10倍？

| 挑战 | 说明 |
|------|------|
| 不确定性 | 每次运行线程调度顺序不同，bug可能时有时无 |
| 竞态条件 | 微秒级的时间差导致不同结果 |
| 死锁 | 线程互相等待，程序挂起，看不出哪里卡住 |
| 数据竞争 | 多个线程同时写同一变量，结果不可预测 |
| 调试器干扰 | 加断点会改变线程调度，bug可能消失（Heisenbug） |

### 2. 多线程bug的4大类型

1. **数据竞争** — 多线程同时访问共享数据，至少一个写
2. **死锁** — 多个线程互相持有对方需要的锁
3. **活锁** — 线程不断重试但无法前进
4. **优先级反转** — 低优先级线程持有高优先级线程需要的锁

## 3. 不同IDE的多线程调试方法

### 1. VS Code + GDB（Linux/MSYS2）

#### 1. 基本多线程调试命令

```
# 查看所有线程
info threads

# 切换到指定线程
thread 2

# 查看所有线程的调用栈
thread apply all bt

# 查看所有线程的变量
thread apply all print variable_name

# 只调试当前线程（其他线程继续运行）
set scheduler-locking on

# 关闭线程锁定（所有线程同时运行）
set scheduler-locking off

# 在指定线程设断点
break file.cpp:42 thread 3

# 查看线程的锁状态
info locks  # 需要gdb 7.0+
```

#### 2. VS Code launch.json配置（多线程调试）

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "name": "C++ 多线程调试",
            "type": "cppdbg",
            "request": "launch",
            "program": "${fileDirname}/${fileBasenameNoExtension}",
            "args": [],
            "cwd": "${workspaceFolder}",
            "MIMode": "gdb",
            "miDebuggerPath": "gdb",
            "setupCommands": [
                {
                    "description": "启用多线程调试",
                    "text": "set pagination off",
                    "ignoreFailures": true
                },
                {
                    "description": "遇到线程创建时不停",
                    "text": "set libthread-db-search-path /usr/lib",
                    "ignoreFailures": true
                }
            ]
        }
    ]
}
```

#### 3. VS Code调试技巧

1. **并行调用栈视图**：调试时左侧CALL STACK显示所有线程的调用栈
2. **线程切换**：点击CALL STACK中的不同线程切换上下文
3. **条件断点**：右键断点→"Edit Breakpoint"→设置条件（如 `thread_id == 3`）
4. **日志断点**：不暂停执行，只输出日志（右键断点→"Logpoint"）

### 2. Visual Studio 2022（Windows，MSVC）

#### 1. 多线程调试窗口

1. **并行堆栈图** — 可视化显示所有线程的调用栈关系，一眼看出死锁
2. **线程标记** — 在源码中标记当前哪些线程在执行
3. **冻结线程** — 右键线程→"冻结"，暂停指定线程，隔离问题

5. **内存窗口** — 调试→窗口→内存，直接查看内存内容

## 4. 多线程调试的通用技巧

### 1. 技巧1：用日志代替断点（避免Heisenbug）

```cpp
#include <stdio.h>
#include <pthread.h>

void* worker(void* arg) {
    long id = (long)arg;
    printf("[线程%ld] 开始执行\n", id);
    // ... 关键操作 ...
    printf("[线程%ld] 操作完成, value=%d\n", id, value);
    return NULL;
}
```

**日志技巧**：
- 每行日志包含线程ID
- 用时间戳标记顺序
- 用互斥锁保护日志输出（否则多线程日志会交错）
- C++中用spdlog的异步日志（线程安全）

### 2. 技巧2：用TSan检测数据竞争（最快定位）

```bash
# 编译时加 -fsanitize=thread
g++ -g -fsanitize=thread -O1 main.cpp -o main -lpthread

# 运行程序
./main
```

TSan输出示例：

```
==================
WARNING: ThreadSanitizer: data race (pid=1234)
  Write of size 4 at 0x7b0400000000 by thread T2:
    #0 worker1 main.cpp:15

  Previous write of size 4 at 0x7b0400000000 by thread T1:
    #0 worker2 main.cpp:23

  Location is global 'shared_value' of size 4 at 0x7b0400000000
==================
```

TSan直接告诉你：
- 哪两个线程发生了竞争
- 哪两个代码位置
- 哪个变量

### 3. 技巧3：用条件断点定位特定线程的问题

```
# GDB: 只在线程3触发断点
break main.cpp:42 if pthread_self() == thread3_id

# VS2022: 断点条件中设置
线程ID == 3
```

### 4. 技巧4：用scheduler-locking隔离线程

```gdb
# 只让当前线程运行，其他线程暂停
set scheduler-locking on

# 单步调试当前线程
next
next

# 恢复所有线程
set scheduler-locking off
```

### 5. 技巧5：死锁快速定位

```gdb
# 程序卡住时，按Ctrl+C中断
# 查看所有线程的调用栈
thread apply all bt

# 找到卡在pthread_mutex_lock/pthread_rwlock_rdlock的线程
# 这些就是死锁的线程

# 查看它们各自持有的锁
thread apply all info locks
```

### 6. 技巧6：用helgrind检测锁问题

```bash
# Valgrind的helgrind工具，检测锁顺序问题和数据竞争
valgrind --tool=helgrind ./myprogram
```

### 7. 技巧7：压力测试暴露并发bug

```cpp
// 反复运行多线程代码，增加发现竞态条件的概率
for (int i = 0; i < 10000; i++) {
    // 运行多线程代码
    run_concurrent_test();
    // 验证结果
    assert(result_is_correct());
}
```

## 5. 内存泄漏排查

### 1. 什么是内存泄漏

分配了内存但从未释放，程序占用的内存持续增长，最终耗尽系统内存。

### 2. 排查方法对比

| 工具 | 平台 | 检测能力 | 性能开销 | 易用性 |
|------|------|---------|---------|--------|
| Valgrind Memcheck | Linux/macOS | 最全面 | 10-20倍慢 | ★★★★☆ |
| AddressSanitizer(ASan) | 全平台 | 泄漏+越界+UAF | 2倍慢 | ★★★★★ |
| Visual Studio CRT | Windows | 泄漏检测 | 几乎无 | ★★★☆☆ |
| Leaks工具 | macOS | 泄漏检测 | 低 | ★★★☆☆ |
| Dr. Memory | Windows/Linux | 泄漏+越界 | 2-5倍慢 | ★★★☆☆ |

### 3. 方法1：ASan（推荐，最快最好）

#### 1. 编译

```bash
# GCC/Clang
g++ -g -fsanitize=address -fno-omit-frame-pointer main.cpp -o main

# CMake
target_compile_options(myapp PRIVATE -fsanitize=address -fno-omit-frame-pointer)
target_link_options(myapp PRIVATE -fsanitize=address)
```

#### 2. 运行

```bash
./main
```

#### 3. ASan输出解读

```
=================================================================
==1234==ERROR: LeakSanitizer: detected memory leaks

Direct leak of 104 byte(s) in 1 object(s) allocated from:
    #0 0x7f8e4c in operator new(unsigned long)
    #1 0x400b3c in create_data() main.cpp:15
    #2 0x400c01 in main main.cpp:30

SUMMARY: AddressSanitizer: 104 byte(s) leaked in 1 allocation(s).
```

ASan直接告诉你：
- 泄漏了多少字节
- 在哪个文件的哪一行分配的
- 完整的调用栈

#### 4. ASan高级选项

```bash
# 检测更严格（初始化检查）
ASAN_OPTIONS="detect_leaks=1:detect_stack_use_after_return=1" ./main

# 只检测泄漏（不检测越界，更快）
g++ -g -fsanitize=leak main.cpp -o main

# 输出泄漏报告到文件
ASAN_OPTIONS="log_path=asan.log" ./main
```

### 4. 方法2：Valgrind（Linux，最全面）

```bash
# 基本用法
valgrind --leak-check=full --show-leak-kinds=all ./myprogram

# 输出解读
# Definitely lost: 确定泄漏（必须修复）
# Indirectly lost: 间接泄漏（修复直接泄漏后自动消失）
# Possibly lost: 可能泄漏（需要检查）
# Still reachable: 程序结束时仍可达（通常可忽略）

# 更详细的输出
valgrind --leak-check=full --track-origins=yes --verbose ./myprogram

# 抑制已知的误报
valgrind --suppressions=myapp.supp ./myprogram
```

### 5. 方法3：Visual Studio（Windows）

```cpp
// 在程序开头添加
#define _CRTDBG_MAP_ALLOC
#include <stdlib.h>
#include <crtdbg.h>

int main() {
    // 设置在程序退出时报告内存泄漏
    _CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF);

    // 你的代码...

    return 0;
}
```

输出示例：

```
Detected memory leaks!
Dumping objects ->
{142} normal block at 0x007A7B40, 104 bytes long.
 Data: <                > CD CD CD CD CD CD CD CD CD CD CD CD CD CD CD CD
Object dump complete.
```

设置断点定位泄漏：

```cpp
// 在泄漏的分配编号处设断点
_CrtSetBreakAlloc(142);
// 再次运行，程序会在第142次分配时中断
```

### 6. 方法4：智能指针（从源头避免泄漏）

```cpp
// 不推荐：手动管理
void bad() {
    int* p = new int[100];
    // 如果这里抛异常或提前return，就泄漏了
    delete[] p;
}

// 推荐：用智能指针
void good() {
    auto p = std::make_unique<int[]>(100);
    // 无论如何都会自动释放
}
```

## 6. 内存溢出/越界排查

### 1. 什么是内存溢出

- **缓冲区溢出**：写入超过分配的大小
- **栈溢出**：递归太深或局部变量太大
- **堆溢出**：malloc(10)但写了20字节

### 2. ASan检测越界（最快最好）

```bash
g++ -g -fsanitize=address main.cpp -o main
./main
```

ASan输出：

```
==1234==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000014
WRITE of size 4 at 0x602000000014 thread T0
    #0 0x400b3c in main main.cpp:12
    #1 0x7f8e4c in __libc_start_main

0x602000000014 is located 0 bytes to the right of 10-byte region
allocated by thread T0 here:
    #0 0x7f8e4c in malloc
    #1 0x400a01 in main main.cpp:10
```

ASan告诉你：
- 越界写入4字节
- 在main.cpp第12行
- 越过了10字节分配区域的末尾
- 该区域在main.cpp第10行分配

### 3. 栈溢出检测

```bash
# 编译时加栈保护
g++ -g -fstack-protector-all main.cpp -o main

# 检查栈大小限制
ulimit -s          # Linux（默认8192KB）
```

栈溢出的典型信号：`Segmentation fault` 或 `SIGABRT`

### 4. UBSan检测未定义行为

```bash
# 编译
g++ -g -fsanitize=undefined main.cpp -o main

# 检测：整数溢出、空指针解引用、数组越界（静态数组）等
./main
```

### 5. MSan检测未初始化内存读取

```bash
# 仅Clang支持
clang++ -g -fsanitize=memory main.cpp -o main
./main
```

## 8. 快速定位问题的决策树

```
程序出了问题？
├── 崩溃（Segmentation Fault）
│   ├── 用ASan重新编译运行 → 直接定位越界/Use-After-Free
│   └── 用GDB运行 → bt查看调用栈 → frame N查看变量
├── 挂起（卡住不动）
│   ├── Ctrl+C中断 → thread apply all bt → 找死锁
│   └── 用helgrind检测锁顺序问题
├── 结果不正确（偶尔出错）
│   ├── 用TSan重新编译运行 → 检测数据竞争
│   └── 加日志追踪线程执行顺序
├── 内存持续增长
│   ├── 用ASan的LeakSanitizer检测泄漏
│   └── 用Valgrind --leak-check=full
└── 性能慢
    ├── 用perf top找热点函数
    └── 用Valgrind --tool=callgrind分析调用
```

## 9. Sanitizer组合使用指南

### 1. 哪些Sanitizer可以同时使用？

| 组合 | 是否可以 | 说明 |
|------|---------|------|
| ASan + UBSan | ✅ 可以 | 最常用组合 |
| ASan + TSan | ❌ 不行 | 互斥 |
| TSan + UBSan | ✅ 可以 | 并发问题排查 |
| ASan + MSan | ❌ 不行 | 互斥 |
| MSan + UBSan | ✅ 可以 | 内存初始化问题 |

### 2. 推荐的编译配置

```cmake
# Debug模式：开启所有检查
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    target_compile_options(myapp PRIVATE
        -g -O1
        -fsanitize=address,undefined
        -fno-omit-frame-pointer
        -Wall -Wextra
    )
    target_link_options(myapp PRIVATE -fsanitize=address,undefined)
endif()

# Thread Debug模式：开启线程检查
if(ENABLE_THREAD_SANITIZER)
    target_compile_options(myapp PRIVATE -g -O1 -fsanitize=thread)
    target_link_options(myapp PRIVATE -fsanitize=thread)
endif()
```

## 10. 实战案例

### 1. 案例1：用ASan 3分钟定位内存泄漏

1. 编译：`g++ -g -fsanitize=address main.cpp -o main`
2. 运行：`./main`
3. 看输出：直接告诉你哪一行泄漏
4. 修复：把new改成make_unique
5. 验证：再次运行，无泄漏报告

### 2. 案例2：用TSan定位数据竞争

1. 编译：`g++ -g -fsanitize=thread main.cpp -o main -lpthread`
2. 运行：`./main`
3. TSan报告：告诉你哪两个线程、哪两行代码竞争
4. 修复：加mutex保护共享变量
5. 验证：再次运行，无竞争报告

### 3. 案例3：用GDB定位死锁

1. 程序卡住，Ctrl+C中断
2. `thread apply all bt`
3. 找到两个卡在`__lll_lock_wait`的线程
4. 查看它们各自持有的锁和等待的锁
5. 发现线程A持有锁1等待锁2，线程B持有锁2等待锁1
6. 修复：统一锁的获取顺序
