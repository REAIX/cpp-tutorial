# 为什么代码可以调试——调试信息深度解析
> 📖 相关章节：[调试技巧](../../04-工程实践/07-调试技巧.md)、[性能优化](../../04-工程实践/09-性能优化.md)

## 1. 通俗理解

把可执行文件想象成一本**翻译后的外文书**：

- **没有调试信息的程序** = 只有外文正文，没有注释、没有页码对照、没有术语表
  - 你能读，但不知道第3章第2段对应原文哪里
  - 遇到不懂的词，查不到原始含义
- **有调试信息的程序** = 附带原文页码对照表 + 术语表 + 章节索引
  - 你可以随时翻到"原文第42页第15行"
  - 遇到变量名，可以查到它的类型、作用域、在内存中的位置

调试器就是一个**双语翻译官**，它需要这本"对照表"才能把机器世界的东西翻译给你看。没有对照表，它只能说"0x4005a6处发生了段错误"，你完全不知道这是什么意思。

## 2. 可调试 vs 不可调试：到底多了什么？

### 1. 一个实验：同一段代码两种编译

```c
// hello.c
#include <stdio.h>

int add(int a, int b) {
    int result = a + b;
    return result;
}

int main() {
    int sum = add(3, 4);
    printf("sum = %d\n", sum);
    return 0;
}
```

```bash
# 不可调试版本
gcc -O2 hello.c -o hello_release

# 可调试版本
gcc -g -O0 hello.c -o hello_debug

# 对比文件大小
ls -l hello_release hello_debug
# -rwxr-xr-x 1 user user 15936 hello_release
# -rwxr-xr-x 1 user user 22656 hello_debug   ← 多了约7KB
```

**可调试版本多了约42%的数据**，这些数据就是调试信息。

### 2. 用 readelf 看多了什么

```bash
# 查看release版本的段（Section）
readelf -S hello_release | grep -E "\.debug|\.symtab"

# 查看debug版本的段
readelf -S hello_debug | grep -E "\.debug|\.symtab"
```

**Release版本**（几乎没有调试段）：

```
  [Nr] Name              Type      Address          Size
  [11] .symtab           SYMTAB    0000000000000000 000108
  [12] .strtab           STRTAB    0000000000000000 0001a0
```

**Debug版本**（多了大量 `.debug_*` 段）：

```
  [Nr] Name              Type      Address          Size
  [11] .symtab           SYMTAB    0000000000000000 000108
  [12] .strtab           STRTAB    0000000000000000 0001a0
  [27] .debug_aranges    PROGBITS  0000000000000000 000030
  [28] .debug_info       PROGBITS  0000000000000000 0000c5
  [29] .debug_abbrev     PROGBITS  0000000000000000 000075
  [30] .debug_line       PROGBITS  0000000000000000 00006a
  [31] .debug_str        PROGBITS  0000000000000000 0000a5
  [32] .debug_line_str   PROGBITS  0000000000000000 00003b
```

**这就是答案：可调试的代码多了 `.debug_*` 系列段，它们存储了源代码与机器码的映射关系。**

## 3. 调试信息的5大核心组成部分

### 1. 总览：调试器需要回答的5个问题

| 调试器的问题 | 对应的调试信息 | 存储位置 |
|-------------|--------------|---------|
| 这条机器指令对应源码哪一行？ | 行号映射 | `.debug_line` |
| 这个地址是什么函数/变量？ | 符号表 | `.symtab` / `.debug_info` |
| 这个变量是什么类型？占多大？ | 类型信息 | `.debug_info` |
| 变量在栈上还是寄存器里？ | 位置描述 | `.debug_info` (DWARF Location Expression) |
| 调用栈怎么回溯？ | 帧信息 | `.debug_frame` / `.eh_frame` |

### 2. 组成部分1：行号映射（.debug_line）

**这是最关键的调试信息**——它建立了"机器指令地址 ↔ 源码行号"的映射表。

```
机器指令地址        源文件          行号
0x0000000000001149  hello.c        4    ← int result = a + b;
0x000000000000114d  hello.c        5    ← return result;
0x0000000000001155  hello.c        8    ← int sum = add(3, 4);
0x000000000000116a  hello.c        9    ← printf("sum = %d\n", sum);
0x0000000000001184  hello.c        10   ← return 0;
```

**没有行号映射时**，调试器只能说：
```
Program received signal SIGSEGV, Segmentation fault.
0x0000000000001149 in ?? ()     ← 问号！不知道是哪个文件哪一行
```

**有行号映射时**，调试器能说：
```
Program received signal SIGSEGV, Segmentation fault.
0x0000000000001149 in add () at hello.c:4    ← 精确定位！
4           int result = a + b;
```

用 `objdump` 查看行号映射：

```bash
objdump -WL hello_debug
# 输出每条指令对应的源码行号
```

### 3. 组成部分2：符号表（.symtab）

符号表记录了函数和全局变量的**名字**与**地址**的对应关系。

```bash
nm hello_debug
# 输出：
# 0000000000001149 T add          ← add函数在地址0x1149
# 0000000000001155 T main         ← main函数在地址0x1155
```

```bash
nm hello_release
# 如果被strip了：
# nm: hello_release: no symbols   ← 没有符号表！
```

**符号表的3个层次**：

| 层次 | 内容 | 保留场景 |
|------|------|---------|
| 全局符号表 `.symtab` | 所有函数和变量的名字与地址 | Debug版本保留，Release版本可能strip |
| 动态符号表 `.dynsym` | 只含动态链接需要的符号 | 即使strip也保留（否则无法链接动态库） |
| 调试符号 `.debug_info` | 局部变量、类型信息、行号等 | 只有 `-g` 编译才有 |

**关键区别**：符号表只能告诉你"地址0x1149叫add"，但不知道add函数的参数类型、局部变量等信息。这些更详细的信息在 `.debug_info` 中。

### 4. 组成部分3：类型与变量信息（.debug_info）

这是DWARF格式最复杂的部分，记录了完整的类型系统和变量信息。

```
.debug_info 中存储的信息：

编译单元: hello.c
├── 函数: add
│   ├── 返回类型: int
│   ├── 参数: a (int, 位置: %edi寄存器)
│   ├── 参数: b (int, 位置: %esi寄存器)
│   ├── 局部变量: result (int, 位置: %eax寄存器 或 [rbp-4])
│   ├── 地址范围: 0x1149 - 0x1154
│   └── 行号范围: 3 - 5
├── 函数: main
│   ├── 返回类型: int
│   ├── 局部变量: sum (int, 位置: [rbp-4])
│   ├── 地址范围: 0x1155 - 0x118a
│   └── 行号范围: 7 - 10
└── 全局类型: (无)
```

**有了这些信息，调试器才能**：
- `print result` → 知道result是int类型，知道它在栈上 `[rbp-4]` 的位置，读取4字节并显示
- `ptype add` → 知道add函数的完整签名 `int(int, int)`
- `info locals` → 知道当前作用域有哪些局部变量

**没有这些信息时**：你只能看到寄存器和原始内存，调试器无法帮你解析变量名和类型。

### 5. 组成部分4：栈帧信息（.debug_frame / .eh_frame）

调试器需要**回溯调用栈**（`backtrace`），这需要知道每个函数的栈帧布局。

```
调用栈回溯需要的信息：

main() 的栈帧:
  ├── 保存的RBP = 0x7fffffffe400    ← 上一层的栈帧指针
  ├── 返回地址 = 0x7f...(__libc_start_main)
  └── 局部变量: sum at [rbp-4]

add() 的栈帧:
  ├── 保存的RBP = 0x7fffffffe3f0
  ├── 返回地址 = 0x000000000000116a (main+21)
  └── 局部变量: result at [rbp-4]
```

`.eh_frame` 和 `.debug_frame` 的区别：

| 特性 | `.eh_frame` | `.debug_frame` |
|------|------------|----------------|
| 生成条件 | 默认就有（C++异常处理需要） | 需要 `-g` |
| 用途 | 异常展开 + 调试 | 纯调试 |
| 格式 | 类似DWARF | 标准DWARF |
| 能否strip | 可以strip但C++异常会坏 | 可以strip |

**重要**：即使不加 `-g`，GCC也会默认生成 `.eh_frame`（因为C++异常处理需要它）。所以即使release版本，GDB的 `bt` 命令通常也能看到调用栈——但看不到变量和行号。

### 6. 组成部分5：宏定义信息（.debug_macro，仅 -g3）

```bash
# -g3 会额外保存宏定义
gcc -g3 hello.c -o hello_debug_full

# 调试时可以查看宏
(gdb) macro expand MAX(3, 4)
# => ((3) > (4) ? (3) : (4))

(gdb) info macro MAX
# Defined at /path/hello.c:2
# #define MAX(a, b) ((a) > (b) ? (a) : (b))
```

普通 `-g` 不包含宏信息，只有 `-g3` 才有。

## 4. DWARF：调试信息的标准格式

### 1. 什么是DWARF

**DWARF** = Debugging With Attributed Record Formats，是Linux/Unix下调试信息的标准格式（与ELF配套）。

| 平台 | 调试信息格式 | 文件形式 |
|------|------------|---------|
| Linux (GCC/Clang) | DWARF | 嵌入ELF文件的 `.debug_*` 段 |
| Windows (MSVC) | PDB (Program Database) | 独立的 `.pdb` 文件 |
| macOS (Clang) | DWARF + dSYM | 独立的 `.dSYM` 包 |

### 2. DWARF的内部结构

```
DWARF 数据结构：

.debug_abbrev    ← 缩写表（模板定义，减少重复）
    │
.debug_info      ← 核心调试信息（引用缩写表）
    │             每个编译单元(Compilation Unit)是一棵树：
    │             DIE (Debug Information Entry)
    │             ├── DW_TAG_compile_unit     (编译单元)
    │             │   ├── DW_TAG_subprogram   (函数)
    │             │   │   ├── DW_TAG_formal_parameter (参数)
    │             │   │   └── DW_TAG_variable  (局部变量)
    │             │   └── DW_TAG_variable      (全局变量)
    │             └── DW_TAG_base_type         (基本类型)
    │
.debug_line      ← 行号表（地址 ↔ 行号映射）
.debug_str       ← 字符串池（减少重复存储）
.debug_aranges   ← 地址范围表（快速查找函数所属编译单元）
.debug_ranges    ← 地址范围列表（非连续代码段）
.debug_frame     ← 栈帧信息（调用栈回溯）
.debug_macro     ← 宏定义（仅 -g3）
.debug_loclists  ← 变量位置列表（DWARF5，变量位置变化时）
.debug_rnglists  ← 范围列表（DWARF5）
```

### 3. DWARF版本演进

| 版本 | 年份 | 重要改进 |
|------|------|---------|
| DWARF 2 | 2000 | 基础格式，GCC默认 |
| DWARF 3 | 2005 | 改进C++支持 |
| DWARF 4 | 2010 | 改进优化代码调试，GCC 4.8+默认 |
| DWARF 5 | 2017 | 更紧凑的编码，改进分割LTO支持，Clang 13+/GCC 11+ |

```bash
# 查看DWARF版本
readelf -wi hello_debug | head -5
# Contents of the .debug_info section:
#   Compilation Unit @ offset 0x0:
#    Version: 5                    ← DWARF版本

# 指定DWARF版本
gcc -g -gdwarf-4 hello.c -o hello   # 强制DWARF4
gcc -g -gdwarf-5 hello.c -o hello   # 强制DWARF5
```

### 4. 用工具查看DWARF内容

```bash
# 查看完整的调试信息（非常长）
readelf -wi hello_debug

# 查看行号表
readelf -wl hello_debug

# 查看符号表
readelf -s hello_debug

# 更友好的DWARF查看工具
dwarfdump hello_debug              # 需要安装
llvm-dwarfdump hello_debug         # LLVM版本
```

## 5. Windows的PDB格式

### 1. PDB与DWARF的关键区别

| 特性 | DWARF (Linux) | PDB (Windows) |
|------|--------------|---------------|
| 存储方式 | 嵌入可执行文件的 `.debug_*` 段 | 独立的 `.pdb` 文件 |
| 分离性 | 需要手动strip | 天然分离 |
| 大小影响 | 增大可执行文件体积 | 不影响exe大小 |
| 生成方式 | `-g` 自动嵌入 | `/Zi` 或 `/Z7` 编译选项 |
| 查看工具 | readelf/dwarfdump | dumpbin / PDBView |

### 2. MSVC的调试编译选项

```
/Z7    调试信息嵌入目标文件(.obj)，链接时嵌入exe（类似DWARF方式）
/Zi    调试信息生成独立的PDB文件（推荐，默认方式）
/ZI    支持Edit and Continue的调试信息（Debug专用）
```

### 3. PDB文件的内容

```
myapp.pdb 包含：
├── DBI Stream (模块信息)
│   ├── 每个编译单元(obj)的贡献
│   └── 源文件列表
├── TPI Stream (类型信息)
│   ├── 基本类型定义
│   ├── 结构体/类定义
│   └── 函数签名
├── IPI Stream (索引类型信息)
├── Symbol Stream (符号信息)
│   ├── 函数地址范围
│   ├── 局部变量位置
│   └── 行号映射
├── Global Symbol Stream
└── Public Symbol Stream (导出符号)
```

### 4. 为什么Windows用独立PDB文件

1. **链接速度**：增量链接时只需更新PDB，不需要重新写入exe
2. **并行编译**：每个.obj的调试信息通过mspdbcore.dll合并到PDB
3. **部署分离**：发布exe时不带PDB，体积小；PDB单独存储用于调试
4. **Edit and Continue**：/ZI支持在调试时修改代码并继续运行

## 7. 调试信息的生命周期

### 1. 从源码到调试信息的完整流程

```
源码 (.c/.cpp)
    │
    ▼ 编译器前端（语法分析、语义分析）
    │
抽象语法树 (AST)
    │
    ├──→ 生成机器码 → .text段
    │
    └──→ 生成调试信息 → .debug_*段
         │
         ▼ 编译器后端
         │
    DWARF/PDB生成器
    │
    ├── 记录每个变量的类型和位置
    ├── 记录每条指令对应的源码行
    ├── 记录每个函数的栈帧布局
    └── 记录作用域嵌套关系
```

### 2. 调试器如何使用这些信息

```
你在GDB中输入: print result

GDB内部执行步骤：
1. 查符号表: result → DW_TAG_variable, 类型int
2. 查位置信息: result → DW_AT_location = [rbp-4]
3. 读取寄存器: rbp = 0x7fffffffe3f0
4. 计算地址: 0x7fffffffe3f0 - 4 = 0x7fffffffe3ec
5. 读内存: 从0x7fffffffe3ec读取4字节
6. 按类型解释: int → 显示为十进制数字
7. 输出: $1 = 7
```

**如果没有调试信息**，步骤1就失败了——GDB不知道"result"是什么。

## 8. 优化如何破坏调试体验

### 1. -O0 vs -O2 的代码差异

```c
int add(int a, int b) {
    int result = a + b;
    return result;
}
```

**-O0 编译结果**（完全对应源码）：

```asm
add:
    push    rbp
    mov     rbp, rsp
    mov     DWORD PTR [rbp-4], edi      ; a 存入栈
    mov     DWORD PTR [rbp-8], esi      ; b 存入栈
    mov     edx, DWORD PTR [rbp-4]      ; 读取 a
    mov     eax, DWORD PTR [rbp-8]      ; 读取 b
    add     eax, edx                    ; a + b
    mov     DWORD PTR [rbp-12], eax     ; result = a + b
    mov     eax, DWORD PTR [rbp-12]     ; return result
    pop     rbp
    ret
```

每个变量都在栈上有明确位置，单步调试逐行对应。

**-O2 编译结果**（高度优化）：

```asm
add:
    lea     eax, [rdi+rsi]    ; 直接计算 a+b，没有result变量
    ret
```

**优化导致的问题**：

| 问题 | 说明 |
|------|------|
| 变量消失 | `result` 被优化掉，调试器找不到它 |
| 行号跳跃 | 单步执行时跳来跳去（指令重排） |
| 函数内联 | `add` 被内联到main中，无法单独调试 |
| 尾调用优化 | 调用栈少一层，bt看不到被优化的函数 |
| 循环展开 | 一行循环变成多条指令，单步混乱 |

### 2. 调试优化代码的技巧

```bash
# 方案1：用 -Og（专门为调试优化的级别）
gcc -g -Og hello.c -o hello
# -Og 优化不破坏调试体验，性能接近-O1

# 方案2：选择性禁用优化
# 只对某个函数禁用优化
#pragma GCC optimize("O0")
int add(int a, int b) {
    int result = a + b;
    return result;
}
#pragma GCC optimize("")

# 方案3：禁止内联
__attribute__((noinline)) int add(int a, int b) {
    int result = a + b;
    return result;
}

# 方案4：保留帧指针（让bt更准确）
gcc -g -O2 -fno-omit-frame-pointer hello.c -o hello
```

## 9. strip：去掉调试信息

### 1. strip的作用

```bash
# 查看strip前的大小
ls -l hello_debug
# -rwxr-xr-x 1 user user 22656 hello_debug

# 去掉所有调试信息
strip hello_debug
ls -l hello_debug
# -rwxr-xr-x 1 user user 14328 hello_debug  ← 减少了37%

# 只去掉调试信息，保留符号表
strip --strip-debug hello_debug

# 只去掉符号表，保留调试信息
strip --strip-unneeded hello_debug
```

### 2. strip的层次

| 命令 | 去掉什么 | 保留什么 | 影响 |
|------|---------|---------|------|
| `strip` | 全部 | 只留 `.dynsym` | 无法调试，无法 `nm` |
| `strip --strip-debug` | `.debug_*`段 | `.symtab` | 能看函数名，不能看变量/行号 |
| `strip --strip-unneeded` | `.symtab` | `.debug_*`段 | 能看行号，不能看函数名 |
| 不strip | 全部保留 | 全部保留 | 完整调试能力 |

### 3. 最佳实践：分离调试信息

```bash
# 方法1：objcopy分离（Linux）
objcopy --only-keep-debug hello hello.debug     # 提取调试信息到独立文件
strip -s hello                                   # 原文件去掉所有调试信息
objcopy --add-gnu-debuglink=hello.debug hello    # 原文件添加调试文件链接

# GDB调试时会自动寻找 hello.debug
gdb ./hello

# 方法2：build-id方式（现代Linux）
# 调试信息安装到 /usr/lib/debug/.build-id/xx/xxx.debug
# GDB通过build-id自动查找

# 方法3：debuginfo包（RPM系）
# yum install hello-debuginfo
# dnf debuginfo-install hello
```

## 10. 跨平台调试信息对比总表

| 特性 | Linux (GCC/Clang) | Windows (MSVC) | macOS (Clang) |
|------|-------------------|----------------|---------------|
| 调试格式 | DWARF | PDB | DWARF + dSYM |
| 存储方式 | 嵌入ELF | 独立.pdb文件 | 独立.dSYM包 |
| 编译选项 | `-g` | `/Zi` | `-g` |
| 调试级别 | `-g0`/`-g1`/`-g2`/`-g3` | `/Z7`/`/Zi`/`/ZI` | 同Linux |
| 查看工具 | readelf/dwarfdump | dumpbin/PDBView | dwarfdump |
| 分离方式 | objcopy --only-keep-debug | 天然分离 | dsymutil |
| strip命令 | strip | 无（PDB已分离） | strip |
| 行号信息 | `.debug_line` | PDB Line Info | `.debug_line` |
| 类型信息 | `.debug_info` | PDB TPI Stream | `.debug_info` |
| 栈帧信息 | `.debug_frame`/`.eh_frame` | PDB FPO Data | `.debug_frame` |
| 符号表 | `.symtab` | PDB Symbol Stream | `.symtab` |

## 11. 实战：对比调试体验

### 1. 无调试信息时的调试体验

```bash
gcc -O2 hello.c -o hello_nosym
strip hello_nosym
gdb ./hello_nosym
```

```
(gdb) break main
Breakpoint 1 at 0x1155                    ← 只有地址，没有文件名和行号

(gdb) run
Breakpoint 1, 0x0000000000001155 in ?? ()  ← 问号！不知道是哪个函数

(gdb) print sum
No symbol "sum" in current context.        ← 找不到变量

(gdb) backtrace
#0  0x0000000000001155 in ?? ()
#1  0x00007f... in ?? ()                   ← 全是问号
```

### 2. 只有符号表时的调试体验

```bash
gcc -g -O0 hello.c -o hello_symonly
strip --strip-debug hello_symonly           # 去掉调试信息，保留符号表
gdb ./hello_symonly
```

```
(gdb) break main
Breakpoint 1 at 0x1155: file hello.c, line 7.  ← 有函数名！

(gdb) run
Breakpoint 1, main () at hello.c:7              ← 知道是main函数

(gdb) print sum
No symbol "sum" in current context.              ← 局部变量还是看不到

(gdb) backtrace
#0  main () at hello.c:7                         ← 调用栈正常
#1  0x7f... in __libc_start_main
```

### 3. 完整调试信息时的调试体验

```bash
gcc -g -O0 hello.c -o hello_full
gdb ./hello_full
```

```
(gdb) break main
Breakpoint 1 at 0x1155: file hello.c, line 7.

(gdb) run
Breakpoint 1, main () at hello.c:7
7           int sum = add(3, 4);

(gdb) step
add (a=3, b=4) at hello.c:4                     ← 参数值可见！
4           int result = a + b;

(gdb) print result
$1 = 0                                           ← 局部变量可见！

(gdb) next
5           return result;

(gdb) print result
$2 = 7                                           ← 值已更新！

(gdb) finish
Run till exit from #0  add (a=3, b=4) at hello.c:5
main () at hello.c:8
8           printf("sum = %d\n", sum);

(gdb) print sum
$3 = 7                                           ← 完美！
```

### 4. 三种调试能力对比

| 能力 | 无调试信息 | 只有符号表 | 完整调试信息 |
|------|-----------|-----------|-------------|
| 函数名 | ❌ `?? ()` | ✅ `main()` | ✅ `main()` |
| 行号 | ❌ | ⚠️ 函数入口行 | ✅ 精确到每行 |
| 局部变量 | ❌ | ❌ | ✅ |
| 参数值 | ❌ | ❌ | ✅ |
| 类型信息 | ❌ | ❌ | ✅ |
| 单步执行 | ⚠️ 汇编级 | ⚠️ 函数级 | ✅ 源码级 |
| 调用栈 | ⚠️ 只有地址 | ✅ 函数名 | ✅ 函数名+参数 |
| 条件断点 | ⚠️ 只能用地址 | ✅ 函数名 | ✅ 变量表达式 |

## 12. 常见问题

### 1. Q1：Release版本能调试吗？

能，但体验很差。如果保留了符号表（没strip），至少能看到函数名和调用栈。如果还有 `.eh_frame`（默认有），`bt` 基本可用。但看不到局部变量和行号。

**最佳实践**：编译Release版本时也加 `-g`，发布时用 `objcopy --only-keep-debug` 分离调试信息单独保存。线上crash时用保存的调试信息分析core dump。

### 2. Q2：-g 和 -g3 有什么区别？

| 选项 | 内容 | 额外体积 |
|------|------|---------|
| `-g` | 行号+变量+类型+栈帧 | 基础 |
| `-g3` | 以上 + 宏定义 | 略多 |
| `-ggdb` | GDB专用格式（更紧凑） | 最小 |

日常开发用 `-g` 即可。需要调试宏时用 `-g3`。

### 3. Q3：为什么有的变量显示 `<optimized out>`？

编译器优化把变量优化掉了（寄存器分配、常量传播、死代码消除等），DWARF中记录了变量的"位置表达式"但该位置在当前指令处无效。

解决方法：
1. 用 `-Og` 代替 `-O2`
2. 对特定函数用 `__attribute__((optimize("O0")))`
3. 用 `volatile` 阻止优化（但会改变语义）

### 4. Q4：如何确认二进制文件是否包含调试信息？

```bash
# Linux
file hello
# 有调试信息: ... not stripped
# 无调试信息: ... stripped

readelf -S hello | grep debug
# 有输出 = 包含调试信息

# Windows
dumpbin /headers hello.exe | findstr Debug
# 有输出 = 包含调试信息目录

# macOS
dsymutil -s hello | head
dwarfdump hello
```

### 5. Q5：LTO（链接时优化）对调试信息的影响？

LTO在链接阶段做跨模块优化，会导致：
- 函数可能被内联到其他编译单元
- 行号映射可能不准确
- 部分变量被优化掉

```bash
# LTO + 调试的正确姿势
gcc -g -O2 -flto hello.c -o hello
# 确保链接时也带 -g，否则LTO后的调试信息不完整
```
