# 什么是MISRA-C编码规范
> 📖 相关章节：[错误处理与信号](../../01-C语言/13-错误处理与信号.md)、[进程与线程](../../01-C语言/24-进程与线程.md)、[网络编程](../../02-CPP/35-网络编程.md)

> "MISRA-C=汽车行业的'交通规则'——不是限制你开车，而是确保你不撞车。"——为安全关键系统制定的C语言编码规范，禁止一切可能导致不可预测行为的写法。

***

### 1. 通俗理解

- **MISRA-C** = Motor Industry Software Reliability Association（汽车行业软件可靠性协会）发布的C语言编码规范
- 就像交通规则不是限制你开车，而是确保所有人安全到达目的地
- 它禁止了一大批C语言中"合法但危险"的写法，比如动态内存分配、递归、goto等
- 目标不是写出"优雅"的代码，而是写出"可预测、可证明安全"的代码

| 概念 | 类比 | 说明 |
|------|------|------|
| MISRA-C | 交通规则 | 约束编码行为，确保安全 |
| 强制规则 | 红灯必须停 | 必须遵守，违反就是不符合 |
| 建议规则 | 建议限速 | 应该遵守，可偏离但需记录理由 |
| 合规检查 | 交警执法 | 用静态分析工具检查代码 |
| 偏离声明 | 特殊通行证 | 违反规则时必须记录原因和风险评估 |

***

### 2. 技术说明

#### 1. MISRA-C的背景

| 维度 | 说明 |
|------|------|
| 发布机构 | MISRA（汽车行业软件可靠性协会） |
| 首版 | 1998年（MISRA-C:1998） |
| 当前版本 | MISRA-C:2012 + AMD1 + AMD2 + MISRA-C:2023 |
| 适用行业 | 汽车、航空、医疗、铁路、核电等安全关键系统 |
| 标准来源 | ISO 26262（汽车功能安全）、IEC 62304（医疗设备软件）等 |
| 性质 | 非法律强制，但行业标准可能要求遵循 |

#### 2. 核心规则分类

| 分类 | 说明 | 违反后果 |
|------|------|---------|
| 强制（Mandatory） | 必须遵守，不允许偏离 | 不符合MISRA-C |
| 必需（Required） | 应当遵守，允许有记录的偏离 | 需要偏离声明 |
| 建议（Advisory） | 推荐遵守 | 建议遵循，不强制 |

#### 3. 典型规则示例

**禁止类规则**：

| 规则编号 | 规则内容 | 分类 | 原因 |
|---------|---------|------|------|
| Rule 21.3 | 禁止使用malloc/calloc/realloc | 必需 | 动态内存可能失败，导致不可预测行为 |
| Rule 21.4 | 禁止使用free | 必需 | 释放后使用、双重释放等风险 |
| Rule 17.2 | 禁止递归 | 必需 | 栈溢出风险，难以证明递归终止 |
| Rule 15.7 | 禁止省略else分支 | 必需 | 遗漏处理逻辑 |
| Rule 16.4 | switch必须有default | 必需 | 处理所有可能的case |
| Rule 22.1 | 禁止使用setjmp/longjmp | 必需 | 跳过析构、局部变量失效 |
| Rule 11.4 | 禁止不同类型指针间的转换 | 建议 | 类型安全问题 |
| Rule 21.1 | 禁止使用标准库的信号处理函数 | 必需 | 信号处理中的异步行为不可预测 |

**必须类规则**：

| 规则编号 | 规则内容 | 分类 | 原因 |
|---------|---------|------|------|
| Rule 8.4 | 函数必须有原型声明 | 必需 | 防止隐式声明导致的类型不匹配 |
| Rule 10.4 | 相同算术类型的操作数 | 必需 | 防止隐式转换导致精度丢失 |
| Rule 14.4 | 循环条件必须为布尔表达式 | 必需 | 防止`if (x = 5)`类错误 |
| Rule 17.7 | 函数返回值必须使用 | 必需 | 防止忽略错误返回 |
| Rule 22.2 | 不能向已关闭的流写入 | 强制 | 未定义行为 |
| Rule 1.3 | 不得有未定义行为 | 强制 | 核心原则 |

#### 4. MISRA-C:2012与MISRA-C:2023的变化

| 维度 | MISRA-C:2012 | MISRA-C:2023 |
|------|-------------|-------------|
| 规则总数 | 143条（含AMD1/AMD2后157条） | 157条 + 新增安全相关规则 |
| C11支持 | 部分支持 | 完整支持C11（_Atomic、_Alignas等） |
| _Atomic | 未涉及 | 新增原子类型相关规则 |
| 安全性 | 关注功能安全 | 增加信息安全（网络安全）维度 |
| 工具支持 | 成熟 | 持续更新 |
| 兼容性 | — | 向后兼容MISRA-C:2012 |

**MISRA-C:2023新增关注点**：

| 新增方向 | 说明 |
|---------|------|
| C11特性 | _Atomic、_Alignas、_Static_assert等新特性的规则 |
| 信息安全 | 防止缓冲区溢出攻击、输入验证等 |
| 代码度量 | 圈复杂度、调用深度等量化指标 |

#### 5. MISRA-C++简介

| 维度 | MISRA-C++ |
|------|-----------|
| 首版 | 2008年（MISRA-C++:2008） |
| 基于标准 | C++03 |
| 规则数量 | 约228条 |
| 新版本 | MISRA-C++:2023（基于C++17） |
| 核心规则 | 禁止异常、禁止RTTI、禁止多重继承、限制模板 |

**MISRA-C++典型规则**：

| 规则 | 内容 | 原因 |
|------|------|------|
| 禁止异常 | 不使用try/catch/throw | 异常行为难以静态分析 |
| 禁止RTTI | 不使用dynamic_cast/typeid | 运行时类型检查有性能和确定性风险 |
| 禁止多重继承 | 不使用多重继承 | 复杂性高，容易出错 |
| 限制模板 | 限制模板使用 | 模板错误信息难以理解，调试困难 |
| 限制STL | 不使用部分STL组件 | 异常安全性、动态内存等问题 |

```

```

#### 7. 是否需要遵循MISRA-C

| 场景 | 是否需要遵循 | 原因 |
|------|------------|------|
| 汽车电子（ISO 26262） | ✅ 必须 | 行业标准要求 |
| 医疗设备（IEC 62304） | ✅ 强烈建议 | 法规要求代码质量保证 |
| 航空电子（DO-178C） | ✅ 强烈建议 | 安全关键系统 |
| 铁路信号（EN 50128） | ✅ 强烈建议 | 安全关键系统 |
| 消费电子应用 | ❌ 不必严格 | 非安全关键，过度约束影响效率 |
| Web服务后端 | ❌ 不必 | 非安全关键，有其他质量保证手段 |
| 个人项目 | ❌ 不必 | 学习精神即可，不必严格遵循 |

**即使不严格遵循，也值得参考的原则**：

1. 避免未定义行为
2. 函数必须有原型声明
3. 不忽略函数返回值
4. switch必须有default
5. 不省略else分支
6. 限制圈复杂度

#### 8. MISRA-C合规流程

```
1. 确定适用规则 → 2. 配置检查工具 → 3. 扫描代码 → 4. 分析违规
     ↓                                                  ↓
6. 持续监控 ← 5. 修复或记录偏离 ← ← ← ← ← ← ← ← ← ←
```

**偏离声明模板**：

| 字段 | 内容 |
|------|------|
| 规则编号 | 违反的MISRA规则 |
| 偏离原因 | 为什么需要违反 |
| 风险评估 | 违反可能带来的风险 |
| 缓解措施 | 如何降低风险 |
| 审批人 | 谁批准了这个偏离 |

### 3. 代码示例：MISRA-C合规 vs 不合规

```c
#include <stdio.h>

/* ===== 不合规写法 ===== */

void non_compliant(int x) {
    int* p = (int*)malloc(sizeof(int));  /* 违反 Rule 21.3: 禁止malloc */

    if (x = 5) {                         /* 违反 Rule 14.4: 赋值作条件 */
        printf("x is 5\n");
    }

    switch (x) {                         /* 违反 Rule 16.4: 无default */
        case 1: printf("one\n"); break;
        case 2: printf("two\n"); break;
    }

    if (x > 0) {                         /* 违反 Rule 15.7: 无else */
        printf("positive\n");
    }

    printf("value: %d\n", *p);           /* 未检查malloc返回值 */
    free(p);                             /* 违反 Rule 21.4: 禁止free */
}


/* ===== 合规写法 ===== */

#define OK    0
#define ERROR (-1)

static int compliant(int x, int* result) {
    if (result == NULL) {                 /* Rule 1.3: 检查指针参数 */
        return ERROR;
    }

    if (x == 5) {                        /* Rule 14.4: 使用==而非= */
        (void)printf("x is 5\n");
    }

    switch (x) {                         /* Rule 16.4: 有default */
        case 1:
            (void)printf("one\n");
            break;
        case 2:
            (void)printf("two\n");
            break;
        default:                         /* Rule 16.4: 必须有default */
            (void)printf("other\n");
            break;
    }

    if (x > 0) {                         /* Rule 15.7: 有else */
        (void)printf("positive\n");
    } else {
        (void)printf("non-positive\n");
    }

    *result = x;
    return OK;                           /* Rule 17.7: 返回值有意义 */
}
```

**合规要点**：

| 不合规 | 合规 | 规则 |
|--------|------|------|
| `malloc`/`free` | 静态分配或栈分配 | Rule 21.3/21.4 |
| `if (x = 5)` | `if (x == 5)` | Rule 14.4 |
| switch无default | switch有default | Rule 16.4 |
| if无else | if-else完整 | Rule 15.7 |
| 忽略返回值 | 检查返回值 | Rule 17.7 |
| 隐式声明 | 显式原型声明 | Rule 8.4 |
| 递归 | 迭代 | Rule 17.2 |

### 4. 常见问题

#### 1. 问题1：MISRA-C是否禁止所有动态内存分配

是的，Rule 21.3禁止使用malloc/calloc/realloc，Rule 21.4禁止使用free。原因是动态内存分配可能失败，且可能导致内存泄漏、碎片化、双重释放等问题。在安全关键系统中，通常在启动时预分配所有需要的内存。

#### 2. 问题2：MISRA-C和CERT C有什么区别

MISRA-C面向安全关键系统（汽车、医疗），侧重编码规范和可预测性；CERT C面向信息安全（防攻击），侧重安全漏洞（缓冲区溢出、注入攻击）。两者有重叠但侧重点不同，安全关键系统通常需要同时遵循两者。

#### 3. 问题3：遵循MISRA-C会让代码更安全吗

遵循MISRA-C可以减少常见的编码错误和未定义行为，提高代码的可预测性和可审查性。但它不能保证代码逻辑正确——业务逻辑错误不在MISRA-C的范围内。MISRA-C是必要条件，不是充分条件。

#### 4. 问题4：非安全关键系统需要关注MISRA-C吗

不必严格遵循，但值得参考其精神。比如"避免未定义行为"、"检查返回值"、"switch有default"等规则对所有项目都有价值。可以根据项目需要选择性遵循部分规则。

***

### 5. 极简总结

**MISRA-C是汽车行业软件可靠性协会发布的C语言编码规范，用于安全关键系统。规则分强制/必需/建议三类，典型规则包括禁止动态内存分配、禁止递归、switch必须有default等。MISRA-C:2023增加了C11支持和信息安全维度。合规检查工具包括Polyspace、LDRA、PC-lint Plus等。非安全关键系统不必严格遵循，但可参考其核心精神。**

| 要点 | 一句话 |
|------|--------|
| MISRA-C | 汽车行业C语言编码规范——安全关键系统的"交通规则" |
| 适用行业 | 汽车、航空、医疗、铁路——出了事要人命的地方 |
| 规则分类 | 强制/必需/建议——强制不可偏离，必需可记录偏离 |
| 典型规则 | 禁止malloc/free/递归/goto——一切不可预测的写法 |
| MISRA-C:2023 | 增加C11支持+信息安全——跟随语言和安全发展 |
| 合规工具 | Polyspace/LDRA/PC-lint/clang-tidy——静态分析检查 |
| 非安全关键 | 不必严格遵循，参考精神即可——避免未定义行为、检查返回值 |
