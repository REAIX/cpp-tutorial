### 2. 什么是编程范式

编程范式（Programming Paradigm）是编程的"世界观"和"方法论"，它决定了你如何组织代码、如何思考问题、如何建模现实世界。

类比：编程范式就像**建筑风格**。哥特式教堂追求高耸入云的垂直感，巴洛克建筑强调华丽装饰，现代主义主张功能至上——它们都是盖房子，但设计理念完全不同。同样，过程式、面向对象、函数式、泛型——它们都能写出可运行的程序，但思考方式和代码组织截然不同。

### 3. 四大范式对比表

| 维度 | 过程式 | 面向对象 | 函数式 | 泛型 |
|------|--------|----------|--------|------|
| 核心思想 | 按步骤执行 | 对象协作 | 函数组合 | 类型无关 |
| 程序模型 | 数据 + 算法 | 对象 + 消息 | 输入 → 输出 | 概念 + 模型 |
| 数据归属 | 全局/局部变量 | 对象封装 | 不可变值 | 参数化类型 |
| 控制流 | 顺序/分支/循环 | 方法调用 | 函数组合/递归 | 编译期展开 |
| 复用方式 | 函数调用 | 继承/组合 | 高阶函数 | 模板实例化 |
| 代表语言 | C、Pascal | Java、C# | Haskell、Lisp | C++模板、Rust |
| C++支持度 | ★★★★★ | ★★★★★ | ★★★☆☆ | ★★★★★ |

### 4. 为什么C++是天然的多范式语言

C++的设计哲学是"不为使用不到的特性付出代价"，同时"提供多种工具让程序员选择"。从C语言继承了过程式，引入了类支持面向对象，模板支持泛型，C++11起又引入lambda支持函数式。这四种范式在C++中不是互相排斥的，而是可以自由组合的。

```cpp
#include <iostream>
#include <vector>
#include <algorithm>
#include <numeric>

int add(int a, int b) {
    return a + b;
}

class Counter {
    int value_ = 0;
public:
    void increment() { ++value_; }
    int get() const { return value_; }
};

template<typename T>
T max_of(T a, T b) {
    return (a > b) ? a : b;
}

int pure_sum(const std::vector<int>& data) {
    return std::accumulate(data.begin(), data.end(), 0);
}

int main() {
    int result = add(1, 2);
    Counter c;
    c.increment();
    auto m = max_of(3.14, 2.72);
    std::vector<int> v{1, 2, 3, 4, 5};
    int s = pure_sum(v);
    std::cout << result << " " << c.get() << " "
              << m << " " << s << std::endl;
}
```

### 5. 过程式范式核心思想

过程式编程的核心公式：

```
程序 = 数据 + 算法
```

程序由一系列按顺序执行的步骤组成，数据和处理数据的函数是分离的。你告诉计算机"先做什么，再做什么，最后做什么"。

类比：**菜谱**——第一步切菜，第二步热油，第三步翻炒，第四步调味。每一步都是明确的指令，数据（食材）在步骤之间传递。

### 6. 过程式典型代码结构

```cpp
#include <cstdio>

struct Student {
    char name[64];
    double score;
};

double calculate_average(struct Student* students, int count) {
    double total = 0.0;
    for (int i = 0; i < count; ++i) {
        total += students[i].score;
    }
    return total / count;
}

void print_report(struct Student* students, int count) {
    double avg = calculate_average(students, count);
    printf("班级平均分: %.2f\n", avg);
    for (int i = 0; i < count; ++i) {
        printf("  %s: %.2f\n", students[i].name, students[i].score);
    }
}

void sort_by_score(struct Student* students, int count) {
    for (int i = 0; i < count - 1; ++i) {
        for (int j = 0; j < count - 1 - i; ++j) {
            if (students[j].score < students[j + 1].score) {
                struct Student temp = students[j];
                students[j] = students[j + 1];
                students[j + 1] = temp;
            }
        }
    }
}

int main() {
    struct Student students[] = {
        {"张三", 85.5},
        {"李四", 92.0},
        {"王五", 78.3},
    };
    int count = sizeof(students) / sizeof(students[0]);
    sort_by_score(students, count);
    print_report(students, count);
    return 0;
}
```

### 7. 过程式的优缺点

**优点：**

| 优点 | 说明 |
|------|------|
| 直观易懂 | 代码执行顺序与书写顺序一致，阅读门槛低 |
| 性能可控 | 没有虚函数、没有对象构造开销，执行路径可预测 |
| 调试简单 | 调用栈清晰，没有复杂的继承链和对象关系 |
| 底层友好 | 直接操作内存，适合硬件交互和系统编程 |

**缺点：**

| 缺点 | 说明 |
|------|------|
| 规模受限 | 代码量大时，函数之间的数据依赖关系变得难以追踪 |
| 复用困难 | 没有继承和组合机制，复用只能靠复制或函数调用 |
| 状态管理 | 全局变量容易导致隐式耦合，局部变量又难以跨函数共享 |

### 8. 过程式最佳实践

```cpp
#include <cstdio>

double celsius_to_fahrenheit(double celsius) {
    return celsius * 9.0 / 5.0 + 32.0;
}

double fahrenheit_to_celsius(double fahrenheit) {
    return (fahrenheit - 32.0) * 5.0 / 9.0;
}

void process_temperature(double temp, char unit) {
    if (unit == 'C' || unit == 'c') {
        double result = celsius_to_fahrenheit(temp);
        printf("%.2fC = %.2fF\n", temp, result);
    } else if (unit == 'F' || unit == 'f') {
        double result = fahrenheit_to_celsius(temp);
        printf("%.2fF = %.2fC\n", temp, result);
    }
}

void run_temperature_converter() {
    double temp = 36.5;
    process_temperature(temp, 'C');
    process_temperature(98.6, 'F');
}

int main() {
    run_temperature_converter();
    return 0;
}
```

三条核心原则：

1. **函数不超过30行，单一职责**：每个函数只做一件事
2. **避免全局变量，用参数传递数据**：减少隐式耦合
3. **自顶向下设计**：先写主流程，再填充细节

### 9. 什么时候用过程式

| 场景 | 原因 |
|------|------|
| 脚本和工具 | 逻辑简单，步骤明确，不需要复杂抽象 |
| 算法实现 | 算法本身就是步骤化的，过程式最自然 |
| 嵌入式开发 | 资源受限，需要精确控制执行和内存 |
| 性能关键路径 | 避免虚函数调用和对象构造开销 |
| 系统底层代码 | 直接操作硬件，过程式更贴近机器模型 |

### 12. 过程式编程在系统编程/嵌入式领域的实战案例

> 过程式编程不是"过时"的范式——它是操作系统内核、嵌入式固件、网络协议栈的基石。

#### 1. Linux内核的C语言风格

Linux内核是过程式编程的巅峰之作——超过3000万行C代码，没有类、没有异常、没有STL，却支撑着全球绝大多数服务器。

**核心设计原则**：

| 原则 | 内核实践 | 代码风格 |
|------|----------|----------|
| 数据驱动 | 结构体+函数指针代替虚函数 | `struct file_operations` |
| 错误码返回 | 所有函数返回int错误码 | `return -ENOMEM;` |
| goto集中清理 | 统一的错误处理出口 | `goto out_free;` |
| 分层架构 | 硬件抽象层→内核层→系统调用层 | 每层独立编译 |
| 最小权限 | 函数尽量短小，单一职责 | 函数不超过24行（建议） |

**内核中的"面向对象"——函数指针表**：

```c
/* Linux内核 — file_operations结构体（简化版） */
struct file_operations {
    int (*open)(struct inode *, struct file *);
    ssize_t (*read)(struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write)(struct file *, const char __user *, size_t, loff_t *);
    int (*release)(struct inode *, struct file *);
};

/* 不同设备注册不同的操作表——这就是过程式的"多态" */
static const struct file_operations ext4_file_ops = {
    .open    = ext4_file_open,
    .read    = ext4_file_read,
    .write   = ext4_file_write,
    .release = ext4_file_release,
};

static const struct file_operations pipe_ops = {
    .open    = pipe_open,
    .read    = pipe_read,
    .write   = pipe_write,
    .release = pipe_release,
};
```

这种模式用结构体+函数指针实现了OOP的核心——封装和多态，但不需要C++的类、继承、虚函数表。内核选择这种方式的原因：
- **零开销**：没有隐式的虚函数表指针、没有RTTI
- **显式控制**：所有函数调用都是可见的，没有隐藏的构造/析构
- **可调试**：调用链清晰，没有异常展开的复杂性

#### 2. 网络协议栈的状态机实现

TCP/IP协议栈是过程式编程的经典应用——协议本质上是状态机，用过程式代码描述状态转换最为自然。

```c
/* TCP状态机 — 过程式实现（简化版） */
typedef enum {
    TCP_CLOSED,
    TCP_LISTEN,
    TCP_SYN_SENT,
    TCP_SYN_RECEIVED,
    TCP_ESTABLISHED,
    TCP_FIN_WAIT_1,
    TCP_FIN_WAIT_2,
    TCP_CLOSING,
    TCP_TIME_WAIT,
    TCP_CLOSE_WAIT,
    TCP_LAST_ACK,
} tcp_state_t;

typedef enum {
    EV_SYN,
    EV_SYN_ACK,
    EV_ACK,
    EV_FIN,
    EV_FIN_ACK,
    EV_CLOSE,
    EV_TIMEOUT,
} tcp_event_t;

typedef struct {
    tcp_state_t state;
    int seq_num;
    int ack_num;
} tcp_connection_t;

tcp_state_t tcp_handle_event(tcp_connection_t *conn, tcp_event_t event) {
    switch (conn->state) {
    case TCP_CLOSED:
        if (event == EV_SYN) {
            conn->state = TCP_SYN_SENT;
            tcp_send_syn(conn);
        } else if (event == EV_CLOSE) {
            conn->state = TCP_LISTEN;
        }
        break;

    case TCP_LISTEN:
        if (event == EV_SYN) {
            conn->state = TCP_SYN_RECEIVED;
            tcp_send_syn_ack(conn);
        }
        break;

    case TCP_SYN_SENT:
        if (event == EV_SYN_ACK) {
            conn->state = TCP_ESTABLISHED;
            tcp_send_ack(conn);
        }
        break;

    case TCP_SYN_RECEIVED:
        if (event == EV_ACK) {
            conn->state = TCP_ESTABLISHED;
        }
        break;

    case TCP_ESTABLISHED:
        if (event == EV_FIN) {
            conn->state = TCP_CLOSE_WAIT;
            tcp_send_ack(conn);
        } else if (event == EV_CLOSE) {
            conn->state = TCP_FIN_WAIT_1;
            tcp_send_fin(conn);
        }
        break;

    case TCP_FIN_WAIT_1:
        if (event == EV_FIN_ACK) {
            conn->state = TCP_TIME_WAIT;
            tcp_send_ack(conn);
        } else if (event == EV_FIN) {
            conn->state = TCP_CLOSING;
            tcp_send_ack(conn);
        }
        break;

    case TCP_TIME_WAIT:
        if (event == EV_TIMEOUT) {
            conn->state = TCP_CLOSED;
        }
        break;

    default:
        break;
    }

    return conn->state;
}
```

**为什么过程式适合协议栈**：
- 协议规范本身就是状态转换表，代码直接映射规范
- 每个状态的处理逻辑独立，函数职责清晰
- 没有对象生命周期管理的复杂性——连接就是结构体+状态
- 性能可预测，适合高并发网络处理

### 13. 过程式编程的设计模式

> 过程式编程并非没有模式——它的模式藏在函数签名、错误码和goto标签中。

#### 1. 错误码返回模式

这是C语言最核心的错误处理模式，也是Linux内核、Windows API、POSIX标准的统一约定。

```c
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>
#include <string.h>

/* 模式1：返回0成功，负数表示错误（Linux内核风格） */
int kernel_style_init(void **ctx) {
    void *buffer = malloc(4096);
    if (!buffer)
        return -ENOMEM;

    FILE *f = fopen("config.txt", "r");
    if (!f) {
        free(buffer);
        return -EIO;
    }

    if (parse_config(f, buffer) != 0) {
        fclose(f);
        free(buffer);
        return -EINVAL;
    }

    fclose(f);
    *ctx = buffer;
    return 0;
}

/* 模式2：返回指针成功，NULL表示错误（C标准库风格） */
void* stdlib_style_alloc(size_t size) {
    if (size == 0 || size > MAX_ALLOC) {
        errno = EINVAL;
        return NULL;
    }

    void *ptr = malloc(size);
    if (!ptr) {
        errno = ENOMEM;
        return NULL;
    }

    return ptr;
}

/* 模式3：输出参数返回结果，返回值仅表示成功/失败 */
bool get_user_info(int uid, user_info_t *out) {
    if (!out)
        return false;

    user_info_t *found = lookup_user(uid);
    if (!found)
        return false;

    *out = *found;
    return true;
}
```

**三种错误码风格对比**：

| 风格 | 返回值含义 | 适用场景 | 代表 |
|------|-----------|----------|------|
| 内核风格 | 0=成功，负数=错误码 | 系统编程、驱动开发 | Linux内核 |
| 标准库风格 | 指针=成功，NULL=失败 | 内存分配、查找操作 | malloc, fopen |
| 布尔风格 | true=成功，false=失败 | 简单操作、查询操作 | Windows API |

#### 2. 资源清理goto模式

这是C语言中最具争议但最实用的模式——Linux内核有超过5万处goto用于集中清理资源。

```c
#include <stdio.h>
#include <stdlib.h>

/* 反面教材：层层嵌套的if-else清理 */
int bad_example(void) {
    void *a = malloc(1024);
    if (a) {
        FILE *f = fopen("data.bin", "rb");
        if (f) {
            void *b = malloc(2048);
            if (b) {
                /* 实际工作逻辑深嵌套在这里 */
                process(a, f, b);
                free(b);
            }
            fclose(f);
        }
        free(a);
    }
    return 0;
}

/* 正面教材：goto集中清理——线性流程，清晰可读 */
int good_example(void) {
    void *a = NULL;
    FILE *f = NULL;
    void *b = NULL;
    int result = -1;

    a = malloc(1024);
    if (!a)
        goto out;

    f = fopen("data.bin", "rb");
    if (!f)
        goto out_free_a;

    b = malloc(2048);
    if (!b)
        goto out_close_f;

    if (process(a, f, b) != 0)
        goto out_free_b;

    result = 0;

out_free_b:
    free(b);
out_close_f:
    if (f) fclose(f);
out_free_a:
    free(a);
out:
    return result;
}
```

**goto清理模式的核心原则**：

| 原则 | 说明 |
|------|------|
| 只向前跳转 | goto标签必须在goto语句之后，绝不向后跳 |
| 标签命名语义化 | `out_free_a`比`cleanup1`更清晰 |
| 逆序释放 | 先分配的最后释放，标签按逆序排列 |
| 单出口函数 | 所有错误路径汇聚到统一的清理代码 |

**为什么不用其他方式**：

| 替代方案 | 问题 |
|----------|------|
| 嵌套if-else | 深层嵌套，工作逻辑被缩进淹没 |
| 重复free代码 | 每个错误路径都写一遍清理，易遗漏 |
| do-while(0) break | 可读性差，break语义不清晰 |
| 函数封装 | 每个资源获取封装成函数，增加调用开销和复杂度 |

#### 3. 分层架构

过程式编程的经典架构模式——将系统分为水平层，每层只与相邻层交互。

```c
/* 三层架构示例：简单的网络应用 */

/* === 底层：硬件/平台抽象层 === */
typedef struct {
    int fd;
    int port;
    int baudrate;
} hal_uart_t;

int hal_uart_open(hal_uart_t *uart, int port, int baudrate) {
    uart->fd = open_serial_port(port, baudrate);
    uart->port = port;
    uart->baudrate = baudrate;
    return uart->fd >= 0 ? 0 : -1;
}

int hal_uart_write(hal_uart_t *uart, const void *data, size_t len) {
    return write(uart->fd, data, len);
}

int hal_uart_read(hal_uart_t *uart, void *buf, size_t len) {
    return read(uart->fd, buf, len);
}

void hal_uart_close(hal_uart_t *uart) {
    if (uart->fd >= 0) close(uart->fd);
    uart->fd = -1;
}

/* === 中间层：协议层 === */
typedef struct {
    hal_uart_t *uart;
    uint16_t seq_num;
} protocol_t;

int protocol_send_frame(protocol_t *proto, uint8_t cmd,
                         const void *payload, size_t len) {
    frame_header_t hdr;
    hdr.cmd = cmd;
    hdr.seq = proto->seq_num++;
    hdr.len = len;

    hal_uart_write(proto->uart, &hdr, sizeof(hdr));
    hal_uart_write(proto->uart, payload, len);

    uint8_t checksum = compute_checksum(&hdr, payload);
    hal_uart_write(proto->uart, &checksum, 1);

    return 0;
}

int protocol_recv_frame(protocol_t *proto, uint8_t *cmd,
                         void *payload, size_t *len) {
    frame_header_t hdr;
    if (hal_uart_read(proto->uart, &hdr, sizeof(hdr)) != sizeof(hdr))
        return -1;

    if (hal_uart_read(proto->uart, payload, hdr.len) != (int)hdr.len)
        return -1;

    uint8_t checksum;
    hal_uart_read(proto->uart, &checksum, 1);

    if (verify_checksum(&hdr, payload, checksum) != 0)
        return -1;

    *cmd = hdr.cmd;
    *len = hdr.len;
    return 0;
}

/* === 顶层：应用层 === */
typedef struct {
    protocol_t proto;
    int device_status;
} app_t;

int app_query_status(app_t *app) {
    uint8_t cmd = CMD_QUERY_STATUS;
    if (protocol_send_frame(&app->proto, cmd, NULL, 0) != 0)
        return -1;

    uint8_t resp_cmd;
    int status;
    size_t len;
    if (protocol_recv_frame(&app->proto, &resp_cmd, &status, &len) != 0)
        return -1;

    app->device_status = status;
    return 0;
}
```

**分层架构的关键约束**：

| 约束 | 说明 | 好处 |
|------|------|------|
| 单向依赖 | 上层调用下层，下层不调用上层 | 避免循环依赖 |
| 接口隔离 | 层与层之间通过函数接口交互 | 可替换实现 |
| 数据封装 | 每层的内部数据对其他层不可见 | 减少耦合 |
| 错误传播 | 下层错误码向上层传播，上层决定处理策略 | 统一错误处理 |

***

### 14. 与OOP/函数式/泛型的范式对比深入

> 没有最好的范式，只有最适合问题域的范式。

#### 1. 每种范式最适合的问题域

| 范式 | 最适合的问题域 | 核心优势 | 典型项目 |
|------|---------------|----------|----------|
| 过程式 | 系统底层、算法实现、状态机、嵌入式 | 执行路径可预测、零抽象开销 | Linux内核、SQLite、Redis |
| 面向对象 | GUI应用、游戏引擎、业务系统、模拟 | 自然建模、封装变化、多态扩展 | Qt、Unreal Engine、Spring |
| 函数式 | 数据转换、并发处理、编译器、金融计算 | 无副作用、可组合、易测试 | Haskell编译器、Excel公式引擎 |
| 泛型 | 容器/算法库、数值计算、类型安全接口 | 类型安全+代码复用、编译期优化 | STL、Eigen、Boost |

**问题域→范式选择决策**：

```
你的问题是什么？
│
├─ "按步骤处理数据，控制硬件" → 过程式
│   例：驱动开发、协议实现、算法
│
├─ "模拟现实世界的实体交互" → 面向对象
│   例：游戏角色、UI组件、业务实体
│
├─ "数据在管道中流转变换" → 函数式
│   例：ETL管道、编译器pass、事件流
│
└─ "同一逻辑适用多种类型" → 泛型
    例：容器、排序算法、数学运算
```

#### 2. C++中如何选择范式

C++的独特之处在于**四种范式可以在同一个程序中自由混合**。关键不是选一种，而是在每个模块选最合适的。

```cpp
#include <iostream>
#include <vector>
#include <algorithm>
#include <memory>
#include <mutex>

/* 过程式：底层算法，步骤明确 */
void bubble_sort(int *arr, int n) {
    for (int i = 0; i < n - 1; i++)
        for (int j = 0; j < n - 1 - i; j++)
            if (arr[j] > arr[j + 1]) {
                int tmp = arr[j];
                arr[j] = arr[j + 1];
                arr[j + 1] = tmp;
            }
}

/* 面向对象：有状态、有生命周期的实体 */
class DataStore {
    std::vector<int> data_;
    std::mutex mtx_;
public:
    void add(int value) {
        std::lock_guard<std::mutex> lock(mtx_);
        data_.push_back(value);
    }

    int sum() const {
        std::lock_guard<std::mutex> lock(mtx_);
        int total = 0;
        for (int v : data_) total += v;
        return total;
    }
};

/* 泛型：类型无关的通用逻辑 */
template<typename Container>
auto compute_average(const Container& c) -> typename Container::value_type {
    if (c.empty()) return {};
    typename Container::value_type sum = 0;
    for (const auto& v : c) sum += v;
    return sum / static_cast<typename Container::value_type>(c.size());
}

/* 函数式：数据变换管道 */
auto make_transformer(int factor) {
    return [factor](int x) { return x * factor; };
}

int main() {
    int raw[] = {5, 3, 1, 4, 2};
    bubble_sort(raw, 5);

    DataStore store;
    for (int v : raw) store.add(v);

    std::vector<double> values = {1.5, 2.5, 3.5};
    auto avg = compute_average(values);

    auto doubler = make_transformer(2);
    std::vector<int> input = {1, 2, 3};
    std::vector<int> doubled;
    std::transform(input.begin(), input.end(),
                   std::back_inserter(doubled), doubler);

    std::cout << "sum=" << store.sum()
              << " avg=" << avg
              << " doubled[0]=" << doubled[0] << std::endl;
}
```

**C++范式选择指南**：

| 模块类型 | 推荐范式 | 原因 |
|----------|----------|------|
| 底层驱动/硬件交互 | 过程式 | 直接控制，无抽象开销 |
| 数据结构与算法 | 泛型 | 类型安全+复用 |
| 业务实体/状态管理 | 面向对象 | 封装+生命周期管理 |
| 数据处理管道 | 函数式 | 无副作用+可组合 |
| 接口/抽象层 | 面向对象+泛型 | 多态+类型安全 |
| 性能关键路径 | 过程式+泛型 | 零开销+编译期优化 |

#### 3. 范式组合的常见模式

| 组合模式 | 示例 | 说明 |
|----------|------|------|
| 过程式+泛型 | STL算法+原始数组 | 泛型提供接口，过程式实现核心 |
| 面向对象+泛型 | CRTP、类型擦除 | 编译期多态+运行时多态 |
| 面向对象+函数式 | 观察者模式+lambda | 对象管理状态，lambda定义行为 |
| 过程式+面向对象 | C API封装C++对象 | 外部C接口，内部C++实现 |

### 15. 过程式编程的常见反模式

> 知道什么不该做，比知道该做什么同样重要。

#### 1. 全局状态滥用

全局变量是过程式编程最大的陷阱——它创造了隐式耦合，让函数的行为变得不可预测。

```c
/* === 反模式：全局状态泛滥 === */
int g_count;
char *g_buffer;
FILE *g_logfile;
int g_error_code;
double g_threshold;

void process_data(void) {
    /* 依赖5个全局变量——任何一处修改都可能破坏此函数 */
    if (g_count > g_threshold) {
        fprintf(g_logfile, "count exceeded\n");
        g_error_code = -1;
        return;
    }
    sprintf(g_buffer, "count=%d", g_count);
}

/* === 正确做法：显式参数传递 === */
typedef struct {
    int count;
    double threshold;
    char *buffer;
    size_t buffer_size;
    FILE *logfile;
} process_context_t;

int process_data_v2(const process_context_t *ctx) {
    if (ctx->count > ctx->threshold) {
        fprintf(ctx->logfile, "count exceeded\n");
        return -1;
    }
    snprintf(ctx->buffer, ctx->buffer_size, "count=%d", ctx->count);
    return 0;
}
```

**全局变量的危害链**：

```
全局变量 → 隐式依赖 → 函数不可测试 → 修改引发连锁反应 → bug难以定位
```

**何时全局变量可接受**：

| 场景 | 原因 | 安全做法 |
|------|------|----------|
| `errno` | C标准库约定 | 只在函数返回后立即读取 |
| 单例硬件资源 | 硬件确实只有一个 | 用访问函数封装 |
| `const`全局配置 | 只读，无副作用 | `static const`限定作用域 |

#### 2. 函数过长

过程式编程容易写出"上帝函数"——一个函数完成所有工作，数百行甚至上千行。

```c
/* === 反模式：上帝函数 === */
void process_order(void) {
    /* 50行：读取输入 */
    /* 30行：验证数据 */
    /* 80行：计算价格 */
    /* 40行：更新库存 */
    /* 60行：生成报表 */
    /* 30行：发送通知 */
    /* 总计300行，无法测试、无法复用、无法理解 */
}

/* === 正确做法：拆分为小函数 === */
int read_order_input(order_t *order);
int validate_order(const order_t *order);
int calculate_price(const order_t *order, price_t *price);
int update_inventory(const order_t *order);
int generate_report(const order_t *order, const price_t *price);
int send_notification(const order_t *order);

int process_order_v2(void) {
    order_t order = {0};
    price_t price = {0};

    if (read_order_input(&order) != 0)      return -1;
    if (validate_order(&order) != 0)         return -2;
    if (calculate_price(&order, &price) != 0) return -3;
    if (update_inventory(&order) != 0)       return -4;
    if (generate_report(&order, &price) != 0) return -5;
    if (send_notification(&order) != 0)      return -6;

    return 0;
}
```

**函数长度的经验法则**：

| 指标 | 建议 | 原因 |
|------|------|------|
| 行数 | ≤50行（理想≤30行） | 一屏可见，理解成本低 |
| 参数 | ≤4个 | 超过4个考虑用结构体封装 |
| 嵌套层级 | ≤3层 | 超过3层用提前返回或提取函数 |
| 圈复杂度 | ≤10 | 分支过多应拆分 |

#### 3. 深层嵌套

过程式代码的另一个典型问题——条件、循环、错误检查层层嵌套，形成"箭头代码"。

```c
/* === 反模式：箭头代码（向右偏移越来越深） === */
void process_user(int user_id) {
    user_t *user = find_user(user_id);
    if (user) {
        if (user->active) {
            if (user->role == ROLE_ADMIN) {
                if (check_permission(user, PERM_WRITE)) {
                    if (save_changes(user) == 0) {
                        notify_user(user, "保存成功");
                    } else {
                        log_error("保存失败");
                    }
                } else {
                    log_error("无写入权限");
                }
            } else {
                log_error("非管理员");
            }
        } else {
            log_error("用户未激活");
        }
    } else {
        log_error("用户不存在");
    }
}

/* === 正确做法：提前返回/继续（卫语句） === */
void process_user_v2(int user_id) {
    user_t *user = find_user(user_id);
    if (!user) {
        log_error("用户不存在");
        return;
    }
    if (!user->active) {
        log_error("用户未激活");
        return;
    }
    if (user->role != ROLE_ADMIN) {
        log_error("非管理员");
        return;
    }
    if (!check_permission(user, PERM_WRITE)) {
        log_error("无写入权限");
        return;
    }
    if (save_changes(user) != 0) {
        log_error("保存失败");
        return;
    }
    notify_user(user, "保存成功");
}
```

**消除嵌套的技巧**：

| 技巧 | 适用场景 | 效果 |
|------|----------|------|
| 卫语句（提前返回） | 条件不满足时直接退出 | 消除else分支 |
| 提取函数 | 嵌套的逻辑块有独立语义 | 减少缩进层级 |
| 状态变量+循环 | 多层if-else本质是状态机 | 线性化流程 |
| 三元运算符 | 简单的条件赋值 | 一行替代四行 |

**反模式总结**：

| 反模式 | 危害 | 信号 | 修复 |
|--------|------|------|------|
| 全局状态滥用 | 隐式耦合、不可测试 | 函数不需要参数就能工作 | 用参数/结构体传递 |
| 函数过长 | 不可理解、不可复用 | 函数超过50行 | 拆分为单一职责小函数 |
| 深层嵌套 | 难以追踪逻辑、易遗漏分支 | 缩进超过3层 | 卫语句、提取函数 |
| 重复代码 | 修改需同步多处 | 复制粘贴代码 | 提取公共函数 |
| 魔法数字 | 含义不明、修改困难 | 代码中出现硬编码常量 | 定义命名常量/枚举 |
