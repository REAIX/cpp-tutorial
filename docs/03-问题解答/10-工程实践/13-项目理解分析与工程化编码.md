# 项目理解分析与工程化编码指南
> 📖 相关章节：[编码规范](../../04-工程实践/00-编码规范.md)、[设计模式](../../04-工程实践/03-设计模式.md)、[单元测试](../../04-工程实践/06-单元测试.md)、[代码审查](../../04-工程实践/08-代码审查.md)

## 1. 通俗理解

把写代码比作做菜：

- **过程化代码** = 把所有食材一股脑扔进锅里，乱炖一气。能吃，但味道混乱，换个厨师就看不懂
- **工程化代码** = 按菜谱分步骤，食材预处理、调料配比、火候控制，每步清晰。换人也能复现
- **理解项目** = 进一个厨房，先看菜单（做什么菜）、看灶台布局（怎么组织的）、看食材库（有什么可用），而不是上来就切菜

## 2. 创建项目时如何理解分析

### 1. 创建项目的5步分析法

```
第1步：明确问题 ────────────────────────────────
  到底要解决什么问题？
  谁会用？怎么用？什么时候用？
  不做会怎样？做了能带来什么价值？

第2步：界定边界 ────────────────────────────────
  做什么？不做什么？
  哪些是核心功能？哪些是锦上添花？
  MVP（最小可用产品）是什么？

第3步：拆解模块 ────────────────────────────────
  系统由哪些模块组成？
  模块之间如何交互？
  每个模块的职责是什么？

第4步：技术选型 ────────────────────────────────
  用什么语言？什么框架？什么库？
  数据怎么存？接口怎么设计？
  有什么技术风险？

第5步：制定计划 ────────────────────────────────
  先做什么？后做什么？
  里程碑是什么？
  怎么验证每一步做对了？
```

### 2. 第1步详解：明确问题

**最常见的错误**：拿到需求就开始写代码，写到一半发现理解错了。

| 错误理解 | 正确理解 |
|---------|---------|
| "用户要一个导出功能" | "用户需要把报表数据发给客户，目前是手动复制粘贴，效率低且易出错" |
| "要加一个搜索框" | "用户在1000条数据中找不到想要的，需要快速定位" |
| "要优化性能" | "页面加载超过5秒，用户流失率30%，需要降到2秒以内" |

**追问法**：对每个需求连续追问3次"为什么"

```
需求：加一个导出Excel功能
为什么？→ 用户要把数据发给客户
为什么手动复制不行？→ 数据量大，容易出错
为什么不用现有导出？→ 现有导出是CSV，客户要Excel格式
→ 真正的需求：自动生成格式化的Excel报表
→ 也许更好的方案：自动发邮件，连导出都省了
```

### 3. 第2步详解：界定边界

```
项目：学生管理系统

核心功能（MVP，必须做）：
├── 学生信息增删改查
├── 班级管理
└── 成绩录入与查询

重要功能（第二版）：
├── 成绩统计分析
├── 数据导入导出
└── 权限管理

锦上添花（第三版）：
├── 家长端查看
├── 成绩趋势图表
└── 自动生成报告

不做：
├── 在线考试（这是另一个系统）
├── 排课系统（复杂度太高）
└── 移动端APP（先做Web）
```

### 4. 第3步详解：拆解模块

**拆模块的核心原则：高内聚、低耦合**

```
学生管理系统模块拆解：

┌──────────────────────────────────────────────┐
│                  表现层（UI）                  │
│   学生页面 / 班级页面 / 成绩页面 / 报表页面    │
├──────────────────────────────────────────────┤
│                  业务层（Logic）               │
│   学生服务 / 班级服务 / 成绩服务 / 报表服务    │
├──────────────────────────────────────────────┤
│                  数据层（Data）                │
│   学生仓库 / 班级仓库 / 成绩仓库              │
├──────────────────────────────────────────────┤
│                  基础设施（Infra）             │
│   数据库 / 缓存 / 日志 / 配置                 │
└──────────────────────────────────────────────┘

每个模块只做一件事：
- 表现层：只管显示和用户交互
- 业务层：只管业务规则和流程
- 数据层：只管数据的存取
- 基础设施：只管技术支撑
```

## 3. 加入已有项目时如何快速上手

### 1. 快速上手的7步法

```
第1步：跑起来 ────────────────────────────────
  把项目克隆下来，编译通过，运行成功
  这一步解决80%的环境问题

第2步：找入口 ────────────────────────────────
  main函数在哪？程序从哪里开始？
  配置文件在哪？启动参数是什么？

第3步：理目录 ────────────────────────────────
  目录结构是什么？每个目录放什么？
  命名规律是什么？

第4步：画地图 ────────────────────────────────
  核心模块有哪些？怎么交互的？
  画一张简单的模块关系图

第5步：读核心 ────────────────────────────────
  核心数据结构是什么？
  最重要的3-5个类/函数是什么？

第6步：跟流程 ────────────────────────────────
  从入口到出口，跟踪一个完整请求的流程
  用调试器单步走一遍

第7步：改小步 ────────────────────────────────
  修一个小bug或加一个小功能
  通过动手改来加深理解
```

### 2. 每步的具体操作

#### 1. 第1步：跑起来

```bash
# 1. 克隆项目
git clone <repo_url>
cd <project>

# 2. 找构建文档
cat README.md              # 先看README
cat INSTALL.md             # 安装说明
cat BUILD.md               # 构建说明
cat CMakeLists.txt         # CMake项目看这个
cat Makefile               # Make项目看这个

# 3. 构建项目
mkdir build && cd build
cmake .. && cmake --build .

# 4. 运行
./program --help           # 先看帮助
./program                  # 试运行
```

**如果跑不起来**：问同事/查Issue/看CI配置。不要跳过这一步，跑不起来说明环境有问题。

#### 2. 第2步：找入口

```bash
# C/C++项目找main函数
grep -rn "int main" src/
grep -rn "int main" *.cpp

# CMake项目看可执行目标
grep "add_executable" CMakeLists.txt
grep "add_executable" */CMakeLists.txt

# 看配置文件
find . -name "*.json" -o -name "*.yaml" -o -name "*.conf" -o -name "*.ini" | head -20
```

#### 3. 第3步：理目录

```
典型C++项目目录结构：

project/
├── CMakeLists.txt        ← 构建入口
├── README.md             ← 项目说明
├── src/                  ← 源代码
│   ├── core/             ← 核心逻辑
│   ├── api/              ← 接口层
│   ├── db/               ← 数据层
│   └── utils/            ← 工具函数
├── include/              ← 公共头文件
├── tests/                ← 测试代码
├── docs/                 ← 文档
├── configs/              ← 配置文件
└── scripts/              ← 脚本工具
```

**快速理解目录的方法**：看每个目录下的CMakeLists.txt或Makefile，了解它编译什么。

#### 4. 第4步：画地图

```
用最简单的方式画模块关系图：

[HTTP请求] → [路由层] → [业务层] → [数据层] → [数据库]
                              │
                              ▼
                          [缓存层]
                              │
                              ▼
                           [Redis]

关键问题：
- 数据从哪里来？到哪里去？
- 中间经过哪些处理？
- 哪些模块是独立的？哪些有依赖？
```

#### 5. 第5步：读核心

```bash
# 找最大的源文件（通常是核心逻辑）
find src/ -name "*.cpp" -exec wc -l {} + | sort -rn | head -10

# 找被include最多的头文件（通常是核心接口）
grep -rh "#include" src/ | sort | uniq -c | sort -rn | head -20

# 找类/结构体定义
grep -rn "^class " src/
grep -rn "^struct " src/
```

**核心数据结构 > 核心算法 > 核心流程**。理解了数据结构，代码就懂了一半。

#### 6. 第6步：跟流程

```
用GDB跟踪一个完整流程：

1. 在main函数设断点
2. 启动调试
3. 逐步跟踪，记录调用路径：
   main() → App::init() → Server::start() → Router::handle() → Handler::process()
4. 画出调用链
5. 在关键节点查看数据变化
```

#### 7. 第7步：改小步

```
第一个修改建议：
1. 修一个简单的bug（找"good first issue"标签）
2. 加一行日志
3. 修改一个提示文字
4. 加一个简单的参数校验

目的：验证你理解了"改代码→编译→测试"的完整流程
```

### 3. 快速上手的时间预算

| 步骤 | 建议时间 | 产出 |
|------|---------|------|
| 跑起来 | 半天 | 能编译运行 |
| 找入口+理目录 | 半天 | 知道代码在哪 |
| 画地图+读核心 | 1-2天 | 模块关系图 |
| 跟流程 | 1天 | 核心调用链 |
| 改小步 | 1-2天 | 第一个PR |
| **合计** | **4-7天** | **基本能干活** |

### 4. 避免的坑

| 坑 | 正确做法 |
|---|---------|
| 从第一行代码开始读 | 从入口开始，按调用链读 |
| 试图理解每一行代码 | 先理解架构，再按需深入 |
| 不问问题闷头看 | 先自己看30分钟，看不懂就问 |
| 一上来就大改 | 先小改，理解后再大改 |
| 忽略测试代码 | 测试代码是最好的文档 |
| 不看Git历史 | git log/git blame能告诉你为什么这么写 |

## 4. 为什么总是写出一坨过程化代码？

### 1. 过程化代码的典型特征

```cpp
// 典型的"一坨"过程化代码
void process_order() {
    // 1. 读取输入
    string customer_name;
    cout << "输入客户名：";
    cin >> customer_name;

    // 2. 查数据库
    mysql_query(conn, "SELECT * FROM customers WHERE name='" + customer_name + "'");
    // ... 解析结果 ...

    // 3. 计算价格
    double total = 0;
    for (int i = 0; i < item_count; i++) {
        total += items[i].price * items[i].quantity;
        if (items[i].quantity > 10) total *= 0.9;
    }

    // 4. 检查库存
    for (int i = 0; i < item_count; i++) {
        mysql_query(conn, "SELECT stock FROM products WHERE id=" + items[i].id);
        // ... 检查 ...
    }

    // 5. 保存订单
    mysql_query(conn, "INSERT INTO orders ...");

    // 6. 发邮件
    smtp_send("订单确认", customer_email, order_details);

    // 7. 打印
    printer_print(order_details);
}
```

**问题清单**：

| 问题 | 说明 |
|------|------|
| 上帝函数 | 一个函数做了7件事，几百行 |
| 硬编码 | SQL语句、邮件配置直接写在逻辑里 |
| 无法测试 | 没有数据库就没法跑 |
| 无法复用 | 换个场景（如Web接口），整个函数废了 |
| 修改风险 | 改价格计算可能影响发邮件 |
| 难以理解 | 新人需要读完全部代码才知道做了什么 |

### 2. 为什么会写成这样？

| 原因 | 心理机制 |
|------|---------|
| **想到哪写到哪** | 大脑是线性思考的，想到什么写什么最自然 |
| **不知道怎么拆** | 没学过设计原则，不知道"高内聚低耦合"怎么落地 |
| **赶进度** | "先跑起来再说"，然后就没有"再说"了 |
| **不知道要变** | 没预见到需求会变化，写死了 |
| **过度设计恐惧** | 听过"不要过度设计"，于是走向另一个极端——不设计 |
| **缺乏练习** | 工程化编码是一种技能，需要刻意练习 |

### 3. 根本原因：缺少"设计"这一步

```
大多数人的编码过程：

  想到需求 → 开始写代码 → 写到哪算哪 → 改bug → 再加功能 → 越来越乱

正确的编码过程：

  理解需求 → 设计方案 → 写代码 → 验证 → 重构
       ↑                                        │
       └──────────── 需求变化时回到这里 ──────────┘
```

**设计不一定要写很长的文档，但一定要在脑子里想清楚再动手。**

## 5. 如何工程化编码：从过程化到工程化

### 1. 工程化编码的6个核心原则

#### 1. 原则1：单一职责（一个函数做一件事）

```cpp
// ❌ 一个函数做所有事
void process_order() {
    validate_input();
    calculate_price();
    check_stock();
    save_order();
    send_email();
    print_receipt();
}

// ✅ 每个函数只做一件事
void process_order(const Order& order) {
    validate(order);
    auto price = calculate_price(order);
    check_stock(order);
    auto saved = save_order(order, price);
    notify_customer(saved);
}
```

**判断标准**：如果你的函数名需要用"和"连接（如"计算价格和检查库存"），说明它做了不止一件事。

#### 2. 原则2：依赖抽象而非实现

```cpp
// ❌ 直接依赖具体实现
class OrderService {
    MySQLDatabase db;        // 绑死了MySQL
    SMTPMailer mailer;       // 绑死了SMTP
    HPPrinter printer;       // 绑死了惠普打印机
};

// ✅ 依赖抽象接口
class IDatabase {
public:
    virtual ~IDatabase() = default;
    virtual Result query(const std::string& sql) = 0;
};

class IMailer {
public:
    virtual ~IMailer() = default;
    virtual void send(const std::string& to, const std::string& body) = 0;
};

class OrderService {
    std::shared_ptr<IDatabase> db;     // 可以是MySQL/PostgreSQL/SQLite
    std::shared_ptr<IMailer> mailer;   // 可以是SMTP/企业微信/短信
public:
    OrderService(std::shared_ptr<IDatabase> db,
                 std::shared_ptr<IMailer> mailer)
        : db(std::move(db)), mailer(std::move(mailer)) {}
};
```

#### 3. 原则3：数据与行为封装在一起

```cpp
// ❌ 数据和行为分离
struct Student {
    string name;
    int age;
    vector<double> scores;
};

// 行为散落在各处
double calculate_average(const Student& s) { ... }
string format_student(const Student& s) { ... }
bool is_honor_student(const Student& s) { ... }

// ✅ 数据和行为封装在类中
class Student {
    string name_;
    int age_;
    vector<double> scores_;
public:
    double average_score() const { ... }
    string format() const { ... }
    bool is_honor() const { ... }

    const string& name() const { return name_; }
    void add_score(double score) { scores_.push_back(score); }
};
```

#### 4. 原则4：错误处理而非忽略

```cpp
// ❌ 忽略错误
FILE* f = fopen("data.txt", "r");
fread(buffer, 1, size, f);     // 如果f是NULL呢？如果读失败呢？
fclose(f);

// ✅ 处理错误
std::expected<std::string, std::string> read_file(const std::string& path) {
    std::ifstream file(path);
    if (!file) {
        return std::unexpected("无法打开文件: " + path);
    }
    std::string content((std::istreambuf_iterator<char>(file)),
                         std::istreambuf_iterator<char>());
    if (content.empty()) {
        return std::unexpected("文件为空: " + path);
    }
    return content;
}
```

#### 5. 原则5：命名即文档

```cpp
// ❌ 看不懂
int calc(int a, int b, int c) {
    int d = a * b;
    if (c > 10) d = d * 9 / 10;
    return d;
}

// ✅ 命名即文档
int calculate_total_price(int unit_price, int quantity, int discount_threshold) {
    int subtotal = unit_price * quantity;
    if (quantity > discount_threshold) {
        subtotal = apply_bulk_discount(subtotal);
    }
    return subtotal;
}
```

#### 6. 原则6：小步提交，持续重构

```
❌ 写了3天代码，一次性提交1000行

✅ 每完成一个小功能就提交：
   commit 1: 添加Order数据结构
   commit 2: 实现价格计算
   commit 3: 添加库存检查
   commit 4: 实现订单保存
   commit 5: 添加邮件通知
```

### 2. 重构过程化代码的实战步骤

以之前的"一坨"代码为例，逐步重构：

#### 1. 第1步：提取函数

```cpp
// 把大函数拆成小函数
void process_order(const OrderInput& input) {
    auto customer = find_customer(input.customer_name);
    auto price = calculate_price(input.items);
    check_stock(input.items);
    auto order = save_order(customer, input.items, price);
    notify_customer(order);
}
```

#### 2. 第2步：引入数据结构

```cpp
// 用结构体/类代替散落的变量
struct OrderInput {
    std::string customer_name;
    std::vector<OrderItem> items;
};

struct OrderItem {
    int product_id;
    double price;
    int quantity;
};

struct Order {
    int order_id;
    Customer customer;
    std::vector<OrderItem> items;
    double total_price;
};
```

#### 3. 第3步：封装到类中

```cpp
class OrderService {
    std::shared_ptr<IDatabase> db_;
    std::shared_ptr<IMailer> mailer_;
public:
    OrderService(std::shared_ptr<IDatabase> db,
                 std::shared_ptr<IMailer> mailer)
        : db_(std::move(db)), mailer_(std::move(mailer)) {}

    Order create_order(const OrderInput& input) {
        auto customer = db_->find_customer(input.customer_name);
        auto price = calculate_price(input.items);
        check_stock(input.items);
        auto order = db_->save_order(customer, input.items, price);
        mailer_->send(customer.email(), format_order(order));
        return order;
    }

private:
    double calculate_price(const std::vector<OrderItem>& items) { ... }
    void check_stock(const std::vector<OrderItem>& items) { ... }
    std::string format_order(const Order& order) { ... }
};
```

#### 4. 第4步：分离关注点

```cpp
// 价格计算独立出来，可单独测试
class PriceCalculator {
public:
    double calculate(const std::vector<OrderItem>& items) const {
        double total = 0;
        for (const auto& item : items) {
            total += item.price * item.quantity;
            if (item.quantity > bulk_discount_threshold_) {
                total = apply_discount(total, bulk_discount_rate_);
            }
        }
        return total;
    }

private:
    int bulk_discount_threshold_ = 10;
    double bulk_discount_rate_ = 0.9;

    double apply_discount(double price, double rate) const {
        return price * rate;
    }
};
```

#### 5. 第5步：添加测试

```cpp
TEST(PriceCalculator, SingleItem) {
    PriceCalculator calc;
    std::vector<OrderItem> items = {{1, 100.0, 1}};
    EXPECT_DOUBLE_EQ(calc.calculate(items), 100.0);
}

TEST(PriceCalculator, BulkDiscount) {
    PriceCalculator calc;
    std::vector<OrderItem> items = {{1, 100.0, 11}};
    EXPECT_DOUBLE_EQ(calc.calculate(items), 990.0);  // 100*11*0.9
}
```

### 3. 重构前后对比

| 维度 | 重构前 | 重构后 |
|------|--------|--------|
| 函数长度 | 200行 | 每个函数<20行 |
| 可测试性 | 无法测试 | 每个类可独立测试 |
| 可复用性 | 不可复用 | PriceCalculator可复用 |
| 可维护性 | 改一处怕影响其他 | 改价格不影响邮件 |
| 可扩展性 | 换数据库要改全部 | 换数据库只需实现IDatabase |
| 可读性 | 需要读完200行 | 看函数名就知道做什么 |

## 6. 工程化编码的思维转变

### 1. 从"写代码"到"设计代码"

| 过程化思维 | 工程化思维 |
|-----------|-----------|
| "我要实现这个功能" | "这个功能属于哪个模块？" |
| "先写出来再说" | "先想清楚接口再实现" |
| "这个变量全局用" | "这个变量的生命周期是什么？" |
| "复制粘贴最快" | "提取公共方法，复用而非复制" |
| "加个if判断就行" | "这个分支会不会越来越多？用策略模式？" |
| "先不管错误" | "如果这里出错了怎么办？" |
| "以后再重构" | "现在就保持代码整洁" |

### 2. 编码的三个层次

```
层次1：能跑 ─────────────────────────────────
  代码能运行，功能能实现
  特征：硬编码、全局变量、大函数、无错误处理

层次2：能改 ─────────────────────────────────
  代码结构清晰，修改方便
  特征：函数拆分、接口抽象、错误处理、可测试

层次3：能长 ─────────────────────────────────
  代码架构灵活，能应对需求变化
  特征：设计模式、依赖注入、插件化、配置驱动
```

**目标**：至少达到层次2。层次3根据项目规模和需求决定。

### 3. 什么时候需要设计模式？

```
不需要设计模式：
├── 一次性脚本
├── 100行以内的工具
├── 概念验证（PoC）
└── 学习练习

需要设计模式：
├── 多人协作的项目
├── 需要长期维护的项目
├── 需求会变化的项目
└── 需要扩展的项目

判断标准：如果3个月后你还要改这段代码，就值得设计好
```

## 7. 工程化编码的实战清单

### 1. 写代码前的检查清单

- [ ] 我理解了需求吗？（能用一句话说清楚吗？）
- [ ] 我知道数据从哪来、到哪去吗？
- [ ] 我知道这个功能属于哪个模块吗？
- [ ] 我设计好接口了吗？（函数签名、参数、返回值）
- [ ] 我考虑了错误情况吗？
- [ ] 我考虑了边界条件吗？

### 2. 写代码时的检查清单

- [ ] 每个函数不超过30行？
- [ ] 每个函数只做一件事？
- [ ] 函数名能说明它做什么？
- [ ] 变量名能说明它是什么？
- [ ] 没有硬编码的常量？
- [ ] 没有重复代码？
- [ ] 错误都处理了？

### 3. 写完代码后的检查清单

- [ ] 能编译通过，无警告？
- [ ] 能跑通基本场景？
- [ ] 能跑通边界场景？
- [ ] 代码能被别人看懂？
- [ ] 3个月后你自己还能看懂？

## 8. 常见问题

### 1. Q1：工程化编码会不会太慢？

**短期慢，长期快**。前20%的时间多花在设计上，后80%的时间会省在调试和修改上。

```
不设计：1天写完 + 3天改bug + 5天加新功能时发现要重写 = 9天
先设计：2天设计 + 1天写完 + 0.5天改bug + 2天加新功能 = 5.5天
```

### 2. Q2：什么时候该重构？

**三的法则**：同一份代码复制3次，就该提取公共方法了。

**童子军原则**：每次修改代码时，让代码比你发现时更好一点。不需要专门安排重构时间，在日常开发中持续改进。

### 3. Q3：怎么避免过度设计？

| 过度设计 | 合理设计 |
|---------|---------|
| 为未来可能的需求预留10个接口 | 为已知的2种变化预留接口 |
| 用了5层继承 | 用1层继承+组合 |
| 写了100行配置代码 | 写10行配置 |
| 引入了不需要的设计模式 | 在需要时才引入模式 |

**判断标准**：如果去掉某个抽象层，代码会变乱，那就是合理的；如果去掉后代码没区别，那就是过度设计。

### 4. Q4：过程化代码就一定不好吗？

不一定。以下场景过程化代码是合理的：

- 一次性脚本
- 算法竞赛代码
- 简单的main函数入口
- 性能极致优化的热路径

**关键是知道什么时候该用过程化，什么时候该用工程化。**
