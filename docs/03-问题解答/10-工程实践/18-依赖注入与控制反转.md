> "不要自己找依赖，让依赖来找你。" — IoC是思想，DI是手段，解耦是目的。

## 1. 什么是控制反转（IoC）

### 1. 定义

控制反转（Inversion of Control）是一种设计原则：**把控制权从自己手里交出去，交给外部容器或框架**。程序不再自己决定"用什么"和"怎么创建"，而是由外部来决定。

### 2. 比喻

```
自己做饭：
  你 ─── 买菜 → 洗菜 → 切菜 → 炒菜 → 吃
  全程你自己控制，每个环节你都亲自参与

叫外卖：
  你 ─── 下单 → 等待 → 吃
  做饭的控制权交给了餐厅，你只管吃

  自己做饭 = 传统编程（自己控制一切）
  叫外卖   = IoC编程（把控制权交出去）
```

### 3. 传统编程 vs IoC编程

```cpp
#include <iostream>
#include <string>

// 传统方式：自己创建依赖，自己控制
class MySQLDatabase {
public:
    void query(const std::string& sql) {
        std::cout << "MySQL执行: " << sql << std::endl;
    }
};

class UserService {
    MySQLDatabase db;  // 自己创建，自己控制
public:
    void getUser() {
        db.query("SELECT * FROM users");  // 硬编码依赖MySQL
    }
};

// IoC方式：不自己创建，由外部传入
class IDatabase {
public:
    virtual ~IDatabase() = default;
    virtual void query(const std::string& sql) = 0;
};

class MySQLDatabase2 : public IDatabase {
public:
    void query(const std::string& sql) override {
        std::cout << "MySQL执行: " << sql << std::endl;
    }
};

class SqliteDatabase : public IDatabase {
public:
    void query(const std::string& sql) override {
        std::cout << "SQLite执行: " << sql << std::endl;
    }
};

class UserService2 {
    IDatabase& db;  // 不创建，只声明需要什么
public:
    UserService2(IDatabase& database) : db(database) {}  // 外部传入
    void getUser() {
        db.query("SELECT * FROM users");
    }
};

int main() {
    // 传统：换数据库？改UserService源码
    UserService s1;
    s1.getUser();

    // IoC：换数据库？只改外部组装
    MySQLDatabase2 mysql;
    UserService2 s2(mysql);       // 用MySQL
    s2.getUser();

    SqliteDatabase sqlite;
    UserService2 s3(sqlite);      // 换成SQLite，UserService2不用改
    s3.getUser();
}
```

```
控制权流向对比：

传统方式：
  UserService ──创建──→ MySQLDatabase
  UserService控制了"用哪个数据库"和"怎么创建"

IoC方式：
  外部代码 ──创建──→ MySQLDatabase
  外部代码 ──注入──→ UserService
  UserService只管"用"，不管"从哪来"
  控制权反转了！
```

## 2. 什么是依赖注入（DI）

### 1. 定义

依赖注入（Dependency Injection）是IoC的一种实现方式：**不由自己创建依赖对象，而是由外部将依赖传入**。

### 2. 比喻

```
没有DI：
  你 ─── 自己去超市 → 买菜 → 回家 → 做饭
  依赖（菜）是你自己获取的

有DI：
  你 ─── 在家等着 → 外卖员把菜送到你家
  依赖（菜）由外部送进来，你不需要知道菜从哪来

  关键区别：你不需要知道"菜从哪来"，只需要"有菜可用"
```

### 3. 三种注入方式

#### 1. 构造函数注入（推荐）

```cpp
class ILogger {
public:
    virtual ~ILogger() = default;
    virtual void log(const std::string& msg) = 0;
};

class ConsoleLogger : public ILogger {
public:
    void log(const std::string& msg) override {
        std::cout << "[LOG] " << msg << std::endl;
    }
};

class OrderService {
    ILogger& logger_;
public:
    OrderService(ILogger& logger) : logger_(logger) {}  // 构造时注入
    void createOrder(const std::string& item) {
        logger_.log("创建订单: " + item);
    }
};

int main() {
    ConsoleLogger logger;
    OrderService service(logger);  // 构造函数注入
    service.createOrder("C++ Primer");
}
```

#### 2. Setter注入

```cpp
class OrderService {
    ILogger* logger_ = nullptr;
public:
    void setLogger(ILogger* logger) {  // Setter注入
        logger_ = logger;
    }
    void createOrder(const std::string& item) {
        if (logger_) logger_->log("创建订单: " + item);
    }
};

int main() {
    ConsoleLogger logger;
    OrderService service;
    service.setLogger(&logger);  // 通过Setter注入
    service.createOrder("C++ Primer");
}
```

#### 3. 接口注入

```cpp
class ILoggerInjectable {
public:
    virtual void injectLogger(ILogger& logger) = 0;
    virtual ~ILoggerInjectable() = default;
};

class OrderService : public ILoggerInjectable {
    ILogger* logger_ = nullptr;
public:
    void injectLogger(ILogger& logger) override {  // 接口注入
        logger_ = &logger;
    }
    void createOrder(const std::string& item) {
        if (logger_) logger_->log("创建订单: " + item);
    }
};
```

### 4. 三种注入方式对比

| 方式 | 时机 | 必需性 | 适用场景 | 推荐度 |
|------|------|--------|----------|--------|
| 构造函数注入 | 对象创建时 | 强制依赖 | 依赖必须存在的情况 | ★★★★★ |
| Setter注入 | 对象创建后 | 可选依赖 | 依赖可有可无的情况 | ★★★☆☆ |
| 接口注入 | 对象创建后 | 声明式强制 | 需要统一注入接口时 | ★★☆☆☆ |

## 3. IoC与DI的关系

### 1. 一句话总结

**IoC是思想，DI是实现。**

```
IoC（控制反转）
  └── 思想层面：把控制权交出去
  └── 回答"要不要自己做？" → 不要，让别人做

DI（依赖注入）
  └── 实现层面：具体怎么把依赖送进来
  └── 回答"怎么交给别人？" → 通过构造函数/Setter/接口注入

比喻：
  IoC = 决定不自己做饭（思想）
  DI  = 具体怎么把饭送到你手上（实现）
       ├── 外卖员送上门（构造函数注入）
       ├── 自己去取餐柜拿（Setter注入）
       └── 通过取餐接口领取（接口注入）
```

### 2. IoC的其他实现方式

DI不是IoC的唯一实现，IoC还有其他形式：

```
IoC的实现方式：
  ├── 依赖注入（DI）── 外部传入依赖对象
  ├── 模板方法模式  ── 父类定义流程，子类填充细节
  ├── 事件驱动      ── 注册回调，由事件源触发
  ├── 服务定位器    ── 从全局容器中查找依赖（有争议）
  └── 观察者模式    ── 订阅通知，被动响应
```

## 4. 为什么需要DI

### 1. 解耦

```cpp
// 硬编码依赖：UserService和MySQLDatabase紧耦合
class UserService {
    MySQLDatabase db;  // 换数据库？改这里
public:
    void getUser() { db.query("SELECT * FROM users"); }
};

// 注入依赖：UserService和具体数据库解耦
class UserService {
    IDatabase& db;  // 只依赖抽象，不依赖具体
public:
    UserService(IDatabase& db) : db(db) {}
    void getUser() { db.query("SELECT * FROM users"); }
};
```

### 2. 可测试

```cpp
#include <cassert>

class MockDatabase : public IDatabase {
public:
    std::string lastQuery;
    void query(const std::string& sql) override {
        lastQuery = sql;  // 记录调用，不真正查数据库
    }
};

void testGetUser() {
    MockDatabase mock;           // 用Mock替代真实数据库
    UserService service(mock);   // 注入Mock
    service.getUser();
    assert(mock.lastQuery == "SELECT * FROM users");  // 验证行为
}

// 没有DI？测试时必须连真实数据库，又慢又不稳定
```

### 3. 可替换

```cpp
// 运行时切换实现，不需要改UserService
IDatabase* createDatabase(const std::string& config) {
    if (config == "mysql")  return new MySQLDatabase2();
    if (config == "sqlite") return new SqliteDatabase();
    throw std::runtime_error("不支持的数据库类型");
}
```

### 4. 对比总结

```
硬编码依赖：
  UserService ──强依赖──→ MySQLDatabase
  ├── 换数据库 → 改源码
  ├── 单元测试 → 连真实数据库
  └── 代码复用 → 只能用于MySQL场景

注入依赖：
  UserService ──弱依赖──→ IDatabase（抽象）
  ├── 换数据库 → 改外部组装
  ├── 单元测试 → 注入Mock
  └── 代码复用 → 任何IDatabase实现
```

## 5. C/C++中的DI实现

### 1. C语言：函数指针/回调

```c
#include <stdio.h>

typedef void (*LogFunc)(const char* msg);

void console_log(const char* msg) {
    printf("[Console] %s\n", msg);
}

void file_log(const char* msg) {
    printf("[File] %s\n", msg);  // 简化示例
}

typedef struct {
    LogFunc log;
} OrderService;

void order_create(OrderService* svc, const char* item) {
    if (svc->log) svc->log("创建订单");
}

int main() {
    OrderService svc1 = { .log = console_log };
    order_create(&svc1, "C Primer");

    OrderService svc2 = { .log = file_log };  // 运行时切换
    order_create(&svc2, "C Primer");
}
```

### 2. C++：纯虚类（接口）

```cpp
class ICache {
public:
    virtual ~ICache() = default;
    virtual std::string get(const std::string& key) = 0;
    virtual void set(const std::string& key, const std::string& val) = 0;
};

class RedisCache : public ICache {
public:
    std::string get(const std::string& key) override { return "redis_value"; }
    void set(const std::string& key, const std::string& val) override {}
};

class LocalCache : public ICache {
public:
    std::string get(const std::string& key) override { return "local_value"; }
    void set(const std::string& key, const std::string& val) override {}
};

class AppService {
    ICache& cache_;
public:
    AppService(ICache& cache) : cache_(cache) {}
    std::string getData(const std::string& key) {
        return cache_.get(key);
    }
};
```

### 3. C++：模板（编译期DI）

```cpp
template<typename CacheT>
class AppService {
    CacheT cache_;
public:
    AppService() = default;
    std::string getData(const std::string& key) {
        return cache_.get(key);
    }
};

class SimpleCache {
public:
    std::string get(const std::string& key) { return "simple_value"; }
};

// 编译期决定依赖，零运行时开销
AppService<SimpleCache> svc;
```

### 4. C++：智能指针 + 工厂

```cpp
#include <memory>

class AppService {
    std::shared_ptr<ICache> cache_;
public:
    AppService(std::shared_ptr<ICache> cache) : cache_(std::move(cache)) {}
    std::string getData(const std::string& key) {
        return cache_->get(key);
    }
};

// 工厂函数负责组装
std::unique_ptr<AppService> createAppService(const std::string& config) {
    std::shared_ptr<ICache> cache;
    if (config == "redis") {
        cache = std::make_shared<RedisCache>();
    } else {
        cache = std::make_shared<LocalCache>();
    }
    return std::make_unique<AppService>(cache);
}
```

### 5. C++ DI框架介绍

| 框架 | 特点 | 适用场景 |
|------|------|----------|
| **Boost.DI** | 编译期DI，零开销，仅头文件 | 高性能C++项目 |
| **fruit** | Google开源，编译期注入 | 大型C++项目 |
| **Google Guice**（Java） | 运行时DI容器 | Java项目参考 |
| **Autofac**（C#） | 运行时DI容器 | C#项目参考 |

```
C++ DI框架选择思路：

编译期DI（Boost.DI / fruit）
  ├── 优点：零运行时开销，编译期检查
  ├── 缺点：编译时间增加，错误信息难读
  └── 适合：性能敏感、类型已知的项目

运行时DI（自建容器）
  ├── 优点：灵活，支持配置驱动
  ├── 缺点：有运行时开销，类型安全性弱
  └── 适合：插件化、动态加载的项目

手动DI（推荐起步方式）
  ├── 优点：简单直接，无额外依赖
  ├── 缺点：大规模项目组装代码多
  └── 适合：中小项目、学习阶段
```

## 6. DI与SOLID原则的关系

### 1. DIP是DI的理论基础

```
SOLID原则中的D — 依赖倒置原则（DIP）：
  1. 高层模块不应该依赖低层模块，两者都应该依赖抽象
  2. 抽象不应该依赖细节，细节应该依赖抽象

DI是DIP的实现手段：
  DIP告诉你"应该依赖抽象"（理论）
  DI告诉你"怎么把抽象传进来"（实践）
```

```cpp
// 违反DIP：高层依赖低层
class BusinessLogic {
    MySQLDatabase db;  // 高层直接依赖低层具体实现
};

// 遵循DIP + DI：高层依赖抽象
class BusinessLogic {
    IDatabase& db;     // 高层依赖抽象
public:
    BusinessLogic(IDatabase& db) : db(db) {}  // DI传入抽象
};
```

### 2. DI与其他SOLID原则

| 原则 | 与DI的关系 |
|------|-----------|
| **SRP**（单一职责） | DI让类不负责创建依赖，职责更单一 |
| **OCP**（开闭原则） | DI让扩展新实现不需要修改已有代码 |
| **LSP**（里氏替换） | DI依赖抽象，任何子类实现都可替换 |
| **ISP**（接口隔离） | DI鼓励定义小接口，避免注入不需要的依赖 |
| **DIP**（依赖倒置） | DI的直接理论基础 |

## 7. DI的常见误区

### 1. 过度注入

```cpp
// 过度注入：一个类依赖了十几个接口
class MegaService {
    ILogger& log;
    ICache& cache;
    IDatabase& db;
    IMessageQueue& mq;
    IConfig& config;
    IMetrics& metrics;
    ITracer& tracer;
    IAuthProvider& auth;
    // ... 还有5个
};
// 问题：类承担了太多职责，违反SRP
// 解决：拆分类，每个类只注入真正需要的依赖
```

### 2. Service Locator反模式

```cpp
// Service Locator：从全局容器中主动查找依赖
class ServiceLocator {
public:
    static IDatabase& getDatabase() { return *instance_; }
    static void setDatabase(IDatabase* db) { instance_ = db; }
private:
    static IDatabase* instance_;
};

class UserService {
public:
    void getUser() {
        auto& db = ServiceLocator::getDatabase();  // 隐式依赖
        db.query("SELECT * FROM users");
    }
};
// 问题：
//   1. 隐式依赖——看接口声明不知道需要什么
//   2. 运行时才能发现缺少依赖
//   3. 难以测试——必须配置全局Locator

// 正确做法：构造函数注入，显式声明依赖
class UserService {
    IDatabase& db_;
public:
    UserService(IDatabase& db) : db_(db) {}  // 显式依赖
};
```

### 3. 为了DI而DI

```cpp
// 不需要DI的情况：工具类、无状态函数、值对象
class MathUtils {
public:
    static int add(int a, int b) { return a + b; }  // 纯函数，不需要DI
};

class Point {  // 值对象，不需要DI
    int x_, y_;
public:
    Point(int x, int y) : x_(x), y_(y) {}
};

// 需要DI的情况：有外部依赖的业务逻辑
class PaymentService {
    IPaymentGateway& gateway_;  // 外部依赖，需要DI
public:
    PaymentService(IPaymentGateway& gw) : gateway_(gw) {}
};
```

```
判断是否需要DI的简单标准：

  依赖是"稳定的"吗？
    ├── 是（如标准库、工具函数）→ 不需要DI
    └── 否（如数据库、网络、文件系统）→ 考虑DI

  需要在测试中替换吗？
    ├── 否 → 不需要DI
    └── 是 → 需要DI

  依赖可能变化吗？
    ├── 否 → 不需要DI
    └── 是 → 需要DI
```

## 8. 速查对照表

| 概念 | 一句话 | 比喻 |
|------|--------|------|
| IoC | 把控制权交出去 | 叫外卖不自己做饭 |
| DI | 外部传入依赖 | 外卖员把饭送到手上 |
| 构造函数注入 | 创建时传入 | 出生就有名字 |
| Setter注入 | 创建后设置 | 后天改名字 |
| 接口注入 | 通过接口传入 | 凭证领取 |
| DIP | 依赖抽象不依赖具体 | 看地图不看实地 |
| Service Locator | 全局查找依赖 | 自己去仓库找东西（反模式） |
| 过度注入 | 注入太多依赖 | 一个人干十个人的活 |

| 注入方式 | 代码形式 | 依赖必需 | 可测试性 | 推荐场景 |
|----------|----------|----------|----------|----------|
| 构造函数 | `Svc(Dep& d)` | 是 | ★★★★★ | 必需依赖 |
| Setter | `setDep(Dep* d)` | 否 | ★★★☆☆ | 可选依赖 |
| 接口 | `injectDep(Dep& d)` | 是 | ★★☆☆☆ | 框架约束 |
| 模板 | `Svc<DepT>` | 是 | ★★★★☆ | 编译期多态 |
| 函数指针(C) | `Svc.log = fn` | 否 | ★★★☆☆ | C语言项目 |
