# 开源许可协议与参与指南
> 📖 相关章节：[编码规范](../../04-工程实践/00-编码规范.md)

## 1. 什么是开源许可协议

### 1. 定义

开源许可协议是一份**法律文书**，明确规定别人可以怎样使用、修改和分发你的代码。它不是技术文档，而是具有法律约束力的协议。

### 2. 为什么重要

```
没有许可协议：
┌──────────────────────────────────────────────────┐
│  代码公开在 GitHub 上 ≠ 别人可以合法使用          │
│  根据《伯尔尼公约》，代码一经创作即受版权保护      │
│  没有许可协议 = 保留所有权利                      │
│  别人复制你的代码 = 侵权                          │
└──────────────────────────────────────────────────┘

有许可协议：
┌──────────────────────────────────────────────────┐
│  明确授予他人使用、修改、分发的权利               │
│  明确使用条件（如必须保留版权声明）               │
│  明确免责条款（作者不对代码造成的问题负责）       │
└──────────────────────────────────────────────────┘
```

### 3. 开源 ≠ 免费

| 概念     | 说明                                         |
| -------- | -------------------------------------------- |
| 开源     | 源代码可查看、可修改（有条件）               |
| 免费     | 不需要付费（与是否开源无关）                 |
| 公有领域 | 没有版权限制，任何人可无条件使用             |

开源软件可以收费（如 Red Hat），免费软件也可能不开源（如微信）。

## 2. 主流开源协议详解

### 1. MIT 协议

```
核心：最宽松，随便用，但要保留版权声明

你可以：
  ✅ 商业使用
  ✅ 修改代码
  ✅ 分发
  ✅ 私有化使用
  ✅ 再授权

你必须：
  📋 保留版权声明和许可声明

你不能：
  ❌ 起诉作者（免责条款）
```

MIT 协议全文核心就一句话：**"随便用，但别找我麻烦，记得带上这个声明。"**

### 2. Apache 2.0 协议

```
核心：宽松 + 专利授权 + 声明修改

MIT 的所有权利 +
  ✅ 专利授权（贡献者授予用户专利许可）
  ✅ 明确商标使用权（不授予）

你必须：
  📋 保留版权声明
  📋 保留 NOTICE 文件（如果有）
  📋 声明对文件的修改部分
  📋 保留所有许可声明
```

### 3. GPL v2 / v3 协议

```
核心：传染性 —— 衍生作品必须也开源

┌──────────────────────────────────────────────┐
│  你的项目（闭源）                              │
│  ┌────────────────────────────────────────┐  │
│  │  GPL 库的代码                           │  │
│  │  ↓ 传染                                │  │
│  │  调用 GPL 库的代码 → 也必须 GPL 开源    │  │
│  │  ↓ 传染                                │  │
│  │  整个项目 → 都必须 GPL 开源             │  │
│  └────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘

GPL v2 vs v3 主要区别：
┌────────────┬──────────────────┬──────────────────────┐
│ 特性        │ GPL v2           │ GPL v3               │
├────────────┼──────────────────┼──────────────────────┤
│ 专利授权    │ 无明确条款       │ 明确授予专利许可     │
│ 反 DRM      │ 无               │ 禁止用 DRM 限制      │
│ 兼容性      │ 与 Apache 2.0    │ 与 Apache 2.0 兼容   │
│            │ 不兼容           │                      │
│ Tivoization│ 允许             │ 禁止                 │
└────────────┴──────────────────┴──────────────────────┘
```

### 4. LGPL 协议

```
核心：弱传染性 —— 动态链接不需要开源

┌──────────────────────────────────────────────┐
│  你的项目（可以闭源）                          │
│  ┌──────────────┐  动态链接  ┌─────────────┐ │
│  │  你的代码     │ ←───────→ │  LGPL 库     │ │
│  │  不需要开源   │           │  必须开源    │ │
│  └──────────────┘           └─────────────┘ │
│                                              │
│  但如果你修改了 LGPL 库本身，修改部分必须开源  │
└──────────────────────────────────────────────┘
```

### 5. BSD 协议

类似 MIT，分为两条款和三条款版本：

| 版本       | 要求                         |
| ---------- | ---------------------------- |
| BSD 2-Clause | 保留版权声明               |
| BSD 3-Clause | 保留版权声明 + 不得用作者名义背书 |

### 6. MPL 2.0 协议

```
核心：文件级传染

┌──────────────────────────────────────────────┐
│  你的项目                                     │
│  ┌─────────────┐  ┌──────────────────────┐  │
│  │ your_file.cpp│  │ mpl_file.cpp         │  │
│  │ 你的代码     │  │ MPL 协议的代码       │  │
│  │ 可以闭源     │  │ 必须保持 MPL 开源    │  │
│  └─────────────┘  └──────────────────────┘  │
│                                              │
│  传染范围：仅限同一文件，不扩散到其他文件     │
└──────────────────────────────────────────────┘
```

### 7. Unlicense

```
核心：放弃所有权利，投入公有领域

你可以：
  ✅ 任何事，没有任何限制

你必须：
  📋 无

注意：某些司法管辖区不承认放弃版权，建议同时提供 MIT 作为备选
```

## 3. 协议对比与选择

### 1. 宽松 vs 传染性对比表

| 协议       | 类型     | 商用 | 修改 | 分发 | 专利 | 传染性 | 复杂度 |
| ---------- | -------- | ---- | ---- | ---- | ---- | ------ | ------ |
| Unlicense  | 公有领域 | ✅   | ✅   | ✅   | ❌   | 无     | 极低   |
| MIT        | 宽松     | ✅   | ✅   | ✅   | ❌   | 无     | 极低   |
| BSD 2-Clause| 宽松    | ✅   | ✅   | ✅   | ❌   | 无     | 极低   |
| BSD 3-Clause| 宽松    | ✅   | ✅   | ✅   | ❌   | 无     | 低     |
| Apache 2.0 | 宽松     | ✅   | ✅   | ✅   | ✅   | 无     | 中     |
| MPL 2.0    | 弱传染   | ✅   | ✅   | ✅   | ✅   | 文件级 | 中     |
| LGPL       | 弱传染   | ✅   | ✅   | ✅   | ✅   | 模块级 | 高     |
| GPL v2     | 强传染   | ✅   | ✅   | ✅   | ❌   | 项目级 | 高     |
| GPL v3     | 强传染   | ✅   | ✅   | ✅   | ✅   | 项目级 | 高     |

### 2. 选择决策树

```
你希望别人怎么用你的代码？
│
├── 随便用，我不在乎
│   └── Unlicense 或 MIT
│
├── 随便用，但希望有专利保护
│   └── Apache 2.0
│
├── 希望修改过的文件保持开源
│   └── MPL 2.0
│
├── 希望作为库被闭源项目使用，但库本身要开源
│   └── LGPL
│
└── 希望所有衍生作品都开源
    ├── 不需要专利条款 → GPL v2
    └── 需要专利条款   → GPL v3
```

## 4. 协议兼容性矩阵

### 1. 组合使用规则

```
能否将 A 协议的代码与 B 协议的代码组合？

          MIT  BSD  Apache  MPL  LGPL  GPL
MIT       ✅   ✅    ✅     ✅    ✅    ✅
BSD       ✅   ✅    ✅     ✅    ✅    ✅
Apache    ✅   ✅    ✅     ✅    ✅    ⚠️v3
MPL       ✅   ✅    ✅     ✅    ✅    ✅
LGPL      ✅   ✅    ✅     ✅    ✅    ✅
GPL       ✅   ✅    ⚠️v3   ✅    ✅    ✅

✅ = 兼容    ⚠️ = 有条件兼容    ❌ = 不兼容
```

### 2. GPL 传染性详解

```
场景1：链接 GPL 库
┌──────────────┐     ┌──────────┐
│ 你的闭源代码  │────→│ GPL 库   │
└──────────────┘     └──────────┘
结果：你的代码必须也 GPL 开源 ✅ 传染

场景2：独立进程通信
┌──────────────┐     ┌──────────┐
│ 你的闭源代码  │────→│ GPL 程序 │
│ (管道/Socket) │     │          │
└──────────────┘     └──────────┘
结果：你的代码不需要开源 ❌ 不传染

场景3：聚合（同一介质分发）
┌──────────────────────────────┐
│ CD-ROM                       │
│  ├── 你的闭源软件 (MIT)      │
│  └── GPL 软件                │
└──────────────────────────────┘
结果：你的软件不需要开源 ❌ 不传染
```

### 3. 动态链接 vs 静态链接对 LGPL 的影响

| 链接方式 | 你的代码是否需要开源 | 说明                       |
| -------- | -------------------- | -------------------------- |
| 动态链接 | 不需要               | 你的代码与 LGPL 库分离     |
| 静态链接 | 不需要，但有义务     | 必须提供目标文件让用户重新链接 |

## 5. C/C++ 项目的许可实践

### 1. 依赖库的协议审计

```bash
# 使用 FOSSA 扫描依赖
fossa analyze

# 使用 scancode 扫描
scancode --license --copyright /path/to/project

# 手动检查 vcpkg 依赖的协议
vcpkg depend-info your-package
```

审计清单：

```
1. 列出所有依赖及其协议
2. 检查协议兼容性
3. 标记 GPL/LGPL 依赖（传染性风险）
4. 确认每个依赖的协议版本
5. 检查是否有依赖冲突
```

### 2. 头文件的许可声明

```cpp
// SPDX-License-Identifier: MIT
// Copyright (c) 2024 Your Name

#ifndef MYLIB_UTILS_H
#define MYLIB_UTILS_H

namespace mylib {

int add(int a, int b);

}

#endif
```

使用 SPDX 标识符是现代推荐做法，简洁且机器可读。

### 3. 第三方库集成注意事项

```
集成第三方库时的检查清单：

┌──────────────────────────────────────────────────┐
│ □ 确认第三方库的协议                              │
│ □ 确认协议与你的项目协议兼容                      │
│ □ 在项目中保留第三方库的 LICENSE 文件             │
│ □ 在 NOTICE 或 README 中声明使用了哪些第三方库    │
│ □ 如果是 GPL/LGPL，评估传染性影响                │
│ □ 如果修改了第三方库，遵守其协议的修改声明要求    │
│ □ 记录第三方库的版本号                            │
└──────────────────────────────────────────────────┘
```

## 6. 如何参与开源项目

### 1. 选择项目

```
寻找适合新手的项目：

1. GitHub 搜索：label:"good first issue"
2. GitHub 搜索：label:"help wanted"
3. 查看 CONTRIBUTING.md 文件
4. 查看项目的 issue 列表
5. 选择你熟悉的技术栈
6. 从小改动开始（文档、测试、bug 修复）
```

### 2. Fork → Branch → PR 流程

```
1. Fork 项目到自己的 GitHub
   ┌──────────┐    Fork     ┌──────────────┐
   │ 原始仓库  │ ──────────→ │ 你的 Fork     │
   └──────────┘             └──────────────┘

2. 克隆到本地
   git clone https://github.com/yourname/project.git

3. 创建功能分支
   git checkout -b fix/memory-leak

4. 开发并提交
   git add .
   git commit -m "fix: 修复 utils.cpp 中的内存泄漏"

5. 推送到 Fork
   git push origin fix/memory-leak

6. 在 GitHub 上创建 Pull Request
   ┌──────────────┐   PR    ┌──────────┐
   │ 你的 Fork     │ ──────→ │ 原始仓库  │
   └──────────────┘         └──────────┘

7. 等待 Code Review，根据反馈修改
8. 合并后同步 Fork
   git remote add upstream https://github.com/original/project.git
   git fetch upstream
   git checkout main
   git merge upstream/main
```

### 3. 代码规范

- 遵循项目的现有代码风格（查看 `.clang-format`、`.editorconfig`）
- 提交信息遵循 Conventional Commits 规范

```
提交信息格式：
<type>(<scope>): <subject>

type 类型：
  feat:     新功能
  fix:      修复 bug
  docs:     文档变更
  style:    代码格式（不影响逻辑）
  refactor: 重构
  test:     测试
  chore:    构建/工具变更

示例：
  feat(parser): 新增 JSON 数组解析支持
  fix(memory): 修复 Buffer 类的内存泄漏
  docs(api): 更新 API 文档
```

### 4. PR 模板

```markdown
## 7. 变更说明
简要描述本次变更的内容和原因。

## 8. 变更类型
- [ ] Bug 修复
- [ ] 新功能
- [ ] 重构
- [ ] 文档更新
- [ ] 测试

## 9. 关联 Issue
Fixes #123

## 10. 测试
描述如何测试本次变更。

## 11. 检查清单
- [ ] 代码遵循项目编码规范
- [ ] 已添加/更新测试
- [ ] 所有测试通过
- [ ] 已更新相关文档
```

### 5. Code Review 礼仪

```
作为 PR 提交者：
  ✅ PR 保持小而专注，便于审查
  ✅ 认真对待每条评审意见
  ✅ 不确定的地方主动提问
  ✅ 及时回复评审意见
  ❌ 不要对批评性意见产生情绪

作为 Reviewer：
  ✅ 对事不对人，评论代码而非作者
  ✅ 提出建设性建议，而非只说"不好"
  ✅ 区分"必须修改"和"建议修改"
  ✅ 及时完成审查
  ❌ 不要用贬低性语言
```

## 7. 创建自己的开源项目

### 1. 选择协议

```
项目类型           → 推荐协议
─────────────────────────────────────
工具/库（希望广泛使用）→ MIT 或 Apache 2.0
库（希望生态开放）    → LGPL 或 MPL 2.0
项目（希望衍生也开源）→ GPL v3
学习/示例代码        → MIT 或 Unlicense
```

### 2. 编写 README

```markdown
# 项目名称

一句话描述项目。

## 14. 功能特性
- 特性1
- 特性2

## 15. 快速开始

### 33. 依赖
- CMake 3.20+
- C++17 编译器

### 34. 构建
```bash
cmake -B build && cmake --build build
```

### 35. 使用
```cpp
#include "mylib/mylib.h"
int main() {
    mylib::hello();
}
```

## 16. 文档
链接到详细文档。

## 17. 贡献
参见 3. CONTRIBUTING.md。

## 18. 许可
本项目基于 [MIT](LICENSE) 协议开源。
```

```markdown

```

### 5. CI/CD 配置

开源项目建议的最小 CI 配置：

```yaml
name: CI
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: 构建
        run: cmake -B build && cmake --build build
      - name: 测试
        working-directory: build
        run: ctest --output-on-failure
```

### 6. 发布流程

```
1. 确保所有测试通过
2. 更新版本号
3. 更新 CHANGELOG.md
4. 创建 Git 标签
5. 推送标签触发 Release 工作流
6. GitHub 自动创建 Release 页面
7. 上传构建产物
```

## 8. 常见误区

### 1. MIT 不等于没有限制

```
❌ 错误理解：MIT 协议就是随便用，没有任何限制
✅ 正确理解：MIT 协议要求保留版权声明和许可声明

违反 MIT 的示例：
  复制 MIT 代码到自己的项目中，删除了版权声明 → 侵权

正确做法：
  在项目中保留原始 LICENSE 文件
  在源文件头部保留版权声明
  或在项目的第三方声明文件中列出
```

### 2. GPL 不会自动传染通过网络访问的服务

```
❌ 错误理解：使用了 GPL 库的 Web 服务，必须开源所有代码
✅ 正确理解：GPL 传染发生在"分发"时，仅提供服务不算分发

场景分析：
┌──────────────────────────────────────────────────┐
│ 你用 GPL 库构建了一个 Web 服务                     │
│ 用户通过浏览器访问你的服务                         │
│ 你没有把软件"分发"给用户                          │
│ → 你的代码不需要开源                              │
└──────────────────────────────────────────────────┘

但 GPL v3 的 AGPL 变体填补了这个漏洞：
  AGPL → 即使通过网络访问也必须开源
```

### 3. 使用开源代码不等于必须开源自己的代码

```
❌ 错误理解：用了开源代码，自己的代码就必须开源
✅ 正确理解：只有使用 GPL 等传染性协议的代码才需要开源

各协议的影响：
┌────────────┬──────────────────────────────────────┐
│ 协议        │ 你的代码是否需要开源                  │
├────────────┼──────────────────────────────────────┤
│ MIT/BSD    │ 不需要                               │
│ Apache 2.0 │ 不需要                               │
│ LGPL       │ 不需要（动态链接时）                  │
│ MPL 2.0    │ 不需要（仅修改的 MPL 文件需要开源）  │
│ GPL        │ 需要（整个衍生作品）                  │
│ AGPL       │ 需要（包括网络服务场景）              │
└────────────┴──────────────────────────────────────┘
```
