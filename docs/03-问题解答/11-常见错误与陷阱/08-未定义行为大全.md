# 未定义行为大全
> 📖 相关章节：[陷阱与技巧](../../04-工程实践/11-陷阱与技巧.md)、[内存管理](../../01-C语言/09-内存管理.md)

> **Undefined behavior means anything can happen, including working correctly by accident.** — C++ Standard
> （未定义行为意味着任何事情都可能发生，包括碰巧正常工作。）

***

### 1. 核心提炼

**未定义行为**（Undefined Behavior, UB）= **C/C++ 标准没有规定结果的行为**。编译器可以任意处理：可能崩溃、可能看似正常、可能格式化硬盘——**全部合法**。

***

### 2. 常见的未定义行为

| 类别 | 示例 |
|------|------|
| 数组越界 | `a[10]` 但数组只有5个元素 |
| 空指针解引用 | `*nullptr` |
| 使用未初始化变量 | `int x; cout << x;` |
| 重复释放 | `delete p; delete p;` |
| 有符号整数溢出 | `INT_MAX + 1` |
| 修改字符串字面量 | `char* s = "hello"; s[0] = 'H';` |
| 迭代器失效后使用 | `v.erase(it); *it;` |
| 多次修改同一变量 | `i = i++;` |
| 返回局部变量引用 | `int& f() { int x=0; return x; }` |
| 析构后使用对象 | `delete p; p->foo();` |
| 严格别名违规 | `float f; int* p = (int*)&f; *p = 1;` |
| 数据竞争 | 两个线程同时写同一变量 |

### 3. 未定义行为为什么可怕

```cpp
int arr[5];
arr[10] = 42;  // UB

// 编译器可能：
// 1. 崩溃（运气好）
// 2. 静默覆盖其他变量（最难调试）
// 3. 什么都不发生（最危险，隐藏bug）
// 4. 被编译器优化掉整段代码
```

UB 最可怕之处：**它可能在你开发时正常工作，发布后崩溃**。因为编译器升级、优化级别变化、平台切换都可能改变 UB 的实际表现。

### 4. 编译器如何利用 UB 优化

编译器基于"UB 不会发生"的假设做优化，这会导致意想不到的结果：

```cpp
int* p = nullptr;
int x = *p;  // UB → 编译器假设这不会发生
// 编译器推理：如果执行到这里，p 不可能是 nullptr
// 所以后续的 if (p == nullptr) 检查会被优化掉！
```

**汇编分析实例：**

```cpp
#include <iostream>

int* get_ptr();

void example() {
    int* p = get_ptr();
    int val = *p;           // 解引用 → 编译器假设p非空
    if (p == nullptr) {     // 编译器认为这个条件永远为false
        std::cout << "null" << std::endl;  // 被优化掉
    }
    std::cout << val << std::endl;
}
```

GCC -O2 优化后的逻辑等价于：

```cpp
void example_optimized() {
    int* p = get_ptr();
    int val = *p;
    std::cout << val << std::endl;
}
```

空指针检查被完全删除，因为编译器认为"既然已经解引用了 p，那 p 一定不是空"。

**另一个经典例子：有符号整数溢出**

```cpp
#include <iostream>

void loop_example() {
    for (int i = 0; i >= 0; ++i) {
        if (i == 100) break;
    }
}
```

编译器推理：`++i` 永远不会溢出（因为溢出是UB），所以 `i >= 0` 永远为真，循环条件可以优化为 `true`。如果缺少 `break`，这个循环会变成死循环。

### 5. 严格别名规则（Strict Aliasing）

严格别名规则：不同类型的指针不能指向同一块内存（少数例外除外）。违反此规则是 UB。

```cpp
#include <iostream>

float f = 1.0f;
int* p = reinterpret_cast<int*>(&f);  // 严格别名违规
int bits = *p;  // UB

std::cout << bits << std::endl;
```

**合法的别名例外：**

| 情况 | 说明 |
|------|------|
| `char*` 指向任何类型 | `char` 可以别名任何对象 |
| `unsigned char*` 指向任何类型 | 同上 |
| `void*` 指向任何类型 | `void*` 可以指向任何对象 |
| 相同类型 | `int*` 指向 `int` |
| 有符号/无符号变体 | `int*` 指向 `unsigned int` |

**类型双关（Type Punning）的正确做法：**

```cpp
#include <iostream>
#include <cstring>

float f = 1.0f;

int safe_bits;
std::memcpy(&safe_bits, &f, sizeof(f));  // 通过memcpy合法

union { float f; int i; } pun;
pun.f = 1.0f;
int union_bits = pun.i;  // C++中技术上UB，但几乎所有编译器支持
```

### 6. 序列点 vs 先序于（Sequenced-Before）

**C 语言用"序列点"（Sequence Point），C++11 起用"先序于"（Sequenced-Before）**。两者解决同一个问题：表达式求值的顺序。

```cpp
int i = 0;
i = i++;  // UB：i的修改之间没有先序于关系

int arr[10];
int idx = 0;
arr[idx] = idx++;  // UB：idx的读取和修改之间没有先序于关系
```

**先序于规则：**

| 表达式 | 是否UB | 原因 |
|--------|--------|------|
| `i = i++` | UB | 赋值和++无先序于关系 |
| `i = ++i` | C++11合法 | ++先序于赋值 |
| `a + b * c` | 合法 | 乘法先序于加法 |
| `f(a++, b++)` | 合法 | 参数求值之间无先序于，但参数求值先序于函数调用 |
| `a[i] = i++` | UB | i的读取和修改无先序于关系 |

C++17 进一步明确了求值顺序：

```cpp
// C++17之前：UB
// C++17：合法，赋值右侧先求值
a[b] = c;
```

### 7. ASan 和 UBSan 实战

#### 1. AddressSanitizer（ASan）

检测内存错误：越界、use-after-free、double-free 等。

```bash
g++ -fsanitize=address -g -O1 program.cpp -o program
./program
```

ASan 典型输出：

```
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000034
READ of size 4 at 0x602000000034 thread T0
    #0 0x4008d7 in main /path/test.cpp:5:10
    #1 0x7f... in __libc_start_main

0x602000000034 is located 0 bytes to the right of 20-byte region
allocated by thread T0 here:
    #0 0x4d3b82 in operator new[](unsigned long)
    #1 0x4008a4 in main /path/test.cpp:4:26
```

#### 2. UndefinedBehaviorSanitizer（UBSan）

检测未定义行为：整数溢出、空指针、类型违规等。

```bash
g++ -fsanitize=undefined -g -O1 program.cpp -o program
./program
```

UBSan 典型输出：

```
test.cpp:4:12: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
test.cpp:8:8: runtime error: null pointer dereference
test.cpp:12:5: runtime error: load of value 128, which is not a valid value for type 'bool'
```

**组合使用 ASan + UBSan：**

```bash
g++ -fsanitize=address,undefined -g -O1 program.cpp -o program
```

**MSVC 上的使用：**

```bash
cl /fsanitize=address /Zi program.cpp
```

MSVC 目前仅支持 ASan，UBSan 需要使用 Clang-cl 或 GCC。

### 8. 未定义行为 vs 未指定行为 vs 实现定义行为

| 类型 | 含义 | 示例 | 可移植性 |
|------|------|------|----------|
| 未定义行为 (UB) | 标准不规定，任何结果都行 | 解引用空指针 | 不可移植，必须避免 |
| 未指定行为 | 标准给了几种选择，编译器选一个 | 函数参数求值顺序 | 不可依赖具体选择 |
| 实现定义行为 | 编译器必须文档说明 | `int` 的大小、字节序 | 可移植但需条件编译 |

```cpp
#include <iostream>

int f() { std::cout << "f"; return 1; }
int g() { std::cout << "g"; return 2; }

int main() {
    int result = f() + g();  // 未指定行为：可能输出fg或gf
    std::cout << " = " << result << std::endl;
}
```

### 9. 实用检测工具汇总

| 工具 | 检测内容 | 编译器 | 命令 |
|------|----------|--------|------|
| ASan | 内存越界、use-after-free | GCC/Clang/MSVC | `-fsanitize=address` |
| UBSan | 整数溢出、空指针、类型违规 | GCC/Clang | `-fsanitize=undefined` |
| MSan | 使用未初始化内存 | GCC/Clang | `-fsanitize=memory` |
| TSan | 数据竞争 | GCC/Clang | `-fsanitize=thread` |
| Valgrind | 内存泄漏、非法读写 | 独立工具 | `valgrind ./program` |
| clang-tidy | 静态分析 | Clang | `clang-tidy program.cpp` |
| cppcheck | 静态分析 | 独立工具 | `cppcheck program.cpp` |

### 10. 如何避免 UB

| 策略 | 说明 |
|------|------|
| 编译警告即错误 | `-Wall -Wextra -Werror` 或 `/W4 /WX` |
| 使用 ASan + UBSan | 开发阶段始终开启 |
| 静态分析 | CI 中集成 clang-tidy / cppcheck |
| 避免裸指针 | 用智能指针和容器 |
| 初始化所有变量 | `int x = 0;` 而非 `int x;` |
| 使用 `at()` 替代 `[]` | 容器越界抛异常而非UB |
| 避免C风格转换 | 用 `static_cast` 等替代 |
| 理解先序于规则 | 不要在表达式中多次修改同一变量 |

```cpp
#include <vector>
#include <memory>
#include <iostream>

void safe_practices() {
    int x = 0;  // 初始化
    auto p = std::make_unique<int>(42);  // 智能指针
    std::vector<int> v = {1, 2, 3};
    int val = v.at(5);  // 越界抛异常而非UB
}

int main() {
    try {
        safe_practices();
    } catch (const std::exception& e) {
        std::cerr << "异常: " << e.what() << std::endl;
    }
}
```

### 11. 未定义行为详解（分类展开）

未定义行为（Undefined Behavior，简称 UB）是 C/C++ 中最令人困惑也最危险的概念。程序出现 UB 后，编译器可以合法地做任何事情——包括产生看似正确的结果、崩溃、或者更糟糕的，看似正确但实际有隐患的结果。

#### 1. 什么是未定义行为？

C++ 标准规定了程序的合法行为。当程序违反了某些规则时，标准说这种行为是"未定义的"，意味着：

- 编译器不需要报错
- 运行结果不可预测
- 编译器可以假设 UB 不会发生（用于优化）

```
未定义行为 ≠ 未指定行为 ≠ 实现定义行为

未定义行为（UB）：完全不可预测，什么都可能发生
未指定行为：有几种可能的结果，但不确定是哪种
实现定义行为：由编译器决定，但必须文档化
```

#### 2. 为什么 UB 如此危险？

##### 编译器优化与 UB

编译器可以假设程序不会出现 UB，并据此进行优化：

```cpp
// ❌ 危险：编译器可能删除整个检查
int* p = getPointer();
if (p != nullptr) {
    // 编译器推理：如果 p 是 nullptr，解引用 *p 是 UB
    // 既然 UB 不会发生，p 一定不是 nullptr
    // 所以这个 if 检查是多余的，可以删除
}
int x = *p;  // 编译器假设 p 不为空
```

```cpp
// ❌ 危险：编译器可能优化掉溢出检查
int checkOverflow(int x) {
    if (x + 100 < x) {  // 有符号溢出是 UB
        return 1;  // 编译器可能删除这个分支
    }
    return 0;
}
// GCC -O2 可能直接返回 0，因为"有符号溢出不会发生"
```

#### 3. 常见未定义行为分类

##### 1. 使用已释放的内存（Use After Free）

```cpp
// ❌ UB：访问已释放的内存
int* p = new int(42);
delete p;
std::cout << *p << std::endl;  // UB！可能打印 42，可能崩溃，可能打印垃圾值

// ❌ UB：更隐蔽的场景
std::vector<int> v = {1, 2, 3};
int& ref = v[0];
v.push_back(4);  // 可能导致重新分配
ref = 10;        // UB！ref 可能指向已释放的内存
```

##### 2. 有符号整数溢出

```cpp
// ❌ UB：有符号整数溢出
int x = INT_MAX;
int y = x + 1;  // UB！有符号溢出

int a = INT_MIN;
int b = a - 1;  // UB！

// ✅ 正确：使用无符号整数（溢出是定义良好的，会回绕）
unsigned int x = UINT_MAX;
unsigned int y = x + 1;  // 定义良好，y = 0

// ✅ 正确：检查溢出
int safeAdd(int a, int b) {
    if (b > 0 && a > INT_MAX - b) throw std::overflow_error("overflow");
    if (b < 0 && a < INT_MIN - b) throw std::overflow_error("underflow");
    return a + b;
}
```

##### 3. 空指针解引用

```cpp
// ❌ UB：解引用空指针
int* p = nullptr;
*p = 10;  // UB！通常段错误，但不保证

// ❌ UB：对空指针的引用
int& ref = *((int*)nullptr);  // UB！
ref = 10;  // UB！

// ✅ 正确：检查空指针
if (p != nullptr) {
    *p = 10;
}
```

##### 4. 读取未初始化的变量

```cpp
// ❌ UB：读取未初始化的变量
int x;
std::cout << x << std::endl;  // UB！值不确定

// ❌ UB：未初始化的指针
int* p;
*p = 10;  // UB！p 指向随机地址

// ❌ UB：分支中未初始化
int y;
if (someCondition) {
    y = 10;
}
std::cout << y << std::endl;  // 如果 someCondition 为 false，UB！

// ✅ 正确：始终初始化
int x = 0;
int* p = nullptr;
int y = 0;
```

##### 5. 数组越界访问

```cpp
// ❌ UB：数组越界
int arr[5] = {1, 2, 3, 4, 5};
int x = arr[10];  // UB！
arr[-1] = 0;      // UB！

// ❌ UB：指针算术越界
int* p = arr + 5;  // 可以指向 arr[5]（past-the-end），但不能解引用
int val = *p;       // UB！解引用 past-the-end 指针

// ✅ 正确：检查边界
if (index >= 0 && index < 5) {
    int x = arr[index];
}
```

##### 6. 数据竞争（Data Race）

```cpp
// ❌ UB：多线程同时读写同一变量
int counter = 0;

// 线程 1
counter++;  // 读-改-写，不是原子操作

// 线程 2
counter++;  // 数据竞争！UB！

// ✅ 正确：使用 mutex
std::mutex mtx;
int counter = 0;

// 线程 1
{
    std::lock_guard<std::mutex> lock(mtx);
    counter++;
}

// ✅ 正确：使用原子操作
std::atomic<int> counter(0);
counter++;  // 原子操作，无数据竞争
```

##### 7. 修改字符串字面量

```cpp
// ❌ UB：修改字符串字面量
char* s = "hello";
s[0] = 'H';  // UB！字符串字面量存储在只读区域

// ✅ 正确：使用字符数组（可修改的副本）
char s[] = "hello";  // 在栈上创建副本
s[0] = 'H';  // OK

// ✅ 正确：使用 std::string
std::string s = "hello";
s[0] = 'H';  // OK
```

##### 8. 多次 `delete`（Double Free）

```cpp
// ❌ UB：双重释放
int* p = new int(42);
delete p;
delete p;  // UB！可能导致堆损坏

// ✅ 正确：释放后置空
delete p;
p = nullptr;  // delete nullptr 是安全的（什么都不做）
delete p;     // OK，删除空指针是 no-op

// ✅ 更好：使用智能指针
auto p = std::make_unique<int>(42);
// 自动释放，不可能双重 delete
```

##### 9. 返回局部变量的引用/指针

```cpp
// ❌ UB：返回局部变量的引用
int& getRef() {
    int x = 42;
    return x;  // UB！x 在函数返回后销毁
}

// ❌ UB：返回局部变量的指针
int* getPtr() {
    int x = 42;
    return &x;  // UB！
}

// ✅ 正确：返回值
int getValue() {
    int x = 42;
    return x;  // OK，返回值的副本
}

// ✅ 正确：使用堆分配
int* getPtr() {
    return new int(42);  // OK，但调用者负责 delete
}
```

##### 10. 错误类型的 `delete`

```cpp
// ❌ UB：通过基类指针删除派生类对象（非虚析构）
class Base { ~Base() {} };
class Derived : public Base { int* data; ~Derived() { delete data; } };

Base* p = new Derived();
delete p;  // UB！不调用 Derived 析构函数

// ✅ 正确：基类使用虚析构函数
class Base { public: virtual ~Base() {} };
```

##### 11. 移位操作超出范围

```cpp
// ❌ UB：移位位数超过类型宽度
int x = 1;
int y = x << 32;  // UB！int 通常是 32 位，移 32 位未定义
int z = x << -1;  // UB！负数移位未定义

// ❌ UB：对负数左移
int a = -1;
int b = a << 1;  // UB！对负值左移未定义

// ✅ 正确
unsigned int x = 1;
unsigned int y = x << 31;  // OK，无符号移位 0-31 都定义良好
```

##### 12. 除以零

```cpp
// ❌ UB：整数除以零
int x = 10 / 0;    // UB！
int y = 10 % 0;    // UB！

// 注意：浮点除以零不是 UB，结果是 inf 或 nan
double z = 10.0 / 0.0;  // z = inf（IEEE 754 定义）
```

#### 4. UB 的"有趣"表现

UB 不一定导致崩溃，它可能：

| 表现 | 示例 |
|------|------|
| 看似正常工作 | 使用已释放的内存恰好没被覆盖 |
| 崩溃 | 空指针解引用 |
| 结果不确定 | 未初始化变量每次运行值不同 |
| 编译器删除代码 | 基于UB不会发生的假设优化掉代码 |
| 时间旅行 | 编译器重排指令，UB 似乎影响了之前的代码 |
| 鼻子恶魔 | 理论上，UB 可以让程序做任何事（包括让鼻子飞出恶魔） |

#### 5. 检测 UB 的工具

| 工具 | 检测的 UB | 使用方法 |
|------|----------|---------|
| **UBSanitizer** | 多种 UB | `g++ -fsanitize=undefined -g main.cpp` |
| **AddressSanitizer** | 内存相关 UB | `g++ -fsanitize=address -g main.cpp` |
| **ThreadSanitizer** | 数据竞争 | `g++ -fsanitize=thread -g main.cpp` |
| **Valgrind** | 内存错误 | `valgrind ./program` |
| **clang-tidy** | 静态分析 | `clang-tidy main.cpp -- -std=c++17` |
| **Cppcheck** | 静态分析 | `cppcheck --enable=all main.cpp` |

##### UBSanitizer 示例

```bash
# 编译
g++ -fsanitize=undefined -g -fno-omit-frame-pointer main.cpp -o main

# 运行
./main

# 检测到 UB 时的输出：
# main.cpp:10:5: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
```

#### 6. 预防 UB 的最佳实践

1. **始终初始化变量** — 消除未初始化读取
2. **检查指针** — 解引用前确认非空
3. **检查数组边界** — 使用 `at()` 或手动检查
4. **使用无符号类型** — 避免有符号溢出 UB
5. **使用智能指针** — 避免使用后释放和双重释放
6. **使用原子操作** — 避免数据竞争
7. **基类虚析构** — 避免通过基类删除的问题
8. **开启 Sanitizer** — 开发和测试时使用
9. **开启编译器警告** — `-Wall -Wextra -Wpedantic`
10. **静态分析** — 集成 `clang-tidy` 到 CI 流程

### 12. 极简总结

**UB = 标准不管 → 编译器任意发挥 → 可能崩溃/看似正常/优化掉代码 → 必须避免 → ASan+UBSan检测 → 严格别名 → 先序于规则 → 编译警告即错误**
