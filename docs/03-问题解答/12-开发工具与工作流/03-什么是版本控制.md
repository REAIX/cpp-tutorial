# 什么是版本控制

## 一个生活类比

你写毕业论文，第一稿存了"论文.docx"，改了几版后变成"论文_修改1.docx"、"论文_修改2.docx"、"论文_最终版.docx"、"论文_最终版2.docx"、"论文_打死不改版.docx"……最后你完全分不清哪个是哪个，也不知道哪次改了什么。

**版本控制系统就是帮你管理这些"版本"的智能助手。** 它记录每次修改的内容、时间、作者，还能随时回到任意历史版本，多人协作时还能自动合并修改。

## 为什么版本控制很重要

### 没有版本控制的痛苦

- 代码改坏了，不知道怎么恢复
- 多人修改同一文件，手动合并冲突
- 不知道某个功能是谁、什么时候改的
- 电脑坏了，代码全丢了
- 想尝试新方案，怕改坏了回不来

### 有版本控制的好处

- 随时回退到任意历史版本
- 多人协作互不干扰
- 完整的修改历史记录
- 远程备份，不怕丢代码
- 自由实验，随时可以撤销

## Git：当今最流行的版本控制系统

`Git` 由 `Linux` 之父 `Linus Torvalds` 在2005年创建，是目前最主流的版本控制工具。

### Git 的核心概念

| 概念 | 说明 | 类比 |
|------|------|------|
| 仓库（Repository） | 存储项目及其历史的数据库 | 一个项目的档案柜 |
| 提交（Commit） | 一次修改的快照 | 档案柜里的一份归档文件 |
| 分支（Branch） | 独立的开发线 | 一条平行时间线 |
| 暂存区（Staging Area） | 准备提交的文件列表 | 整理好准备归档的文件 |
| 远程仓库（Remote） | 网络上的仓库副本 | 异地备份的档案柜 |

### Git 基本工作流

```
工作目录 → git add → 暂存区 → git commit → 本地仓库 → git push → 远程仓库
                                                                    ↓
工作目录 ← git pull ← 本地仓库 ← git fetch ← 远程仓库
```

## Git 基础操作

### 初始化仓库

```bash
# 在当前目录创建新仓库
git init

# 或者克隆远程仓库
git clone https://github.com/user/project.git
```

### 日常三步曲：add → commit → push

```bash
# 1. 查看哪些文件被修改了
git status

# 2. 将修改的文件加入暂存区
git add main.cpp          # 添加单个文件
git add .                 # 添加所有修改

# 3. 提交到本地仓库
git commit -m "修复了计算器除零崩溃的bug"

# 4. 推送到远程仓库
git push
```

### 查看历史

```bash
# 查看提交历史
git log
git log --oneline         # 简洁模式

# 查看某次提交的详细修改
git show abc1234

# 查看当前修改的内容
git diff
```

### 拉取更新

```bash
# 拉取并合并远程更新
git pull

# 仅拉取不合并（更安全）
git fetch
git merge origin/main
```

## 分支：并行开发的利器

分支是 `Git` 最强大的功能之一。想象你在写一本书，突然想尝试一种新的叙事方式，但又怕改坏了原来的内容——你可以复印一份，在副本上大胆尝试，满意了再合并回去。

```bash
# 创建并切换到新分支
git checkout -b feature/login

# 在新分支上开发...
git add .
git commit -m "添加登录功能"

# 切回主分支
git checkout main

# 合并新分支
git merge feature/login

# 删除已合并的分支
git branch -d feature/login
```

### 常见分支策略

| 分支 | 用途 | 示例 |
|------|------|------|
| `main` / `master` | 稳定版本，随时可发布 | 生产环境代码 |
| `develop` | 开发主线 | 日常开发集成 |
| `feature/*` | 新功能 | `feature/user-auth` |
| `hotfix/*` | 紧急修复 | `hotfix/crash-fix` |
| `release/*` | 发布准备 | `release/v1.2` |

## GitHub 与 GitLab

`Git` 是版本控制工具，`GitHub` 和 `GitLab` 是基于 `Git` 的代码托管平台——你可以理解为"存代码的云盘+社交平台"。

| 平台 | 特点 | 适合 |
|------|------|------|
| `GitHub` | 全球最大，开源社区活跃 | 开源项目、个人作品集 |
| `GitLab` | 可自建服务器，CI/CD集成好 | 企业内部项目 |
| `Gitee`（码云） | 国内访问快，中文友好 | 国内团队协作 |

## C/C++ 项目的 .gitignore

`.gitignore` 文件告诉 `Git` 哪些文件不需要版本控制：

```gitignore
# 编译产物
*.o
*.obj
*.exe
*.out
*.app

# 构建目录
build/
cmake-build-*/

# IDE 文件
.vscode/
.idea/
*.swp
*.swo
*~

# 系统文件
.DS_Store
Thumbs.db

# 依赖目录
vcpkg_installed/
conan/
```

**为什么要 `.gitignore`？** 编译产物和IDE配置是本地生成的，每个人环境不同，不应该提交到仓库。而且二进制文件会让仓库体积暴增。

## 常见问题

### "commit message 怎么写？"

好的提交信息应该简洁明了地说明"做了什么"：

```bash
# 好的写法
git commit -m "修复计算器除零崩溃问题"
git commit -m "添加用户登录功能"

# 不好的写法
git commit -m "修改"
git commit -m "fix"
git commit -m "更新了一些东西"
```

### "代码改坏了怎么办？"

```bash
# 撤销工作区的修改（未add）
git checkout -- main.cpp

# 撤销暂存（已add，未commit）
git reset HEAD main.cpp

# 回退到上一次提交（已commit）
git reset --hard HEAD~1
```

> ⚠️ `git reset --hard` 会丢失未提交的修改，慎用！

### "合并冲突了怎么办？"

当两个人修改了同一行代码时，`Git` 无法自动合并，会产生冲突：

```
<<<<<<< HEAD
int result = a / b;  // 你的修改
=======
int result = b == 0 ? 0 : a / b;  // 别人的修改
>>>>>>> feature/safe-div
```

解决方法：手动选择保留哪个版本（或合并两者），然后：

```bash
git add main.cpp
git commit -m "解决除法运算的合并冲突"
```

## 初学者的 Git 工作流建议

1. 每天开始工作前：`git pull`
2. 写完一个小功能：`git add` + `git commit`
3. 一天工作结束：`git push`
4. 做实验性修改：先建分支
5. 提交信息写清楚做了什么

## 总结

版本控制不是可选项，而是现代软件开发的**基础设施**。就像你不会不用"保存"功能一样，你也不应该不用版本控制。

初学者至少要掌握：`init`、`add`、`commit`、`push`、`pull`、`log` 这六个命令。先养成"频繁提交"的习惯，其他高级功能在实践中自然学会。
