# 什么是链接器与加载器
> 📖 相关章节：[编译与链接](../../01-C语言/17-编译与链接.md)、[编译器原理](../../10-编译器与工具链开发/00-编译器原理概述.md)

> "要点直击：链接器把多个目标文件合并为一个可执行文件，解决符号引用和地址重定位；加载器把可执行文件从磁盘加载到内存并启动执行，动态链接在运行时才解析符号——理解链接和加载，就理解了程序从源代码到运行的最后一公里。"

***

## 1. 链接器的工作原理

### 1. 为什么需要链接器

```
问题：一个大型程序由多个源文件组成

  main.cpp    → 编译 → main.o
  utils.cpp   → 编译 → utils.o
  network.cpp → 编译 → network.o
  ...

每个.o文件独立编译，但它们之间有引用关系：
  main.o 调用了 utils.o 中的 readConfig()
  main.o 调用了 network.o 中的 connectServer()

问题：
  └── main.o编译时不知道readConfig()的地址
  └── 每个函数调用留下一个"空洞"等待填充
  └── 链接器负责填充这些"空洞"

链接器的职责：
  ├── 符号解析 — 找到每个符号的定义
  ├── 地址分配 — 给每个段分配虚拟地址
  ├── 重定位   — 填充所有"空洞"（地址引用）
  └── 输出     — 生成可执行文件或共享库
```

### 2. 链接的两种方式

```
静态链接（Static Linking）：
  ┌──────┐  ┌──────┐  ┌──────┐
  │main.o│  │utils.o│  │libc.a│
  └──┬───┘  └──┬───┘  └──┬───┘
     │         │         │
     └────┬────┴────┬────┘
          │  静态    │
          │  链接器  │
          ▼         ▼
     ┌──────────────────┐
     │   可执行文件       │  ← 所有代码都在一个文件中
     │  (包含libc的副本)  │
     └──────────────────┘

动态链接（Dynamic Linking）：
  ┌──────┐  ┌──────┐
  │main.o│  │utils.o│
  └──┬───┘  └──┬───┘
     │  动态    │
     │  链接器  │
     ▼         ▼
  ┌──────────────┐     ┌──────────┐
  │ 可执行文件    │ ──→ │ libc.so  │  ← 运行时才加载
  │ (不含libc)   │     └──────────┘
  └──────────────┘

对比：
  ┌──────────────┬──────────────┬──────────────┐
  │ 维度          │ 静态链接      │ 动态链接      │
  │ ────────────┼─────────────┼───────────── │
  │ 可执行文件大小│ 大            │ 小            │
  │ 启动速度     │ 快            │ 稍慢          │
  │ 内存使用     │ 多(每个进程一份)│ 少(共享一份)  │
  │ 更新库       │ 需重新编译     │ 替换.so即可   │
  │ 兼容性       │ 好            │ 需要ABI兼容   │
  └──────────────┴──────────────┴──────────────┘
```

### 3. 链接器的详细工作流程

```
步骤1：符号解析（Symbol Resolution）
  └── 扫描所有目标文件的符号表
  └── 强符号：函数和已初始化的全局变量
  └── 弱符号：未初始化的全局变量、__attribute__((weak))
  └── 规则：
      ├── 不允许两个强符号同名
      ├── 一个强符号+多个弱符号 → 选强符号
      └── 多个弱符号 → 选任意一个

步骤2：地址分配（Section Merging & Allocation）
  └── 合并相同类型的段
  │   main.o的.text + utils.o的.text → 可执行文件的.text
  │   main.o的.data + utils.o的.data → 可执行文件的.data
  └── 为每个段分配虚拟地址
      .text → 0x400000
      .data → 0x600000
      .bss  → 0x601000

步骤3：重定位（Relocation）
  └── 遍历所有重定位条目
  └── 根据符号的实际地址修改代码中的引用
  └── 例如：call 0x000000 → call 0x401234

步骤4：输出可执行文件
  └── 写入ELF/PE/Mach-O格式
  └── 包含程序头、段头、代码、数据等
```

## 2. 符号解析与重定位

### 1. 符号表

```
每个目标文件都有一个符号表，记录：

  符号名    类型      绑定     段       偏移     大小
  ────────┼────────┼───────┼───────┼───────┼─────
  main    | FUNC    | GLOBAL | .text  | 0x0000 | 64
  readCfg | FUNC    | GLOBAL | .text  | 0x0040 | 128
  counter | OBJECT  | GLOBAL | .data  | 0x0000 | 4
  buffer  | OBJECT  | GLOBAL | .bss   | 0x0000 | 1024
  helper  | FUNC    | LOCAL  | .text  | 0x00c0 | 32

符号类型：
  ├── FUNC   — 函数
  ├── OBJECT — 变量
  ├── SECTION — 段名
  └── FILE   — 源文件名

符号绑定：
  ├── LOCAL  — 局部符号（文件内可见）
  ├── GLOBAL — 全局符号（所有文件可见）
  └── WEAK   — 弱符号（可被同名强符号覆盖）
```

```bash
# 查看符号表
nm main.o
nm -C main.o            # C++名称还原
readelf -s main.o       # ELF格式详细信息
objdump -t main.o       # 通用格式
```

### 2. 重定位

```
重定位 = 修改代码中的地址引用

编译时留下的"空洞"：
  // main.o中的代码（未链接）
  call 0x00000000    ; 调用readConfig，地址待定
  movl $0x00000000, %eax  ; 引用counter变量，地址待定

链接后填充实际地址：
  call 0x00401040    ; readConfig的实际地址
  movl $0x00601000, %eax  ; counter的实际地址

重定位条目：
  偏移      类型            符号        加数
  0x0012   R_X86_64_PC32  readConfig   -4
  0x0018   R_X86_64_PC32  counter      -4

重定位类型：
  ├── R_X86_64_PC32   — 32位PC相对地址
  ├── R_X86_64_PLT32  — 通过PLT的调用
  ├── R_X86_64_32     — 32位绝对地址
  ├── R_X86_64_64     — 64位绝对地址
  └── R_X86_64_GOTPCREL — 通过GOT的引用
```

### 3. 重定位的计算

```
PC相对重定位的计算公式：
  S + A - P

  S = 符号的实际地址（Symbol value）
  A = 加数（Addend，通常为-4）
  P = 被修改位置的实际地址（Place）

示例：
  假设：
    readConfig的地址 S = 0x401040
    加数 A = -4
    call指令的位置 P = 0x401012

  重定位值 = S + A - P
           = 0x401040 + (-4) - 0x401012
           = 0x2A

  所以call指令变为：call 0x2A（相对偏移）
  执行时：PC + 0x2A = 0x401012 + 5 + 0x2A = 0x401040 ✓
  （+5是因为call指令本身5字节）
```

## 3. 动态链接机制

### 1. 动态链接的流程

```
动态链接的完整流程：

1. 编译时
   clang -fPIC -shared -o libutils.so utils.cpp
   clang -c main.cpp
   clang main.o -lutils -o main

2. 链接时（静态部分）
   └── 记录main依赖libutils.so
   └── 对libutils.so中的符号创建PLT/GOT条目
   └── 不解析符号的实际地址

3. 加载时（动态部分）
   └── 加载器读取可执行文件的DT_NEEDED条目
   └── 加载libutils.so到内存
   └── 动态链接器(ld-linux.so)解析符号
   └── 填充GOT表

4. 运行时
   └── 首次调用通过PLT→GOT→动态链接器
   └── 后续调用直接通过GOT跳转
```

### 2. 位置无关代码（PIC）

```
PIC（Position Independent Code）= 不依赖绝对地址的代码

为什么需要PIC：
  └── 共享库可能被加载到任意地址
  └── ASLR每次加载地址不同
  └── 代码不能包含绝对地址

PIC的实现方式：
  ├── 通过GOT访问全局变量 — 间接寻址
  ├── 通过PLT调用函数     — 间接跳转
  └── 使用PC相对寻址      — 相对偏移

编译PIC：
  clang -fPIC -shared -o libutils.so utils.cpp

  -fPIC  — 生成位置无关代码
  -fpic  — 生成位置无关代码（更小的GOT，有限制）
```

### 3. 动态链接库的版本管理

```
SO-NAME版本管理：
  libutils.so → libutils.so.1 → libutils.so.1.2.3
  └── libutils.so      — 开发时链接的名字
  └── libutils.so.1    — SO-NAME，主版本号
  └── libutils.so.1.2.3 — 完整版本号

版本规则：
  ├── 主版本号变化 — ABI不兼容，需重新编译
  ├── 次版本号变化 — 新增接口，向后兼容
  └── 补丁号变化   — Bug修复，完全兼容

符号版本：
  ├── 允许同一个.so中存在同一函数的多个版本
  └── 新版本可以与旧版本共存
  └── 例如：glibc的memcpy@GLIBC_2.2.5和memcpy@GLIBC_2.14
```

## 4. 加载器的工作流程

### 1. Linux下的程序加载

```
execve()系统调用触发加载：

步骤1：读取ELF头
  └── 检查魔数（0x7f 'E' 'L' 'F'）
  └── 确定文件类型（可执行/共享库）
  └── 找到程序头表（Program Header Table）

步骤2：映射段到内存
  └── 遍历程序头表中的LOAD段
  └── 为每个段分配虚拟地址空间
  └── 将文件内容映射到内存（mmap）
  └── .text段：可读可执行
  └── .data段：可读可写
  └── .bss段：只分配空间，清零

步骤3：设置栈和堆
  └── 分配栈空间（通常8MB）
  └── 压入命令行参数和环境变量
  └── 分配堆空间（初始为空，按需扩展）

步骤4：动态链接
  └── 检查PT_INTERP段，找到动态链接器
  └── 加载ld-linux-x86-64.so.2
  └── 动态链接器加载所有依赖的共享库
  └── 解析符号，填充GOT
  └── 执行初始化函数（.init_array）

步骤5：跳转入口点
  └── 跳转到ELF头中指定的入口点（e_entry）
  └── 通常是_start → __libc_start_main → main()
```

### 2. Windows下的程序加载

```
Windows PE加载流程：

步骤1：CreateProcess
  └── 打开.exe文件
  └── 创建进程对象和主线程

步骤2：映射PE文件
  └── 读取PE头
  └── 以ImageBase为基址映射各节
  └── 如果基址被占用，执行重定位

步骤3：加载DLL
  └── 遍历导入表（Import Table）
  └── 加载每个依赖的DLL
  └── 解析导入函数地址

步骤4：重定位和修复
  └── 如果加载地址与ImageBase不同，执行基址重定位
  └── 填充IAT（Import Address Table）

步骤5：执行
  └── 调用DllMain（每个DLL的初始化）
  └── 跳转到入口点
```

### 3. 进程的内存布局

```
Linux进程的虚拟内存布局（典型）：

  高地址
  ┌──────────────────┐ 0xFFFFFFFFFFFFFFFF
  │ 内核空间          │ （无法直接访问）
  ├──────────────────┤ 0x7FFFFFFFFFFF
  │ 栈（向下增长）     │
  │                  │
  │                  │
  │ 共享库映射区      │ ← libc.so, libstdc++.so等
  │                  │
  │                  │
  │ 堆（向上增长）     │
  ├──────────────────┤
  │ BSS段（未初始化）  │
  │ Data段（已初始化） │
  │ Text段（代码）     │
  ├──────────────────┤ 0x400000
  │ 不可访问区域      │
  └──────────────────┘ 0x0

查看进程内存映射：
  cat /proc/PID/maps
  pmap PID
```

## 5. PLT/GOT详解

### 1. PLT/GOT的结构

```
PLT（Procedure Linkage Table）— 过程链接表
  └── 代码段中的一段跳板代码
  └── 每个外部函数一个条目

GOT（Global Offset Table）— 全局偏移表
  └── 数据段中的一个地址数组
  └── 每个外部符号一个条目

结构示意：
  .plt段（代码）：
    PLT[0]:  特殊条目，跳到动态链接器
    PLT[1]:  printf@plt
    PLT[2]:  malloc@plt
    PLT[3]:  strlen@plt

  .got.plt段（数据）：
    GOT[0]:  .dynamic的地址
    GOT[1]:  link_map的地址
    GOT[2]:  _dl_runtime_resolve的地址
    GOT[3]:  printf的实际地址（初始为PLT[1]下一条指令）
    GOT[4]:  malloc的实际地址
    GOT[5]:  strlen的实际地址
```

### 2. 延迟绑定的完整过程

```
第一次调用printf的完整过程：

1. 程序执行 call printf
   → 跳转到 PLT[1]（printf@plt）

2. PLT[1]执行：
   jmp *GOT[3]     → GOT[3]初始值指向PLT[1]下一条指令
   push $0          → 压入符号索引0（printf在.rel.plt中的索引）
   jmp PLT[0]       → 跳到PLT[0]

3. PLT[0]执行：
   push GOT[1]      → 压入link_map
   jmp *GOT[2]      → 跳到_dl_runtime_resolve

4. _dl_runtime_resolve执行：
   ├── 根据link_map和符号索引查找printf的实际地址
   ├── 将实际地址写入GOT[3]
   └── 跳转到printf的实际地址

5. 后续调用printf：
   jmp *GOT[3]     → GOT[3]已是实际地址，直接跳转
```

### 3. 用GDB观察PLT/GOT

```bash
# 编译带调试信息的程序
gcc -g -no-pie -o main main.c

# GDB调试
gdb ./main

# 查看PLT
(gdb) disassemble printf@plt

# 查看GOT
(gdb) x/gx &printf@GOT

# 在调用前后观察GOT变化
(gdb) break main
(gdb) run
(gdb) x/gx &printf@GOT     # 调用前：指向PLT
(gdb) step
(gdb) x/gx &printf@GOT     # 调用后：指向实际地址
```

### 4. PLT/GOT的安全问题

```
GOT覆写攻击：
  └── 缓冲区溢出 → 覆盖GOT中的函数地址
  └── 下次调用该函数时跳转到攻击者代码

RELRO防护：
  ├── No RELRO    — GOT完全可写（不安全）
  ├── Partial RELRO — GOT[0-2]只读，其余可写（默认）
  └── Full RELRO  — 启动时解析所有符号，整个GOT只读

  # 编译选项
  gcc -z norelro main.c    # 无RELRO
  gcc -z lazy main.c       # 部分RELRO（默认）
  gcc -z now main.c        # 完全RELRO

  # 检查RELRO状态
  readelf -d main | grep RELRO
  readelf -l main | grep GNU_RELRO
```

## 6. 常用工具

```bash
# 查看ELF文件信息
readelf -h main          # ELF头
readelf -l main          # 程序头
readelf -S main          # 段头
readelf -s main          # 符号表
readelf -r main          # 重定位表
readelf -d main          # 动态段

# 查看依赖
ldd main                 # 查看动态库依赖
ldtree main              # 递归查看依赖树

# 反汇编
objdump -d main          # 反汇编
objdump -d -j .plt main  # 只反汇编PLT段

# 符号操作
nm main                  # 列出符号
nm -D main               # 列出动态符号
nm -C main               # C++名称还原

# 去除符号
strip main               # 去除所有符号
strip --strip-unneeded main  # 去除不需要的符号

# 动态库操作
ldconfig                 # 更新共享库缓存
ldconfig -p              # 查看缓存中的库
```

## 7. 极简总结

| 概念 | 一句话 |
|------|--------|
| 链接器 | 合并目标文件——符号解析+重定位 |
| 静态链接 | 所有代码打包——大但独立 |
| 动态链接 | 运行时加载——小但依赖.so |
| 符号解析 | 找到符号定义——强符号优先 |
| 重定位 | 填充地址引用——S+A-P |
| 加载器 | 磁盘→内存——映射段+动态链接 |
| PLT/GOT | 延迟绑定——首次调用才解析 |
| RELRO | GOT保护——Full RELRO最安全 |

**链接器 = 符号解析 + 重定位，加载器 = 映射 + 动态链接，PLT/GOT实现延迟绑定，RELRO保护GOT安全。**
