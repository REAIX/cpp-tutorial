## 1. 命名规范

### 1. 概念与定义

**编码规范（coding standard）**：C++中用于编写清晰、易读、可维护代码的规范。编码规范可以分为命名规范、代码格式、注释规范、函数规范、类规范等。例如命名规范用于规范代码的命名，代码格式用于规范代码的格式，注释规范用于规范代码的注释。

**命名规范（naming convention）**：C++中用于规范代码命名的规范。命名规范可以分为文件命名、类命名、函数命名、变量命名、常量命名、命名空间命名等。例如文件命名用于规范文件的命名，类命名用于规范类的命名，函数命名用于规范函数的命名。

**代码格式（code format）**：C++中用于规范代码格式的规范。代码格式可以分为缩进、行宽、空格、空行、换行等。例如缩进用于规范代码的缩进，行宽用于规范代码的行宽，空格用于规范代码的空格。

**注释规范（comment convention）**：C++中用于规范代码注释的规范。注释规范可以分为单行注释、多行注释、文档注释、Doxygen风格注释等。例如单行注释用于规范单行注释的格式，多行注释用于规范多行注释的格式，文档注释用于规范文档注释的格式。

**函数规范（function convention）**：C++中用于规范函数的规范。函数规范可以分为函数命名、函数参数、函数返回值、函数注释等。例如函数命名用于规范函数的命名，函数参数用于规范函数的参数，函数返回值用于规范函数的返回值。

**类规范（class convention）**：C++中用于规范类的规范。类规范可以分为类命名、类成员、类继承、类注释等。例如类命名用于规范类的命名，类成员用于规范类的成员，类继承用于规范类的继承。

### 2. 通用原则
- **可读性优先**：命名应该清晰表达含义
- **一致性**：整个项目使用统一的命名风格
- **避免缩写**：除非是广泛认可的缩写（如`URL`、`HTTP`）
- **避免歧义**：命名应该唯一，避免与其他标识符冲突

### 3. 文件命名
- **头文件**：使用`.h`或`.hpp`后缀，如`student.h`
- **源文件**：使用`.cpp`后缀，如`student.cpp`
- **命名风格**：小写字母，单词之间用下划线分隔，如`file_handler.cpp`

### 4. 类命名
- **风格**：大驼峰（PascalCase），如`Student`、`FileHandler`
- **避免前缀**：不要使用`C`或`T`作为类前缀
- **接口命名**：使用`I`前缀，如`IComparable`

### 5. 函数命名
- **风格**：小驼峰（camelCase），如`addStudent`、`getScore`
- **动词开头**：函数名应该以动词开头，如`calculateSum`、`printMessage`
- **避免缩写**：除非是广泛认可的缩写，如`init`、`calc`

### 6. 变量命名
- **风格**：小驼峰（camelCase），如`studentName`、`score`
- **名词开头**：变量名应该以名词开头，如`age`、`name`
- **避免缩写**：除非是广泛认可的缩写，如`idx`、`len`

### 7. 常量命名
- **风格**：全大写，单词之间用下划线分隔，如`MAX_SIZE`、`PI`
- **前缀**：使用`k`前缀，如`kMaxSize`、`kPi`

### 8. 命名空间命名
- **风格**：小写字母，单词之间用下划线分隔，如`my_lib`
- **避免缩写**：除非是广泛认可的缩写，如`std`、`boost`

## 2. 代码格式

### 1. 缩进
- **风格**：使用4个空格缩进，不要使用制表符
- **一致性**：整个项目使用统一的缩进风格

### 2. 行宽
- **最大行宽**：120个字符
- **换行**：超过最大行宽时换行，换行时对齐到合适的位置

### 3. 空格
- **运算符两侧**：添加空格，如`a + b`、`c = d`
- **逗号后面**：添加空格，如`func(a, b, c)`
- **括号两侧**：不要添加空格，如`func(a, b)`、`if (condition)`
- **大括号**：左大括号不换行，右大括号换行，如：
```cpp
if (condition) {
    // 代码实现
} else {
    // 代码实现
}
```

### 4. 空行
- **函数之间**：添加一个空行
- **类成员之间**：添加一个空行
- **逻辑块之间**：添加一个空行

### 5. 换行
- **函数参数**：超过最大行宽时换行，每个参数占一行
- **条件语句**：复杂条件语句换行，每个条件占一行
- **表达式**：复杂表达式换行，每个子表达式占一行

## 3. 注释规范

### 1. 通用原则
- **简洁明了**：注释应该简洁，避免冗长
- **准确无误**：注释应该准确反映代码的功能
- **及时更新**：代码修改时，注释也要同步更新
- **适度适量**：不要过度注释，也不要注释不足

### 2. 文件注释
- **位置**：文件开头
- **内容**：文件说明、作者、创建日期、版本号等
- **格式**：Doxygen风格注释

### 3. 类注释
- **位置**：类定义之前
- **内容**：类说明、功能、设计思路等
- **格式**：Doxygen风格注释

### 4. 函数注释
- **位置**：函数定义之前
- **内容**：函数说明、参数、返回值、注意事项等
- **格式**：Doxygen风格注释

### 5. 变量注释
- **位置**：变量定义旁边或上方
- **内容**：变量说明、用途、限制条件等
- **格式**：单行注释

### 6. 代码块注释
- **位置**：代码块之前
- **内容**：代码块说明、功能、设计思路等
- **格式**：单行注释或多行注释

## 4. 函数规范

### 1. 函数设计
- **单一职责**：一个函数只做一件事
- **函数长度**：函数长度不超过50行
- **参数数量**：参数数量不超过5个
- **返回值**：返回值应该清晰表达含义，避免使用`int`作为返回值表示多种含义

### 2. 函数声明
- **位置**：头文件中声明函数
- **格式**：函数声明应该包含参数类型和名称
- **默认参数**：避免使用默认参数，除非是必要的

### 3. 函数实现
- **位置**：源文件中实现函数
- **格式**：函数实现应该包含详细的注释
- **错误处理**：函数应该处理错误，返回错误码或抛出异常

### 4. 函数调用
- **格式**：函数调用应该包含参数名称，提高可读性
- **参数顺序**：参数顺序应该合理，重要的参数放在前面

## 5. 类规范

### 1. 类设计
- **单一职责**：一个类只做一件事
- **类大小**：类大小不超过1000行
- **成员数量**：成员数量不超过20个
- **继承层次**：继承层次不超过3层

### 2. 类声明
- **位置**：头文件中声明类
- **格式**：类声明应该包含访问控制、成员变量、成员函数等
- **访问控制**：使用`public`、`protected`、`private`控制成员访问

### 3. 类实现
- **位置**：源文件中实现类的成员函数
- **格式**：类实现应该包含详细的注释
- **错误处理**：类的成员函数应该处理错误，返回错误码或抛出异常

### 4. 类使用
- **格式**：类使用应该包含详细的注释
- **内存管理**：类的对象应该使用智能指针管理内存
- **异常安全**：类的成员函数应该保证异常安全

## 6. 变量规范

### 1. 变量设计
- **单一职责**：一个变量只做一件事
- **变量类型**：选择合适的变量类型，避免使用`int`表示多种含义
- **变量初始化**：变量应该初始化，避免未初始化的变量
- **变量作用域**：变量作用域应该尽可能小

### 2. 变量声明
- **位置**：变量应该在使用之前声明
- **格式**：变量声明应该包含变量类型和名称
- **变量初始化**：变量应该在声明时初始化

### 3. 变量使用
- **格式**：变量使用应该包含详细的注释
- **变量修改**：变量修改应该有明确的意图
- **变量传递**：变量传递应该使用引用或指针，避免拷贝

## 7. 错误处理

### 1. 错误处理原则
- **尽早发现错误**：在错误发生时立即处理
- **错误信息清晰**：错误信息应该清晰表达错误原因
- **错误处理一致**：整个项目使用统一的错误处理风格
- **避免隐藏错误**：不要忽略错误，应该处理或传递错误

### 2. 错误处理方式
- **返回错误码**：使用`int`或`enum`表示错误码
- **抛出异常**：使用`throw`抛出异常，使用`try-catch`捕获异常
- **断言**：使用`assert`检查条件，用于调试阶段
- **日志**：使用日志记录错误信息

### 3. 错误处理最佳实践
- **避免使用`errno`**：`errno`不是线程安全的
- **避免使用`goto`**：`goto`会导致代码可读性降低
- **使用智能指针**：智能指针可以自动管理内存，避免内存泄漏
- **使用RAII**：RAII可以自动管理资源，避免资源泄漏

## 8. 性能规范

### 1. 性能优化原则
- **不要过早优化**：先保证代码正确性和可读性，再进行性能优化
- **测量，不要猜测**：使用性能分析工具找到性能瓶颈
- **优化有最大收益的部分**：80%的时间花在20%的代码上
- **保持代码可读性**：过度优化会降低可维护性

### 2. 性能优化方法
- **编译器优化**：使用合适的编译器优化级别
- **内存优化**：减少内存分配和拷贝，使用内存池
- **算法优化**：选择合适的算法和数据结构
- **缓存优化**：优化缓存命中率，减少缓存颠簸
- **并行优化**：使用多线程或并行计算

### 3. 性能优化最佳实践
- **避免不必要的计算**：缓存计算结果，避免重复计算
- **避免不必要的内存分配**：使用栈内存代替堆内存
- **避免不必要的拷贝**：使用移动语义代替拷贝
- **避免不必要的I/O**：减少I/O次数，使用缓冲区

---

## 9. 安全规范

### 1. 安全原则
- **输入验证**：验证所有输入，避免注入攻击
- **内存安全**：避免内存泄漏、缓冲区溢出、野指针等
- **线程安全**：避免竞态条件、死锁等
- **异常安全**：保证异常发生时资源不泄漏

### 2. 安全最佳实践
- **使用智能指针**：智能指针可以自动管理内存，避免内存泄漏
- **使用RAII**：RAII可以自动管理资源，避免资源泄漏
- **使用标准库**：标准库经过严格测试，安全性更高
- **避免使用裸指针**：裸指针容易导致内存泄漏和野指针
- **避免使用`goto`**：`goto`会导致代码可读性降低

## 10. 自动格式化与静态分析

### 1. 概念与定义

**clang-format**：LLVM/Clang项目提供的自动代码格式化工具，可根据配置文件自动调整代码风格，确保团队代码格式一致。

**clang-tidy**：LLVM/Clang项目提供的静态分析工具，可检查代码中的bug、风格问题和现代化改进建议，是C++代码质量保障的重要工具。

**静态分析（static analysis）**：在不运行代码的情况下，通过分析源代码来发现潜在问题的技术。静态分析可以检测出编译器无法发现的bug、风格问题和性能问题。

### 2. clang-format配置详解

#### 1. clang-format文件格式

`.clang-format`文件使用YAML格式，放置在项目根目录下。clang-format会从当前目录向上查找该文件，直到找到为止。

```yaml
# .clang-format 文件示例
# 基于 Google 风格进行定制
BasedOnStyle: Google
```

#### 2. 核心配置项详解

**BasedOnStyle**：指定基础风格，可选值如下：

| 值 | 说明 |
|---|---|
| `Google` | Google C++风格指南 |
| `LLVM` | LLVM项目风格（默认值） |
| `Mozilla` | Mozilla项目风格 |
| `Chromium` | Chromium项目风格 |
| `Microsoft` | 微软风格 |
| `WebKit` | WebKit项目风格 |

```yaml
# 基于 Google 风格，然后覆盖需要自定义的选项
BasedOnStyle: Google
```

**IndentWidth / TabWidth / UseTab**：控制缩进方式

```yaml
# 缩进宽度为4个空格
IndentWidth: 4
# 制表符宽度为4
TabWidth: 4
# 不使用制表符，使用空格
UseTab: Never
# 可选值：Never（从不）、Always（总是）、ForIndentation（仅缩进）、ForContinuationAndIndentation
```

**ColumnLimit**：行宽限制

```yaml
# 每行最大120个字符
ColumnLimit: 120
# 设为0表示不限制行宽
ColumnLimit: 0
```

**AllowShortFunctionsOnASingleLine**：短函数是否放在单行

```yaml
# 可选值：None（从不）、InlineOnly（仅内联函数）、Empty（仅空函数）、All（所有短函数）
AllowShortFunctionsOnASingleLine: Empty
```

**BreakBeforeBraces**：大括号风格

```yaml
# 可选值：Attach（K&R风格）、Linux、Allman、Stroustrup、Whitesmiths、GNU、WebKit、Custom
# Attach风格：左大括号跟在上一行
BreakBeforeBraces: Attach
# Allman风格：左大括号独占一行
# BreakBeforeBraces: Allman
```

各风格对比：

```cpp
// Attach 风格（K&R风格，Google/LLVM默认）
if (condition) {
    doSomething();
}

// Allman 风格
if (condition)
{
    doSomething();
}

// Linux 风格（函数定义用Allman，其他用Attach）
int main()
{
    if (condition) {
        doSomething();
    }
}

// Stroustrup 风格（函数和类用Attach，控制语句用Attach，但else前换行）
if (condition) {
    doSomething();
}
else {
    doSomethingElse();
}
```

**PointerAlignment**：指针对齐方式

```yaml
# 可选值：Left（左对齐）、Right（右对齐）、Middle（中间对齐）
PointerAlignment: Left
```

```cpp
// Left：指针符号靠近变量名
int* ptr;
const char* name;

// Right：指针符号靠近类型名
int *ptr;
const char *name;

// Middle：指针符号居中
int * ptr;
const char * name;
```

**SortIncludes**：头文件排序

```yaml
# 是否自动对 #include 排序
# 可选值：Never（从不）、CaseSensitive（区分大小写排序）、CaseInsensitive（不区分大小写排序）
SortIncludes: CaseSensitive
```

**AlignConsecutiveAssignments / AlignConsecutiveDeclarations**：连续赋值/声明对齐

```yaml
# 连续赋值语句对齐
AlignConsecutiveAssignments: true
# 连续声明语句对齐
AlignConsecutiveDeclarations: true
```

```cpp
// 开启对齐后
int    x     = 1;
double y     = 2.0;
float  z     = 3.0f;

// 关闭对齐
int x = 1;
double y = 2.0;
float z = 3.0f;
```

#### 3. 完整的.clang-format配置示例

```yaml
# 基于 Google 风格的完整配置示例
BasedOnStyle: Google

# 缩进设置
IndentWidth: 4
TabWidth: 4
UseTab: Never
AccessModifierOffset: -4    # 访问修饰符缩进偏移
IndentCaseLabels: false     # case标签不缩进
IndentCaseBlocks: false     # case块不缩进
NamespaceIndentation: None  # 命名空间内不缩进

# 行宽与换行
ColumnLimit: 120
AllowShortFunctionsOnASingleLine: Empty
AllowShortIfStatementsOnASingleLine: Never
AllowShortLoopsOnASingleLine: false
AllowShortEnumsOnASingleLine: true
AlwaysBreakTemplateDeclarations: Yes

# 大括号风格
BreakBeforeBraces: Attach
BraceWrapping:
  AfterCaseLabel: false
  AfterClass: false
  AfterControlStatement: Never
  AfterEnum: false
  AfterFunction: false
  AfterNamespace: false
  AfterStruct: false
  BeforeCatch: false
  BeforeElse: false
  IndentBraces: false

# 指针对齐
PointerAlignment: Left
DerivePointerAlignment: false

# 引用对齐
ReferenceAlignment: Left

# 头文件排序
SortIncludes: CaseSensitive
IncludeBlocks: Regroup     # 重新分组 #include 块

# 对齐
AlignConsecutiveAssignments: true
AlignConsecutiveDeclarations: true
AlignAfterOpenBracket: Align
AlignOperands: Align
AlignTrailingComments: true

# 空格
SpaceAfterCStyleCast: false
SpaceBeforeAssignmentOperators: true
SpaceBeforeParens: ControlStatements
SpacesInParentheses: false
SpacesInSquareBrackets: false

# 其他
BinPackArguments: false    # 函数参数不打包
BinPackParameters: false   # 函数声明参数不打包
AllowAllArgumentsOnNextLine: true
AllowAllParametersOfDeclarationOnNextLine: true
```

#### 4. 命令行用法

```bash
# 格式化单个文件（原地修改）
clang-format -i src/main.cpp

# 使用项目目录下的 .clang-format 文件
clang-format -i -style=file src/main.cpp

# 格式化整个项目的 .cpp 和 .h 文件
find src -name "*.cpp" -o -name "*.h" | xargs clang-format -i

# 仅查看格式化结果，不修改文件（输出到标准输出）
clang-format src/main.cpp

# 检查文件是否需要格式化（不修改，仅提示差异）
```

### 3. clang-tidy静态分析

#### 1. clang-tidy的作用

clang-tidy是一个基于Clang的C++"linter"工具，主要功能包括：

- **静态分析**：检测编译器无法发现的潜在bug
- **代码风格检查**：确保代码符合指定的编码规范
- **现代C++建议**：推荐使用C++11/14/17/20的新特性替代旧写法
- **性能优化建议**：发现可以改进性能的代码模式
- **可读性改进**：提高代码的可读性和可维护性

#### 2. clang-tidy配置文件格式

`.clang-tidy`文件同样使用YAML格式，放置在项目根目录下：

```yaml
Checks: 'modernize-*,bugprone-*'
WarningsAsErrors: ''
HeaderFilterRegex: '.*'
FormatStyle: file
```

#### 3. 常用检查组

**modernize-\***：现代化建议，推荐使用新标准特性

| 检查项 | 说明 |
|---|---|
| `modernize-use-auto` | 建议使用`auto`替代冗长的类型声明 |
| `modernize-use-nullptr` | 建议使用`nullptr`替代`NULL`或`0` |
| `modernize-use-override` | 建议使用`override`关键字 |
| `modernize-use-using` | 建议使用`using`替代`typedef` |
| `modernize-use-noexcept` | 建议使用`noexcept`替代`throw()` |
| `modernize-redundant-void-arg` | 移除多余的`void`参数 |
| `modernize-loop-convert` | 建议使用范围for循环 |
| `modernize-make-unique` | 建议使用`std::make_unique` |
| `modernize-make-shared` | 建议使用`std::make_shared` |
| `modernize-pass-by-value` | 建议按值传递+移动代替按const引用传递+拷贝 |
| `modernize-avoid-c-arrays` | 建议使用`std::array`替代C风格数组 |
| `modernize-use-emplace` | 建议使用`emplace_back`替代`push_back` |

```cpp
// modernize-use-auto 示例
// 修改前
std::map<std::string, int>::iterator it = m.find("key");
// 修改后
auto it = m.find("key");

// modernize-use-nullptr 示例
// 修改前
int* p = NULL;
// 修改后
int* p = nullptr;

// modernize-use-override 示例
// 修改前
class Derived : public Base {
    void foo();
};
// 修改后
class Derived : public Base {
    void foo() override;
};

// modernize-loop-convert 示例
// 修改前
for (std::vector<int>::iterator it = v.begin(); it != v.end(); ++it) {
    std::cout << *it;
}
// 修改后
for (const auto& elem : v) {
    std::cout << elem;
}
```

**bugprone-\***：常见bug检测

| 检查项 | 说明 |
|---|---|
| `bugprone-narrowing-conversions` | 检测窄化转换 |
| `bugprone-unchecked-iterator-access` | 检测未检查的迭代器访问 |
| `bugprone-suspicious-string-compare` | 检测可疑的字符串比较 |
| `bugprone-integer-division` | 检测整数除法导致的意外截断 |
| `bugprone-misplaced-widening-cast` | 检测放错位置的宽化转换 |
| `bugprone-assignment-in-if-condition` | 检测if条件中的赋值 |
| `bugprone-copy-constructor-init` | 检测拷贝构造函数未调用基类拷贝构造 |
| `bugprone-move-forwarding-reference` | 检测不正确的`std::move`使用 |
| `bugprone-easily-swappable-parameters` | 检测容易混淆的参数 |
| `bugprone-exception-escape` | 检测异常逃逸 |

```cpp
// bugprone-narrowing-conversions 示例
// 警告：double 到 int 的窄化转换
int x = 3.14;

// bugprone-suspicious-string-compare 示例
// 警告：应该使用 == 而非 strcmp
if (strcmp(a, b)) {  // 逻辑与直觉相反！
    // ...
}

// bugprone-assignment-in-if-condition 示例
// 警告：if条件中的赋值可能是笔误（应为 ==）

    // ...
}
```

**performance-\***：性能优化建议

| 检查项 | 说明 |
|---|---|
| `performance-move-const-arg` | 检测对const值的`std::move` |
| `performance-unnecessary-value-param` | 建议按const引用传递而非按值传递 |
| `performance-for-range-copy` | 检测范围for循环中不必要的拷贝 |
| `performance-implicit-conversion-in-loop` | 检测循环中的隐式转换 |
| `performance-inefficient-string-concatenation` | 检测低效的字符串拼接 |
| `performance-inefficient-algorithm` | 建议使用更高效的算法 |
| `performance-no-automatic-move` | 检测未触发的自动移动 |
| `performance-noexcept-move-constructor` | 建议移动构造函数加`noexcept` |
| `performance-type-promotion-in-math-fn` | 检测数学函数中的类型提升 |

```cpp
// performance-unnecessary-value-param 示例
// 修改前：按值传递，产生不必要的拷贝
void process(std::string data, int count);
// 修改后：按const引用传递
void process(const std::string& data, int count);

// performance-move-const-arg 示例
// 警告：对const值调用std::move无效
void foo(const std::string s) {
    bar(std::move(s));  // std::move对const无效，仍会拷贝
}

// performance-for-range-copy 示例
// 修改前：每个元素都拷贝
for (auto item : container) { ... }
// 修改后：使用const引用
for (const auto& item : container) { ... }
```

**readability-\***：可读性改进

| 检查项 | 说明 |
|---|---|
| `readability-identifier-naming` | 标识符命名规范检查 |
| `readability-function-size` | 函数大小限制检查 |
| `readability-magic-numbers` | 魔法数字检查 |
| `readability-redundant-access-specifiers` | 冗余访问修饰符检查 |
| `readability-simplify-boolean-expr` | 简化布尔表达式 |
| `readability-braces-around-statements` | 语句加大括号检查 |
| `readability-const-return-type` | const返回类型检查 |
| `readability-container-size-empty` | 建议使用`empty()`替代`size() == 0` |
| `readability-implicit-bool-conversion` | 隐式bool转换检查 |
| `readability-non-const-parameter` | 非const参数检查 |

```cpp
// readability-identifier-naming 示例（需配置命名规则）
// 可配置：类名用PascalCase，函数名用camelCase，变量名用lower_case
class my_class {};      // 警告：类名应为 PascalCase
class MyClass {};       // 正确

// readability-function-size 示例
// 可配置最大行数、最大参数数、最大语句数等
void hugeFunction() {
    // 超过配置的行数限制时发出警告
    // ...
}

// readability-container-size-empty 示例
// 修改前

// readability-magic-numbers 示例
// 警告：魔法数字
```

**cppcoreguidelines-\***：C++核心指南检查

| 检查项 | 说明 |
|---|---|
| `cppcoreguidelines-pro-type-reinterpret-cast` | 禁止使用`reinterpret_cast` |
| `cppcoreguidelines-pro-type-cstyle-cast` | 禁止使用C风格转换 |
| `cppcoreguidelines-pro-type-static-cast-downcast` | 禁止使用`static_cast`向下转型 |
| `cppcoreguidelines-pro-bounds-pointer-arithmetic` | 禁止指针算术运算 |
| `cppcoreguidelines-pro-bounds-constant-array-index` | 禁止非常量数组索引 |
| `cppcoreguidelines-avoid-magic-numbers` | 避免魔法数字 |
| `cppcoreguidelines-init-variables` | 变量必须初始化 |
| `cppcoreguidelines-prefer-member-initializer` | 优先使用成员初始化列表 |
| `cppcoreguidelines-special-member-functions` | 特殊成员函数规则（Rule of Five） |

```cpp
// cppcoreguidelines-init-variables 示例
// 警告：变量未初始化
int x;
// 建议：初始化变量
int x = 0;

// cppcoreguidelines-prefer-member-initializer 示例
// 修改前：构造函数体内赋值
class Foo {
    int val_;
public:
    Foo(int v) { val_ = v; }
};
// 修改后：使用成员初始化列表
class Foo {
    int val_;
public:
    Foo(int v) : val_(v) {}
};

// cppcoreguidelines-special-member-functions 示例
// 警告：定义了析构函数但未定义移动操作
class Bar {
public:
    ~Bar();
    // 缺少移动构造函数和移动赋值运算符
};
```

#### 6. 与CMake集成

在CMake中启用clang-tidy，可以在编译时自动运行静态分析：

```cmake
# 在 CMakeLists.txt 中配置
# 方法一：直接设置
set(CMAKE_CXX_CLANG_TIDY "clang-tidy;-p;${CMAKE_BINARY_DIR}")

# 方法二：带配置文件路径
set(CMAKE_CXX_CLANG_TIDY "clang-tidy;-p;${CMAKE_BINARY_DIR};--config-file=${CMAKE_SOURCE_DIR}/.clang-tidy")

# 方法三：条件启用（仅在开发者模式下启用）
option(ENABLE_CLANG_TIDY "启用 clang-tidy 静态分析" OFF)
if(ENABLE_CLANG_TIDY)
    find_program(CLANG_TIDY_EXE NAMES clang-tidy)
    if(CLANG_TIDY_EXE)
        set(CMAKE_CXX_CLANG_TIDY "${CLANG_TIDY_EXE};-p;${CMAKE_BINARY_DIR}")
        message(STATUS "已启用 clang-tidy: ${CLANG_TIDY_EXE}")
    else()
        message(WARNING "未找到 clang-tidy")
    endif()
endif()
```

```bash
# 使用 CMake 构建，启用 clang-tidy
cmake -B build -DENABLE_CLANG_TIDY=ON
cmake --build build
```

#### 7. 自动修复

### 4. 其他工具

#### 1. cppcheck（轻量级静态分析）

cppcheck是一个不依赖编译器的C/C++静态分析工具，专注于检测bug而非风格问题：

- 未初始化的变量

IWYU的常见建议：

```cpp
// IWYU 建议：移除未使用的头文件
```

#### 3. cpplint（Google风格检查）

cpplint是Google开发的C++风格检查工具，遵循Google C++风格指南：

```bash

cpplint src/*.cpp src/*.h

# 指定过滤规则
cpplint --filter=-legal/copyright,-build/header_guard src/

# 递归检查

# 输出为特定格式
```

常用过滤规则：

| 规则 | 说明 |

| `-build/include_order` | 忽略头文件顺序检查 |
| `-readability/streams` | 允许使用流（streams） |
| `-runtime/references` | 允许按非const引用传递 |
| `-whitespace/braces` | 忽略大括号空白检查 |

> **提示**：以上工具各有侧重，建议组合使用。clang-format负责格式化，clang-tidy负责深度静态分析和现代化建议，cppcheck作为补充静态分析，IWYU管理头文件依赖，cpplint用于Google风格合规检查。在实际项目中，通常clang-format + clang-tidy的组合已能满足大部分需求。

9. 安全规范：遵循安全原则，避免常见的安全漏洞
10. 自动格式化与静态分析：使用clang-format自动格式化，使用clang-tidy进行静态分析
11. 最佳实践：提高代码可读性、可维护性、可扩展性和可测试性

### 2. 最佳实践
1. 遵循编码规范，整个项目使用统一的风格
2. 先保证代码正确性和可读性，再进行性能优化
3. 使用性能分析工具找到性能瓶颈
4. 使用单元测试保证代码正确性
5. 使用版本控制系统管理代码
