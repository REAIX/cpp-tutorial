## 本章导读

代码审查是软件开发过程中的重要环节，它可以帮助我们发现代码中的问题，提高代码质量，促进团队成员之间的知识共享。本章将介绍代码审查的基本原则、流程和技巧，帮助你成为一名优秀的代码审查者。

### 1. 概念与定义

**代码审查（code review）**：C++中用于检查代码质量的过程。代码审查可以分为自我审查、同伴审查、团队审查等。例如自我审查用于检查自己的代码，同伴审查用于检查同伴的代码，团队审查用于检查团队的代码。

**代码质量（code quality）**：C++中用于表示代码的质量。代码质量可以分为可读性、可维护性、可扩展性、可测试性、性能等。例如可读性表示代码的易读性，可维护性表示代码的易维护性，可扩展性表示代码的易扩展性。

**代码审查流程（code review process）**：C++中用于进行代码审查的流程。代码审查流程可以分为提交代码、分配审查者、审查代码、反馈意见、修改代码、合并代码等。例如提交代码用于将代码提交到版本控制系统，分配审查者用于将代码分配给审查者，审查代码用于审查代码的质量。

**代码审查技巧（code review technique）**：C++中用于进行代码审查的技巧。代码审查技巧可以分为检查代码的可读性、检查代码的可维护性、检查代码的可扩展性、检查代码的可测试性、检查代码的性能等。例如检查代码的可读性用于检查代码的易读性，检查代码的可维护性用于检查代码的易维护性，检查代码的可扩展性用于检查代码的易扩展性。

**代码审查工具（code review tool）**：C++中用于进行代码审查的工具。代码审查工具可以分为GitHub Pull Request、GitLab Merge Request、Gerrit等。例如GitHub Pull Request用于进行代码审查，GitLab Merge Request用于进行代码审查，Gerrit用于进行代码审查。

### 2. 为什么要做代码审查？

代码审查的价值远不止"找Bug"，它在多个维度上为团队和项目带来收益：

| 维度 | 收益 | 说明 |
|------|------|------|
| **质量** | 减少缺陷 | 研究表明代码审查可以发现60%~90%的缺陷 |
| **知识** | 知识共享 | 审查过程让团队成员互相学习代码和业务逻辑 |
| **一致** | 风格统一 | 确保代码符合团队规范，降低长期维护成本 |
| **设计** | 改进设计 | 审查者从不同视角审视设计，发现架构问题 |
| **传承** | 降低风险 | 避免关键知识只存在于个别人脑中（`bus factor`） |
| **成长** | 个人提升 | 无论审查者还是被审查者，都能从中学习 |

> 🔬 **IBM的实证研究**：每小时代码审查投入可避免33小时的后续维护工作。代码审查的投资回报率（`ROI`）极高。

## 1. 代码审查的基本原则

### 1. 尊重与礼貌
- 审查代码时要尊重作者的劳动成果
- 提出意见时要礼貌、客观
- 避免使用攻击性语言

### 2. 关注代码质量
- 检查代码的可读性
- 检查代码的可维护性
- 检查代码的可扩展性
- 检查代码的可测试性
- 检查代码的性能

### 3. 保持一致性
- 检查代码是否符合编码规范
- 检查代码是否符合团队的代码风格
- 检查代码是否符合项目的代码结构

### 4. 提出具体建议
- 提出具体的改进建议
- 避免使用模糊的语言
- 提供可操作的解决方案

### 5. 保持高效
- 及时审查代码
- 避免拖延
- 提供明确的反馈

### 6. 区分问题优先级

审查意见并非同等重要，应当明确区分：

| 优先级 | 标记 | 说明 | 示例 |
|--------|------|------|------|
| **必须修改** | 🔴 `Must Fix` | 存在Bug、安全隐患或逻辑错误 | 内存泄漏、空指针解引用 |
| **建议修改** | 🟡 `Should Fix` | 代码质量或设计问题 | 命名不清晰、缺少错误处理 |
| **可选优化** | 🟢 `Nitpick` | 风格偏好或微小的改进建议 | 换行方式、注释措辞 |

> 💡 **建议**：在审查评论前加上优先级标记，让作者清楚哪些必须改、哪些可以忽略，避免无谓的争论。

## 2. 代码审查的流程

### 1. 提交代码
- 开发者将代码提交到版本控制系统
- 发起代码审查请求

### 2. 分配审查者
- 项目负责人或团队成员分配审查者
- 审查者收到代码审查请求

### 3. 审查代码
- 审查者仔细阅读代码
- 检查代码的质量
- 提出改进建议

### 4. 反馈意见
- 审查者将反馈意见发送给开发者
- 开发者收到反馈意见

### 5. 修改代码
- 开发者根据反馈意见修改代码
- 提交修改后的代码

### 6. 合并代码
- 审查者审查修改后的代码
- 确认代码符合要求
- 合并代码到主分支

### 7. 典型工作流详解

以 `GitHub Pull Request` 为例，一个完整的代码审查工作流如下：

```
开发者                        审查者                       主分支
  │                            │                            │
  │  1. 创建分支，编写代码       │                            │
  │─────────────────────────────│                            │
  │  2. 提交 PR（含描述/测试）   │                            │
  │───────────────────────────>│                            │
  │                            │  3. 审查代码                │
  │                            │  - 逐文件阅读               │
  │                            │  - 运行本地测试             │
  │                            │  - 添加行内评论             │
  │  4. 收到审查反馈            │                            │
  │<───────────────────────────│                            │
  │  5. 修改代码并推送           │                            │
  │───────────────────────────>│                            │
  │                            │  6. 审查修改，Approve       │
  │                            │──────────────────────────>  │
  │                            │                   7. 合并    │
  │<─────────────────────────────────────────────────────────│
  │  8. 删除分支                │                            │
```

> 💡 **PR描述模板建议**：
> - **What**：本次改动做了什么？
> - **Why**：为什么要做这个改动？
> - **How**：如何实现的？
> - **Test**：如何验证的？（附测试截图或日志）

## 3. 代码审查清单

代码审查清单（`review checklist`）是确保审查全面性的重要工具。以下是一份通用的审查清单：

### 3.1 正确性（Correctness）

| 检查项 | 说明 |
|--------|------|
| 逻辑是否正确 | 代码是否实现了预期功能 |
| 边界条件 | 是否处理了空输入、零值、最大值等边界情况 |
| 错误处理 | 异常和错误是否被正确捕获和处理 |
| 并发安全 | 多线程访问时是否存在数据竞争 |
| 资源管理 | 内存、文件句柄等资源是否正确释放 |

### 3.2 可读性（Readability）

| 检查项 | 说明 |
|--------|------|
| 命名规范 | 变量名、函数名、类名是否清晰且符合规范 |
| 代码结构 | 函数长度是否合理，嵌套是否过深 |
| 注释质量 | 注释是否解释了"为什么"而非"做什么" |
| 一致性 | 代码风格是否与项目保持一致 |

### 3.3 可维护性（Maintainability）

| 检查项 | 说明 |
|--------|------|
| 耦合度 | 模块之间是否过度耦合 |
| 内聚度 | 单个模块是否职责单一 |
| 重复代码 | 是否存在可以提取的重复逻辑 |
| 硬编码 | 是否存在魔法数字或硬编码的配置 |

### 3.4 性能（Performance）

| 检查项 | 说明 |
|--------|------|
| 算法复杂度 | 时间和空间复杂度是否可接受 |
| 不必要拷贝 | 是否存在可以避免的对象拷贝 |
| 内存分配 | 是否存在频繁的堆内存分配 |
| I/O操作 | 是否有不必要的磁盘或网络I/O |

### 3.5 安全性（Security）

| 检查项 | 说明 |
|--------|------|
| 输入验证 | 外部输入是否经过校验和清洗 |
| 缓冲区溢出 | 是否存在越界访问风险 |
| 敏感信息 | 日志或错误信息中是否泄露敏感数据 |
| 权限控制 | 是否正确实现了访问控制 |

### 3.6 可测试性（Testability）

| 检查项 | 说明 |
|--------|------|
| 单元测试 | 是否有对应的单元测试 |
| 可模拟性 | 依赖是否可以通过接口替换以便测试 |
| 测试覆盖 | 关键路径是否被测试覆盖 |

> 💡 **建议**：将此清单保存为团队共享文档，每次审查时对照检查，确保不遗漏关键维度。

## 4. 代码审查的技巧

### 1. 检查代码的可读性
- 检查变量名是否清晰
- 检查函数名是否清晰
- 检查注释是否清晰
- 检查代码的缩进是否一致
- 检查代码的空行是否合理

### 2. 检查代码的可维护性
- 检查代码的复杂度
- 检查代码的重复度
- 检查代码的耦合度
- 检查代码的内聚度
- 检查代码的可测试性

### 3. 检查代码的可扩展性
- 检查代码的模块化程度
- 检查代码的接口设计
- 检查代码的抽象程度
- 检查代码的灵活性
- 检查代码的可复用性

### 4. 检查代码的可测试性
- 检查代码是否有单元测试
- 检查代码是否容易测试
- 检查代码的测试覆盖率
- 检查代码的测试用例
- 检查代码的测试框架

### 5. 检查代码的性能
- 检查代码的时间复杂度
- 检查代码的空间复杂度
- 检查代码的内存使用
- 检查代码的CPU使用
- 检查代码的I/O操作

### 6. 高效审查的实用技巧

#### 6.1 控制审查规模

研究表明，人在一次审查中能高效处理的代码量有限：

| 代码行数 | 审查效率 | 缺陷发现率 |
|----------|----------|------------|
| < 200 行 | ⭐⭐⭐⭐⭐ | 最高 |
| 200~400 行 | ⭐⭐⭐⭐ | 较高 |
| 400~800 行 | ⭐⭐⭐ | 中等 |
| > 800 行 | ⭐⭐ | 急剧下降 |

> 💡 **建议**：将大的 `PR` 拆分为多个小的 `PR`，每个 `PR` 聚焦一个功能点，审查效率更高。

#### 6.2 分层审查

不要试图一次审查所有方面，建议按层次逐步检查：

1. **第一遍**：快速浏览，理解整体设计和改动意图
2. **第二遍**：逐行检查逻辑正确性和边界条件
3. **第三遍**：关注代码风格、命名和注释

#### 6.3 利用上下文

- 阅读代码前先看 `PR` 描述和关联的 `Issue`
- 理解改动的业务背景和设计意图
- 必要时在本地拉取代码并运行测试

## 5. C/C++代码审查要点

C/C++语言有其独特的陷阱和关注点，审查时需要特别留意。

### 5.1 内存管理

```cpp
// ❌ 问题代码：裸 new/delete，容易忘记释放
void process() {
    int* data = new int[100];
    // ... 如果中间抛出异常，data 永远不会被释放
    delete[] data;
}

// ✅ 改进代码：使用智能指针
void process() {
    auto data = std::make_unique<int[]>(100);
    // ... 即使抛出异常，data 也会自动释放
}
```

**审查要点**：
- 是否使用了裸 `new`/`delete`？优先使用 `std::unique_ptr` 或 `std::shared_ptr`
- 是否存在内存泄漏（`memory leak`）的可能？
- 是否存在双重释放（`double free`）的风险？
- 是否正确处理了 `new` 失败的情况？

### 5.2 指针与引用

```cpp
// ❌ 问题代码：返回局部变量的引用
const int& getValue() {
    int x = 42;
    return x;  // 悬空引用（dangling reference）！
}

// ❌ 问题代码：未检查空指针
void printLength(const std::string* str) {
    std::cout << str->length();  // 如果 str 为 nullptr，未定义行为
}

// ✅ 改进代码
void printLength(const std::string* str) {
    if (str == nullptr) {
        std::cerr << "null pointer\n";
        return;
    }
    std::cout << str->length();
}
```

**审查要点**：
- 是否存在悬空指针/引用（`dangling pointer/reference`）？
- 指针是否可能为 `nullptr`？是否做了空指针检查？
- 是否使用了 `reinterpret_cast` 或 C 风格强制转换？是否有更安全的替代方案？

### 5.3 资源管理（RAII）

```cpp
// ❌ 问题代码：手动管理文件资源
void readFile(const std::string& path) {
    FILE* fp = fopen(path.c_str(), "r");
    if (!fp) return;
    // ... 如果中间 return 或抛出异常，文件句柄泄漏
    fclose(fp);
}

// ✅ 改进代码：利用 RAII 自动管理
void readFile(const std::string& path) {
    std::ifstream ifs(path);
    if (!ifs) return;
    // ... ifs 析构时自动关闭文件
}
```

**审查要点**：
- 资源（文件、锁、套接字等）是否遵循 `RAII` 原则？
- 是否存在获取资源后未释放的路径（包括异常路径）？

### 5.4 未定义行为

```cpp
// ❌ 问题代码：常见的未定义行为
int a = 0;
int b = a++;  // 在同一表达式中读写同一变量（C++17前）
int c = a + ++a;  // 未定义行为

// ❌ 越界访问
std::vector<int> v = {1, 2, 3};
int x = v[5];  // 未定义行为，应使用 v.at(5)

// ❌ 有符号整数溢出
int max = INT_MAX;
int result = max + 1;  // 未定义行为
```

**审查要点**：
- 是否存在未定义行为（`undefined behavior`）？
- 数组/容器访问是否可能越界？是否应使用 `at()` 代替 `[]`？
- 是否存在有符号整数溢出？
- 是否存在数据竞争（`data race`）？

### 5.5 头文件与编译

```cpp
// ❌ 问题代码：头文件中 using namespace
// my_header.h
using namespace std;  // 污染所有包含此头文件的编译单元

// ❌ 缺少 include guard
// my_header.h
class MyClass { /* ... */ };
// 多次包含会导致重定义错误

// ✅ 改进代码
// my_header.h
#ifndef MY_HEADER_H_
#define MY_HEADER_H_

namespace myproject {
class MyClass { /* ... */ };
}  // namespace myproject

#endif  // MY_HEADER_H_

// ✅ C++20 模块方式（推荐）
// my_module.cppm
export module my_module;
export namespace myproject {
class MyClass { /* ... */ };
}
```

**审查要点**：
- 头文件是否有 `include guard` 或 `#pragma once`？
- 头文件中是否使用了 `using namespace`？
- 是否存在不必要的头文件包含？
- 是否存在循环依赖？

### 5.6 C++特有陷阱速查表

| 陷阱 | 示例 | 推荐做法 |
|------|------|----------|
| 切片（`slicing`） | `Base b = derived;` | 使用引用或指针 |
| 隐式转换 | `void f(bool b); f(42);` | 使用 `explicit` 关键字 |
| 静态初始化顺序 | 全局变量互相依赖 | 使用函数内静态变量 |
| 虚析构 | `Base* p = new Derived; delete p;` | 基类析构函数声明为 `virtual` |
| 异常安全 | 构造函数中 `new` 抛出异常 | 使用 `RAII` 和智能指针 |
| 移动语义 | `return std::move(local_var);` | 直接 `return local_var;`（`NRVO`） |

## 6. 如何给出反馈

给出高质量的反馈是代码审查的核心技能。好的反馈能帮助作者成长，差的反馈则可能引发冲突。

### 6.1 反馈的分类

| 类型 | 示例 | 说明 |
|------|------|------|
| **问题** | "这里空指针检查缺失，可能导致崩溃" | 指出实际的Bug或风险 |
| **建议** | "考虑使用 `std::optional` 代替返回 `-1` 表示失败" | 提供更好的替代方案 |
| **疑问** | "这里的逻辑我不太理解，能否解释一下？" | 请作者澄清，而非假设有问题 |
| **赞扬** | "这个抽象很优雅，学到了" | 肯定好的代码，激励作者 |

### 6.2 反馈的表达方式

```cpp
// ❌ 糟糕的反馈：指责性
"这段代码写得太烂了，怎么连空指针都不检查？"

// ✅ 好的反馈：描述问题 + 影响 + 建议
"这里 `ptr` 可能为 `nullptr`（当 `find()` 返回 `end()` 时），
解引用会导致未定义行为。建议在解引用前添加空指针检查。"
```

**好反馈的原则**：

1. **对事不对人**：评价代码，而非评价人
   - ❌ "你写错了"
   - ✅ "这段逻辑有个边界条件问题"

2. **解释原因**：不仅指出问题，还要说明为什么是问题
   - ❌ "这里不要用 `reinterpret_cast`"
   - ✅ "`reinterpret_cast` 绕过了类型系统，容易引入难以调试的Bug，建议用 `static_cast` 或重新设计接口"

3. **提供方案**：给出具体的改进建议
   - ❌ "这个函数太长了"
   - ✅ "这个函数有80行，建议将数据处理部分提取为 `processData()` 函数，I/O部分提取为 `writeOutput()` 函数"

4. **用疑问句代替命令句**：给作者思考的空间
   - ❌ "把这里改成 `const auto&`"
   - ✅ "这里是否可以用 `const auto&` 避免不必要的拷贝？"

### 6.3 反馈模板

```
[优先级标记] 问题/建议/疑问

**现象**：描述你看到的内容
**问题**：为什么这是一个问题
**建议**：具体的改进方案（附代码示例）
```

示例：

```
🟡 Should Fix

**现象**：`getUserById()` 函数在用户不存在时返回空对象
**问题**：调用者无法区分"用户不存在"和"用户数据为空"两种情况
**建议**：返回 `std::optional<User>`，让调用者显式处理用户不存在的情况

```cpp
// 改进前
User getUserById(int id);

// 改进后
std::optional<User> getUserById(int id);
```
```

## 7. 如何接受反馈

接受代码审查同样是一门学问，正确的心态和行为能让审查过程更高效、更愉快。

### 7.1 正确心态

- **审查的是代码，不是你**：代码有问题不代表你能力不行
- **审查是学习机会**：审查者的意见可能包含你不知道的知识
- **代码是团队的资产**：审查的目的是让代码更好，而非证明谁对谁错

### 7.2 回应反馈的原则

| 原则 | 说明 |
|------|------|
| **先理解再回应** | 确保你理解了审查者的意思，再决定是否接受 |
| **感谢每条反馈** | 即使你不认同，也先感谢对方花时间审查 |
| **解释而非争辩** | 如果你不同意，解释你的理由而非直接否定 |
| **区分事实和偏好** | 事实性问题（Bug、安全隐患）必须修改；风格偏好可以讨论 |
| **及时回应** | 不要让审查反馈石沉大海，即使暂时没空修改也要回复 |

### 7.3 处理分歧

当审查者和作者意见不一致时：

1. **先确认理解一致**：确保双方讨论的是同一个问题
2. **用数据说话**：引用规范文档、性能测试结果等客观依据
3. **寻求第三方意见**：邀请其他团队成员参与讨论
4. **遵循团队规范**：如果团队有明确的规范，以规范为准
5. **记录决策**：将最终决定和理由记录在 `PR` 评论中，供未来参考

```cpp
// 示例：处理分歧的评论对话

// 审查者：建议这里用 std::unordered_map 代替 std::map，
//         查找性能从 O(log n) 提升到 O(1)

// 作者：感谢建议！这里 key 的数量通常不超过 10 个，
//       我测试过 unordered_map 在小数据量下反而更慢
//       （哈希开销大于红黑树查找），所以选择了 map。
//       详见性能测试结果：[链接]

// 审查者：有道理，小数据量确实如此。那加个注释说明一下选择理由？

// 作者：好的，已添加注释。
```

## 9. 代码审查的反模式

反模式（`anti-pattern`）是看似合理但实际上有害的做法。识别并避免这些反模式，能让代码审查更有效。

### 9.1 橡皮图章审查（Rubber Stamping）

```text
❌ 审查者只是点 "LGTM"（Looks Good To Me），没有认真看代码
```

**危害**：代码审查形同虚设，缺陷和设计问题无法被发现。

**解决方案**：
- 要求审查者至少提出一条评论（哪怕是赞扬）
- 对审查者进行考核，确保审查质量
- 限制每人同时审查的 `PR` 数量

### 9.2 完美主义审查（Perfectionism）

```text
❌ 审查者对每一行代码都提出修改意见，要求"完美"才能合并
```

**危害**：合并周期过长，开发者积极性受挫，项目进度受阻。

**解决方案**：
- 区分"必须修改"和"可选优化"
- 接受"足够好"的代码，后续迭代改进
- 遵循"两遍规则"：第二轮审查只检查第一轮的修改

### 9.3 微观管理审查（Micromanagement）

```text
❌ 审查者纠结于变量命名、换行方式等风格偏好，忽视架构和逻辑问题
```

**危害**：浪费审查时间，忽略真正重要的问题，引发不必要的争论。

**解决方案**：
- 使用 `Clang-Format` 自动处理格式问题
- 将编码规范文档化，风格问题引用规范即可
- 审查者应聚焦于逻辑、设计和安全

### 9.4 对立式审查（Adversarial Review）

```text
❌ 审查者与作者形成对立关系，审查变成"找茬比赛"
```

**危害**：团队氛围恶化，开发者害怕提交代码，审查变成政治博弈。

**解决方案**：
- 强调审查是"协作"而非"对抗"
- 审查者也要提交代码接受审查，形成互惠关系
- 团队负责人以身作则，展示建设性的审查态度

### 9.5 审查瓶颈（Review Bottleneck）

```text
❌ 所有 PR 都必须由某一个人审查，此人成为瓶颈
```

**危害**：合并延迟，单点故障，知识过度集中。

**解决方案**：
- 培养多名审查者，轮值审查
- 使用 `CODEOWNERS` 按模块分配审查者
- 鼓励交叉审查，不同团队成员互相审查

### 9.6 反模式速查表

| 反模式 | 特征 | 危害 | 解决方案 |
|--------|------|------|----------|
| 橡皮图章 | 只点 `LGTM` 不看代码 | 审查无效 | 要求至少一条评论 |
| 完美主义 | 要求代码"完美"才能合并 | 效率低下 | 区分优先级，接受迭代改进 |
| 微观管理 | 纠结风格，忽视架构 | 抓小放大 | 自动化格式，聚焦逻辑 |
| 对立式 | 审查变成"找茬" | 团队对立 | 强调协作，以身作则 |
| 审查瓶颈 | 单人审查所有 `PR` | 合并延迟 | 培养多名审查者 |

代码审查不仅是一个技术流程，更是团队文化的体现。健康的审查文化能让团队持续进步。

- 导致代码质量问题

- 解决方案：建立代码审查的质量标准

- 导致开发者无法修改代码
- 影响代码审查效率
- 解决方案：提出具体的改进建议

- 导致开发者无法确定修改方向

- 解决方案：拆分 `PR`，每个 `PR` 聚焦一个功能点

- 审查者不了解业务背景
- 作者不了解审查者的技术关注点
- 解决方案：`PR` 描述包含充分的业务上下文，审查前先沟通

## 13. 代码审查的案例分析

### 1. 案例1：代码可读性问题

**问题代码**：
```cpp
int f(int a, int b) {
    return a + b;
}
```

**审查意见**：
- 函数名`f`过于简单，应该使用更有意义的函数名
- 变量名`a`和`b`过于简单，应该使用更有意义的变量名

**改进代码**：
```cpp
int add(int x, int y) {
    return x + y;
}
```

### 2. 案例2：代码可维护性问题

**问题代码**：
```cpp
void process_data(int *data, int size) {
    for (int i = 0; i < size; i++) {
        if (data[i] > 0) {
            data[i] *= 2;
        } else {
            data[i] = 0;
        }
    }
}
```

**审查意见**：
- 使用裸指针和尺寸参数传递数组，容易出错，建议使用`std::vector`
- 缺少边界检查，传入空指针或零尺寸时行为未定义
- 数据转换逻辑与遍历逻辑耦合，可以提取转换函数提高可读性和可测试性

**改进代码**：
```cpp
int transform_positive(int value) {
    return value * 2;
}

int transform_non_positive(int value) {
    return 0;
}

void process_data(std::vector<int>& data) {
    if (data.empty()) {
        return;
    }

    for (auto& value : data) {
        if (value > 0) {
            value = transform_positive(value);
        } else {
            value = transform_non_positive(value);
        }
    }
}
```

### 3. 案例3：内存安全问题

**问题代码**：
```cpp
class UserManager {
public:
    void addUser(const std::string& name) {
        users.push_back(new User(name));
    }

    User* findUser(const std::string& name) {
        for (auto* user : users) {
            if (user->getName() == name) {
                return user;
            }
        }
        return nullptr;
    }

    ~UserManager() {
        for (auto* user : users) {
            delete user;
        }
    }

private:
    std::vector<User*> users;
};
```

**审查意见**：
- 🔴 `Must Fix`：手动管理 `User*` 的生命周期，如果 `addUser` 后 `vector` 扩容导致迭代器失效，或异常抛出，可能内存泄漏
- 🔴 `Must Fix`：缺少拷贝构造函数和赋值运算符，默认的浅拷贝会导致双重释放
- 🟡 `Should Fix`：`findUser` 返回裸指针，调用者可能忘记检查 `nullptr`
- 🟡 `Should Fix`：线性查找效率低，数据量大时应使用 `std::unordered_map`

**改进代码**：
```cpp
class UserManager {
public:
    void addUser(const std::string& name) {
        users_.emplace(name, std::make_unique<User>(name));
    }

    User* findUser(const std::string& name) {
        auto it = users_.find(name);
        return it != users_.end() ? it->second.get() : nullptr;
    }

private:
    std::unordered_map<std::string, std::unique_ptr<User>> users_;
};
```

### 4. 案例4：并发安全问题

**问题代码**：
```cpp
class Counter {
public:
    void increment() { count_++; }  // 数据竞争！
    int get() const { return count_; }  // 数据竞争！
private:
    int count_ = 0;
};
```

**审查意见**：
- 🔴 `Must Fix`：`count_++` 不是原子操作，多线程并发调用会导致数据竞争（`data race`），属于未定义行为
- 🟡 `Should Fix`：`get()` 与 `increment()` 之间没有同步，可能读到过期值

**改进代码**：
```cpp
#include <atomic>

class Counter {
public:
    void increment() { count_.fetch_add(1, std::memory_order_relaxed); }
    int get() const { return count_.load(std::memory_order_relaxed); }
private:
    std::atomic<int> count_{0};
};
```

### 5. 案例5：API设计问题

**问题代码**：
```cpp
// 返回 -1 表示失败，调用者容易忘记检查
int parseConfig(const std::string& path, Config& out);
```

**审查意见**：
- 🟡 `Should Fix`：使用输出参数 + 错误码的方式不够现代，且调用者容易忽略错误
- 🟢 `Nitpick`：函数名 `parseConfig` 建议改为 `parse_config` 以符合C++命名惯例

**改进代码**：
```cpp
#include <expected>
#include <string>

// C++23: 使用 std::expected 明确表达成功/失败
std::expected<Config, std::string> parse_config(const std::string& path);

// C++17/20 替代方案：使用 std::optional 或自定义 Result 类型
```

## 14. 代码审查的总结

代码审查是保证代码质量的重要手段，它可以帮助我们发现代码中的问题，提高代码质量，促进团队成员之间的知识共享。通过学习代码审查的基本原则、流程和技巧，你可以成为一名优秀的代码审查者，为项目的成功做出贡献。

### 核心要点回顾

| 要点 | 说明 |
|------|------|
| **审查是协作** | 不是挑刺，而是共同提升代码质量 |
| **自动化先行** | 格式和常见错误交给工具，人工聚焦逻辑和设计 |
| **小而频繁** | 小 `PR` 审查效率高，大 `PR` 质量难保证 |
| **对事不对人** | 评价代码，不评价人 |
| **持续改进** | 定期回顾审查流程，根据团队反馈优化 |

> 🎯 **记住**：代码审查的终极目标不是"阻止坏代码合并"，而是"帮助团队写出更好的代码"。当审查文化健康时，每个人都是受益者。

希望本章的内容对你有所帮助，祝你在代码审查的道路上取得成功！
