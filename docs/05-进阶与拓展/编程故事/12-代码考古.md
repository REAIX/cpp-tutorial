## 1. 什么是代码考古

### 1. 像考古学家一样研究代码

考古学家通过发掘地层中的遗物来还原历史，代码考古学家则通过挖掘版本控制系统和代码仓库来还原技术演进的历史。每一次commit都是一个地层，每一个分支都是一条文明线索。

```
代码考古 vs 传统考古

传统考古                          代码考古
┌──────────────────┐             ┌──────────────────┐
│ 地层 → 版本历史   │             │ git log → 版本历史│
│ 遗物 → 源代码     │             │ 源代码 → 数字遗物 │
│ 铭文 → 注释       │             │ 注释 → 数字铭文   │
│ 遗址 → 代码仓库   │             │ 仓库 → 数字遗址   │
│ 文物修复 → 重构   │             │ 重构 → 代码修复   │
│ 碳14测年 → 时间戳 │             │ 时间戳 → 精确到秒 │
└──────────────────┘             └──────────────────┘
```

### 2. 为什么旧代码值得研究

| 原因 | 说明 |
|------|------|
| 理解设计决策 | 今天的架构是过去无数选择的累积 |
| 避免重复犯错 | 历史上的Bug模式会反复出现 |
| 传承工程智慧 | 老代码中蕴含着教科书不会教的技巧 |
| 应对遗产系统 | 全球仍有大量关键系统运行着几十年前的代码 |
| 技术演进规律 | 理解过去才能预测未来 |

### 3. 代码是数字文明的化石

就像地层中的化石记录了生命的演化，代码仓库记录了人类计算思维的演化。从打孔卡片到高级语言，从单机程序到分布式系统，每一层代码都是人类文明的一个切片。

## 2. 阿波罗11号源代码 — 人类最关键的代码

### 1. Margaret Hamilton与MIT团队

1969年7月20日，阿波罗11号登月舱"鹰"在月球表面着陆。在着陆前的最后几分钟，导航计算机连续触发了1201和1202号警报——内存溢出。如果此时计算机崩溃，登月任务将被迫中止。

正是Margaret Hamilton领导的MIT仪器实验室团队编写的错误恢复机制，让计算机在内存溢出时能够自动重启并恢复关键任务，而不是彻底死机。这一设计挽救了登月任务。

```
阿波罗11号登月关键时刻

1969.07.20 登月时间线
│
├── 20:05  登月舱开始下降
├── 20:10  计算机触发1202警报（内存溢出）
│          └── AGC自动重启，恢复导航任务 ← Hamilton的代码！
├── 20:11  计算机再次触发1201警报
│          └── 再次自动恢复 ← 关键设计！
├── 20:17  "休斯顿，这里是静海基地。鹰已着陆。"
│
└── 如果没有错误恢复机制 → 任务中止，返回轨道
```

### 2. AGC的极端约束

阿波罗导航计算机（AGC）的硬件约束在今天看来不可思议：

| 参数 | AGC规格 | 现代对比 |
|------|---------|---------|
| 内存 | 约76KB（2048字可擦写磁芯存储器+36864字只读绳存储器，16位/字） | 普通手机8GB+ |
| 时钟频率 | 2.048 MHz | 现代CPU 3-5 GHz |
| 字长 | 16位 | 64位 |
| 存储 | 2048字可擦写磁芯存储器+36864字只读绳存储器 | TB级SSD |
| 功耗 | 55W | 笔记本电脑65W+ |
| 重量 | 32kg | 手机200g |

在72KB的内存中，Hamilton的团队实现了：

- 导航计算
- 飞船姿态控制
- 雷达数据处理
- 宇航员界面
- **完整的错误检测与恢复系统**

### 3. 虚拟机架构

AGC采用了一种类似虚拟机的架构——这是最早的虚拟机概念之一：

```c
// AGC虚拟机架构简化示意

// 解释器指令集（在AGC原生指令之上的一层虚拟机）
// 这种设计让代码更紧凑——在约76KB的限制下至关重要

// AGC解释器指令示例
enum agc_interp_opcode {
    OP_ADDR = 0x00,    // 加载地址
    OP_CLEAR = 0x01,   // 清零
    OP_SET = 0x02,     // 置位
    OP_DAD = 0x03,     // 双精度加法
    OP_DSU = 0x04,     // 双精度减法
    OP_BZF = 0x05,     // 零跳转
    OP_TCF = 0x06,     // 条件跳转
    OP_SQUARE = 0x07,  // 平方运算
    OP_MP = 0x08,      // 乘法
    OP_DV = 0x09,      // 除法
};

// 错误恢复机制的核心设计
void agc_error_recovery(int alarm_code) {
    // 保存当前关键状态
    save_critical_state();

    // 根据警报类型决定处理方式
    switch (alarm_code) {
        case 1201:  // VAC区域溢出
        case 1202:  // 核心集溢出
            // 关键设计：只重启非关键任务
            // 保留导航和姿态控制
            restart_non_essential_tasks();
            break;
        default:
            full_restart();
            break;
    }

    // 恢复关键状态
    restore_critical_state();
}
```

### 3. 为什么不能重写

面对COBOL系统的老化，一个自然的问题是：为什么不重写？答案远比想象中复杂：

| 障碍 | 说明 |
|------|------|
| 业务逻辑深埋代码中 | 几十年的业务规则写在代码里，没有人完全理解所有规则 |
| 重写风险极高 | 金融系统的任何错误都可能导致资金损失 |
| 测试困难 | 如何验证新系统与旧系统行为完全一致？ |
| 成本巨大 | 估计全美银行系统重写需数千亿美元 |
| 时间不够 | 重写一个大型COBOL系统需要5-10年 |
| 人员断层 | 既懂老系统又懂新技术的复合型人才极度稀缺 |


## 4. Y2K38 — 下一个千年虫

### 1. 什么是Y2K38

Y2K38（又称Unix Millennium Bug）是指32位Unix时间戳将在2038年1月19日03:14:07 UTC发生溢出的问题。

```
Unix时间戳溢出示意

32位有符号整数范围：-2,147,483,648 到 2,147,483,647

时间戳增长：
...
2038.01.19 03:14:06  →  2,147,483,646
2038.01.19 03:14:07  →  2,147,483,647  ← 32位有符号整数最大值
2038.01.19 03:14:08  → -2,147,483,648  ← 溢出！时间倒退到1901年！

时间线可视化：
                溢出点
                  │
1901 ─────────────┼───────────── 2038 ──→
                  │
     ← 负数区域 →│← 正数区域 →
                  │
         时间突然跳回1901年！
```

```c
// Y2K38问题的根源
#include <stdio.h>
#include <time.h>

int main() {
    time_t t = 0x7FFFFFFF;  // 32位有符号整数最大值
    printf("溢出前: %s", ctime(&t));
    // 输出: 溢出前: Tue Jan 19 03:14:07 2038

    t = t + 1;  // 溢出
    printf("溢出后: %s", ctime(&t));
    // 在32位系统上输出: 溢出后: Fri Dec 13 20:45:52 1901
    // 时间倒退了137年！

    return 0;
}
```

### 2. 与Y2K的区别

| 方面 | Y2K（2000年问题） | Y2K38（2038年问题） |
|------|-------------------|---------------------|
| 根源 | 两位数年份存储 | 32位时间戳溢出 |
| 影响范围 | 主要影响COBOL系统 | 影响所有使用time_t的C/C++程序 |
| 修复难度 | 相对简单（扩展年份字段） | 需要将time_t从32位扩展到64位 |
| 预警时间 | 提前数十年开始修复 | 距离2038年越来越近 |
| 后果 | 由于提前修复，实际影响较小 | 嵌入式系统可能无法升级 |

### 3. 影响范围

Y2K38的影响远不止服务器——嵌入式系统才是最大的隐患：

```

│  ├── 工业控制系统（SCADA/PLC）                   │
│  ├── 汽车电子控制单元（ECU）                     │
│  └── 银行ATM和POS终端                           │
```

### 4. Linux内核的修复历程

Linux内核对Y2K38的修复是一个漫长的过程：

| 时间 | 里程碑 |
|------|--------|
| 2013 | 开始讨论内核层面的Y2K38修复方案 |
| 2018 | glibc开始支持64位time_t（32位兼容层） |
| 2019 | Linux内核5.x系列逐步修复文件系统时间戳 |
| 2020 | ext4文件系统支持大于2038年的时间戳 |
| 2022 | Linux内核持续修复各子系统的32位时间戳 |
| 2023 | musl libc默认使用64位time_t |
| 进行中 | 大量嵌入式Linux系统仍未修复 |

**时间线**：

| 时间 | 事件 |
|------|------|
| 1970.01.01 | Unix纪元开始，time_t定义为32位有符号整数 |
| 2000 | Y2K危机提醒人们关注时间表示问题 |
| 2013 | Linux社区开始认真讨论Y2K38修复 |
| 2018 | glibc开始提供64位time_t支持 |
| 2020 | 部分文件系统完成修复 |
| 2038.01.19 | 溢出日期（如果未修复） |

**教训**：数据类型的选取看似小事，却可能影响数十年后的系统运行。选择数据类型时，永远考虑最大可能值。

## 5. Linux内核的史诗演进 — 从1万行到3000万行

### 1. 1991年：一切从一封邮件开始

1991年8月25日，芬兰赫尔辛基大学21岁的学生Linus Torvalds在comp.os.minix新闻组发了一封著名的邮件：

```
From: torvalds@klaava.Helsinki.FI (Linus Benedict Torvalds)
Newsgroups: comp.os.minix
Subject: What would you like to see most in minix?
Date: 25 Aug 91 20:57:08 GMT

Hello everybody out there using minix -

I'm doing a (free) operating system (just a hobby, won't be big and
professional like gnu) for 386(486) AT clones. This has been brewing
since april, and is starting to get ready. I'd like any feedback on
things people like/dislike in minix, as my OS resembles it somewhat
(same physical layout of the file-system (due to practical reasons)
among other things).

I've currently ported bash(1.08) and gcc(1.40), and things seem to work.
This implies that I'll get something practical within a few months, and
I'd like to know what features most people would want. Any suggestions
are welcome, but I won't promise I'll implement them :-)

                Linus (torvalds@kruuna.helsinki.fi)
```

"just a hobby, won't be big and professional"——这可能是科技史上最谦虚的开场白。

### 3. Linus的代码风格变迁

Linus的编码风格在30年间发生了显著变化：

```c
// 早期Linux内核风格（1991年）—— 简洁、直接、个人化

/*
 *  linux/kernel/panic.c
 *
 *  Copyright (C) 1991, 1992  Linus Torvalds
 */

/*
 * This function is used through-out the kernel (include mm/filemap.c)
 * to indicate a major problem.
 */
void panic(const char * fmt, ...)
{
    // 直接、粗暴、没有花哨的错误处理
```

## 6. Windows源码泄露事件（2004年）

### 1. 泄露经过

2004年2月12日，Windows 2000和Windows NT 4.0的部分源代码出现在互联网上。泄露的代码总量约660MB，包含约3.08亿行代码中的部分核心组件。

```
Windows源码泄露事件时间线

2004.02.12  源码出现在P2P网络和IRC频道
            │
            ▼
2004.02.12  微软确认泄露属实
            │
            ▼
2004.02.13  安全社区开始分析泄露源码
            │
            ▼
2004.02.14  首个基于泄露源码的安全漏洞被发现
            │   （IE浏览器缓冲区溢出）
            ▼
2004.02     微软向FBI报案
            │
            ▼
2004-2005   更多安全漏洞被发现
            │
            ▼
2004        泄露源头追踪：Mainsoft公司
            （微软共享源码计划合作伙伴）
```

### 2. 泄露源码中发现的安全漏洞

泄露源码公布后，安全研究人员（和攻击者）开始系统地分析代码，发现了多个安全漏洞：

| 漏洞 | 组件 | 严重程度 | 发现时间 |
|------|------|---------|---------|
| IE浏览器缓冲区溢出 | mshtml.dll | 高危 | 泄露后2天 |
| BMP图像处理漏洞 | gdi32.dll | 高危 | 泄露后1周 |
| ICO文件解析漏洞 | user32.dll | 中危 | 泄露后2周 |
| 多个整数溢出 | 内核组件 | 高危 | 泄露后数月 |

```c
// 泄露源码中发现的典型漏洞模式（简化示意）

// IE浏览器中的缓冲区溢出漏洞
void ProcessImageTag(char *html_content) {
    char buffer[256];
    // 从HTML中提取img标签的src属性
    char *src = extract_attribute(html_content, "src");
    // 没有检查src长度！
    strcpy(buffer, src);  // 经典的缓冲区溢出
    process_image(buffer);
}

// 修复后
void ProcessImageTag(char *html_content) {
    char buffer[256];
    char *src = extract_attribute(html_content, "src");
    strncpy(buffer, src, sizeof(buffer) - 1);  // 限制复制长度
    buffer[sizeof(buffer) - 1] = '\0';          // 确保终止
    process_image(buffer);
}
```

### 3. 泄露源头

调查发现，泄露源头是Mainsoft公司——微软"共享源码计划"（Shared Source Initiative）的合作伙伴。Mainsoft使用Windows源码开发将Windows应用移植到Unix/Linux的工具。一名Mainsoft的员工将源码泄露到了互联网上。

### 4. 闭源vs开源的安全辩论

这次泄露引发了关于闭源与开源安全性的激烈辩论：

```
闭源 vs 开源安全辩论

闭源安全论                          开源安全论
┌──────────────────┐               ┌──────────────────┐
│ "通过隐蔽实现安全" │               │ "通过透明实现安全" │
│                  │               │                  │
│ · 攻击者看不到代码│               │ · 任何人都能审计  │
│ · 漏洞不易被发现 │               │ · 漏洞更容易被发现│
│ · 但一旦泄露...  │               │ · Linus定律：     │
│   后果极其严重   │               │   "足够多的眼睛， │
│                  │               │    所有Bug都无所遁│
│ Windows泄露证明：│               │    形"            │
│ 隐蔽≠安全       │               │                  │
│ 漏洞一直存在     │               │ Linux证明了：     │
│ 只是被隐藏了     │               │ 开放也能安全      │
└──────────────────┘               └──────────────────┘
```

**时间线**：

| 时间 | 事件 |
|------|------|
| 2004.02.12 | Windows 2000/NT4源码泄露 |
| 2004.02.14 | 首个漏洞被发现 |
| 2004 | 微软确认泄露源头为Mainsoft |
| 2004-2005 | 基于泄露源码发现多个漏洞 |
| 2004 | 微软加强共享源码计划的访问控制 |

**教训**：安全不能依赖于代码的保密性（Security by Obscurity）。如果代码的安全性依赖于"没人能看到代码"，那么代码一旦泄露，所有安全假设都会崩塌。

### 2. 好的注释是时间胶囊

AGC源代码的注释在50年后仍然让人感动和受益。好的注释不是解释"代码做了什么"，而是记录"为什么这样做"：

| 注释类型 | 示例 | 价值 |
|---------|------|------|
| 决策注释 | "选择快速排序而非归并排序，因为内存受限" | ★★★★★ |
| 警告注释 | "不要修改此计算顺序，精度会损失" | ★★★★★ |
| 上下文注释 | "此公式来自ISO 8601标准第3.2节" | ★★★★ |
| TODO注释 | "TODO: 优化此循环，当前O(n²)" | ★★★ |
| 显而易见注释 | "i++ // i加1" | ★ |

### 4. 代码的生命力超出想象

- AGC的代码在50年后仍然可以被阅读和运行
- COBOL的代码在60年后仍然处理着全球大部分金融交易
- 旅行者号的代码在45年后仍然在240亿公里外运行
- Linux内核的代码在33年后仍然在持续演进

**给开发者的五条建议**：

1. **写代码时假设它会运行50年**——因为你无法保证它不会
2. **注释记录"为什么"而非"是什么"**——未来的考古学家需要理解你的决策
3. **选择数据类型时考虑极限值**——Y2K38的教训
4. **不要过度依赖"临时方案"**——AGC的"临时修复"飞到了月球
5. **对遗产代码保持敬畏**——它能在生产环境运行这么多年，一定有它的道理
