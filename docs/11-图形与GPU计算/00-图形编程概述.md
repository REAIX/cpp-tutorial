## 1. GPU架构基础

### 1.1 GPU与CPU的设计差异

GPU（Graphics Processing Unit）最初是为图形渲染而设计的专用处理器，但其强大的并行计算能力使其逐渐成为通用计算的重要平台。

| 特性 | CPU | GPU |
|------|-----|-----|
| 核心数量 | 少（4-64个） | 多（数千个） |
| 单核性能 | 强（高主频、深流水线） | 弱（低主频、浅流水线） |
| 缓存 | 大（MB级L3缓存） | 小（每SM共享少量缓存） |
| 分支预测 | 强大 | 简单 |
| 设计目标 | 低延迟 | 高吞吐 |
| 适用场景 | 复杂逻辑、串行任务 | 数据并行、SIMD任务 |

### 1.2 GPU核心架构

现代NVIDIA GPU采用SIMT（Single Instruction, Multiple Threads）架构：

```
┌─────────────────── GPU ───────────────────┐
│  ┌─── GPC ───┐  ┌─── GPC ───┐            │
│  │ ┌─SM─┐ ┌─SM─┐ │ ┌─SM─┐ ┌─SM─┐        │
│  │ │CUDA│ │CUDA│ │ │CUDA│ │CUDA│        │
│  │ │Core│ │Core│ │ │Core│ │Core│        │
│  │ └────┘ └────┘ │ └────┘ └────┘        │
│  └───────────────┘ └───────────────┘      │
│  ┌─── 全局显存 (VRAM) ──────────────┐    │
│  │         HBM2 / GDDR6X            │    │
│  └──────────────────────────────────┘    │
└──────────────────────────────────────────┘
```

**SM（Streaming Multiprocessor）** 是GPU的基本计算单元，每个SM包含：

- **CUDA核心**：执行整数和浮点运算的基本单元
- **Tensor核心**：执行矩阵乘法加速（AI推理/训练）
- **RT核心**：执行光线追踪加速（光线求交）
- **共享内存**：SM内部的高速缓存（约100KB）
- **寄存器文件**：每个线程的私有寄存器

#### 1.2.1 GPU微架构演进

NVIDIA GPU微架构经历了多代演进，每代都在SM设计上做了重要改进：

| 微架构 | 代号 | 年份 | SM中CUDA核心 | 关键特性 |
|--------|------|------|--------------|---------|
| Kepler | GK | 2012 | 192 | 动态并行、Hyper-Q |
| Maxwell | GM | 2014 | 128 | 能效比大幅提升 |
| Pascal | GP | 2016 | 128/64 | NVLink、统一内存改进 |
| Volta | GV | 2017 | 64 | Tensor核心首次引入 |
| Turing | TU | 2018 | 64 | RT核心、Mesh Shader |
| Ampere | GA | 2020 | 128 | 第二代RT/Tensor核心 |
| Ada Lovelace | AD | 2022 | 128 | 第三代RT核心、SER |
| Hopper | GH | 2022 | 128 | TMA、分布式共享内存 |

> 💡 **关键理解**：从Volta开始，SM中的CUDA核心数从128降为64（Volta/Turing），但每个核心的性能提升使得总体计算能力更强。Ampere又恢复到128核心/SM，但核心设计已完全不同于Kepler时代。

#### 1.2.2 SM内部结构详解

以Ampere架构的SM为例，其内部结构如下：

```
┌────────────────── SM (Ampere) ──────────────────┐
│                                                   │
│  ┌─── Sub-Partition 0 ───┐ ┌─── Sub-Partition 1 ───┐
│  │  ┌─────────────────┐  │ │  ┌─────────────────┐  │
│  │  │  16x FP32 Cores │  │ │  │  16x FP32 Cores │  │
│  │  │  16x INT32 Cores│  │ │  │  16x INT32 Cores│  │
│  │  │  8x FP64 Cores  │  │ │  │  8x FP64 Cores  │  │
│  │  │  1x Tensor Core │  │ │  │  1x Tensor Core │  │
│  │  └─────────────────┘  │ │  └─────────────────┘  │
│  │  WARP Scheduler       │ │  WARP Scheduler       │
│  │  Register File (64KB) │ │  Register File (64KB) │
│  └────────────────────────┘ └────────────────────────┘
│                                                   │
│  ┌─── Sub-Partition 2 ───┐ ┌─── Sub-Partition 3 ───┐
│  │  (同上结构)            │ │  (同上结构)            │
│  └────────────────────────┘ └────────────────────────┘
│                                                   │
│  ┌─── 共享资源 ──────────────────────────────────┐ │
│  │  共享内存 (L1/Shared): 最高128KB               │ │
│  │  L1数据缓存: 可配置                            │ │
│  │  纹理缓存                                      │ │
│  │  1x 第三代RT核心                               │ │
│  └────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────┘
```

> 🔬 **FP32/INT32双发射**：从Turing开始，SM支持FP32和INT32指令在同一时钟周期内并行执行，这意味着整数地址计算和浮点运算可以同时进行，无需串行等待。

#### 1.2.3 Warp调度机制

Warp是GPU调度的基本单位，包含32个线程。SM中的Warp调度器每个时钟周期选择一个就绪的Warp发射指令：

```
时钟周期  Warp0    Warp1    Warp2    Warp3
  1      [ADD]    ...      ...      ...     ← Warp0发射ADD
  2      [等待]   [MUL]    ...      ...     ← Warp0等待结果，Warp1发射MUL
  3      [等待]   [等待]   [LD]     ...     ← 切换到Warp2发射加载
  4      [ADD]    [等待]   [等待]   [SFU]   ← Warp0结果就绪，继续执行
  ...
```

> 💡 **延迟隐藏**：GPU通过在多个Warp之间快速切换来隐藏内存延迟。当某个Warp等待内存数据时，调度器会切换到其他就绪的Warp继续执行，而不是像CPU那样依赖大缓存来减少延迟。这就是为什么GPU需要大量线程来保持高利用率——足够的Warp可以确保总有就绪的Warp可供调度。

#### 1.2.4 Tensor核心与RT核心

**Tensor核心** 专门用于矩阵乘加运算（MMA），对AI推理和训练至关重要：

```
普通CUDA核心：D = A * B + C（逐元素，需要多条指令）
Tensor核心：  D[4x4] = A[4x4] * B[4x4] + C[4x4]（单条指令完成矩阵乘加）

Ampere第三代Tensor核心支持：
- FP16: 每时钟每核心 256 FMA
- BF16: 每时钟每核心 256 FMA
- TF32: 每时钟每核心 128 FMA
- INT8: 每时钟每核心 512 整数运算
- INT4/INT1: 用于量化推理
```

**RT核心** 专门用于光线追踪中的光线求交计算：

```
传统CUDA核心光线求交：
  对场景中每个三角形，逐个检测光线是否相交 → O(n)复杂度

RT核心光线求交：
  1. BVH遍历：硬件加速的层次包围盒遍历
  2. 光线-三角形求交：专用硬件单元
  → 复杂度大幅降低，光线追踪性能提升数倍
```

#### 1.2.5 AMD与Intel GPU架构对比

除了NVIDIA，AMD和Intel也有各自的GPU架构：

| 特性 | NVIDIA Ampere | AMD RDNA 3 | Intel Xe HPG |
|------|--------------|------------|--------------|
| 计算单元名 | SM | CU (Compute Unit) | Xe Core |
| 基本调度单位 | Warp (32线程) | Wavefront (32/64线程) | SIMT Thread (16线程) |
| 矩阵加速 | Tensor Core | Matrix Core | XMX (Xe Matrix Extensions) |
| 光追加速 | RT Core | Ray Accelerator | Ray Tracing Unit |
| 共享内存 | 最高128KB/SM | 最高128KB/CU | 最高512KB/Xe Core |
| 图形API | CUDA, OpenGL, Vulkan, DX12 | ROCm, OpenGL, Vulkan, DX12 | oneAPI, OpenGL, Vulkan, DX12 |

> ⚠️ **跨平台注意**：CUDA是NVIDIA专有技术，在AMD和Intel GPU上不可用。如果需要跨平台GPU计算，应考虑：
> - **OpenCL**：跨平台但性能通常不如原生API
> - **Vulkan Compute**：现代跨平台选择，性能接近原生
> - **SYCL/DPC++**：基于C++的跨平台异构编程模型
> - **HIP**：AMD的CUDA兼容层，可将CUDA代码移植到AMD GPU

#### 1.3.1 各级内存详解

| 内存类型 | 容量 | 延迟 | 带宽 | 访问范围 | 生命周期 |
|---------|------|------|------|---------|---------|
| 寄存器 | ~256KB/SM | ~1周期 | 极高 | 线程私有 | 线程 |
| 共享内存 | ~128KB/SM | ~5周期 | ~1.9TB/s | Block内共享 | Block |
| L1缓存 | ~128KB/SM | ~30周期 | 高 | SM私有 | 自动管理 |
| L2缓存 | ~6MB(4090) | ~100周期 | 中 | 所有SM | 自动管理 |
| 全局显存 | 8-24GB+ | ~400周期 | ~1TB/s | 所有线程 | 应用 |
| 常量内存 | 64KB | ~5周期(缓存命中) | 高 | 所有线程 | 应用 |
| 纹理内存 | - | ~100周期(缓存) | 高 | 所有线程 | 应用 |

#### 1.3.2 显存类型与带宽

现代GPU使用的显存类型直接影响带宽，而带宽是GPU性能的关键瓶颈：

| 显存类型 | 典型带宽 | 代表GPU | 位宽 |
|---------|---------|---------|------|
| GDDR6 | 448-960 GB/s | RTX 3060-3080 | 128-384 bit |
| GDDR6X | 760-1008 GB/s | RTX 3080-3090 | 256-384 bit |
| GDDR7 | 1200+ GB/s | RTX 4070 Ti SUPER+ | 192-384 bit |
| HBM2 | 1.2-2.0 TB/s | A100, H100 | 3072-6144 bit |
| HBM3 | 3.0+ TB/s | H200 | 6144 bit |

> 🔬 **为什么带宽如此重要？** GPU的计算能力远超内存供给能力。以RTX 4090为例，其FP32计算能力约82.6 TFLOPS，但显存带宽仅约1 TB/s。这意味着如果每个浮点运算需要从显存读取一个数据，实际利用率不到2%。因此，**数据复用**（通过共享内存、缓存、Tiling等）是GPU编程优化的核心。

#### 1.3.3 内存合并访问

全局内存访问是否"合并"（Coalesced）对性能影响巨大：

```cpp
// ✅ 合并访问：同一Warp中连续线程访问连续地址
// 线程0访问addr+0, 线程1访问addr+4, 线程2访问addr+8, ...
// GPU可以将32次访问合并为1-2次内存事务
__global__ void coalescedAccess(const float* input, float* output, int n) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) {
        output[idx] = input[idx] * 2.0f;  // 连续线程访问连续地址
    }
}

// ❌ 非合并访问：同一Warp中线程跨步访问
// 线程0访问addr+0, 线程1访问addr+stride*4, ...
// 每次访问都是独立的内存事务，带宽利用率极低
__global__ void stridedAccess(const float* input, float* output,
                               int n, int stride) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int accessIdx = idx * stride;  // 跨步访问
    if (accessIdx < n) {
        output[idx] = input[accessIdx] * 2.0f;
    }
}

// ❌ 结构体数组(AoS)导致非合并访问
struct ParticleAoS {
    float x, y, z;    // 位置
    float vx, vy, vz; // 速度
    float r, g, b, a; // 颜色
};

// ✅ 数组结构(SoA)实现合并访问
struct ParticleSoA {
    float* x, *y, *z;    // 所有粒子的x坐标连续存储
    float* vx, *vy, *vz; // 所有粒子的vx连续存储
    float* r, *g, *b, *a;
};
```

## 2. 图形渲染管线

### 2.1 管线概述

图形渲染管线（Graphics Pipeline）是将3D场景数据转化为2D屏幕像素的一系列处理阶段。理解管线是图形编程的基础。

```
应用阶段(CPU) → 几何阶段(GPU) → 光栅化阶段(GPU) → 像素阶段(GPU)
     │                │                │                 │
  场景数据          顶点变换          三角形→片段       颜色计算
  视锥裁剪          图元组装          插值               混合输出
  绘制调用          裁剪/投影
```

现代图形管线还可以包含更多可选阶段：

```
完整现代管线（以Vulkan/DX12为例）：

输入装配 → 顶点着色 → 曲面细分(可选) → 几何着色(可选) → 光栅化 → 片段着色 → 输出合并
              │              │                 │                           │            │
          MVP变换      细分控制/评估      图元生成/修改              纹理/光照     深度/模板测试
          骨骼动画      LOD细分           法线贴图生成               阴影计算      颜色混合

现代扩展管线阶段（Vulkan/DX12）：
  任务着色器(Task Shader) → 网格着色器(Mesh Shader) → 光栅化 → ...
  （替代传统输入装配+顶点着色器，更灵活的几何处理）
```

### 2.2 管线各阶段详解

#### 应用阶段（Application Stage）

在CPU上执行，负责准备场景数据并发出绘制命令：

```cpp
// 应用阶段示例：准备渲染数据
struct SceneData {
    std::vector<Vertex> vertices;      // 顶点数据
    std::vector<uint32_t> indices;     // 索引数据
    glm::mat4 viewMatrix;             // 视图矩阵
    glm::mat4 projectionMatrix;       // 投影矩阵
    std::vector<Light> lights;        // 光源数据
};

void renderFrame(const SceneData& scene) {
    // 1. 视锥裁剪（粗粒度）
    // 2. 排序（透明物体从后往前，不透明物体从前往后）
    // 3. 设置渲染状态
    // 4. 发出绘制调用（Draw Call）
    for (const auto& mesh : scene.meshes) {
        if (isInFrustum(mesh, scene.viewMatrix)) {
            drawMesh(mesh);  // 发出Draw Call
        }
    }
}
```

#### 几何阶段（Geometry Stage）

在GPU上执行，处理顶点数据：

```glsl
// 顶点着色器（Vertex Shader）- 几何阶段的核心
#version 450 core

layout(location = 0) in vec3 aPosition;  // 顶点位置
layout(location = 1) in vec3 aNormal;    // 顶点法线
layout(location = 2) in vec2 aTexCoord;  // 纹理坐标

uniform mat4 uModel;       // 模型矩阵
uniform mat4 uView;        // 视图矩阵
uniform mat4 uProjection;  // 投影矩阵

out vec3 vWorldPos;        // 传递到片段着色器的世界坐标
out vec3 vNormal;          // 传递到片段着色器的法线
out vec2 vTexCoord;        // 传递到片段着色器的纹理坐标

void main() {
    vec4 worldPos = uModel * vec4(aPosition, 1.0);
    vWorldPos = worldPos.xyz;
    vNormal = mat3(transpose(inverse(uModel))) * aNormal;
    vTexCoord = aTexCoord;
    gl_Position = uProjection * uView * worldPos;
}
```

#### 光栅化阶段（Rasterization Stage）

将几何图元转换为片段（Fragment）：

```
三角形顶点 → 边方程计算 → 采样点覆盖测试 → 属性插值 → 片段

┌─────────────────┐
│  ·  ·  ·  ·  · │  三角形内部的像素点
│  ·  ■  ■  ·  · │  被标记为片段
│  ·  ■  ■  ■  · │  顶点属性通过重心
│  ·  ·  ■  ■  · │  坐标插值到每个片段
│  ·  ·  ·  ·  · │
└─────────────────┘
```

光栅化阶段是硬件固定功能（不可编程），但其行为对渲染结果影响巨大：

**重心坐标插值** 是光栅化的核心机制，它决定了顶点属性如何平滑过渡到每个片段：

```cpp
// 重心坐标插值原理（CPU端演示）
// 三角形三个顶点 V0, V1, V2
// 片段P的重心坐标 (w0, w1, w2)，满足 w0+w1+w2=1
// 插值属性：attr(P) = w0*attr(V0) + w1*attr(V1) + w2*attr(V2)

struct Vec3 { float x, y, z; };

// 计算点P在三角形V0V1V2中的重心坐标
void barycentricCoordinates(const Vec3& P,
                             const Vec3& V0, const Vec3& V1, const Vec3& V2,
                             float& w0, float& w1, float& w2) {
    float denom = (V1.y - V2.y) * (V0.x - V2.x) + (V2.x - V1.x) * (V0.y - V2.y);
    w0 = ((V1.y - V2.y) * (P.x - V2.x) + (V2.x - V1.x) * (P.y - V2.y)) / denom;
    w1 = ((V2.y - V0.y) * (P.x - V2.x) + (V0.x - V2.x) * (P.y - V2.y)) / denom;
    w2 = 1.0f - w0 - w1;
}

// 透视正确插值（重要！直接线性插值在透视投影下会出错）
// 必须除以w分量进行插值，再除以插值后的1/w
// GLSL中 smooth interpolation (默认) 自动处理透视正确插值
// flat interpolation 不插值，直接取 provoking vertex 的值
// noperspective interpolation 线性插值，不考虑透视
```

> ⚠️ **常见陷阱**：深度值（gl_FragCoord.z）的插值不是线性的！在透视投影下，深度值与1/w成线性关系。这意味着Z缓冲的精度在近处密集、远处稀疏，这就是**Z-fighting**（深度冲突）在远距离更常见的原因。

#### 像素阶段（Pixel Stage）

计算每个片段的最终颜色：

```glsl
// 片段着色器（Fragment Shader）- 像素阶段的核心
#version 450 core

in vec3 vWorldPos;
in vec3 vNormal;
in vec2 vTexCoord;

uniform sampler2D uDiffuseMap;    // 漫反射贴图
uniform vec3 uLightPos;           // 光源位置
uniform vec3 uLightColor;         // 光源颜色
uniform vec3 uCameraPos;          // 相机位置

out vec4 FragColor;

void main() {
    // 基础颜色
    vec3 albedo = texture(uDiffuseMap, vTexCoord).rgb;

    // 光照计算（Blinn-Phong模型）
    vec3 N = normalize(vNormal);
    vec3 L = normalize(uLightPos - vWorldPos);
    vec3 V = normalize(uCameraPos - vWorldPos);
    vec3 H = normalize(L + V);

    // 环境光
    float ambientStrength = 0.1;
    vec3 ambient = ambientStrength * albedo;

    // 漫反射
    float diff = max(dot(N, L), 0.0);
    vec3 diffuse = diff * uLightColor * albedo;

    // 镜面反射
    float spec = pow(max(dot(N, H), 0.0), 32.0);
    vec3 specular = spec * uLightColor * 0.5;

    FragColor = vec4(ambient + diffuse + specular, 1.0);
}
```

### 2.3 可编程管线 vs 固定管线

| 特性 | 固定管线（旧式） | 可编程管线（现代） |
|------|----------------|------------------|
| 顶点处理 | 固定变换 | 顶点着色器 |
| 曲面细分 | 不支持 | 曲面细分着色器 |
| 几何处理 | 不支持 | 几何着色器 |
| 片段处理 | 固定纹理混合 | 片段着色器 |
| 输出合并 | 固定混合 | 可编程混合 + 深度测试 |

### 2.4 曲面细分与几何着色器

#### 2.4.1 曲面细分着色器（Tessellation Shader）

曲面细分是现代管线中的可选阶段，用于在GPU端动态增加几何细节：

```
顶点着色器 → 细分控制着色器(TCS) → 固定功能细分器 → 细分评估着色器(TES) → 几何着色器
                │                        │                      │
           设置细分级别           生成新顶点坐标          计算新顶点属性
           传递控制点             (三角形/四边形/等值线)    基于参数化曲面
```

```glsl
// 细分控制着色器（Tessellation Control Shader）
#version 450 core
layout(vertices = 3) out;  // 每个patch3个控制点

in vec3 vPosition[];
out vec3 tcPosition[];

uniform float uTessLevel;  // 细分级别

void main() {
    // 传递控制点
    tcPosition[gl_InvocationID] = vPosition[gl_InvocationID];

    // 设置细分级别（仅由一个线程设置）
    if (gl_InvocationID == 0) {
        gl_TessLevelInner[0] = uTessLevel;  // 内部细分级别
        gl_TessLevelOuter[0] = uTessLevel;  // 外边细分级别
        gl_TessLevelOuter[1] = uTessLevel;
        gl_TessLevelOuter[2] = uTessLevel;
    }
}

// 细分评估着色器（Tessellation Evaluation Shader）
#version 450 core
layout(triangles, equal_spacing, cw) in;

in vec3 tcPosition[];
out vec3 tePosition;
out vec3 teNormal;

uniform mat4 uModelViewProjection;

void main() {
    // 重心坐标
    vec3 bary = gl_TessCoord;

    // 插值位置
    vec3 pos = bary.x * tcPosition[0]
             + bary.y * tcPosition[1]
             + bary.z * tcPosition[2];

    tePosition = pos;
    // 可在此计算法线（基于参数化曲面）
    teNormal = normalize(pos);  // 球体简化法线

    gl_Position = uModelViewProjection * vec4(pos, 1.0);
}
```

> 💡 **曲面细分的典型应用**：
> - **地形渲染**：根据距离相机的远近动态调整细分级别（近处高细分，远处低细分）
> - **位移贴图（Displacement Mapping）**：在细分后的顶点上应用高度图，实现真实的表面细节
> - **角色面部细节**：近距离时增加面部几何细节

#### 2.4.2 几何着色器（Geometry Shader）

几何着色器可以接收一个图元，生成零个或多个新图元：

```glsl
// 几何着色器示例：法线可视化
#version 450 core
layout(triangles) in;                    // 输入：三角形
layout(line_strip, max_vertices = 6) out; // 输出：线段（最多6个顶点）

in vec3 vNormal[];
in vec3 vPosition[];

uniform mat4 uProjection;
uniform float uNormalLength;

void main() {
    for (int i = 0; i < 3; ++i) {
        // 顶点位置
        gl_Position = uProjection * vec4(vPosition[i], 1.0);
        EmitVertex();

        // 法线端点
        vec3 endPos = vPosition[i] + vNormal[i] * uNormalLength;
        gl_Position = uProjection * vec4(endPos, 1.0);
        EmitVertex();

        EndPrimitive();
    }
}
```

> ⚠️ **性能警告**：几何着色器在大多数GPU上性能较差，因为其输出大小不确定，导致GPU无法高效并行处理。在实际游戏引擎中，几何着色器使用越来越少，通常被计算着色器或网格着色器替代。

### 2.5 输出合并阶段

输出合并（Output Merger）是管线的最后阶段，负责深度测试、模板测试和颜色混合：

```
片段着色器输出 → 深度测试 → 模板测试 → 颜色混合 → 帧缓冲
                  │           │           │
              比较深度值    自定义掩码   Alpha混合
              丢弃被遮挡    操作        加法/乘法混合
```

```cpp
// OpenGL中配置输出合并状态
void setupOutputMerger() {
    // 深度测试
    glEnable(GL_DEPTH_TEST);
    glDepthFunc(GL_LESS);        // 深度小于当前值时通过
    glDepthMask(GL_TRUE);        // 允许写入深度缓冲

    // 模板测试
    glEnable(GL_STENCIL_TEST);
    glStencilFunc(GL_EQUAL, 1, 0xFF);   // 模板值等于1时通过
    glStencilOp(GL_KEEP, GL_KEEP, GL_REPLACE);  // 通过时替换模板值

    // 颜色混合
    glEnable(GL_BLEND);
    glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA);  // Alpha混合
    // glBlendFunc(GL_ONE, GL_ONE);  // 加法混合（用于粒子效果）
    // glBlendFuncSeparate(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA,
    //                     GL_ONE, GL_ZERO);  // 分别设置RGB和Alpha混合
}
```

> 🔬 **Early-Z优化**：现代GPU在片段着色器执行前进行早期深度测试（Early Depth Test），被遮挡的片段不会执行片段着色器，大幅节省计算。但如果片段着色器中使用了`discard`、修改了深度值（`gl_FragDepth`）或开启了Alpha Test，GPU必须禁用Early-Z，导致性能下降。因此，应尽量避免在片段着色器中使用`discard`。

### 2.6 现代管线扩展：网格着色器

网格着色器（Mesh Shader）是Vulkan 1.3和DX12 Ultimate引入的新管线阶段，替代了传统的输入装配+顶点着色器：

```
传统管线：
  输入装配(索引缓冲) → 顶点着色器 → ...

网格着色器管线：
  任务着色器(可选) → 网格着色器 → ...
  （直接在GPU上生成图元，无需索引缓冲）
```

```glsl
// 网格着色器示例（GL_NV_mesh_shader扩展）
#version 450 core
#extension GL_NV_mesh_shader : require

layout(local_size_x = 32) in;           // 工作组大小
layout(triangles, max_vertices = 64, max_primitives = 124) out;

// 网格着色器直接输出顶点和图元
void main() {
    uint idx = gl_LocalInvocationID.x;

    // 直接生成顶点（无需从缓冲区读取）
    vec3 pos = computeVertexPosition(idx);
    gl_MeshVerticesNV[idx].gl_Position = uProjection * vec4(pos, 1.0);

    // 生成图元索引
    if (idx < 124) {
        gl_PrimitiveIndicesNV[idx] = computeIndex(idx);
    }

    // 设置图元数量
    gl_PrimitiveCountNV = 40;
}
```

> 💡 **网格着色器的优势**：
> - **消除输入装配瓶颈**：不再需要从CPU端传递索引缓冲
> - **GPU端LOD**：任务着色器可以根据距离选择不同的细分级别
> - **更好的culling**：可以在任务着色器中进行簇级（Cluster）裁剪
> - **Unreal Engine 5的Nanite**：虚拟几何系统就利用了类似的思路

## 3. CPU与GPU协作模型

### 3.1 命令缓冲区模型

CPU与GPU通过命令缓冲区（Command Buffer）进行异步通信：

```
CPU端                          GPU端
┌──────────────┐              ┌──────────────┐
│  记录命令     │──提交──→     │  执行命令     │
│  (Record)    │              │  (Execute)   │
│              │              │              │
│  继续记录     │              │  渲染帧N     │
│  下一帧命令   │              │              │
└──────────────┘              └──────────────┘
     ↑                              ↑
     │         命令缓冲区            │
     │  ┌────────────────────┐      │
     └──│ DrawCommands...    │──────┘
        │ SetState...        │
        │ DrawCommands...    │
        └────────────────────┘
```

### 3.2 同步机制

```cpp
// CPU-GPU同步示例（以Vulkan风格伪代码展示）

// 方式1：围栏（Fence）- 用于CPU等待GPU完成
void waitForGpu(VkFence fence) {
    // 提交工作到GPU
    vkQueueSubmit(queue, 1, &submitInfo, fence);

    // CPU等待GPU完成
    vkWaitForFences(device, 1, &fence, VK_TRUE, UINT64_MAX);
    vkResetFences(device, 1, &fence);
}

// 方式2：信号量（Semaphore）- 用于GPU内部同步
void renderFrame() {
    // 信号量：图像获取 → 渲染完成
    VkSemaphore imageAvailableSemaphore;
    VkSemaphore renderFinishedSemaphore;

    // 获取交换链图像（GPU操作）
    vkAcquireNextImageKHR(device, swapchain, UINT64_MAX,
                           imageAvailableSemaphore, VK_NULL_HANDLE, &imageIndex);

    // 提交渲染命令，等待图像获取完成
    VkPipelineStageFlags waitStages[] = {
        VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT
    };
    submitInfo.waitSemaphoreCount = 1;
    submitInfo.pWaitSemaphores = &imageAvailableSemaphore;
    submitInfo.pWaitDstStageMask = waitStages;
    submitInfo.signalSemaphoreCount = 1;
    submitInfo.pSignalSemaphores = &renderFinishedSemaphore;

    // 呈现：等待渲染完成
    presentInfo.waitSemaphoreCount = 1;
    presentInfo.pWaitSemaphores = &renderFinishedSemaphore;
}
```

```cpp

// 方式1：暂存缓冲区（Staging Buffer）- 最常用
void uploadDataToGpu(const void* cpuData, size_t size, VkBuffer gpuBuffer) {
    // 1. 创建暂存缓冲区（CPU可见内存）
    VkBuffer stagingBuffer;
    VkDeviceMemory stagingMemory;
    createBuffer(size,
                 VK_BUFFER_USAGE_TRANSFER_SRC_BIT,
                 VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT | VK_MEMORY_PROPERTY_HOST_COHERENT_BIT,
                 stagingBuffer, stagingMemory);

    // 2. 将数据复制到暂存缓冲区
    void* mapped;
    vkMapMemory(device, stagingMemory, 0, size, 0, &mapped);
    memcpy(mapped, cpuData, size);
    vkUnmapMemory(device, stagingMemory);

    // 3. 从暂存缓冲区复制到GPU本地缓冲区（设备端执行）
    VkCommandBuffer cmd = beginSingleTimeCommands();
    VkBufferCopy copyRegion = {0, 0, size};
    vkCmdCopyBuffer(cmd, stagingBuffer, gpuBuffer, 1, &copyRegion);
    endSingleTimeCommands(cmd);

    // 4. 清理暂存缓冲区
    vkDestroyBuffer(device, stagingBuffer, nullptr);
    vkFreeMemory(device, stagingMemory, nullptr);
}
```

## 4. 图形API概览

### 4.1 主流图形API对比

| 特性 | OpenGL | Vulkan | DirectX 12 | Metal |
|------|--------|--------|------------|-------|
| 平台 | 跨平台 | 跨平台 | Windows/Xbox | Apple平台 |
| 抽象级别 | 高 | 低 | 低 | 中低 |
| 驱动开销 | 大 | 小 | 小 | 小 |
| 多线程 | 有限 | 原生支持 | 原生支持 | 原生支持 |
| 学习曲线 | 平缓 | 陡峭 | 陡峭 | 中等 |
| 首次发布 | 1992 | 2016 | 2015 | 2014 |
| 语言绑定 | C/C++ | C/C++ | C++ | C++/ObjC/Swift |

#### 4.1.1 API设计哲学对比

```
OpenGL的设计哲学：
  "驱动帮你想" → 驱动自动管理内存、同步、状态
  优点：简单易用，快速上手
  缺点：驱动开销大，行为不可预测，难以调试

Vulkan/DX12的设计哲学：
  "你自己管" → 应用显式控制一切
  优点：性能可控，行为可预测，多线程友好
  缺点：代码量大（初始化500+行），容易出错

Metal的设计哲学：
  "适度控制" → 介于OpenGL和Vulkan之间
  优点：比Vulkan简洁，比OpenGL高效
  缺点：仅限Apple平台
```

#### 4.1.2 性能特征对比

| 性能指标 | OpenGL | Vulkan | DX12 | Metal |
|---------|--------|--------|------|-------|
| Draw Call开销 | 高(~10μs) | 低(~1μs) | 低(~1μs) | 低(~2μs) |
| 状态切换开销 | 高(隐式) | 低(显式) | 低(显式) | 低(显式) |
| 多线程录制 | 困难 | 原生 | 原生 | 原生 |
| 内存控制 | 驱动管理 | 应用管理 | 应用管理 | 应用管理 |
| 管线状态 | 运行时编译 | 离线+运行时 | 离线+运行时 | 离线+运行时 |

> 💡 **Draw Call是CPU端瓶颈**：每次Draw Call都需要CPU向GPU提交渲染命令。OpenGL的Draw Call开销约10微秒，这意味着在单线程下，每秒最多约10万次Draw Call。Vulkan/DX12通过命令缓冲区复用和多线程录制，可以将Draw Call开销降低到约1微秒。

#### 4.1.3 着色器编译流程

不同API的着色器编译流程差异显著：

```
OpenGL着色器编译：
  GLSL源码 → glShaderSource → glCompileShader → glLinkProgram → 使用
  （运行时编译，驱动负责优化和生成GPU指令）

Vulkan着色器编译：
  GLSL/HLSL源码 → glslangValidator/glslc → SPIR-V字节码 → vkCreateShaderModule → 使用
  （离线编译为SPIR-V，驱动只需将SPIR-V翻译为GPU指令）

DirectX 12着色器编译：
  HLSL源码 → dxc/fxc → DXIL/DXBC字节码 → CreateRootSignature + CreatePipelineState → 使用
  （离线编译为DXIL，驱动在创建PSO时生成GPU指令）

Metal着色器编译：
  MSL源码 → Xcode编译 → Metallib字节码 → newLibrary → newRenderPipelineState → 使用
  （完全离线编译，运行时零编译开销）
```

```cpp
// Vulkan着色器编译示例（使用glslc）
// 1. 离线编译GLSL到SPIR-V
// 命令行：glslc vertex.glsl -o vertex.spv
// 命令行：glslc fragment.glsl -o fragment.spv

// 2. 运行时加载SPIR-V
VkShaderModule createShaderModule(VkDevice device, const std::vector<char>& code) {
    VkShaderModuleCreateInfo createInfo{};
    createInfo.sType = VK_STRUCTURE_TYPE_SHADER_MODULE_CREATE_INFO;
    createInfo.codeSize = code.size();
    createInfo.pCode = reinterpret_cast<const uint32_t*>(code.data());

    VkShaderModule shaderModule;
    if (vkCreateShaderModule(device, &createInfo, nullptr, &shaderModule) != VK_SUCCESS) {
        throw std::runtime_error("failed to create shader module!");
    }
    return shaderModule;
}

// 3. 读取SPIR-V文件
std::vector<char> readFile(const std::string& filename) {
    std::ifstream file(filename, std::ios::ate | std::ios::binary);
    size_t fileSize = (size_t)file.tellg();
    std::vector<char> buffer(fileSize);
    file.seekg(0);
    file.read(buffer.data(), fileSize);
    file.close();
    return buffer;
}
```

> ⚠️ **着色器编译陷阱**：
> - OpenGL运行时编译意味着首次渲染可能卡顿（着色器编译卡顿，Shader Compilation Stuttering）
> - 不同GPU驱动对GLSL的编译优化差异很大，同一着色器在不同驱动上性能可能相差数倍
> - Vulkan/DX12的离线编译可以避免运行时卡顿，但需要额外的构建步骤
> - 建议使用着色器变体（Shader Variant）系统预编译所有可能用到的着色器组合

## 5. 计算着色器与GPGPU

### 5.1 计算着色器概述

计算着色器（Compute Shader）是图形管线之外的着色器阶段，用于通用GPU计算（GPGPU）。它不经过图形管线的固定阶段，可以灵活地组织线程进行并行计算。

```
传统图形管线：
  顶点 → 曲面细分 → 几何 → 光栅化 → 片段 → 输出

计算着色器：
  任意数据 → 计算着色器 → 任意输出
  （完全可编程，无固定阶段）
```

### 5.2 计算着色器示例

```glsl
// 计算着色器示例：图像模糊处理
#version 450 core

layout(local_size_x = 16, local_size_y = 16, local_size_z = 1) in;

layout(binding = 0, rgba8) uniform readonly image2D uInputImage;
layout(binding = 1, rgba8) uniform writeonly image2D uOutputImage;

uniform int uRadius;  // 模糊半径

void main() {
    ivec2 pixelCoords = ivec2(gl_GlobalInvocationID.xy);
    ivec2 imageSize = imageSize(uInputImage);

    // 边界检查
    if (pixelCoords.x >= imageSize.x || pixelCoords.y >= imageSize.y) {
        return;
    }

    vec4 color = vec4(0.0);
    float totalWeight = 0.0;

    // 高斯模糊核
    for (int dx = -uRadius; dx <= uRadius; ++dx) {
        for (int dy = -uRadius; dy <= uRadius; ++dy) {
            ivec2 sampleCoords = pixelCoords + ivec2(dx, dy);

            // 边界钳制
            sampleCoords = clamp(sampleCoords, ivec2(0), imageSize - ivec2(1));

            float weight = exp(-float(dx * dx + dy * dy) / (2.0 * float(uRadius * uRadius)));
            color += imageLoad(uInputImage, sampleCoords) * weight;
            totalWeight += weight;
        }
    }

    color /= totalWeight;
    imageStore(uOutputImage, pixelCoords, color);
}
```

### 5.5 粒子系统示例

```cpp
// 使用计算着色器实现粒子系统
#include <GL/glew.h>
#include <vector>

struct Particle {
    float position[3];   // 位置
    float velocity[3];   // 速度
    float color[4];      // 颜色
    float life;          // 生命值
    float padding[3];    // 对齐填充
};

class ParticleSystem {
public:
    void init(int maxParticles) {
        maxCount = maxParticles;

        // 创建粒子缓冲区
        glGenBuffers(1, &particleBuffer);
        glBindBuffer(GL_SHADER_STORAGE_BUFFER, particleBuffer);
        glBufferData(GL_SHADER_STORAGE_BUFFER,
                     maxParticles * sizeof(Particle),
                     nullptr, GL_DYNAMIC_DRAW);
        glBindBufferBase(GL_SHADER_STORAGE_BUFFER, 0, particleBuffer);
    }

    void update(float deltaTime) {
        glUseProgram(computeProgram);

        // 设置uniform
        glUniform1f(glGetUniformLocation(computeProgram, "uDeltaTime"), deltaTime);
        glUniform1f(glGetUniformLocation(computeProgram, "uTime"), currentTime);

        // 调度计算着色器
        int workGroups = (maxCount + 63) / 64;  // local_size_x = 64
        glDispatchCompute(workGroups, 1, 1);

        glMemoryBarrier(GL_SHADER_STORAGE_BARRIER_BIT);
        currentTime += deltaTime;
    }

    void render() {
        // 使用顶点着色器渲染粒子
        glUseProgram(renderProgram);
        glBindBuffer(GL_ARRAY_BUFFER, particleBuffer);

        // 设置顶点属性
        glEnableVertexAttribArray(0);  // position
        glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, sizeof(Particle), (void*)0);
        glEnableVertexAttribArray(1);  // color
        glVertexAttribPointer(1, 4, GL_FLOAT, GL_FALSE, sizeof(Particle), (void*)24);

        glDrawArrays(GL_POINTS, 0, maxCount);
    }

private:
    GLuint particleBuffer = 0;
    GLuint computeProgram = 0;
    GLuint renderProgram = 0;
    int maxCount = 0;
    float currentTime = 0.0f;
};
```

```glsl
// 粒子更新计算着色器
#version 450 core

layout(local_size_x = 64) in;

struct Particle {
    vec3 position;
    vec3 velocity;
    vec4 color;
    float life;
    vec3 padding;
};

layout(std430, binding = 0) buffer ParticleBuffer {
    Particle particles[];
};

uniform float uDeltaTime;
uniform float uTime;

// 伪随机数生成
float hash(float n) {
    return fract(sin(n) * 43758.5453);
}

void main() {
    uint idx = gl_GlobalInvocationID.x;
    if (idx >= particles.length()) return;

    Particle p = particles[idx];

    // 更新生命值
    p.life -= uDeltaTime;

    // 如果粒子死亡，重新生成
    if (p.life <= 0.0) {
        p.position = vec3(0.0);
        p.velocity = vec3(
            (hash(idx + uTime) - 0.5) * 2.0,
            hash(idx * 3.0 + uTime) * 3.0 + 1.0,
            (hash(idx * 7.0 + uTime) - 0.5) * 2.0
        );
        p.life = hash(idx * 13.0 + uTime) * 3.0 + 1.0;
        p.color = vec4(hash(idx + 1.0), hash(idx + 2.0), hash(idx + 3.0), 1.0);
    }

    // 应用重力
    p.velocity.y -= 9.8 * uDeltaTime;

    // 更新位置
    p.position += p.velocity * uDeltaTime;

    // 透明度随生命值衰减
    p.color.a = clamp(p.life, 0.0, 1.0);

    particles[idx] = p;
}
```

#### 6.2.3 前向渲染 vs 延迟渲染

```
前向渲染（Forward Rendering）：
  对每个物体，计算所有光照
  Draw Call: O(物体数 × 光源数)
  优点：简单、支持MSAA、透明物体
  缺点：光源多时性能差

延迟渲染（Deferred Rendering）：
  第一遍：渲染G-Buffer（位置、法线、材质）
  第二遍：对每个像素计算所有光照
  Draw Call: O(物体数) + O(像素数 × 光源数)
  优点：光源数量几乎不影响性能
  缺点：不支持MSAA、G-Buffer带宽大、透明物体需额外处理

现代混合方案（Forward+ / Tiled / Clustered）：
  1. 计算着色器将光源分配到屏幕空间Tile/Cluster
  2. 前向渲染，每个像素只计算相关Tile/Cluster的光源
  优点：支持MSAA、支持大量光源、支持透明
  缺点：实现复杂
```

### 7.2 GPU Driven Rendering

GPU Driven Rendering是现代引擎的核心趋势，将更多决策从CPU转移到GPU：

```cpp
// 传统渲染流程（CPU驱动）
// CPU: 遍历可见物体 → 设置状态 → 发出Draw Call → GPU执行

// GPU Driven渲染流程
// CPU: 上传场景数据 → 发出少量间接绘制命令
// GPU: 裁剪 → 排序 → 实例化 → 绘制

// 间接绘制（Indirect Draw）示例
struct DrawCommand {
    uint32_t vertexCount;       // 顶点数
    uint32_t instanceCount;     // 实例数（由计算着色器填写）
    uint32_t firstVertex;       // 起始顶点
    uint32_t firstInstance;     // 起始实例

};

void gpuDrivenRender(GLuint commandBuffer, int meshCount) {
```

### 8.3 移动端GPU注意事项

```cpp
// 移动端GPU（Mali, Adreno, Apple GPU）与桌面GPU的关键差异：

// 1. Tile-Based渲染架构
// 移动GPU采用分块渲染（TBR/TBDR），将屏幕分成小块逐块处理
// 优势：减少显存带宽消耗（对功耗敏感）
// 劣势：不支持某些桌面端优化（如异步计算）

// 2. 半精度优化
// 移动GPU对FP16有硬件加速，应尽量使用mediump
// GLSL中：
// precision mediump float;  // 使用FP16
// precision highp float;    // 使用FP32

// 3. 带宽是最大瓶颈
// 移动端显存带宽通常只有桌面端的1/5-1/10
// 延迟渲染的G-Buffer在移动端代价很高
// 推荐使用前向渲染或TBDR优化的延迟渲染

// 4. 纹理压缩格式
// 桌面端：BC (DXT) 压缩
// Android：ETC2 (OpenGL ES), ASTC (Vulkan)
// iOS：ASTC
// 跨平台：ASTC是最佳选择（质量高、所有现代移动GPU支持）
```

> ⚠️ **Apple Silicon注意事项**：
> - Apple M1/M2/M3芯片使用统一内存架构（UMA），CPU和GPU共享同一块物理内存
> - 这意味着`cudaMemcpy`等数据传输操作在Apple平台上是零拷贝的
> - 但Metal API仍然需要显式管理缓冲区，不能直接使用CPU指针
> - Apple GPU的TBDR架构对渲染流程有特殊要求，需要正确使用Load/Store Action

## 9. 本章小结

本章概述了图形编程的基础知识，包括以下核心要点：

| 主题 | 核心要点 |
|------|---------|
| GPU架构 | SIMT模型、SM核心、微架构演进、Tensor/RT核心、内存层次、合并访问 |
| 图形管线 | 应用→几何→光栅化→像素四阶段，曲面细分、几何着色器、输出合并、网格着色器 |
| CPU-GPU协作 | 命令缓冲区、围栏/信号量同步、数据传输、暂存缓冲区 |
| 图形API | OpenGL（简洁）、Vulkan（显式）、DX12（Windows）、Metal（Apple），着色器编译流程 |
| 计算着色器 | GPGPU通用计算、图像处理、物理模拟、粒子系统 |
| 性能优化 | Draw Call优化、状态排序、实例化渲染、前向/延迟渲染选择 |
| 游戏引擎 | UE5 Nanite/Lumen、Unity SRP、GPU Driven Rendering |
| 跨平台 | SPIR-V工具链、移动端TBR架构、纹理压缩格式选择 |

**关键理解**：

1. **GPU是并行处理器**：设计目标是高吞吐而非低延迟，适合数据并行任务
2. **图形管线是核心概念**：所有图形API都围绕管线设计，理解管线是学习图形编程的基础
3. **CPU与GPU是异步协作**：通过命令缓冲区通信，需要合理的同步策略
4. **API选择看需求**：快速原型用OpenGL，极致性能用Vulkan/DX12，Apple平台用Metal
5. **计算着色器扩展了GPU用途**：不仅限于图形渲染，还可用于通用并行计算
6. **带宽是GPU编程的核心瓶颈**：优化数据访问模式比优化计算更重要
7. **现代引擎趋向GPU Driven**：将更多决策从CPU转移到GPU，减少CPU-GPU通信开销
